# 00. 공통 개요: 무엇을, 어떻게, 누가 만드나

> **📌 9/30 오후 변경 (먼저 읽어 주세요)**
> 1. **AI 코드 수정 = P0, 데모 핵심** (✅ 9/30, 양서윤 제안 → 팀 합의). 플랜 단계에서 AI가 환경 의존 코드(하드코딩된 `SECRET_KEY`, `localhost` 주소, 쿠키 `Secure`·ProxyFix 설정)를 **환경변수로 읽도록 고치는 diff**를 만들고, 사람이 승인한 뒤 빌드합니다. 지원 패턴은 로그인 시나리오의 2~3개로 한정하고, 그 밖은 보고만 합니다. 코드 수정 토글은 유지하며 **데모에서는 ON**, OFF면 보고만 합니다. AI가 실패하면 이전에 승인된 패치를 쓰고 화면에 표시합니다. (이전의 "토글 기본 OFF, AI 패치는 나중"을 대체)
> 2. **이미지는 1개** (✅). 수정된 코드로 이미지를 한 번만 빌드해 온프렘·클라우드에 같은 이미지를 씁니다. 환경 차이(DB 주소·계정·TLS, 도메인, 시크릿, 쿠키·프록시 플래그, 로그)는 설정 주입과 provider(`onprem.py`/`aws.py`)의 배포 명세가 흡수합니다. 환경별로 이미지를 따로 만들지 않습니다(교차 검증의 전제).
> 3. **멀티 아키텍처 빌드가 기본** (✅). `linux/amd64` + `linux/arm64`를 한 태그(이미지 목록, index)로 빌드합니다. 온프렘(예: Apple Silicon)과 Fargate의 CPU가 달라도 같은 이미지가 돕니다. 릴리스의 기준은 **index digest**이고, 환경별로 실제 받은 플랫폼 digest도 기록합니다. 자세한 약속은 [01 공통 계약 3-4절](01_공통-계약.md#3-4-이미지-1개--멀티-아키텍처-빌드--9월-30일-오후).
> 4. **백엔드 웹 프레임워크 = FastAPI** (✅ 9/30 확정, Django 아님). 계획·실행기·레지스트리 코어는 프레임워크와 무관한 파이썬으로 짜고, 웹 층(관리 페이지·API)만 FastAPI를 씁니다.
> 5. **변경 탐지 = 스냅샷 내용 해시** (✅ 9/30 오후). git 커밋이 아니라 로컬 폴더 스냅샷의 파일별 해시를 **대상 환경별 마지막 성공 배포** 스냅샷과 비교합니다(커밋 안 한 코드도 배포 가능). 비교는 실행기 DB의 해시 목록으로 앱 안에서 하고, diff가 필요할 때만 이전 스냅샷 zip(로컬 캐시, 없으면 S3)을 씁니다. S3 업로드는 **승인 뒤**(AI 수정 적용본)입니다. 이전에 승인된 같은 패치는 자동 재사용합니다. 자세한 약속은 [01 공통 계약 3-6절](01_공통-계약.md#3-6-변경-탐지-스냅샷-내용-해시--9월-30일-오후).

## 1. 무엇을 만드나

### 1-1. 주제 (✅ 장부 1)

> 로컬에서 만든 앱을 **딸깍 한 번**으로 **온프렘과 클라우드에 동시에** 배포한다. 환경 차이로 깨지는 부분을 흡수하고, 두 환경이 똑같이 동작하는지 **교차 검증**까지 끝낸다.

- "동시에" = 두 환경을 **동시에 시작**해 병렬로 진행하고, **로컬 검증이 필요한 지점에서만 기다린** 뒤 이어간다.
- "환경 차이를 고친다"의 범위: **AI 코드 수정 P0**(✅ 9/30 오후). 플랜 단계에서 환경 의존 코드를 환경변수로 읽도록 고치는 diff → 사람 승인 → 이미지 1번 빌드. 토글 유지, 데모 ON(OFF면 보고만).
  - AI는 **어떤 설정 키가 환경마다 달라야 하는지 분류**한다.
  - **코드가** 대상 환경 값으로 바꿔 넣는다.
  - 실패하면 AI가 **원인을 설명**하고 보고한다.

## 3. 전체 구조

### 3-1. 그림

```text
[운영자 브라우저] ─ 채팅 · 승인 버튼 · 도메인 입력 ─▶ 127.0.0.1 (관리 페이지 포트 💭 8765)

[컨트롤 플레인 = 파이썬 앱 1개 · 운영자 PC · 한 프로세스]
  web       관리 웹: 채팅, 계획 카드, 승인 화면, 2열 진행(SSE), 결과 카드, 설정(도메인)
  plan      ① 분석·계획 → ② 계획 검증 (+ Dockerfile이 없을 때 생성·검사)
  infra     AI Terraform: 제안 → 검사 → plan 요약 → (사람 승인 뒤) apply
  executor  plan.json 실행, 대기 지점, 잠금, 롤백, 기록, 환경 정보 스냅샷(RunContext)
  registry  툴 40개. 실행기·웹은 이름으로만 조회
            └ ci(빌드·푸시) · cd(interface + providers/aws·onprem) · infra · verify · ops
  core.ai   call_ai ─▶ Claude(cli / api / replay) · Jev        ※ 제안만 돌려받음

      │ AWS API                                   │ docker API (unix 소켓 / ssh)
      ▼                                           ▼
[AWS 서울 ap-northeast-2]                       [온프렘: tier별 서버, 부족하면 tier별 컨테이너]
  S3(수정본 zip, 승인 뒤) → CodeBuild ─push─▶ (Docker Hub)   web: nginx      (8080 공개)
  ALB 443 (80→301) → ECS Fargate(web + was)       was: flaskr     (8000, web에서만)
    → 공유 RDS MySQL 안 앱 DB `flaskr`            db : MySQL 8.4  (3306, was에서만)
  Secrets Manager(앱 시크릿 · Docker Hub 토큰)
  Terraform state(S3, 플랫폼 층 / 앱 층)

[Docker Hub (AWS 밖)]
  CodeBuild가 push ─▶ 같은 index digest를 ECS 태스크와 온프렘 web·was가 읽기 전용 토큰으로 pull(각자 CPU에 맞는 플랫폼을 받음)
```

- 두 환경이 **같은 이미지 index digest**(`docker.io/<조직>/<이미지>@sha256:…`)를 참조합니다. 태그가 아니라 digest가 "같은 코드"의 기준입니다.
- 멀티 아키텍처라 실제로 받는 플랫폼 이미지는 다를 수 있습니다(ARM과 AMD64의 플랫폼 digest는 정상적으로 다름). 그래서 "같은 이미지" = index digest 일치이고, 각 환경의 실제 digest는 그 index의 플랫폼 항목에 속하는지로 확인합니다.
- 컨트롤 플레인은 운영자 PC에만 있습니다. 클라우드에는 API로 원격 배포합니다(클라우드용 컨트롤 플레인 없음, ✅ 장부 10).
- 온프렘은 AWS 자격 없이 Docker Hub **읽기 전용 토큰**으로 pull합니다(✅ 장부 28).

### 3-2. 앱 안 모듈

| 모듈 | 하는 일 | AI | 주 담당 |
|---|---|---|---|
| `web` | 관리 화면, 채팅, 계획 카드, 승인 화면, 진행, 결과, 설정, 환경별 설정 변환 표 | 채팅 의도(툴을 거쳐서) | 양서윤 |

| `infra` | 기존 리소스 탐지, AI HCL 초안, 정적 게이트·정책 검사, plan 요약, 승인 뒤 apply | HCL 초안 | 유상준 |

## 4. 5단계 파이프라인

### 4-1. 단계 (✅ 장부 2)

| 단계 | 하는 일 | AI | 결과물 |
|---|---|---|---|
| ① 플랜 | 요청 접수, 환경 정보 스냅샷, 바뀐 tier, 환경 키 분류, 인프라 요구 도출, step 선택. (필요 시) Dockerfile 초안, Terraform 초안 | 분류·step 선택, Dockerfile·HCL 초안 | facts, 계획 초안, 초안들 |
| ② 계획 검증 | 카탈로그 + facts + 초안 → 최종 `plan.json` 조립·검사. (필요 시) Dockerfile 검사·검증 빌드, 인프라 검사·plan 요약 | **없음**(검사기는 AI를 import하지 못함) | `plan.json` + `plan_hash`, plan 요약 |
| [사람 승인] | **한 화면·한 번 승인**: 계획 카드 + (패치 diff) + (Dockerfile) + (IAM·인프라 plan) 확인 → **[배포]** | – | 대상별 승인 기록(패치·배포·인프라 각자 해시) |
| ③ 빌드 | 바뀐 tier만 CodeBuild(승인된 수정본 스냅샷, 멀티 아키텍처) → Docker Hub, index digest·플랫폼별 digest 기록. Dockerfile이 없던 tier는 ①②에서 AI가 만들고 검사·승인된 파일로 빌드 | 없음 | manifest 초안, 신호 `images_ready` |
| ④ 배포 | 두 트랙 동시. (있으면) 인프라 apply, 설정·시크릿 주입, DB 마이그레이션, tier 교체 | 없음 | 환경별 배포 결과, 환경 정보 갱신 |
| ⑤ 검증 및 보고 | 헬스·스모크·TLS, 교차 비교, 실패 원인 설명, 보고 | 원인 설명·보고 요약 | 비교 표, 보고 카드 |

### 4-2. 트랙과 대기 지점

```text
[배포] 클릭 뒤 (실행기, AI 없음)

build : build.was ─▶ (내장) digest 확인 ─▶ ◆ images_ready (G0)
local : (G0 대기) config ─▶ db ─▶ was 교체 ─▶ health ─▶ smoke ─▶ ◆ local_verified (G1)
cloud : tls 확인 ······ (G1 대기) ······ infra apply ─▶ 시크릿 값 ─▶ config ─▶ db ─▶ app ─▶ health · tls · smoke ─▶ ◆ cloud_verified
verify: (local_verified ∧ cloud_verified = G2) compare ─▶ report(항상 마지막)
```

- 세 트랙(build·local·cloud)은 **동시에** 시작합니다. 이미지가 필요한 step만 G0를 기다립니다.
- 클라우드의 **상태 변경** step(DB 마이그레이션, 서비스 전환, 권한 변경이 있는 인프라 apply)은 **G1(`local_verified`) 뒤**입니다(✅ 장부 6).
- 로컬이 실패하면 G1이 실패 → 클라우드는 대기 지점에서 멈춥니다(`ABORTED_AT_GATE`). 클라우드는 바뀐 것이 없어 롤백도 없습니다.
- 위 cloud 줄은 v2 시크릿 장면 기준입니다. 인프라 변경이 없는 배포에서는 infra apply가 빠집니다.

## 7. AI 경계

### 7-1. AI가 하는 것 / 안 하는 것 (✅ 장부 4·21·23·26)

| AI가 만드는 것(제안) | 누가 판정·실행하나 |
|---|---|
| 채팅 의도 JSON(`deploy_request` / `status_query` / `explain_last_run` / `unknown`) | 코드가 enum·ref 확인. 실행은 사람의 [배포] 클릭 |
| 분석 분류(키마다 secret / plain / address) | 규칙과 대조, 충돌하면 secret 쪽 |
| step 선택(조건부·선택 step의 포함/제외 + 이유) | 계획 검증(코드)이 필수 step 강제, 근거 없는 제외 무효 |
| Terraform HCL·IAM 초안 | 정적 게이트·정책 검사·plan → 사람 승인 → `apply_infra`(코드) |
| Dockerfile 초안(없을 때만) | 정적 검사·검증 빌드 → 사람 승인 |
| 코드 패치 diff(환경 의존 코드 2~3개 패턴, 토글 ON, P0) | 허용 파일·패턴·문법 검사(코드) → 사람 승인 → 승인된 diff만 적용 |
| 실패 원인 설명, 보고 요약 | 표시만. 롤백·판정은 규칙 |

| AI가 절대 하지 않는 것 |
|---|
| 툴 직접 호출, 빌드·배포·검증·롤백·잠금 실행 |
| 비밀값 보기·만들기(키 **이름**만 봄. SECRET_KEY 난수는 코드가 만듦) |
| 도메인·IP·digest·ARN·시크릿 위치 만들기(환경 정보에서 코드가 채움) |
| Terraform state·출력 원문 보기(가린 요약만) |
| 필수 step 빼기, 순서·대기 지점 정하기 |
| 승인 |

- 코드·diff·로그는 **신뢰할 수 없는 입력**입니다. AI 입력 전에 비밀값을 가리고 데이터 태그로 감쌉니다.
- 한 프로세스라 물리 격리는 없습니다. import 규칙 + 런타임 가드 + "LLM은 툴을 못 부른다"는 구조로 막습니다. 발표에서 "프로세스 격리"라고 말하지 않습니다.

### 7-2. 사람이 누르는 승인

| 승인 | 언제 | 묶는 대상 | 상태 |
|---|---|---|---|
| [배포] | 모든 run | 계획(`plan_hash`) | ✅ 사람 승인(장부 4) / 묶는 방식 💭 |
| [패치 diff 승인] | 토글 ON이고 AI가 패치를 만들었을 때(데모 ON) | 원본 스냅샷 해시·diff 해시·수정본 스냅샷 해시 | ✅ 9/30 오후. 내용이 바뀌면 재승인. 세 해시가 같고 이전 기록이 승인이면 재사용 |

## 11. 용어집

| 용어 | 뜻 |
|---|---|
| 딸깍 | 채팅 한 번 + 승인 클릭으로 두 환경 배포가 끝나는 것 |
| 컨트롤 플레인 | 우리 앱(파이썬 앱 1개). 운영자 PC에서 돎 |
| 툴 / 레지스트리 | 툴 = 레지스트리에 등록한 파이썬 함수(40개). 레지스트리 = 이름 → 함수·메타정보 표 |
| step | 계획 안의 실행 단위. 같은 툴이 여러 step에 쓰임(예: `deploy_tier`가 tier·대상별로) |
| 트랙 | build / local / cloud / verify. 세 트랙이 동시에 시작 |
| 신호·대기 지점 | 신호 4개(`infra_ready`, `images_ready`, `local_verified`, `cloud_verified`). step의 `wait_for`가 신호를 기다림 |
| G0 / G1 / G2 | G0 = `images_ready`, G1 = `local_verified`(클라우드 상태 변경의 관문), G2 = 두 환경 검증 완료(교차 비교 시작) |
| step 층 | 내장(계획에 안 보임) / 필수(AI가 못 뺌) / 조건부(규칙 조건이 참일 때만 뺌) / 선택(AI 자유) |
| effect | step 영향. `read` / `additive_prep`(서비스 동작을 안 바꾸는 준비) / `state_change`(서비스·공유 데이터를 바꿈) |
| facts | 실행기가 계산한 사실(바뀐 경로·해시·키 이름 등). AI가 읽음. 값은 없음 |
| 실행 컨텍스트(`RunContext`) | 코드만 채우는 값(digest·도메인·ARN·IP·시크릿 위치). AI·계획·툴 입력에 없음 |
| 환경 정보 | 값의 원본 4곳: Terraform 출력, 관리 페이지 설정, 온프렘 인벤토리, 실행기 DB |
| 가린 요약 | AI에 보내도 되는 환경 정보 요약(키 이름·tier·리소스 종류·개수·있음/없음) |
| plan.json / PlanDraft | PlanDraft = AI 초안(포함/제외 결정). plan.json = 계획 검증이 조립한 최종 계획. 실행기는 plan.json만 실행 |
| 규칙 계획 | AI가 실패하거나 불합격일 때 규칙으로 만든 계획. AI 없이도 E2E가 되게 함 |
| manifest | 릴리스 기록(이미지 index digest·플랫폼별 digest, 설정 참조, 스키마 버전). 봉인 뒤 불변 |

| 부트스트랩 / 업데이트 | 부트스트랩 = 이전 릴리스가 없는 초기 배포(v1). 업데이트 = 개선 배포(v2) |

| 코드 소유 틀 | AI가 못 건드리는 Terraform 고정 부분(버전·provider·backend·이름 규칙·경계) |
| 스모크 / 교차 검증 | 스모크 = 같은 시나리오를 각 환경에서 실행. 교차 검증 = 두 결과를 정규화해 비교 |
| 예상된 차이 | 교차 비교에서 일부러 제외하는 차이(스킴·쿠키 Secure·DB TLS 등) |
| 개발값 | 개발 환경에 일부러 둔 값(`sqlite:`, `localhost:5000`, `SECRET_KEY=dev`). 배포 때 코드가 바꿈 |
| 토글 | 코드 수정 토글. 데모 ON(AI 코드 수정 P0), OFF면 보고만 |
| replay | 저장된 AI 응답을 재생하는 backend. 테스트·비상용, 화면에 "저장된 응답" 표시 |
| Jev | 판단 전용 AI(예/아니오 확률, 보기 선택). 문장을 만들지 않음 |
| P0 / P1 / P2 | P0 = 10/1 E2E에 필요, P1 = 10/2, P2 = 나중 |
| `env_release` | 환경별 현재·직전 릴리스와 상태(`SUCCEEDED`/`ROLLED_BACK`/`DIVERGED`/`NEEDS_HUMAN`) |
| `ddak` | 프로젝트 가칭(R7) |
