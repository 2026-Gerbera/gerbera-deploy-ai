## 1. 오늘 확정·정정된 것

### 1-1. 트리거와 앱 저장소 브랜치 보호

- 파이프라인은 앱 저장소 `prod`에 코드가 반영될 때(PR merge) 시작합니다.
- 브랜치 보호는 `prod`에만 겁니다. PR merge 필수, force push 금지, 삭제 금지입니다.
- `main`·`ai-prod`는 파이프라인이 직접 push하므로 보호하지 않습니다. `deployed/*` 태그는 `--force-with-lease`로 옮기므로 태그 보호도 걸지 않습니다.
- `prod/onprem`처럼 `prod/` 아래 브랜치는 만들지 않습니다. Git ref가 충돌해서 `prod`를 만들 수 없게 됩니다.
- 감시는 준석님 `watch.py`가 `prod`를 주기적으로 확인(polling)합니다. 앱 조립부는 이미 저장된 설정의 감시 브랜치(기본 `prod`)를 넘깁니다. `watch.py` 단독 실행 기본값 `main` → `prod` 정정은 준석님께 요청 중입니다.

### 1-2. 수동 배포는 허용된 ref만

- 수동 배포는 감시 브랜치(기본 `prod`)와 `v*` 태그만 고를 수 있습니다. 임의 SHA나 `main`·`ai-prod` 같은 다른 브랜치는 거부합니다.
- annotated 태그는 태그가 가리키는 커밋 SHA로 고정합니다. 태그는 `refs/tags/`로만 해석해서 같은 이름의 브랜치와 섞이지 않습니다.

### 1-3. 온프렘·클라우드 독립 진행

- 두 환경 사이에 대기 지점이 없습니다. 한쪽이 실패해도 다른 쪽은 끝까지 가고, 실패한 환경만 롤백합니다.
- 교차 검증은 둘 다 성공했을 때만 돕니다.
- `main`은 고른 대상이 모두 성공하고, 둘 다면 교차 검증까지 통과했을 때만 옮깁니다. 교차 검증이 실패하거나(`PARITY_FAILED`, 클라우드 롤백) 비교할 수 없으면(`FAILED_VERIFY`, 롤백 없음) `main`은 그대로입니다.
- 이때도 성공한 환경의 `deployed/*` 태그는 실제 배포 상태대로 옮깁니다.

### 1-4. 배포 방식은 롤링

- 온프렘·클라우드 모두 롤링 교체입니다. 클라우드는 ECS Fargate 롤링입니다(승환님 확인).
- 블루그린은 준석님 제안입니다. 1차가 끝난 뒤 검토 후보로 둡니다.
- 실측에서 롤링 교체 순간 502가 1건 나와 drain 처리를 검토합니다(3절).

### 1-5. 데모 목표: 1차와 2차

- **1차(오늘 목표):** 기본 Flask 앱에 이미지·박스를 추가한 변경으로 파이프라인 E2E를 확인합니다.
- **2차:** 실제 로직과 LLM 기능(분석·AI 패치·인프라 생성)을 검증합니다.
- v2 내용은 미정입니다. 로그인은 후보 중 하나입니다. 문서에 남은 로그인·`SECRET_KEY` 장면은 후보 예시입니다.
- 1차 결과만으로 LLM·AWS 전체가 끝났다고 말하지 않습니다.

### 1-6. 사람 개입은 승인 클릭뿐

- 사람이 하는 일은 제품 승인 화면 클릭뿐입니다. 수동 terraform 적용, 수동 스크립트, 수동 초기화는 없습니다.
- 초기 인프라: 승인 1회 → 코드가 SDK로 state 버킷·권한 경계 생성 → 플랫폼 적용 → state를 원격(S3)으로 이전. 별도 [기반 승인] 버튼은 없고, 기반 템플릿 해시는 인프라 승인 해시에 함께 묶입니다.
- 받아들이는 1회 준비는 AWS 자격증명, 도메인 구매, VPN 끄기입니다(6-1). 다만 지금은 자동화 전이라 남은 수동 단계가 있습니다(6-2). 이 단계들은 없애야 할 대상입니다.

### 1-7. Terraform 생성과 실행 분담

- Terraform 본문은 `generate_infra`가 만들고 사람이 승인합니다. (10/3 정정: 실제 구현은 서윤님이고 PR #17로 통합됐습니다. 이전 표기 "준석님 `generate_infra`"는 실제와 달랐습니다.)
- 준우 C1 몫은 부트스트랩과 `validate_infra`·`plan_infra`·`apply_infra` 실행 경로·정책입니다.
- `generate_infra` 입출력 계약 초안은 #8에 있습니다. (10/3 정정: 서윤님 구현이 이 계약과 수정 7 출력 계약을 지키는지는 클라우드 재개 때 확인합니다.)

### 1-8. 승인 트리 = 배포 트리

- `ai-prod`는 `prod` merge 뒤 관리 파일을 승인 트리로 고정한 merge 커밋입니다. 빌드·배포는 이 커밋만 씁니다.
- 이전 AI 패치는 merge만으로 남지 않습니다. (10/3 정정: 패치 OFF는 "새 AI 제안 없음, 이전 승인 패치를 유지할 수 없으면 승인 전에 멈춤"입니다. "패치 OFF면 이전 AI 패치가 빠진다"는 폐기했습니다.)
- `deployed/onprem`·`deployed/cloud` 태그는 실제로 배포된 상태를 가리킵니다.

### 1-9. 빌드

- 이미지는 tier별(web·was)입니다. db는 공식 mysql 이미지를 digest로 고정해 씁니다(커스텀 빌드 없음).
- CodeBuild 소스는 그 run의 `ai-prod` 커밋 SHA입니다(`sourceVersion` 고정, #9).
- 플랫폼 buildspec은 StartBuild의 `buildspecOverride`로 강제합니다(#8 정책). CodeBuild 프로젝트에 들어가는 buildspec은 실패만 하는 상수입니다. #9는 아직 override를 보내지 않으므로 승환님 다음 PR에서 넣습니다. 우선순위는 **P0**입니다. (10/3 정정: 온프렘 빌드는 로컬 빌드 백엔드 `DDAK_BUILD_BACKEND=local`이 CodeBuild와 같은 buildspec을 실행 PC에서 실행하므로, CodeBuild·override가 없어도 온프렘 경로는 막히지 않습니다.)
- `image_repository` 형식을 하나로 맞춰야 합니다. 권장안은 `ns/repo`로 두고 툴이 `docker.io/`를 붙이는 것입니다(확인 대기).
- `build_image` 툴은 아직 등록되지 않았습니다. #8의 `RunContext.source_binding`(승인 사본)을 쓸 예정입니다.

### 1-10. PR 본문 형식

- PR 본문은 `.github/pull_request_template.md` 형식(변경 내용·확인한 것)을 따릅니다.
- 템플릿에 "AI 사용" 칸은 없습니다. AI 사용 기록은 `docs/ai-usage/<역할>.md`에 남기고, PR "변경 내용"에 기록 위치를 한 줄 적습니다.

### 1-11. VPN

- 데스크톱 VPN(Findthegap TLS 가로채기)이 켜져 있으면 GitHub·Docker Hub·Claude API 연결이 실패합니다. 데모·리허설 중에는 VPN을 끕니다.

### 4-3. 막히는 이유(코드 근거 요약)

1. **`build_image` 미등록:** `cloud/build/tools`에 툴이 없고 입출력 계약도 없습니다. 빌드 step이 있는 계획은 모두 준비에서 `UnknownToolError`로 끝납니다. 등록해도 `buildspecOverride`를 보내지 않으면 실빌드는 실패합니다(프로젝트 buildspec이 실패 상수).
2. **온프렘만 배포해도 클라우드 플랫폼이 먼저 필요(10/3 정정: 로컬 빌드 백엔드로 해소):** 빌드는 CodeBuild 하나뿐이고, CodeBuild 프로젝트 이름·이미지 저장소는 `apply_infra`가 성공한 run에서만 저장됩니다. 그래서 `generate_infra` 등록과 첫 플랫폼 적용이 먼저입니다. 그런데 `apply_infra`는 클라우드·둘 다 run에서만 돌아서, 온프렘만으로는 플랫폼을 만들 수 없습니다(4-4 ①).
3. **온프렘 새 앱 DB:** 계획은 deploy.yaml의 tier(web·was)만 배포 step으로 만들고, db 컨테이너 step과 db 이미지 digest 공급이 없습니다. 마이그레이션은 인벤토리의 기존 env 파일만 쓰고 DB·계정을 만들지 않습니다. `ensure_app_database`는 미구현이고, 새 DB 이름·계정은 결정 대기(G9d)입니다. 기존 temp-box flaskr DB는 보존합니다(4-4 ②).
4. **첫 배포 설정 주입:** analyze가 코드 안 기본값 키(`APP_ENV`·`MIGRATE_MODE`)를 외부 필수 키로 넘겨서 `inject_env_config`가 거부할 수 있습니다(G9c).
5. **클라우드 배포:** AwsProvider의 deploy·rollback·migrate_db·inject_config가 미구현입니다. 이 상태로 클라우드 배포가 호출되면 롤백도 실패해서 run 전체가 `NEEDS_HUMAN`이 되고, 프로젝트 잠금이 남아 다음 run이 막힙니다. **AwsProvider 구현 전에는 클라우드·둘 다를 실제 모드로 돌리지 않습니다.** 예외: 첫 플랫폼 적용을 클라우드 부트스트랩 run 1회로 하기로 정하면(4-4 ①), 그 run은 클라우드 배포 실패를 예상 결과로 받아들이고 `NEEDS_HUMAN`·잠금 위험을 먼저 확인한 뒤 돌립니다.
6. **클라우드 검증 키:** 플랫폼 출력 허용 목록에 `health_check`가 요구하는 `region`·`ecs_cluster`·`ecs_service`·`target_group_arn`이 없고, `verify_tls`가 요구하는 `region`도 없습니다(`verify_tls`의 alb·certificate·listener 키는 이미 있음). 그래서 `INFRA_MISSING`으로 끝납니다(이번 감사에서 확인). `verify_tls`의 `:443` 리다이렉트 판정 결함, health의 전역 digest 비교·폴링 없음도 남아 있습니다.
7. **운영 UI:** 배포 시작 버튼·라우트가 없고, 설정 화면은 도메인만 받습니다. 저장소 URL·감시 브랜치·기본 대상·자동 감지는 공개 API로만 저장할 수 있습니다. 준비에 실패한 run의 승인 페이지는 HTTP 500이고, 승인 화면에 인프라 요약(C-18)이 보이지 않습니다.
8. **앱 저장소:** 기본 브랜치가 아직 `dev`이고 `prod` 보호가 꺼져 있습니다. `ai-prod`·`main`은 제품이 없으면 만들어 push하므로 수동 생성은 필요 없습니다. 1차 v2(이미지·박스) 커밋은 아직 없습니다.
9. **부트스트랩 인프라 step 강제(E6) 미구현:** 새 secret 키가 없는 첫 클라우드 배포는 계획에 `apply_infra`가 들어가지 않습니다(4-4 ③).

### 4-4. 구조상 확인된 공백 (결정 필요)

툴을 등록해도 그대로 남는 공백입니다. 다른 문서의 같은 주장은 "설계 목표, 현재 미구현/스크립트 경로만 실측"으로 표시했습니다.

- **① 온프렘 1차 run 전에 플랫폼을 먼저 적용하는 경로가 없음(10/3 정정: (다) 온프렘용 로컬 빌드 어댑터로 정해 해소).** 온프렘만 배포해도 빌드는 CodeBuild를 씁니다. 그런데 CodeBuild 프로젝트(플랫폼 출력)는 클라우드·둘 다 run의 `apply_infra`에서만 만들어집니다.
  - 코드 근거: `src/ddak/app.py` `_infra_approval`은 `targets == "onprem"`이면 바로 건너뜁니다. `src/ddak/executor/selection.py` `select_plan`은 온프렘 run에서 cloud 섹션을 뺍니다.
  - 후보: (가) platform-only 인프라 run을 만든다. (나) AwsProvider 전에 클라우드 부트스트랩 run 1회를 허용한다. 이때 클라우드 배포 실패로 `NEEDS_HUMAN`·프로젝트 잠금이 남는지 먼저 확인해야 하고, ③ 때문에 새 secret 키가 없으면 `apply_infra`가 계획에 들어가지 않습니다. (다) 온프렘용 로컬 빌드 어댑터를 둔다.
  - 결정 필요: 정준우·안승환.
- **② 제품 계획에 db tier 배포 step이 없음.** `deploy_tier`는 deploy.yaml의 tier(web·was)만 만들고, `prepare_db`는 DB가 이미 있다고 가정합니다. 새 앱용 DB·계정 생성(`ensure_app_database`, 김준석, `src/ddak/onprem/provision`)은 미구현입니다. 그래서 3티어 db 기동은 지금 검증 스크립트 경로(`harness/scripts/o1_onprem.py`)에서만 실측됐습니다. 새 DB 이름·계정 결정은 G9d(김준석)입니다.
- **③ 부트스트랩 인프라 step 강제(E6) 미구현.** `src/ddak/core/contracts/step_catalog.py`의 `deploy.infra.cloud`는 `skip_rule="no_infra_change"`이고, `plan/validate/rules.py`는 `infra_inputs_changed`로 판단합니다. `plan/analyze/logic.py`는 새 secret 키가 있을 때만 이 값을 참으로 둡니다. `plan/` 아래에 부트스트랩 분기는 없습니다. 담당은 김준석(validate·planner)과 정준우 중 확인이 필요합니다(🟡).

### 4-5. 1차 최단 순서

1. `build_image` 등록(override·형식 통일 포함) + 계약 승인
2. 첫 플랫폼 적용 경로 결정(4-4 ①) + AWS 자격증명 준비(6-1) + `generate_infra` 등록 + 첫 플랫폼 적용 실측(CodeBuild 프로젝트 출력 확보)

6. 클라우드: E6(4-4 ③), `sync_env_to_cloud`, AwsProvider 4개, 검증 키 계약, 승인 화면 C-18, TLS 판정 수정

### 서윤님 (클라우드 검증·관리 페이지)

1. **P0** 배포 시작 UI: 대상(온프렘/클라우드/둘 다)과 ref(감시 브랜치 또는 `v*` 태그)를 고르면 `request_deployment`로 run을 만들고 상태를 보여 줍니다. 지금은 라우트도 버튼도 없습니다. 자동 감지에는 이 버튼이 아니라 설정 화면(2번)이 필요합니다. 시작 버튼은 `v*` 태그 수동 재배포(v1→v2→v1 리허설)와 API 직접 호출을 없애는 데 필요합니다.
2. **P0** 설정 화면에 저장소 URL, 감시 브랜치(기본 `prod`), 기본 대상, 자동 감지를 추가합니다. 온프렘 전용은 도메인 없이 저장할 수 있어야 합니다. 저장은 `save_project_settings(..., expected_version)`로 합니다.
3. **P0** 준비에 실패한 run의 승인 페이지를 500 대신 4xx로 응답하고, 결과 화면에 phase·code·detail·missing_tool을 보여 줍니다. 온프렘 단독 실패에 "클라우드 상태 변경 전" 문구가 뜨는 것을 고치고, 종료 상태에 `FAILED_VERIFY`를 추가합니다.
4. **P1** 웹의 store 직접 호출을 service 공개 API로 바꿉니다.
5. **P1** 클라우드: 승인 화면에 인프라 요약(C-18)·snapshot·step 목록을 보여 줍니다. `verify_tls`의 `:443` 판정을 고치고, health를 tier별 digest 비교와 deadline 안 폴링으로 고칩니다. health·`verify_tls`가 요구하는 키를 플랫폼 출력과 맞춥니다(준우·승환님과).

나중: 승인 화면 패치 가림 제거와 원문 표시(2차 패치 장면 전), Host 검사 확대·SSE 수정·웹 테스트, `post_report` 입력 확장, `/events`·`/api/chat` 501 정리와 채팅, 대시보드의 "로컬 검증 후 클라우드" 문구 정리, `collect_diagnostics`·`watch_post_deploy`, Slack 알림.

### 준우 (실행기·온프렘 + C1 부트스트랩·실행 경로)

0. **P0** O2 연동에서 나온 실행기 결함을 고칩니다(4-4-1): 실행 폴더 절대 경로, 빌드하지 않은 tier의 이전 이미지 넘겨주기. 이어서 FAKE 모드 cloud 첫 배포용 인프라 fixture 주입 지점도 만듭니다.
1. **P0** `build_image` 입출력 계약 승인(승환님 `NEEDS_CONTEXT`)과 `image_repository` 형식 확정.
2. **P0** 첫 플랫폼 적용 경로(4-4 ①)를 승환님과 정하고, `generate_infra` 등록 뒤 실제 AWS에서 첫 플랫폼 run을 1회 검증합니다(지금까지 fixture뿐).
3. **P0** 운영 준비: 준석님이 만든 IAM(또는 SSO) 사용자로 액세스 키를 직접 만들어 실행 PC(준우 PC)에 설정(6-1). 6-2의 남은 수동 단계 중 준우 몫인 프로젝트 설정 저장(웹 UI 전까지 공개 API)과 실행 PC gitleaks 설치. 앱 저장소 push 권한은 저장소 쪽 담당 확인 뒤 받습니다.
4. **P0** 팀 툴이 연결되면 새 승인으로 온프렘만 → 클라우드만 → 둘 다를 돌려 실패·복구·전체 시간을 다시 잽니다(기존 VM 시간은 재사용하지 않음).
5. **P1** 클라우드 검증 출력 계약(`region`·`ecs_cluster`·`ecs_service`·`target_group_arn`)을 서윤·승환님과 합의합니다.
6. **P1** 첫 클라우드 run의 층 순서(platform → app, 실행 역할·앱 시크릿 ARN)를 승환님과 정합니다.
7. **P1** Docker Hub 토큰 공급 방식을 승환님과 정합니다.
8. smoke·compare 새 계약 승인 기록, 패치 OFF 동작 확인.

나중: RunContext 검증 출력 필드(민영님 요청), import-linter 계약에 패치 검사기 추가, 3티어 데모 초기화(DB 포함), 온프렘 롤링 drain, 승인 대기 InfraBinding 재시작 복구, 낡은 표기 정리.

## 6. 데모 전 사전 준비(사람)

### 6-1. 받아들이는 1회 계정 준비

| 항목 | 내용 | 담당 |
|---|---|---|
| AWS 자격증명 | 팀 AWS 계정 관리자인 김준석(10/2 사용자 확인)이 정준우용 IAM 사용자(또는 SSO 사용자)를 만듭니다. 정준우가 자기 액세스 키를 직접 만들어 제품을 실행하는 PC(지금은 정준우 PC)에 설정합니다. 키는 채팅으로 주고받지 않고, 화면·로그·AI 입력에도 넣지 않습니다 | 사용자 생성 김준석 / 키 생성·설정 정준우 |
| 도메인 구매 | `gerbera.cloud` 구매, DNS는 Cloudflare. 클라우드 HTTPS와 TLS 검사에 필요합니다. 사면 공지합니다 | 담당 확인 필요 |
| VPN 끄기 | 데모·리허설 중 데스크톱 VPN을 끕니다(1-11) | 실행 PC 사용자 |

### 6-2. 현재 남은 수동 단계 (자동화 대상)

결정 6("사람 개입은 승인 클릭뿐")과 어긋나는 단계입니다. 자동화하기 전까지는 사람이 합니다.

| 항목 | 내용 | 담당 |
|---|---|---|
| 앱 저장소 브랜치·보호 | 기본 브랜치 `dev` → `prod`. `prod`만 보호(PR merge 필수, force push·삭제 금지). `main`·`ai-prod`·`deployed/*`는 보호하지 않습니다. `prod/` 아래 브랜치는 만들지 않습니다. 실행 PC 계정에 push 권한을 줍니다 | 담당 확인 필요(저장소는 장민영이 만듦) |
| 온프렘 인벤토리·`public_url` 갱신 | quick tunnel 주소는 재시작마다 바뀝니다. provision이 자동 기록하기 전까지 사람이 인벤토리를 고칩니다 | 자동 기록은 김준석(provision, 10/1 B7). 그 전 수동 갱신은 담당 확인 필요 |
| ACM DNS 검증 CNAME | 자동화하지 않으면 Cloudflare에 사람이 1회 추가합니다(10/1 B10) | 담당 확인 필요 |
| gitleaks 설치 | 실행 PC에 설치합니다. 없으면 후보 커밋 전 비밀 검사가 실패합니다 | 정준우(실행 PC) |
| 프로젝트 설정 저장 | 설정 화면이 생기기 전까지 공개 API(`save_project_settings`)로 저장합니다 | 정준우. 설정 화면은 양서윤(5절 서윤님 2번) |

공유 환경(온프렘 VM, ECS)에는 한 번에 한 명만 배포하고 채팅방에 알리는 규칙은 그대로입니다.
