# O2 김준석: 입구·분석 + AI 계획·계획 검증 + 온프렘 인프라

> **📌 10/1 밤 회의:** 브랜치 이름 `prod`(개발자) → `ai-prod`(후보) → `main`(배포된 코드), 환경별 기록은 태그 `deployed/onprem`·`deployed/cloud`. 온프렘·클라우드 대기 지점 제거(독립 진행, 교차 검증은 둘 다 성공 시).

> **📌 10/1 저녁 변경 (트리거 개편):** `receive_deploy_request`는 저장소 URL·브랜치(기본 `prod`)를 받아 임시 폴더로 가져오고(`git fetch` + `git archive`), `detect_changed_tiers`는 커밋 기준으로 새 `prod` 커밋을 환경별 마지막 성공 `source_sha`(그 배포에 쓴 `prod` 커밋, 릴리스 기록)와 비교합니다(태그 `deployed/<환경>`은 패치가 들어간 후보 커밋이라 비교 기준 아님). `generate_plan`·`validate_plan`은 run별 대상(온프렘만/클라우드만/둘 다)을 반영합니다. 채팅 의도에 "대상 선택"(온프렘/클라우드/둘 다)과 "질문"이 들어가고 질문에는 읽기 전용으로 답합니다(`call_ai`). E4/V15(cloud 단독 거부)는 없어집니다(툴 입출력·의도 스키마 변경은 15절 절차). V8은 클라우드 step의 `local_verified` 대기를 더 이상 강제하지 않습니다(10/1 밤 분리로 대기 지점 제거). 본문의 G1(`local_verified`) 대기·`ABORTED_AT_GATE` 서술 중 고치지 못한 곳은 10/1 밤 분리로 대기 지점 제거 — 구현 때 정리합니다([docs/21 §4](../../../docs/21_트리거-개편-문서-수정-목록.md)). 상세: [docs/20](../../../docs/20_트리거-개편-git-브랜치-기준.md)

> **📌 10/1 변경 (C1 분담):** 유상준 하차로 C1을 정준우·김준석이 나눕니다. `cloud/infra/tools/generate_infra`(AI Terraform HCL 초안)를 김준석이 맡습니다(분담 ✅, 세부 🟡 김준석 확인 대기). 이유: `call_ai`·Jev·분석·계획을 이미 맡아 analyze → planner → generate_infra가 한 라인이 되고, 분석의 비밀값 분류가 곧 시크릿 리소스 입력입니다. 입력은 분석 결과(비밀값 키 분류)와 환경 정보(`terraform output`), 출력은 `var/infra/<run_id>/` 아래 HCL 파일 + 메타(리소스 목록·이유)이고 backend·provider·자격증명 블록은 코드가 주입합니다(🟡 정준우와 먼저 합의, [roles/C1](C1_클라우드인프라-AI테라폼-10월1일%20수정본.md)). 9/30 밤 일정 행의 "유상준"은 당시 기록입니다.

> **📌 10/1 변경 (온프렘 VM):** Notion "온프렘 인프라 프로비저닝 방법"(web .10 · was .11 · db .12 · mon .13)은 테스트·구축 **예시**입니다. 실제 환경은 새로 구축하고 네트워크는 정준우가 엽니다. 인벤토리에 tier별 VM 주소·SSH 사용자·키 경로·호스트 키 지문·선택 `ssh.jump_host`를 담고, 공개 URL `public_url`은 provision이 기록합니다. **외부 공개는 Cloudflare Tunnel로 확정(✅ 10/1 밤 (2), 담당 김준석)**: provision이 web VM에 cloudflared를 띄우고, 도메인(`gerbera.cloud`, 구매 예정)을 사기 전에는 quick tunnel(cloudflared 로그에서 주소를 읽어 `public_url`에 자동 기록, 재시작마다 주소가 바뀜), 산 뒤에는 이름 있는 터널(`onprem.gerbera.cloud` 같은 고정 호스트명)로 바꿉니다. EC2 frp는 기각했습니다. 외부 접속이 https라 온프렘 쿠키 Secure·ProxyFix는 켭니다(`public_url` 스킴을 따르는 규칙: https면 켬, http면 끔). VM은 web(nginx + cloudflared)·was(Traefik + app-1..3)·db(MySQL) 3대이고 mon은 쓰지 않습니다. 맞출 것(🟡): ECR → Docker Hub, DB 그림 postgres → MySQL, WAS 프록시 예시 Node `trust proxy` → Flask ProxyFix([01 3-7](../01_공통-계약.md#3-7-온프렘-vm-환경--10월-1일)).

> **📌 9/30 오후 변경:** **AI 코드 수정이 P0**입니다. 분석에서 환경 의존 코드 패턴(하드코딩된 `SECRET_KEY`, 코드 안 `localhost` 주소, 쿠키 `Secure`·ProxyFix 하드코딩)을 탐지하면, 계획에 패치 step을 넣습니다(토글 ON, 데모 ON). 지원 패턴 밖은 보고로만 남깁니다([01 3-5](../01_공통-계약.md#3-5-ai-코드-수정-약속--p0-9월-30일-오후)). 백엔드 웹 프레임워크는 FastAPI로 확정됐습니다(✅ 9/30, Django 아님).

## 1. 한 줄 요약과 핵심

**한 줄:** 배포 요청을 받아 "무엇이 바뀌었고 무엇이 필요한지"를 사실(facts)로 만들고, 그 사실로 안전한 `plan.json`을 조립·검사합니다. 그리고 온프렘 환경(MySQL·네트워크·인벤토리·Docker Hub 로그인)을 준비합니다.

| 왜 중요한가 | 설명 |
|---|---|
| 실행기는 `plan.json`만 실행합니다 | 계획이 틀리면 뒤 단계가 전부 틀립니다. 실행기(정준우 O1)는 계획을 다시 판단하지 않습니다 ✅ |
| `validate_plan`이 AI 경계의 관문입니다 | AI가 무엇을 제안하든 필수 step 삽입, 금지 키 거부, 대기 지점 강제는 이 코드가 합니다 ✅(장부 5) |
| AI 없이도 끝까지 가야 합니다 | 규칙 계획만으로 E2E가 돌아야 합니다. AI(Jev·Claude)는 더하기·설명만 합니다 ✅(장부 5·8) |
| 시크릿 장면의 출발점입니다 | v2에서 새 키 `SECRET_KEY`를 찾아 인프라 요구 해시를 바꾸는 것이 O2 코드입니다. 이게 없으면 인프라 step이 안 켜집니다 ✅(장부 32) |
| `call_ai`가 막히면 인프라도 막힙니다 | 💭 05 역할표상 `call_ai`는 O2 담당입니다. 본인(김준석)의 `generate_infra`(P0, C1 분담)가 이것을 부릅니다 |
| 온프렘 값의 원본을 만듭니다 | 온프렘 서버 주소·DB 주소·`.env` 경로는 O2가 쓰는 인벤토리 파일에서만 나옵니다 ✅(장부 27) |

## 2. 최종 목표와 완료 기준

**최종 목표(10/3 제출·10/4 데모 기준):** v2(`feature/login`) 코드(스냅샷)를 넣으면 AI 없이도 올바른 `plan.json`이 나오고 검증을 통과합니다. v2는 인프라 요구 해시가 바뀌어 `deploy.infra.cloud`가 들어갑니다(온프렘 검증을 기다리지 않음, 10/1 밤 분리). 부트스트랩이면 인프라 step이 클라우드 첫 step입니다. 온프렘에서 두 tier가 Docker Hub 이미지를 받아 MySQL에 붙어 돕니다.

**완료 기준 (P0, 10/1 23:59 E2E 기준 💭)**
- [ ] v2 스냅샷 → 규칙 계획 → `plan.json` 생성·검증 통과. `build.was`만 포함, `build.web`은 이유와 함께 제외
- [ ] v2 계획에 `deploy.config.*`, `deploy.db.*`, `deploy.secrets.cloud`, `deploy.infra.cloud` 포함. 모양이 [02 §6-4](../../docs/02_파이프라인과-계획.md) 골든 예시와 같음
- [ ] 부트스트랩 계획: `mode=bootstrap`, 조건부 step 전부 강제 포함, `deploy.infra.cloud`가 클라우드 첫 step, 빈 DB 검사(V18)
- [ ] facts JSON 2종(v2·부트스트랩) + `plan.json` 2종(update·bootstrap) 산출
- [ ] `validate_plan` 테스트: 통과 사례 + 불합격 사례(아래 5절 표의 규칙마다 1개 이상)

- [ ] 인프라 요구(`infra_needs`)와 해시: v1과 v2의 해시가 다름(시크릿 키 이름 `SECRET_KEY` 추가)
- [ ] 환경 정보 **가린 요약** 변환 함수 + 테스트(ARN·IP·도메인·엔드포인트가 결과에 없음)
- [ ] `call_ai`: live backend 1개(`api` 또는 `cli`) + `replay` 동작, 본인의 `generate_infra`(C1 분담)가 호출 가능
- [ ] `call_ai` replay 응답 fixture(데모 비상용)

- [ ] 인벤토리 `platform.onprem.yaml` 작성
- [ ] 각 tier 호스트에서 Docker Hub **읽기 전용 토큰**으로 `docker login` → digest pull 성공(정준우 O1과 확인, AWS 자격 없이)

### 6-2. 형식 요약 (착수용 요약, 전부 💭. 공통 계약과 다르면 공통 계약을 따름)

**`PlanDraft` (AI 또는 규칙이 만듦)**
```json
{
  "decisions": [
    {"step": "build.web", "include": false, "reason": "web/·nginx/ 변경 없음"},
    {"step": "verify.watch.cloud", "include": false, "reason": "데모 시간"}
  ],
  "add_scenarios": ["auth"],
  "warnings": [{"code": "indirect_config", "message": "from_prefixed_env 사용 흔적"}]
}
```
- `decisions[].step`: 조건부·선택 step id enum만(필수 step id는 enum에 없음). `add_scenarios`: {`base`, `auth`}. `warnings[].code`: enum(`indirect_config`, `hardcoded_secret`, `unsupported_migration` 등).

**`plan.json` 핵심 필드**

| 필드 | 누가 채움 | 비고 |
|---|---|---|
| `schema` | 조립기 | `ddak.plan/v1`(`ddak`은 가칭) |
| `run_id`, `project`, `mode` | 코드 | `mode`: `update` / `bootstrap` |
| `facts_hash`, `plan_hash` | 코드·조립기 | 정규화 JSON의 sha256 |
| `planner` | 조립기 | `by`(ai/rule), `provider`(jev/claude-api/claude-cli/replay/rule), `model`, `source`, `attempts`, `fallback` |
| `toggles` | 코드 | `{"code_patch": false}`(일반 실행 기본 OFF, 데모 ON ✅ 9/30 오후) |
| `build` / `deploy.local` / `deploy.cloud` / `verify` | 조립기 | 각각 `steps[]`, `skipped[]`. 배열 순서 = 실행 순서 |
| step `id`·`tool`·`target`·`tier`·`params`·`layer`·`effect`·`wait_for`·`signal`·`run` | 조립기(카탈로그) | `effect`·`wait_for`·`signal`은 AI가 써도 덮어씀. `wait_for`는 항상 배열. 신호는 4개 고정: `infra_ready`, `images_ready`, `local_verified`, `cloud_verified` |
| step `by`·`reason`·`evidence` | AI/규칙 | 표시용 |
| `skipped[]` | 조립기 | `skip_rule`(결정적 규칙 id) 필수 |
| `invalidated[]` | 조립기 | 예: `{"id":"deploy.db.cloud","attempt":"skip","by":"ai","result":"forced_include","why":"migrations_unchanged(cloud)=false"}` |

- step id 패턴 `^[a-z][a-z0-9_]*(\.[a-z0-9_]+){1,3}$`(점이 하나 이상, 그래서 `verify.report`). 전체 골든 예시는 [02 §6-4](../../docs/02_파이프라인과-계획.md).

**v2 step 판정 요약**

| step | v2 | 근거 fact / 규칙 |
|---|---|---|
| `build.was` | 포함 | `tree_changed.was` |
| `build.web` | 제외 | `tree_unchanged`(모든 대상 마지막 성공과 같고 그 digest가 Docker Hub에 있음) |
| `deploy.config.local` | 포함 | 새 키 SECRET_KEY·SESSION_COOKIE_SECURE |
| `deploy.db.local` / `deploy.db.cloud` | 포함 | `pending_migrations`(0002) |
| `deploy.was.local` | 포함 / `deploy.web.local` 제외 | digest 변경 / `digest_deployed` |
| `deploy.infra.cloud` | 포함 | `infra_inputs_changed`(V22), update 포함 → `state_change`(V23) |
| `deploy.secrets.cloud` → `deploy.config.cloud` → `deploy.app.cloud` | 포함 | V6 결합 |
| `deploy.dbinit.cloud` | 제외 | `db_initialized` |
| `deploy.tls.cloud`, 헬스·스모크·`verify.tls.cloud`·`verify.compare`·`verify.report` | 필수 | 층: 필수 |
| `verify.watch.cloud` | 제외 | 선택 |

- `tree_changed`·`tree_unchanged`는 옛 이름입니다. 뜻은 "빌드 입력 파일의 내용 해시(스냅샷 해시 목록)가 대상 환경의 마지막 성공과 다름/같음"입니다. git 트리 해시가 아닙니다([01 3-6절](../01_공통-계약.md#3-6-변경-탐지-스냅샷-내용-해시--9월-30일-오후)).

**`analyze_project` 출력 중 키 분류**
```json
{"keys": [{"key": "SECRET_KEY", "class": "secret", "varies_by_env": true,
           "policy": "generate_per_env",
           "evidence": [{"file": "flaskr/__init__.py", "line": 14}], "why": "세션 서명"}],
 "unsupported": []}
```
- `class`: secret / plain / address. `policy`: `generate_per_env` · `platform_ref` · `derive_from_public_url` · `derive_from_public_scheme` · `platform_profile` · `constant`.
- 정적 스캔 대상: `os.environ[...]`, `os.getenv`, `app.config[...] =`, `from_mapping`, (`from_prefixed_env`는 흔적만 경고).

**인프라 요구 `infra_needs` (C-17)**
- 필드: tier · 포트 · DB 엔진 · 시크릿 키 **이름** · 헬스 경로 · desired 규칙. 값·도메인·계정 ID 없음.
- v1: 시크릿 키 `DATABASE_URL`(+ 💭 `DATABASE_URL_MIGRATOR`). v2: 여기에 `SECRET_KEY` 추가 → 해시 변경.

**가린 요약 (C-22)**
- 담는 것: 키 이름, tier, 리소스 종류·개수, "시크릿 `ddak/flaskr/*` 2개 있음" 같은 사실.
- 빼는 것: ARN, 엔드포인트, IP, 도메인, 계정 ID, state·plan·출력 원문, 비밀값.

**온프렘 인벤토리 `platform.onprem.yaml` (C-04)**
```yaml
targets:
  onprem:
    mode: container            # container | vm
    public_scheme: http                # vm: public_url 스킴(https/http)을 따름
    public_url: "http://localhost:8080"   # vm: provision이 기록한 공개 주소(quick tunnel "https://<무작위>.trycloudflare.com" 또는 이름 있는 터널 "https://onprem.gerbera.cloud")
    hosts:
      web: { docker: "unix:///var/run/docker.sock" }   # vm: "ssh://deploy@<web IP>"
      was: { docker: "unix:///var/run/docker.sock" }   # vm: "ssh://deploy@<was IP>"
      db:  { docker: "unix:///var/run/docker.sock", prebuilt: true }
    addresses:
      was_upstream: "172.30.0.10:8000"   # vm: "<was IP>:8000"
      db_host: "flaskr-db:3306"          # vm: "<db IP>:3306"
    env_file: "/srv/flaskr/was.env"
    registry: { provider: dockerhub }   # 토큰 값은 파일에 없음(각 호스트의 docker login)
```

```json
{"action": "deploy_request|status_query|explain_last_run|unknown", "target": "both|local", "ref": "feature/login"}
```
- 부작용이 있는 것은 `deploy_request`뿐이고, 이것도 사람이 [배포]를 눌러야 실행됩니다 ✅(장부 4-a). `ref` 존재는 코드가 확인합니다.

## 7. AI 사용 경계

| AI가 하는 것 | AI가 하지 않는 것 |
|---|---|
| 키마다 secret/plain/address 분류, 환경마다 달라야 하는지(Jev, 대체 Claude, P1) | 값 보기·생성, IP·도메인 만들기, 규칙이 찾은 키 지우기 |
| 조건부·선택 step 포함/제외 제안 + 이유, `auth` 시나리오 추가, 경고(P1) | 필수 step 빼기, 순서·`wait_for`·`signal` 정하기, 계획에 값 넣기, 인프라 step 빼기(V22) |
| 채팅 문장 → 의도 JSON(P1) | 실행·승인, `ref` 존재 판단 |
| (본인 `generate_infra`가 `call_ai`로) HCL 초안 | apply, IAM 생성(사람 승인 뒤 코드) |
| – | `validate_plan` 판정(순수 함수, AI import 금지 ✅) |
| – | 마이그레이션 파괴형 판정, 관문·롤백 판단, 보고 심각도(규칙·고정 표) |

- 규칙이 바닥입니다. AI 답은 step을 **늘리거나 경고하는 쪽으로만** 반영합니다(Jev는 diff 속 악의적 문장에 흔들릴 수 있음). 분류가 규칙과 다르거나 Jev 신뢰도가 낮으면(💭 0.7 미만) secret 쪽 + 사람 확인.
- 정직한 문장: 골든 패스의 탐지는 규칙으로 다 됩니다. AI의 가치는 규칙이 못 보는 이유로 step·시나리오를 **넣는 것**과 **설명**입니다. "AI가 계획을 결정한다"고 말하지 않습니다.
- Jev를 쓰지 않는 곳: 마이그레이션 파괴형 판정, 관문·롤백, 보고 심각도, 채팅 의도.
