## 1. 한 줄 요약과 핵심

**한 줄 요약:** 바뀐 tier를 CodeBuild로 빌드해 Docker Hub에 digest로 올리고, 그 digest를 ECS Fargate에 배포합니다. 시크릿 값은 코드가 난수로 넣고 아무도 보지 않게 합니다. 클라우드가 실패하면 클라우드만 이전 태스크 정의로 되돌립니다.

**왜 중요한가**

| 이유 | 내용 |
|---|---|
| "같은 이미지" 약속의 클라우드 쪽 | 온프렘과 클라우드가 **같은 이미지 index digest**를 쓴다는 주장은 C2 코드가 지킵니다. 증거는 태스크 정의의 index digest = manifest, 그리고 `describe_tasks`의 `imageDigest`(index 또는 플랫폼 digest)가 manifest index의 플랫폼 항목에 속하는 것입니다(플랫폼 digest는 ARM과 AMD64가 정상적으로 다름). |
| 데모 클라우드 열의 대부분 | 빌드(40~85초 [추정]), 시크릿 값 쓰기, 태스크 정의 등록, 마이그레이션 태스크, ECS 롤링(65~127초 [추정], 온프렘과 독립)이 전부 C2 코드입니다. 3분 대본의 시간은 여기 실측으로 정해집니다. |
| 시크릿 장면의 증명 | v2 라이브 장면(✅ 장부 32)의 "값은 Terraform state·AI·화면에 없다"를 실제로 지키는 곳이 `sync_env_to_cloud`입니다. |
| AI가 없는 영역 | C2 툴에는 AI가 없습니다. 결정적 코드로 끝까지 도는 것이 전부입니다. |

## 2. 최종 목표와 완료 기준

**최종 목표**
- 10/3 제출·중간보고 전에: v2 로그인 배포 run의 클라우드 트랙이 끝까지 돌고, 실패하면 클라우드만 롤백됩니다. 부트스트랩(v1 첫 배포)도 같은 코드로 돕니다.
- 10/4 결선 라이브 데모(참고): 같은 run을 한 번 라이브로 합니다. 부트스트랩은 녹화로 보여 줍니다(💭 [docs/03 10절](../../docs/03_골든패스-시나리오.md)).

**완료 기준** (10/1 23:59 E2E 기준, 💭 [docs/05 4-4절](../../docs/05_역할과-일정.md))
- [ ] 같은 이미지(index digest `docker.io/<조직>/<저장소>@sha256:…`)가 ECS에 뜬다. `describe_tasks`의 `imageDigest`가 manifest index의 플랫폼 항목에 속한다(index가 오면 manifest index와 같음). 관측값을 정규화해 기록한다.
- [ ] 클라우드 앱이 공유 RDS 안 앱 DB `flaskr`에 **앱 계정**으로 TLS 연결된다(클라우드 `/version`의 `db.dialect = mysql`).
- [ ] v2 `SECRET_KEY` 값이 Terraform state·로그·화면·manifest·AI 입력 어디에도 없다. 남는 것은 ARN뿐이다.
- [ ] **부트스트랩 1회**: web+was 빌드 → DB 비밀 쓰기 → 앱 DB·계정 생성 → 첫 태스크 정의 → migrate 0001 → 서비스 기동.
- [ ] **업데이트 3회 연속**: `build.was`만 빌드되고 web은 rel-v1 digest 재사용. 그중 1회 이상 시크릿 장면(PutSecretValue → `secrets` valueFrom → 배포).
- [ ] **실패 주입**(온프렘 migrate 건너뛰기): 클라우드는 영향 없이 독립적으로 계속 진행한다(✅ 10/1 밤 분리).
- [ ] 클라우드 실패 때 `rollback_tier`가 이전 태스크 정의로 되돌린다(💭 리허설에서 1회 이상 주입).
- [ ] 단계별 소요 초를 3회 이상 기록한다(CodeBuild 프로비저닝·빌드·push, RunTask, ECS 롤링).
- [ ] 툴마다 fake 정상 1개·실패 1개 + moto 호출 형태 테스트가 있고, 코드 템플릿의 검사 명령(`make check`)이 통과한다.

## 3. 파이프라인에서 내 위치

### 3-1. 5단계 중 어디

| 단계 | C2 코드 | 비고 |
|---|---|---|
| ① 플랜 | 없음 | – |
| ② 계획 검증 | 없음 | 계획(plan.json)을 받기만 합니다 |
| ③ 빌드 | `build_image`(cloud), `push_image`, 플랫폼 buildspec | 공통 트랙. 끝나면 신호 `images_ready`(G0) |
| ④ 배포 | `sync_env_to_cloud`, `inject_env_config`(cloud), `prepare_db`(cloud), `deploy_tier`(cloud), 실패 시 `rollback_tier`(cloud) | 클라우드 트랙. 온프렘 검증을 기다리지 않고 독립 진행(✅ 10/1 밤 분리, 장부 6 대체) |
| ⑤ 검증 및 보고 | 직접 없음 | 양서윤(C3)의 `health_check`·`smoke_test`가 내 배포를 확인합니다 |

- 온프렘 쪽 같은 툴(`inject_env_config`·`prepare_db`·`deploy_tier`·`rollback_tier`의 local)은 정준우(O1)의 onprem provider입니다. 클라우드의 `ensure_tls`는 정준우(C1 몫), `health_check`는 양서윤(C3)입니다.

### 3-2. v2(로그인) 데모 run에서 내 코드가 불리는 순간

- 시각은 [배포] 클릭 기준이고 전부 [추정]입니다([docs/03 7절](../../docs/03_골든패스-시나리오.md)).
- v2에서는 새 시크릿이 인프라 apply로 생기므로, **인프라 apply 전에 C2가 하는 일은 빌드뿐**입니다(10/1 밤: G1 대기 제거).

| 시각 [추정] | step | 내 코드 | 하는 일 |
|---|---|---|---|
| 0초 | 잠금 뒤 `build.was` | `build_image(tiers=[was])` | 승인 뒤 수정본 스냅샷 zip을 S3에(버전 ID, 업로드 주체 = `build_image` ✅ 9/30 오후), `StartBuild`(바뀐 tier만) |
| 0~85초 | (CodeBuild 안) | 플랫폼 buildspec | push 토큰으로 `docker login` → 멀티 아키텍처 빌드(`--platform linux/amd64,linux/arm64`, P0는 QEMU) → Docker Hub push → index digest·플랫폼별 digest를 exported variable로 |
| 40~85초 | 빌드 뒤(내장) | `push_image` | Docker Hub에 digest가 있는지 확인 → manifest `images.was.ref` 기록 → G0 `images_ready` |
| (동시에) | `deploy.tls.cloud` | –(정준우, C1 `ensure_tls` 확인 모드) | 이후 클라우드 트랙은 인프라 apply로 이어짐(온프렘 대기 없음, 10/1 밤) |
| 52~110초 | (온프렘 병행) `local_verified` | – | 온프렘 검증 통과(O1·O3). 클라우드는 기다리지 않음(10/1 밤 분리, 시각은 구현 때 다시 계산) |
| (대기 없음) | `deploy.infra.cloud` | –(정준우, C1 `apply_infra`) | 앱 층 시크릿 1개 + 실행 역할 정책 1개. 새 시크릿 ARN이 환경 정보(Terraform 출력)에 들어감 |
| 이어서 | `deploy.secrets.cloud` | `sync_env_to_cloud(keys=[SECRET_KEY])` | 값이 없는지 확인 → 난수 생성 → `PutSecretValue` → 값 버림 → ARN만 반환 |
| 이어서 | `deploy.config.cloud` | `inject_env_config(target=cloud)` | app·migrate 태스크 정의 새 리비전 등록. 서비스는 전환하지 않음 |
| (위 셋 합쳐 12~60초) | | | IAM 전파가 늦으면 첫 태스크가 새 시크릿을 못 읽을 수 있음(확인 필요) |
| 이어서 | `deploy.db.cloud` | `prepare_db(target=cloud, migrations=[0002])` | migrate 태스크 `RunTask`(25~45초) → exitCode + CloudWatch의 `MIGRATE_RESULT` 줄 |
| 이어서 | `deploy.app.cloud` | `deploy_tier(target=cloud)` | `UpdateService(새 리비전)` → 새 대상 healthy + `/version` release_id 일치까지 폴링(35~70초) |
| 129~297초 | `verify.*.cloud` | –(C3) | health·TLS·스모크 → `cloud_verified` |
| 실패하면 | 내장 | `rollback_tier(target=cloud)` | 이전 app 태스크 정의 ARN으로 `UpdateService` |

## 4. 만들 것 목록

- 모든 입력에 `run_id`가 있으므로 표에서는 뺐습니다. **입력에 도메인·IP·digest·ARN·비밀값은 없습니다.** 그런 값은 실행 컨텍스트(환경 정보 스냅샷, "ctx")에서 코드가 채웁니다(✅ 장부 6·27).
- AI 사용은 전부 "없음"입니다. `cloud.build`·`cd` 모듈에는 AI 툴이 없습니다(💭 레지스트리 규칙).

## 5. 꼭 있어야 하는 과정 (필수 동작·안전장치)

### 5-1. 빌드

- [ ] 배포 참조는 **digest 고정만** 씁니다(`docker.io/<조직>/<저장소>@sha256:<64hex>`). 태그는 표시용(💭 `<tier>-<release_id>`)입니다. 어댑터가 태그 참조를 거부합니다. (digest 고정 ✅ 장부 28)
- [ ] push 토큰은 buildspec `env.secrets-manager`로 받아 `docker login --password-stdin`만 합니다. **빌드 인자·secret mount로 `docker build`에 넘기지 않습니다.** 로그에 찍지 않습니다. (방식 ✅ 장부 28, 세부 💭)
- [ ] 소스의 `buildspec.yml`은 무시하고 플랫폼 buildspec만 씁니다. privileged는 Docker 빌드에만 씁니다. 💭
- [ ] 멀티 아키텍처가 기본입니다(✅ 9/30). buildx `--platform linux/amd64,linux/arm64`로 한 태그(index)에 묶고, 릴리스 기준은 index digest, `platform_digests`(amd64·arm64)도 함께 기록합니다(인덱스 digest ≠ 플랫폼별 digest). P0는 QEMU로 시작하고 빌드 시간을 잽니다.
- [ ] buildspec 첫 줄에서 override로 받은 env 값의 형식을 정규식으로 검사하고, 틀리면 값을 출력하지 않고 종료합니다(💭 E32 대응, [research/IAM 14-6](../../../research/2026-09-30_IAM-최소권한-설계.md)).
- [ ] 두 빌드 step이 모두 켜지면 CodeBuild **1회**로 묶습니다(tier 목록 env). 💭
- [ ] Dockerfile이 생성본이면 승인 기록(sha256)이 있는 것만 빌드합니다(V26, P1).

### 5-2. 시크릿 값

- [ ] 값은 코드가 시스템 난수로 만듭니다(`secrets.token_hex(32)`). 환경 간 공유 금지, 이미 있으면 재사용합니다(매번 바꾸면 전원 로그아웃). (✅ 장부 13·32)
- [ ] **값이 없을 때만** `PutSecretValue`합니다. 배포 역할에는 `GetSecretValue`가 없으므로, 값 존재 여부는 `DescribeSecret`의 버전 단계(`AWSCURRENT`)로 봅니다(💭 구현 방법).
- [ ] `CreateSecret`은 하지 않습니다. 시크릿 **리소스**는 AI Terraform(`generate_infra`, 김준석)이 값 없이 만듭니다. (✅ 장부 32)
- [ ] 값은 메모리에서 바로 버립니다. 출력·manifest·이벤트·로그에는 **ARN만** 남깁니다. 비밀 필드는 pydantic `SecretStr`, 문자열은 redact를 거칩니다.
- [ ] Docker Hub 토큰 값은 코드가 다루지 않습니다. 사람이 Secrets Manager에 넣습니다. 채팅·저장소에 붙여넣지 않습니다.

### 5-3. 태스크 정의·배포·롤백

- [ ] ARN·엔드포인트·서브넷은 **환경 정보(Terraform 출력, C-03)에서만** 읽습니다. 하드코딩 금지, state 원문 파싱 금지. (✅ 장부 27)
- [ ] 태스크 정의 등록은 서비스 전환이 아닙니다(`additive_prep`). 전환은 `deploy_tier`에서만 합니다.
- [ ] ECS는 **시작 때만** 시크릿을 주입합니다. 시크릿이 바뀌면 새 리비전 + 새 배포가 필요합니다(V6 결합).
- [ ] `deploy_tier`는 ECS `COMPLETED`를 기다리지 않습니다. "새 대상 healthy + `/version` release_id 일치"로 끝냅니다. ALB는 대상이 전부 unhealthy면 fail-open이므로 "트래픽이 간다"를 통과 근거로 쓰지 않습니다. 💭
- [ ] 롤백은 **앱만, 클라우드만**, 이전 app 태스크 정의 ARN으로 합니다. DB는 되돌리지 않습니다(추가형 마이그레이션만). (✅ 장부 6)
- [ ] 롤백은 **현재 상태를 먼저 조회**하고 필요한 것만 하는 멱등 동작입니다. 타임아웃 뒤에는 `update_service`가 이미 나갔을 수 있습니다. 롤백이 실패하면 `NEEDS_HUMAN`입니다.
- [ ] 부트스트랩은 롤백 대상이 없습니다. 실패하면 중지(desired 0)입니다.

### 5-4. DB

- [ ] 클라우드 migrate는 온프렘 검증을 기다리지 않습니다(✅ 10/1 밤 분리, 장부 6 대체). migrate 태스크는 마이그레이션 계정 시크릿을 씁니다(💭 장부 35).
- [ ] 결과 판정은 exitCode + `MIGRATE_RESULT` 한 줄(C-09)입니다. 러너가 `GET_LOCK`과 문장 단위 가드를 가집니다(장민영).
- [ ] `mode=init`은 `IF NOT EXISTS`로 없을 때만 만듭니다. 앱 계정은 최소 권한입니다(✅ 장부 23, 💭 DML만 + `REQUIRE SSL`). SQL은 정준우(C1 몫)가 설계한 템플릿을 씁니다.
- [ ] RDS 관리형 마스터 시크릿은 **DB 초기화 태스크 실행 역할만** 읽습니다. 그 역할은 배포 역할의 PassRole 목록에 넣지 않습니다(research/IAM E29). 실행 자격은 결정 필요(10-2절 #3).

### 5-5. 공통

- [ ] 모든 ④ 툴은 `lock_token`을 받고, 틀리면 `LOCK_INVALID`입니다.
- [ ] 어댑터가 `ctx.deadline`을 스스로 지킵니다(boto3 waiter 최대 횟수). 실행기의 취소는 스레드 안 boto3 호출을 멈추지 못합니다.
- [ ] `state_change` step은 자동 재시도하지 않습니다. 재시도는 툴 안의 읽기 폴링에서만 합니다. 💭
- [ ] 오류 메시지·`detail`에 비밀값·계정 ID·절대 경로를 넣지 않습니다(관리 페이지·LLM·Slack으로 흘러감).
- [ ] C2 툴은 스스로 승인하지 않습니다. 실행기가 사람 승인(한 화면·한 번 승인, 패치·배포·인프라 기록이 대상별로 따로 저장됨 ✅ 9/30) 뒤에만 부릅니다. `sync_env_to_cloud`는 별도 승인 없이 [배포] 클릭으로 갈음합니다(💭 현재값).

### 6-3. 형식 요약 (최종본은 공통 계약)

**이미지 참조** (✅ 장부 28, 태그 규칙 💭)
```text
배포:  docker.io/<조직>/<저장소>@sha256:<64hex>
태그:  <tier>-<release_id>        # 표시용. 저장소가 1개면 web·was를 태그로 나눔(N37)
```

**CD provider 결과** (💭 함수·인자, ✅ 인터페이스 구조 장부 29)
```text
deploy(tier, ctx) / rollback(tier, ctx) / migrate_db(migrations, ctx) / inject_config(keys, ctx)
  → ProviderResult{provider, function, applicable(기본 true), changed, detail(≤400자, 비밀·계정 ID·절대 경로 금지)}
```
- aws provider에서 C2 몫은 `deploy`·`rollback`·`migrate_db`·`inject_config`입니다(`providers/aws.py`는 위임 한 줄씩, 구현은 `ecs.py`·`secrets.py`·`database.py`). `ensure_tls`는 정준우, `health_check`는 양서윤입니다.
- provider는 코드가 target으로 고릅니다(fake 모드면 fake provider). AI가 고르지 않습니다.
- 수행 불가는 `DdakToolError(ErrorCode, 메시지)`. 주로 쓸 코드 💭: `ADAPTER_TIMEOUT`, `ADAPTER_FAILED`, `PRECONDITION_FAILED`, `INFRA_MISSING`, `LOCK_INVALID`, `CONFIG_INVALID`.

**태스크 정의 모양** (💭, D3=(a) 한 태스크 2컨테이너 가정)

  "requiresCompatibilities": ["FARGATE"],

  "runtimePlatform": {"cpuArchitecture": "(X86_64 또는 ARM64, 멀티 아키텍처라 둘 다 가능)"},

## 7. AI 사용 경계

| AI가 하는 것 (내 영역 주변, 전부 다른 역할의 툴) | AI가 하지 않는 것 (내 영역) |
|---|---|
| 새 키 분류: `SECRET_KEY` = secret(김준석 O2, Jev/Claude) → 내가 받는 키 목록의 근거 | 시크릿 값 생성·열람. 값은 코드 난수뿐 |
| AI Terraform: 시크릿 컨테이너·실행 역할 권한·CodeBuild 프로젝트 제안(김준석 `generate_infra`). 검증·사람 승인 뒤 apply(정준우) | buildspec·빌드 명령·태스크 정의 작성 |
| (Dockerfile이 없을 때) Dockerfile 초안(장민영 O3, P1). 승인된 것만 빌드 | provider 선택, digest·ARN·엔드포인트·도메인 결정 |
| 실패 원인 설명(`diagnose_parity_gap`, 장민영 O3). 내 오류 시그니처(redact)가 입력 | 배포·롤백·재시도 실행이나 판단 |

- 원칙: AI는 제안만 만들고, 실행은 검증·사람 승인 뒤 코드가 합니다(✅ 장부 4-a).
- 강제 수단(💭): `cloud.build`·`cd` 모듈은 AI 호출 창구(`call_ai`)를 import하지 않습니다. 레지스트리 규칙상 두 모듈에는 AI 툴이 없습니다.
- 내 코드는 AI에게 아무것도 보내지 않습니다. AI 쪽에는 환경 정보의 **가린 요약**(키 이름·종류·개수·있음/없음)만 갑니다(✅ 장부 27).
