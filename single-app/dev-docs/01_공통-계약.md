### 1-2. 데코레이터와 시그니처 (💭 모양)

```python
# src/ddak/cd/tools/prepare_db/tool.py  — AI 없는 배포 툴이 CD provider를 부르는 모양
from ddak.cd.dispatch import select_provider
from ddak.core.contracts.context import RunContext
from ddak.core.contracts.tools.prepare_db import PrepareDbInput, PrepareDbOutput
from ddak.core.registry import tool


@tool("prepare_db")  # 이름·위치·시그니처가 카탈로그와 다르면 앱 기동 실패
def prepare_db(inp: PrepareDbInput, ctx: RunContext) -> PrepareDbOutput:
    provider = select_provider(inp.target, ctx.adapter_mode)  # aws / onprem / fake. AI가 고르지 않음
    result = provider.migrate_db(inp.migrations, ctx)        # 주소·시크릿 ARN·digest는 ctx에서
    return PrepareDbOutput.from_result(inp, result)
```

```python
# AI 툴 모양 — AI가 실패해도 규칙 경로로 E2E가 돌아야 함
@tool("generate_plan")
def generate_plan(inp: GeneratePlanInput, ctx: RunContext) -> GeneratePlanOutput:
    facts = load_facts(inp, ctx)                                       # 키 이름·해시만, 값 없음
    try:
        draft = call_ai(purpose="plan_draft", schema=PlanDraft, data=facts.for_ai())
    except DdakToolError:                                              # AI_UNAVAILABLE / AI_OUTPUT_INVALID
        draft = rule_draft(facts)                                      # 규칙 계획
    return GeneratePlanOutput(run_id=inp.run_id, draft=draft)
```

- `call_ai`는 **`uses_ai=True` 툴 안에서만** 부를 수 있습니다. 그 밖에서 부르면 `AI_NOT_ALLOWED`입니다.
- 동기 함수(boto3·docker 호출) 또는 `async def` 둘 다 됩니다. 동기 함수는 실행기가 스레드에서 부릅니다.

### 3-2. 함수 ↔ 툴 ↔ provider

| 인터페이스 함수 | 부르는 툴 | aws provider(cloud, 안승환) | onprem provider(local, 정준우) |
|---|---|---|---|
| `deploy(tier, ctx)` | `deploy_tier` | 태스크 정의 새 리비전으로 `update_service` | tier 컨테이너를 digest로 재생성 |
| `rollback(tier, ctx)` | `rollback_tier` | 이전 태스크 정의 ARN으로 `update_service` | 이전 digest로 재생성 |
| `health_check(ctx)` | `health_check` | `/health/ready` + ECS `imageDigest`(양서윤, index 소속 확인) | `/health/ready` + `docker inspect` digest(장민영, index 소속 확인) |
| `migrate_db(migrations, ctx)` | `prepare_db` | 일회성 ECS 태스크(마이그레이션 계정) | was 호스트 일회성 컨테이너 |
| `inject_config(keys, ctx)` | `inject_env_config` · `sync_env_to_cloud` | 빈 시크릿에 난수 `PutSecretValue` + 태스크 정의 `secrets` valueFrom·`repositoryCredentials` | was `.env`(v2 난수 SECRET_KEY 포함) |
| `ensure_tls(mode, ctx)` | `ensure_tls` | ACM·443·HSTS·80→301·DNS(정준우, C1) | **해당 없음**(`applicable=False`, 로컬 HTTPS ⏸. 온프렘 외부 접속 스킴은 `public_url`을 따름, 3-7절) |

- AWS 진입점은 `cloud/deploy/providers/aws.py`(AwsProvider) 하나이고 **위임만** 합니다(✅ 10/1): `deploy`·`rollback`·`migrate_db`·`inject_config` → 안승환 `cloud/deploy/`의 `ecs.py`·`secrets.py`·`database.py`, `ensure_tls` → 정준우(C1) `cloud/tls/`, `health_check` → 양서윤 `cloud/health/`. 자세한 규칙은 [02](02_디렉토리-소유.md)입니다.
- GCP·Azure는 후순위입니다(CSP 우선순위 AWS 1순위). `cd/interface.py`의 `ProviderName`에는 GCP·AZURE가 있고 폴더·골격만 있습니다. 선택하면 명시적 "미지원" 오류가 나며 해커톤 동안 구현하지 않습니다(✅ 10/1 변경, 이전 "코드도 없다" 대체).
- 💭 공통 설정값 합치기(김준석 제안의 "Helm식 공유"): `deploy.yaml` 공통 키 → 대상별 덮어쓰기(`targets.local` / `targets.cloud`) → 환경 정보(코드가 채우는 주소·ARN·digest) 순서로 합쳐 provider에 **같은 모양**으로 넘깁니다. 템플릿 엔진은 쓰지 않습니다.

### 3-4. 이미지 1개 + 멀티 아키텍처 빌드 (✅ 9월 30일 오후)

> **10/2 정정:** "이미지 1개"는 두 환경이 같은 이미지를 공유한다는 뜻입니다. 이미지는 tier별(web·was)로 빌드하고, db는 공식 mysql digest를 씁니다(커스텀 빌드 없음). 빌드 소스는 그 run의 ai-prod 커밋 SHA입니다(3-6절).

**원칙**
- 코드는 하나로 고치고(AI 코드 수정 → 사람 승인), 이미지는 **한 번만** 빌드합니다. 온프렘·클라우드가 같은 이미지를 씁니다.
- 환경 차이는 이미지 밖에서 흡수합니다.

| 항목 | 온프렘 | 클라우드 | 흡수하는 곳 |
|---|---|---|---|
| DB 주소 | MySQL 서버 IP:3306 | RDS 엔드포인트 | `DATABASE_URL` 환경변수 |
| DB 계정·비밀번호 | `.env`(난수) | Secrets Manager | 배포 때 주입(ECS는 secrets valueFrom) |
| DB TLS | 없음 | 필수 + CA 검증 | `DATABASE_URL`의 TLS 옵션. RDS CA 번들은 이미지에 포함(온프렘에선 안 쓰임) |
| 앱 DB·계정 생성, 마이그레이션 | 같은 이미지·같은 명령, 일회성 컨테이너 | 같은 이미지·같은 명령, ECS 일회성 태스크 | provider(`onprem/deploy/provider.py` / `cloud/deploy/providers/aws.py`) |
| 쿠키 `Secure`·ProxyFix | `public_url` 스킴을 따름(https면 켬, http면 끔, 3-7절) | 켬 | 환경변수 플래그 |
| 로그 | docker 로그 | CloudWatch | 배포 명세(compose / 태스크 정의) |
| 포트·헬스 경로 | 같음 | 같음 | – |

**멀티 아키텍처 (기본)**
- 빌드: `docker buildx build --platform linux/amd64,linux/arm64 --push` 로 한 태그에 두 플랫폼을 묶습니다(이미지 목록 = index).
- CodeBuild에서 만드는 방법(💭, 담당 안승환): ① x86 빌드 환경에서 QEMU 에뮬레이션으로 두 플랫폼 빌드(간단, arm64 빌드가 느림) 또는 ② x86·ARM 빌드 환경에서 각각 빌드 후 `docker buildx imagetools create`로 합치기(빠름, CodeBuild ARM 서울 리전 지원 확인 필요). P0는 ①로 시작하고 빌드 시간을 잽니다.
- 배포: 온프렘 docker와 ECS는 자기 CPU에 맞는 플랫폼을 자동으로 받습니다. Fargate `runtimePlatform`은 X86_64·ARM64 어느 쪽이든 동작합니다(💭 비용은 ARM64가 약간 유리).
- 릴리스 기록: 기준은 **index digest**(`docker.io/<조직>/<이미지>@sha256:<index>`)입니다. 릴리스 목록에 `image_index_digest`와 `platform_digests`(amd64·arm64)를 함께 적습니다. 교차 검증의 "같은 이미지"는 index digest 일치로 판정합니다. 각 환경이 실제로 돌리는 이미지의 digest는 플랫폼별이라(ARM과 AMD64는 정상적으로 다름) 서로 같을 필요가 없고, 그 tier index의 `platform_digests` 항목에 속하면 합격입니다. 환경별로 관측한 플랫폼과 그 플랫폼의 실제 digest를 함께 기록합니다. ECS가 보고하는 digest가 index인지 플랫폼 digest인지는 확인이 필요하며, 정규화(index면 그대로 대조, 플랫폼이면 index 소속 확인)는 안승환·양서윤이 맡습니다. 10/1 저녁: 릴리스 기록에 `prod` 커밋·후보 커밋 SHA도 적고, 이미지 라벨에 후보 커밋 SHA를 남깁니다(3-6절).
- Docker Hub 푸시: 태그는 불변으로 쓰고(예: `r-<run_id>`), 배포는 항상 digest로 고정합니다.

### 3-6. 변경 탐지·후보 커밋: git 브랜치 기준 (✅ 10월 1일 저녁)

> 9/30 오후의 "로컬 폴더 스냅샷 내용 해시" 방식을 대체합니다. 결정 원문: [docs/20](../../docs/20_트리거-개편-git-브랜치-기준.md).

| 순서 | 무엇을 | 담당 |
|---|---|---|
| 0 | 시작: ① 수동(관리 페이지 채팅 지시, 자동 감지 끔) 또는 ② 자동(감시 브랜치의 새 커밋을 10~30초마다 확인, webhook 없음). 둘 다 승인 관문은 그대로 | 김준석(채팅 의도·감시): 준석님 기존 watch.py가 감시(main → prod 변경 요청) |
| 1 | 저장소 URL·브랜치(기본 `prod`)를 받아 임시 폴더로 가져옴(`git fetch` + `git archive`). 소스는 이 시점의 `prod` 커밋 SHA로 고정. 제외 목록(`.env*`, `instance/`, `*.sqlite`, `.git/` 등)은 코드 고정 유지 | 김준석(`receive_deploy_request`) |
| 2 | 새 `prod` 커밋을 **선택한 대상 환경별 마지막 성공 `source_sha`**(그 배포에 쓴 `prod` 커밋, 릴리스 기록)와 비교 → 바뀐 파일·tier 확정. `deployed/<환경>` 태그(적용된 패치가 들어 있는 후보 커밋)와는 비교하지 않음 | 김준석(`detect_changed_tiers`) |
| 3 | 바뀐 파일의 diff는 git에서 두 커밋을 비교해 만듦 → AI 분석 입력(신뢰할 수 없는 입력). 이전 스냅샷 zip·S3 폴백은 쓰지 않음 | 김준석 |
| 4 | 패치 재사용 적합성을 최신 prod에서 확인하고 맞지 않으면 패치 단계에서 재제안. 그 run의 승인 패치를 prod 원본에 적용한 build_files를 후보 기준으로 삼음. 이전 패치가 merge만으로 자동 승인·유지되는 것은 아님 | 장민영(패치·재사용 검증), 정준우(승인 트리 적용) |
| 5 | 승인 전 prod 원본에 승인 패치를 적용한 후보 트리 해시를 기록. 승인 뒤 ai-prod에 `prod`를 merge하고 승인 build_files로 관리 파일을 확정한 merge 커밋을 **일반 push**(이력 보존). 후보 관리 트리 해시를 다시 대조. git 충돌은 승인 트리로 해결해서 멈추지 않고 merge_conflicts로 기록. 재사용 패치가 새 prod에 맞지 않으면 승인 전 패치 단계에서 재제안 | 정준우(ai-prod 갱신·push·해시 대조, 실행기), 장민영(재사용 적합성·패치 내용·비밀값 검사) |
| 6 | 그 run의 후보 커밋 SHA를 CodeBuild `sourceVersion`에 고정해 빌드(브랜치 HEAD 아님). tier별 이미지(web·was), db는 공식 mysql digest, 멀티 아키텍처. 플랫폼 buildspec은 `buildspecOverride`로 강제. 이미지 라벨에 후보 커밋 SHA. S3는 대체 경로(✅ #9) | 안승환(`build_image`) |
| 7 | 배포·검증에 성공한 환경의 릴리스 기록에 `source_sha`(쓴 `prod` 커밋)와 `candidate_sha`(빌드·배포한 ai-prod 커밋)를 남기고, 환경별 태그 `deployed/<환경>`을 `candidate_sha`에 붙임(실제로 도는 코드, 롤백 기준). `main`은 선택 대상이 모두 성공하고 (둘 다면) 교차 검증도 통과했을 때만 `candidate_sha`로 fast-forward(배포된 코드, 파이프라인만). 교차 검증 실패·비교 불가면 `main` 미이동, 성공한 환경 태그만 이동(✅ 10/2). 다음 변경 탐지는 `source_sha`를 씀. 태그와 `main`은 **기록**이고 배포 트리거가 아님 | 정준우(`record_deploy_log`) |

- 릴리스 기록에 **`prod` 커밋 SHA(`source_sha`)와 후보 커밋 SHA(`candidate_sha`)를 둘 다** 남깁니다(필수). 변경 탐지는 `source_sha`, `deployed/<환경>` 태그·이미지 라벨·롤백은 `candidate_sha` 기준입니다. 새 패치가 없어도 관리 트리를 승인 build_files로 고정합니다. 패치 OFF면 prod 원본이 승인 트리여서 이전 AI 패치가 빠집니다(**정준우 확인 대기**). 최초 동일 부모인 경우 부모는 하나일 수 있습니다.
- 기준은 환경별입니다. 한쪽이 실패했거나 한쪽만 배포했으면 태그 `deployed/onprem`과 `deployed/cloud`가 다른 커밋을 가리킬 수 있습니다(온프렘·클라우드는 독립 진행, ✅ 10/1 밤).
- 데모 저장소는 공개입니다. ai-prod 커밋에는 "환경변수에서 읽게 바꾸는 코드"만 담고 실제 비밀값은 담지 않습니다(push 직전 검사). 커밋 메시지만 코드가 고정하고 author·committer는 실행 사용자의 Git 신원을 그대로 사용하며 AI 표시를 넣지 않습니다.
- ai-prod에는 파이프라인만 커밋합니다. 사람은 직접 커밋하지 않고, 잘못된 패치는 승인 내용을 고쳐 새 후보를 만듭니다. push 권한은 개인 PC 모드에서 사용자 본인의 git 인증을 쓰고, AI 입력·로그·이벤트에 넣지 않습니다.
- 승인한 diff는 관리 페이지에서 내려받을 수 있게 합니다. ai-prod → prod 되돌림 PR(개발자 코드에 패치 반영)은 추후입니다.
- 환경별 기록은 태그 `deployed/onprem`·`deployed/cloud`로 정했습니다(✅ 10/1 밤). 남은 결정: 폴링 간격(10~30초 중). CodeBuild 소스는 ai-prod 커밋 SHA로 확정(#9 merge, S3는 대체 경로, [docs/21](../../docs/21_트리거-개편-문서-수정-목록.md)).
- **로컬 폴더 모드(개인 시험용):** 9/30 오후 방식(폴더 zip + 파일별 sha256 목록, 같은 제외 목록, 환경별 마지막 성공 해시 목록과 비교)은 개인 시험용으로 남겨도 됩니다. 실행기는 입력이 폴더라 그대로 동작합니다.

**외부 공개 (✅ 10/1 밤 (2): Cloudflare Tunnel로 확정, 정준우)**

온프렘 외부 공개는 **Cloudflare Tunnel**로 정했습니다(구축 담당 김준석). 파이프라인 코드는 방식을 몰라도 되고 인벤토리 `public_url`(provision이 기록)만 읽습니다. EC2 frp 중계는 검토했으나 기각했습니다(아래 표에 기록용으로 남김).

구축은 간단합니다: web VM 안에 `cloudflared`만 설치하고 quick tunnel은 `cloudflared tunnel --url http://localhost:80` 한 줄로 엽니다(컨테이너로 띄워도 같음). 도메인(`gerbera.cloud`, 구매 예정)을 사기 전에는 quick tunnel, 산 뒤에는 이름 있는 터널을 씁니다.

| 항목 | 내용 |
|---|---|
| 터널: 구축 | web VM에 `cloudflared` 컨테이너 하나. 바깥으로만 연결하므로 들어오는 포트·공인 IP·EC2가 필요 없습니다. 온프렘 안에서 구축이 끝납니다 |

| 도메인·DNS | `gerbera.cloud`(구매 예정, 아직 구매 전). DNS는 Cloudflare. 클라우드 앱 레코드(예: `app.gerbera.cloud`)는 Cloudflare **프록시를 끄고(DNS only)** ALB를 가리켜 TLS가 ALB의 ACM에서 끝나게 합니다(`verify_tls` 그대로). ACM DNS 검증 CNAME은 Cloudflare에 1회 추가합니다(외부 DNS 모드). 도메인은 사람이 관리 페이지에 입력합니다 |
| 검토한 대안(미사용): 공인 IP | 포트 포워딩으로 web VM을 직접 공개합니다(+ 도메인이 있으면 certbot) |
| 실제 IP | 터널이면 nginx가 `CF-Connecting-IP` 헤더로 복원합니다(`set_real_ip_from` = cloudflared 주소). (기각한 frp 안은 PROXY protocol v2였음) |
| 검토한 대안(기각): EC2 frp 중계 | EC2 t4g + EIP + frps에 web VM의 frpc가 붙습니다. 기본은 http(`http://<EIP>/`)이고 HTTPS는 도메인 + certbot이 있을 때만 됩니다. 보안: SSH 22는 내 IP만 허용, frp 토큰은 난수(저장소·Notion 금지). AWS 인스턴스·보안 그룹·토큰 관리가 늘어납니다. **기각 이유: 처음 구축 시 AWS 의존, 인스턴스·포트·토큰 관리 부담** |
| 교차 검증 | 온프렘·클라우드 **두 공개 URL 모두**로 합니다 |
| 조건 | VM이 인터넷으로 나갈 수 있어야 합니다(네트워크는 정준우가 구성). VM이 올라 있는 정준우 데스크톱이 켜져 있고 온라인이어야 합니다. 터널은 행사장 망이 UDP 7844를 막으면 `--protocol http2`를 씁니다 |

**파이프라인 범위 (web·was·db, ✅ 10/2 3티어 결정)**
- 실행기의 온프렘 provider가 tier별 VM의 Docker를 **SSH로 원격 호출**합니다(`DOCKER_HOST=ssh://<VM>` 또는 docker context).
- 최초 배포는 db(공식 mysql digest)→was→web을 파이프라인이 배포합니다. 업데이트는 바뀐 tier만 롤링으로 교체합니다(web 입력이 같으면 이전 web 이미지 재사용). DB 데이터는 보존합니다.
  - db 배포는 설계 목표이고 현재 미구현입니다. 제품 계획은 deploy.yaml tier(web·was)만 `deploy_tier`로 만들고 db step·digest 공급이 없습니다. 3티어 db 기동은 검증 스크립트 경로(`harness/scripts/o1_onprem.py`)만 실측했습니다. G9d·`ensure_app_database`(김준석) 뒤 연결합니다([10/2 요약 4-4](roles/00_10월2일-변경사항.md)).
- was 배포 = app-1..3을 새 이미지 digest로 **하나씩 교체** + Traefik 라벨 부여. 실패하면 이전 digest로 롤백합니다(11-2절).
- 이미지는 **Docker Hub**(읽기 전용 토큰)에서 받습니다. **ECR 아님**. VM에는 AWS 자격증명이 없습니다.
- ARM VM(Apple Silicon)이 있어서 **멀티 아키텍처 이미지는 계속 필수**입니다(3-4절).
- db 컨테이너는 최초 배포 때만 만들고 이후 업데이트에서는 컨테이너·볼륨을 지우거나 교체하지 않습니다. 마이그레이션은 was VM의 일회성 컨테이너가 MySQL 3306으로 접속해서 합니다.
- 관리 앱(파이프라인)은 VM에 닿는 PC에서 실행합니다(✅ 10/1 밤 (2): VM이 있는 정준우 데스크톱에서 실행하거나 브리지 네트워크로 닿게 함. 호스트 전용 대역이면 그 PC에서만 접근 가능).
- 외부 CI/CD 도구(Jenkins·ArgoCD 등)는 쓰지 않습니다. 실행기가 그 역할입니다(✅ 10/1).

**초기 접근 준비 (파이프라인 전에 1회)**
- was VM(필요하면 web도)에 `deploy` 사용자를 만들고 공개 키를 등록합니다. 비밀번호 로그인은 끄고, `docker` 그룹에 넣습니다(docker 그룹은 root와 같은 권한임을 알고 씁니다).
- 파이프라인 노트북에 각 VM의 호스트 키 지문을 등록합니다(`known_hosts`).
- db VM은 SSH가 필요 없습니다. 앱 DB·계정만 준비합니다.
- 사람 또는 provision 스크립트(cloud-init 등)가 1회 수행합니다. AI는 관여하지 않습니다.
- `ops` `preflight_check`에서 SSH 접속·`docker version`·호스트 키 일치를 확인합니다.
- 배스천이 있는 환경은 인벤토리 `ssh.jump_host`(선택, ProxyJump)로 같은 코드가 동작합니다.

**인벤토리 필드** (형식 💭, 8-4절 예시의 `mode: vm` 형태)

| 필드 | 설명 |
|---|---|
| tier별 VM 주소 | web·was·db. 예: was `192.168.56.11` |
| SSH 사용자 | 예: `deploy` |
| SSH 키 경로 | 경로만 적습니다. 키 내용은 저장소에 두지 않습니다 |
| 호스트 키 지문 | VM마다 노트북 `known_hosts`에 등록한 지문. 접속 때 일치를 확인합니다(불일치면 중단) |
| `ssh.jump_host`(선택) | 배스천이 있을 때 주소. 있으면 ProxyJump로 접속합니다 |
| 공개 URL | `public_url`: provision이 기록(코드는 방식 무관. quick tunnel이면 임시 주소 자동 기록, 이름 있는 터널이면 고정 `https://onprem.gerbera.cloud`) |

**쿠키 `Secure`·ProxyFix**: 온프렘 쿠키 `Secure`·ProxyFix는 `public_url` 스킴을 따릅니다. https면 켜고(`X-Forwarded-Proto: https`), http면 끕니다(http에서 Secure 쿠키는 Safari·`http.cookiejar`에서 로그인 유지가 깨집니다). 외부 공개가 Cloudflare Tunnel(https)로 확정돼 외부 접속에서는 켭니다(✅ 10/1 밤 (2)). ProxyFix가 믿는 프록시 hop 수는 cloudflared → nginx → Traefik 체인에 맞아야 합니다(맞지 않으면 클라이언트 IP·스킴 판단이 틀어집니다). O3의 ProxyFix 패치 패턴이 이 값을 환경변수로 읽도록 합니다. 실제 hop 수는 헤더를 찍어 본 뒤 확정합니다(💭).

**보안**
- Cloudflare 이름 있는 터널의 터널 토큰은 비밀값입니다(저장소·Notion 금지, 13절). quick tunnel은 토큰이 없습니다. (기각한 frp 안이라면 frp 토큰도 비밀값이고 EC2 SSH 22는 내 IP만 열었어야 합니다.)
- SSH 키 내용은 저장소·AI 입력에 넣지 않습니다. 키 파일 경로만 인벤토리에 둡니다.

**김준석과 맞출 것 (🟡)**

| # | 항목 | Notion 내용 | 이 문서 기준 |
|---|---|---|---|
| 1 | 이미지 저장소 | ECR | Docker Hub (읽기 전용 토큰) |
| 2 | DB | 그림은 postgres, 단계는 mysql | MySQL |
| 3 | 서브넷 | 192.168.56.x, frpc 예시는 192.168.64.10 | 실제 구성은 새로 구축(예시 IP 무관) |
| 4 | WAS 프록시 예시 | Node `trust proxy` | Flask ProxyFix |
| 5 | 외부 공개 | EC2 frp 중계 | ✅ Cloudflare Tunnel(10/1 밤 (2), 정준우 확정). EC2 frp는 기각 |

## 4. `plan.json` (💭 스키마, 원본 [../docs/02](../docs/02_파이프라인과-계획.md) 6절)

### 4-1. 두 층

| 층 | 누가 만듦 | 담을 수 있는 것 | 담을 수 없는 것 |
|---|---|---|---|
| `PlanDraft` | `generate_plan`(AI) 또는 규칙 | 조건부·선택 step의 포함/제외 + 이유, 스모크 시나리오 추가, 경고 | 필수·내장 step, 순서, `wait_for`/`signal`, 도메인·digest·명령 같은 값 |
| `Plan`(= `plan.json`) | `validate_plan`(조립기, 순수 함수) | 카탈로그 + facts + 초안을 합친 최종 계획 | – |

- **실행기는 `Plan`만 실행합니다.**

### 4-2. `PlanDraft` (AI 출력)

```json
{
  "decisions": [
    {"step": "build.web",          "include": false, "reason": "web/·nginx/ 변경 없음"},
    {"step": "deploy.web.local",   "include": false, "reason": "web digest 동일"},
    {"step": "verify.watch.cloud", "include": false, "reason": "데모 시간"}
  ],
  "add_scenarios": ["auth"],
  "warnings": [{"code": "indirect_config", "message": "from_prefixed_env 사용 흔적"}]
}
```

| 필드 | 제약 |
|---|---|
| `decisions[].step` | 카탈로그의 **조건부·선택** step id enum. 필수 step id는 enum에 없음 |
| `decisions[].include` | bool |
| `decisions[].reason` | 200자 이하, 표시용 |
| `add_scenarios` | {`base`, `auth`} enum |
| `warnings[].code` | enum(예: `indirect_config`, `hardcoded_secret`, `unsupported_migration`) |

### 4-3. `Plan` 필드

| 필드 | 필수 | 누가 채움 | 설명 |
|---|---|---|---|
| `schema` | ✓ | 조립기 | `ddak.plan/v1` |
| `run_id` | ✓ | 실행기 | 12절 이름 규칙 |
| `project` | ✓ | 코드 | `deploy.yaml`의 `project` |
| `mode` | ✓ | 코드 | `update` / `bootstrap`(이전 성공 릴리스 없음) |
| `facts_hash` | ✓ | 코드 | facts 정규화 JSON sha256. 실행 시작 때 재계산, 다르면 재계획(V11) |
| `plan_hash` | ✓ | 조립기 | 켜진 step·params 정규화 JSON sha256. 매 step 직전 대조(V12) |
| `planner` | ✓ | 조립기 | `by`(ai/rule), `provider`(jev/claude-api/claude-cli/replay/rule), `model`, `source`, `attempts`, `fallback` |
| `toggles` | ✓ | 코드 | `{"code_patch": false}`(일반 실행 기본 OFF, 데모는 ON) |
| `build` / `deploy.local` / `deploy.cloud` / `verify` | ✓ | 조립기 | 각각 `steps[]`, `skipped[]`. 순서 = 배열 순서(카탈로그가 결정) |
| `build.signal` | ✓ | 조립기 | `images_ready` |
| step `id` · `tool` | ✓ | 조립기 | `id` = step id(12절), `tool` = 레지스트리 이름. 같은 툴이 여러 step에 쓰이므로 둘을 나눔 |
| step `target` · `tier` | 해당 시 | 조립기 | 트랙과 일치. `tier`는 `deploy.yaml`에 있어야 함 |
| step `params` | 선택 | AI/규칙 → 검증 | **step별 허용 키만**(예: `migrations`, `scenarios`, `mode`, `keys`). 금지 키는 6-2절 |
| step `layer` | ✓ | 조립기 | `mandatory` / `conditional` / `optional`(내장은 계획에 없음) |
| step `effect` | ✓(기본 `read`) | **조립기(카탈로그)** | `read` / `additive_prep` / `state_change`. AI가 써도 덮어씀 |
| step `by` · `reason` · `evidence` | 선택 | AI/규칙 | 표시용. 판정에 쓰지 않음 |
| step `wait_for` · `signal` | 해당 시 | **조립기(카탈로그)** | AI가 써도 덮어씀. `wait_for`는 **항상 배열** |
| step `run` | 해당 시 | 조립기 | `finally`만. verify 섹션에서만. 앞이 실패해도 실행 |
| `skipped[]` | ✓ | 조립기 | `id`, `tool`, `target`·`tier`, `layer`, `by`, `reason`, `skip_rule`(결정적 규칙 id) |
| `invalidated[]` | ✓ | 조립기 | AI가 빼려 했으나 무효화된 것. 예: `{"id":"deploy.db.cloud","attempt":"skip","by":"ai","result":"forced_include","why":"migrations_unchanged(cloud)=false"}` |
| `warnings[]` | 선택 | AI/규칙 | 보고 이슈로 올림 |

- `timeout_s`는 계획에 싣지 않습니다. 실행기가 레지스트리·step 카탈로그에서 읽습니다.
- **계획 어디에도 도메인·IP·digest·ARN·비밀값이 없습니다.**
- 💭 10/1 저녁: run별 대상 선택에 맞춰 `targets`(`local`/`cloud`/`both`)와 `source`(저장소·브랜치·`prod` 커밋·후보 커밋) 필드가 필요합니다. 선택하지 않은 대상의 `deploy.*`는 빈 `steps[]`로 두는 안이 있습니다. 계획 스키마 변경이라 15절 절차(`NEEDS_CONTEXT`)로 정합니다.

```json
       "wait_for": ["local_verified", "cloud_verified"]},
      {"id": "verify.report", "tool": "post_report", "layer": "mandatory", "run": "finally"}
    ],
    "skipped": [
      {"id": "verify.watch.cloud", "tool": "watch_post_deploy", "target": "cloud", "layer": "optional", "by": "ai",
       "reason": "데모 시간", "skip_rule": "optional"}
    ]
  },
  "invalidated": [],
  "warnings": []
}
```

읽는 법:
- `build.web`이 빠진 것은 web 입력(nginx·static·web Dockerfile)이 v1과 같아서입니다. rel-v1 web digest를 재사용합니다.
- `deploy.infra.cloud`가 들어간 것은 새 비밀 키 `SECRET_KEY`가 인프라 요구 해시를 바꿨기 때문입니다(✅ 장부 32). 실행 역할 정책 **변경**(in-place update)이 있으므로 `state_change`입니다(V23).
- 그 뒤에 `deploy.secrets.cloud`(빈 시크릿에 난수) → `deploy.config.cloud`(태스크 정의에 새 ARN) → `deploy.db.cloud` → `deploy.app.cloud` 순서입니다. 시크릿 ARN이 인프라 apply 뒤에야 생기기 때문입니다.
- `deploy.dbinit.cloud`는 부트스트랩에서 이미 앱 DB·계정을 만들어 `skipped`입니다.
- 예시의 `"code_patch": false`는 일반 실행 기본값입니다. 데모(토글 ON)에서는 `true`이고, 패치 툴은 "계획 밖"이라 step으로 나오지 않습니다(3-5절).
- 예시의 `tree_changed`·`tree_unchanged`·"트리 해시"는 옛 이름입니다. 뜻은 "빌드 입력 파일의 내용 해시가 대상 환경의 마지막 성공과 다름/같음"입니다(3-6절. 10/1 저녁부터 기준은 환경별 마지막 성공 `source_sha`(그때 쓴 `prod` 커밋), `deployed/<환경>` 태그 아님). 이름을 바꾸려면 15절 절차로(골든 plan 파일·원본 02도 함께).

### 5-2. effect (대기 지점 규칙의 근거, 💭)

| effect | 뜻 | 예 | 클라우드에서 G1 전 실행 |
|---|---|---|---|
| `read` | 읽기만 | TLS 확인, 헬스, 스모크(테스트 데이터는 씀) | 허용 |
| `additive_prep` | 서비스 중인 동작을 바꾸지 않는 추가형 준비 | 값이 **없는** 시크릿에 값 쓰기, 태스크 정의 새 리비전 등록(서비스 미전환), 이미지 빌드, plan이 create뿐인 인프라 apply(부트스트랩), 앱 DB·계정 없을 때만 생성 | 해당 없음(10/1 밤 분리) |
| `state_change` | 서비스 동작이나 공유 데이터를 바꿈 | DB 마이그레이션, 서비스 전환, 온프렘 `.env` 쓰기, 기존 시크릿 덮어쓰기, update가 있는 인프라 apply | 해당 없음(10/1 밤 분리) |

## 7. 실행기 대기 지점·상태·잠금·승인

### 7-1. 신호와 대기 지점

| 신호 | 누가 여나 | 누가 기다리나 | 상태 |
|---|---|---|---|
| `infra_ready` | `deploy.infra.cloud` | 부트스트랩의 `build.*` | 💭 |
| `images_ready` (G0) | build 트랙 끝(digest 확인) | 이미지가 필요한 step(`deploy.config.*`) | ✅ |
| `local_verified` (G1) | `verify.smoke.local` | `verify.compare`만(클라우드 step은 안 기다림, 10/1 밤 분리) | ✅ 10/1 밤 |
| `cloud_verified` | `verify.smoke.cloud` | `verify.compare` | ✅ |

- 신호 이름은 **이 4개로 고정**합니다. AI는 신호를 만들거나 지울 수 없습니다.
- `wait_for`는 항상 배열입니다(신호 하나도 `["images_ready"]`).
- 트랙이 끝날 때 열지 못한 자기 신호는 **실패로 닫습니다**. 기다리던 step은 `GateFailed`로 멈춥니다.

| # | 규칙 | 상태 |
|---|---|---|
| W0 | 선택한 대상의 트랙만 동시에 시작(둘 다면 build·local·cloud 세 트랙). 선택하지 않은 대상의 신호는 "해당 없음"으로 닫음(실패 아님) | ✅ 장부 1·6 · 10/1 저녁 |
| W1 | ~~클라우드 `state_change` step은 `wait_for: local_verified`~~ → 클라우드 step은 온프렘 신호를 기다리지 않음(독립 진행) | ✅ 10/1 밤 분리(장부 6 대체) |
| W2 | ~~G1 전 클라우드는 `read`·`additive_prep`만~~ → 폐지(대기 지점 제거) | ✅ 10/1 밤 분리(N1 해소) |
| W3 | 로컬 트랙은 클라우드를, 클라우드 트랙은 로컬을 기다리지 않음 | ✅ (10/1 밤 확장) |
| W4 | 한 환경이 실패하면 그 환경만 롤백하고 다른 환경은 계속 진행(`ABORTED_AT_GATE` 폐지) | ✅ 10/1 밤 분리(장부 6 대체) |
| W5 | (둘 다일 때) compare는 G2(두 신호, 둘 다 성공했을 때만). 하나라도 없으면 compare 생략, 보고만. 단일 대상이면 compare 없음 | 💭 |
| W7 | 부트스트랩: 인프라 apply가 실패하면 빌드·로컬 트랙은 대기 지점에서 멈춤 | 💭 |

```python
# 실행기 모양(💭). 기준 구현은 코드 템플릿의 최소 실행기
async def run_step(step, track, ctx):
    ctx.assert_plan_hash()                         # V12
    for g in step.wait_for:                        # 항상 배열
        await ctx.gates[g].wait()                  # 실패하면 GateFailed
    t = REGISTRY.get(step.tool)                    # 검증된 이름만
    inp = build_input(t, step, track.target, ctx)  # run_id·target·tier·lock_token은 실행기가 채움
    out = await asyncio.wait_for(asyncio.to_thread(t.fn, inp, ctx), t.spec.timeout_s)
    ctx.record(step, out)                          # 이벤트 + run 로그
    if getattr(out, "passed", True) is False:
        raise CheckFailed(step.id)
    if step.signal:
        ctx.gates[step.signal].open()
```

### 7-2. 상태 머신 (💭)

| 수준 | 상태 |
|---|---|
| run 진행 | `CREATED → ANALYZED → PLANNED → VALIDATED → AWAITING_APPROVAL → APPROVED → BUILDING ∥ DEPLOYING → COMPARING → REPORTED → (최종)`. 10/1 저녁: run에 시작 방식 `trigger`(`manual`/`auto`)와 대상을 기록하고, 대상이 둘 다가 아니면 `COMPARING`은 건너뜀 |
| run 최종 | `SUCCEEDED` / `FAILED_BEFORE_DEPLOY`(`VALIDATION_FAILED`·`BLOCKED`·`REJECTED`·`BUILD_FAILED`·`INFRA_INVALID`·`INFRA_APPLY_FAILED`·`DOCKERFILE_INVALID`) / `FAILED_LOCAL` / `FAILED_CLOUD` / `PARITY_FAILED` / `NEEDS_HUMAN` / `CANCELLED` |
| 트랙 | `PENDING → RUNNING(step i) ⇄ WAITING(gate) → VERIFIED(signal) → DONE` / 실패: `FAILED → ROLLING_BACK → ROLLED_BACK \| ROLLBACK_FAILED` / ~~클라우드: `ABORTED_AT_GATE`~~(10/1 밤 분리로 폐지) / run 대상에서 빠진 트랙: `N/A`(해당 없음, 실패 아님, 10/1 저녁) |
| step | `pending` / `waiting` / `running` / `succeeded` / `failed` / `skipped` / `aborted` |
| 환경(`env_release`, 대상별 1행) | `current_release`, `previous_release`, `status`(`SUCCEEDED`/`ROLLED_BACK`/`DIVERGED`/`NEEDS_HUMAN`), `last_success_sha`(10/1 저녁: 마지막 성공 릴리스의 `source_sha`(쓴 `prod` 커밋, 변경 탐지 기준)와 `candidate_sha`(빌드·배포한 ai-prod 커밋 = 태그 `deployed/<환경>`·이미지 라벨, 롤백 기준)를 함께 참조. 이전: 원본 스냅샷 해시 참조), `updated_at` |

### 7-3. 잠금

| 잠금 | 방식 |
|---|---|
| 배포 잠금(프로젝트당 1개, 내장) | 💭 실행기 SQLite `locks`. 하트비트 10초, TTL 10분. 두 번째 요청은 **거절**(대기열 없음). ④ 툴은 `lock_token`을 받고, 틀리면 `LOCK_INVALID` |
| 마이그레이션 잠금 | MySQL `GET_LOCK('flaskr_migrate', 10)` → 끝나면 `RELEASE_LOCK` |
| Terraform 상태 잠금 | S3 backend `use_lockfile=true`(Terraform 1.11+), DynamoDB 없음 💭 |

- 실행기 잠금은 각자 PC의 SQLite라 **노트북끼리 공유되지 않습니다**. 실제 클라우드 대상 run은 한 번에 한 명만 합니다. 10/1 저녁: 동시 실행 잠금은 추후(⏸, 서버로 옮기면 로컬 잠금으로 해결). 테스트 기간에는 공유 환경(온프렘 VM·ECS) 배포를 한 번에 한 명, 채팅방에 알리고 진행합니다.

### 7-4. 승인 기록 (C-19, 💭)

- 원본은 담을 항목(승인자·시각·묶는 sha256·승인 종류)만 정했습니다. 아래 필드 이름은 이 문서의 제안입니다.

| 필드 | 뜻 |
|---|---|
| `run_id` | 어느 run의 승인인가 |
| `kind` | `patch` / `deploy` / `infra`(IAM·인프라) / `dockerfile`. 기반(foundation)은 별도 종류가 아니라 `infra` 해시에 포함(✅ 10/2). 패치는 `prod` 커밋·diff·후보 트리 해시를 함께 기록(10/1 저녁) |
| `bound_to` | 패치 `prod` 커밋 SHA·diff sha256·후보 트리 해시(10/1 저녁, 이전: 원본·수정본 스냅샷 해시), `plan_hash`(배포), 인프라 = 저장 plan 바이트 해시·기반 템플릿 해시·backend 대상/이전 여부를 묶은 해시(기반 별도 기록 없음, ✅ 10/2), Dockerfile sha256. 상세 모델은 approval.py |
| `approver`, `approved_at` | 승인자, 시각 |
| `decision` | `approved` / `denied` |
| `session_caller` | (부트스트랩 infra 승인만) 관리자 단기 세션의 caller ARN. 키 값은 넣지 않음 |

- ✅ 결정(N40, 9/30): 한 화면에서 패치 diff·배포 계획·(있으면) 인프라 plan·IAM 변경을 확인하고 한 번 승인합니다. 같은 approval_id로 묶되 기록은 대상별(`patch`·`deploy`·`infra` 등)로 따로 저장하고, 각자 자기 해시에 묶습니다. 항목을 숨긴 포괄 승인은 없습니다.
- 패치 기록은 `prod` 커밋 SHA·diff 해시·후보 트리 해시 셋에 묶습니다(10/1 저녁). ai-prod의 이전 패치는 merge만으로 자동 유지·승인하지 않습니다. 최신 prod 적합성을 확인해 그 run의 승인 build_files에 포함된 패치만 배포하며, merge 커밋 하나의 관리 트리를 이 승인 트리로 고정합니다. 패치 OFF면 이전 AI 패치가 빠집니다(**정준우 확인 대기**). 패치 내용이 바뀌면 재승인입니다. 이전 패치는 프로젝트와 세 해시가 모두 같고 이전 기록이 승인일 때만 재사용하며(run이 달라도 됨, 화면에 표시), 배포·인프라 승인은 이전 run에서 자동 재사용하지 않습니다. 어느 대상이든 내용이 바뀌면 그 대상은 새 승인이 필요합니다.
- 승인 POST는 `Host`·`Origin` 검사 + CSRF 토큰(P0 💭). 운영자 브라우저의 악성 페이지가 대신 누르는 것을 막습니다.
- 💭 Slack P1 승인 버튼도 같은 승인 기록을 씁니다.

## 10. 진행 이벤트 형식 (💭 C-13)

```json
{"run_id":"run-20261003-1412","seq":42,"ts":"2026-10-03T14:13:05Z","type":"step.finished","stage":"deploy",
 "step":"deploy.db.cloud","tool":"prepare_db","target":"cloud","layer":"conditional","by":"rule",
 "status":"succeeded","elapsed_s":31.4,"detail":"0002 적용, 스키마 서명 일치"}
```

| `type` | 언제 |
|---|---|
| `run.state` | run 상태 전이 |
| `step.started` / `step.finished` / `step.skipped` | step 시작·끝·생략 |
| `gate.waiting` / `gate.opened` / `gate.failed` | 대기 지점 |
| `rollback.started` / `rollback.finished` | 롤백 |
| `ai.call` | provider, model, latency_ms, cost_usd, source |
| `report.ready` | 보고 완료 |

| 필드 | 규칙 |
|---|---|
| `seq` | run 안에서 0부터 증가 |
| `ts` | ISO 8601 UTC |
| `stage` | `plan` / `validate` / `build` / `deploy` / `verify_report` / `common` / `ops` |
| `status` | `succeeded` / `failed` / `check_failed` / `skipped` / `waiting` 등 |
| `detail` | 표시용, redact 후 최대 4096자 |

- JSONL(`var/runs/<run_id>/events.jsonl`)에 **먼저** 쓰고 SSE로 내보냅니다. 관리 페이지는 스트림 하나에서 `event:` 타입으로 2열을 나눕니다.
- SSE가 끊기면 `run_id`로 JSONL을 다시 읽어 재생합니다. 모든 문자열은 redact.
- 💭 Slack 알림은 새 형식 없이 이 이벤트와 보고 카드(C-16)를 그대로 보냅니다.

### 15-2. 계약을 바꿔야 할 때

1. 직접 고치지 않고 멈춥니다. `NEEDS_CONTEXT`로 보고합니다: 필요한 결정, 선택지, 각각의 영향.
2. 넘기는 사람과 받는 사람이 함께 정합니다. 결정은 결정 장부(원본 00, 문서 정리 정준우)에 남깁니다.
3. 저장소가 생긴 뒤에는 `contract-change` 이슈·라벨 + 같은 PR에서 스키마 스냅샷 갱신 + 계약 승인자(미정, N19) 또는 짝의 승인. 파괴형 변경은 공지하고 소비자 PR을 함께 냅니다.

| 보고 | 쓸 때 | 담을 것 |
|---|---|---|
| `DONE` | 끝났을 때 | 바뀐 파일, 실행한 명령과 결과, 남은 우려 |
| `NEEDS_CONTEXT` | 설계 결정이 필요할 때(툴 이름·파라미터·스키마·이벤트·카탈로그·`deploy.yaml` 키 변경 포함) | 필요한 결정, 선택지와 영향 |
| `BLOCKED` | 더 진행할 수 없을 때 | 막힌 원인, 시도한 것 |
