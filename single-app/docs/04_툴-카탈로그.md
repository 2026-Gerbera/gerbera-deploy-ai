## 1. 레지스트리 형식

### 1-1. 원칙

| # | 원칙 | 이유 |
|---|---|---|
| R1 | 툴 이름은 카탈로그(`core/registry.py`의 40행, `canonical_names()`)에 있는 것만 등록 | 이름·계약을 바꾸려면 계약 변경 PR이 필요하게 |
| R2 | 한 이름은 한 번만 등록 | 중복 등록을 기동 때 잡음 |
| R3 | 입력은 `ToolInput`(`run_id` 필수), 출력은 `ContractModel`(`extra="forbid"`, `frozen=True`) 상속. 등록 함수는 카탈로그 모듈 아래(`ddak.<모듈>.`)에 있어야 함 | 하네스 `core/contracts/base.py`, `registry.py` |
| R4 | 함수 시그니처는 `(inp, ctx) -> Output`. MCP 호출 규약 `{"payload": …}`는 없어짐 | 직접 호출 |
| R5 | 모든 툴 모듈을 import해 레지스트리를 채우는 곳은 조립 진입점 `ddak.app`(`load_tools()`) **하나**. 모듈별 `tools/` 아래 `<툴>/tool.py`를 자동 탐색(`pkgutil.iter_modules`)하므로 툴마다 한 줄씩 추가하는 중앙 파일은 없음 | 병렬 개발 충돌 방지(하네스 "중앙 조립 파일 금지") |
| R6 | 실행기·웹은 툴 모듈을 import하지 않고 **레지스트리 이름으로만** 호출 | "실행 경로에 AI 없음" import 계약이 간접 import로 깨지지 않게 [판단] |
| R7 | 환경별 구현 선택은 코드가 함. cd 툴은 `select_provider(target, 어댑터 모드)`로 provider를, 나머지 모듈은 `select_adapter`(target·`deploy.yaml`·어댑터 모드)로 어댑터를, 이미지 저장소는 `deploy.yaml` `targets.cloud.registry`로 고름. AI가 고르지 않음 | 하네스 `cd/providers/__init__.py`, `core/adapters.py`, `ci/registries/__init__.py` |
| R8 | 도메인·digest·IP·시크릿 위치·ARN은 입력에 없음. `RunContext`(환경 정보 스냅샷)에서 코드가 채움 | ✅ 장부 6·17·27 |

### 1-3. 카탈로그와 데코레이터 (하네스 구현, 💭)

- 메타정보는 카탈로그에 **한 번만** 적습니다. 담당자는 자기 툴 디렉토리의 `tool.py`에서 `@tool("<이름>")`으로 함수만 붙입니다.
- `@tool`이 검사하는 것: 카탈로그에 있는 이름인가, `tool_fn` 종류인가, 함수가 카탈로그 모듈(`ddak.<모듈>.`) 아래에 있는가, 시그니처가 `(inp: ToolInput 하위, ctx: RunContext) -> ContractModel 하위`인가, 두 번 등록하지 않았는가. 어긋나면 앱 기동(import) 때 `RegistryError`.

```python
# src/ddak/core/registry.py (카탈로그 행, 계약 파일)
# (이름, 모듈, 단계, 층, 플래그, 대상, 담당 "공통/local/cloud/ui")
("prepare_db", _CD, _S.DEPLOY, _L.CONDITIONAL, "lock de", "both", "O1/O1/C2"),  # 추가형만
("generate_dockerfile", _PL, _S.PLAN, _L.OUTSIDE, "ai ro", "", "O3"),  # Dockerfile이 없을 때만
("push_image", _CI, _S.BUILD, _L.BUILTIN, "", "", "C2"),  # 💭 digest 확인·기록
```

```python
# src/ddak/cd/tools/prepare_db/tool.py  (AI 없는 배포 툴, CD provider를 부름)
from ddak.cd.providers import select_provider
from ddak.core.contracts.context import RunContext  # 모듈 최상단에서 import
from ddak.core.contracts.tools.prepare_db import PrepareDbInput, PrepareDbOutput
from ddak.core.registry import tool


@tool("prepare_db")  # 이름·위치·시그니처가 카탈로그와 다르면 앱 기동 실패
def prepare_db(inp: PrepareDbInput, ctx: RunContext) -> PrepareDbOutput:
    provider = select_provider(inp.target, ctx.adapter_mode)  # AI가 고르지 않음(aws / onprem / fake)
    result = provider.migrate_db(inp.migrations, ctx)  # DB 주소·시크릿 ARN·digest는 ctx(환경 정보)
    return PrepareDbOutput.from_result(inp, result)  # 필드는 계약 문서
```

```python
# src/ddak/plan/tools/generate_plan/tool.py  (AI 툴, 모양만)
@tool("generate_plan")
def generate_plan(inp: GeneratePlanInput, ctx: RunContext) -> GeneratePlanOutput:
    facts = load_facts(inp, ctx)                          # 키 이름·해시만, 값 없음
    try:
        draft = call_ai(purpose="plan_draft", schema=PlanDraft, data=facts.for_ai())
    except DdakToolError:                                 # AI_UNAVAILABLE / AI_OUTPUT_INVALID
        draft = rule_draft(facts)                         # 규칙 계획 경로(AI 없이도 E2E)
    return GeneratePlanOutput(run_id=inp.run_id, draft=draft)
```

```python
# src/ddak/app.py  (조립 진입점, R5)
TOOL_PACKAGES = ("ddak.core.tools", "ddak.plan.tools", "ddak.infra.tools", "ddak.ci.tools",
                 "ddak.cd.tools", "ddak.verify.tools", "ddak.ops.tools")

def load_tools() -> Registry:
    for name in TOOL_PACKAGES:
        import_tools(importlib.import_module(name))       # <툴>/tool.py import → @tool이 등록
    return REGISTRY
# 아직 구현하지 않은 툴은 REGISTRY.missing()으로 보임(make contract-smoke). 💭 전부 구현되면 기동 때 빠짐 검사
```

- `call_ai`·`request_approval`·`stream_progress`처럼 step으로 호출되지 않는 core 기능은 하네스에서 카탈로그 메타정보만 두고 `@tool` 등록 대상에서 뺐습니다(`kind`가 `library`/`executor_fn`) 💭. 그래서 등록 함수(`tool_fn`)는 37개입니다.
- `call_ai`는 contextvar `current_tool`이 `uses_ai=True` 툴이 아니면 `AI_NOT_ALLOWED`를 던집니다(하네스 `test_ai_guard.py`).
- 실행기 쪽 호출은 [02 파이프라인 8-8](02_파이프라인과-계획.md#8-8-실행기-골격-코드-모양-)의 `REGISTRY[step.tool]`입니다.

### 1-4. 입력·출력·실패 규약 (하네스 유지)

| 구분 | 규칙 |
|---|---|
| 입력 | `run_id` 필수. `target`은 대상 있는 툴만. `tier`는 패턴 `^[a-z][a-z0-9_-]{0,31}$`를 실행 시 `deploy.yaml`과 대조. ④ 툴은 `lock_token`. 자유 문자열 명령·빌드 명령 재정의·IAM 역할 재정의 입력 금지. 비밀 필드는 `SecretStr` |
| 출력 | 계약 모델만(원시값·dict 금지). AI 툴은 `ai_usage`(model, 토큰, cost_usd, latency_ms)와 `source`(하네스 `Source`: live/cache/fixture/replay 💭). cd provider 함수는 공통 `ProviderResult`(`applicable`·`changed`·`detail` ≤400자)를 돌려주고 툴이 자기 출력 모델로 옮김 |
| 수행 불가 | `DdakToolError(ErrorCode, 메시지)` |
| 해당 없음 | 실패가 아님. 온프렘 `ensure_tls`는 `ProviderResult(applicable=False)`(로컬 HTTPS ⏸) |

### 1-6. CD 공통 인터페이스 + provider, 이미지 저장소 어댑터 (✅ 장부 28·29, 함수·인자 💭)

| 인터페이스 함수 | 부르는 툴 | aws provider(cloud) | onprem provider(local) |
|---|---|---|---|
| `deploy(tier, ctx)` | `deploy_tier` | 태스크 정의 새 리비전으로 `update_service` | tier 컨테이너를 digest로 재생성 |
| `rollback(tier, ctx)` | `rollback_tier` | 이전 태스크 정의 ARN으로 `update_service` | 이전 digest로 재생성 |
| `health_check(ctx)` | `health_check` | `/health/ready`, ECS `imageDigest` | `/health/ready`, `docker inspect` digest |
| `migrate_db(migrations, ctx)` | `prepare_db` | 일회성 ECS 태스크(마이그레이션 계정) | was 호스트 일회성 컨테이너 |
| `inject_config(keys, ctx)` | `inject_env_config` · `sync_env_to_cloud` | 빈 시크릿에 PutSecretValue(난수) + 태스크 정의 `secrets` valueFrom·`repositoryCredentials` | was `.env`(난수 SECRET_KEY 포함) |
| `ensure_tls(mode, ctx)` | `ensure_tls` | ACM·443·HSTS·80→301·DNS | **해당 없음**(`applicable=False`) |

- provider는 코드가 고릅니다(`select_provider(target, adapter_mode)`: fake 모드면 `FakeProvider`, local이면 onprem, cloud면 aws). GCP·Azure는 후순위라 코드가 없습니다(CSP 우선순위 AWS 1순위).
- 💭 공통 설정값(김준석 제안의 "Helm식 공유"): `deploy.yaml` 공통 키 → provider별 덮어쓰기(`targets.local`/`targets.cloud`) → 환경 정보(코드가 채우는 주소·ARN·digest)를 코드가 합쳐 같은 모양으로 넘깁니다. 템플릿 엔진은 쓰지 않습니다.
- 담당: aws provider 안승환(C2) · `ensure_tls` 유상준(C1) · `health_check` cloud 양서윤(C3) / onprem provider 정준우(O1) · `health_check` local 장민영(O3). 결정 기록(양서윤 제안 채택, 김준석 제안 반영): [harness/docs/decisions/2026-09-30-cd-provider-structure.md](../../harness/docs/decisions/2026-09-30-cd-provider-structure.md).

| 이미지 저장소 어댑터 | 위치 | 하는 일 | 상태 |
|---|---|---|---|
| Docker Hub | `ci/registries/dockerhub.py` | 배포 참조 `docker.io/<조직>/<이미지>@sha256:<64hex>` 조립. 태그·잘못된 digest 거부. 표시용 태그 `<tier>-<release_id>`(저장소 1개면 web·was를 태그로) | **기본** ✅ 장부 28 |
| ECR | `ci/registries/ecr.py` | ECR 참조 조립. 켜면 ECR 리포지토리·권한·(프라이빗이면) 엔드포인트가 다시 필요 | 옵션 💭 |

- 이미지 저장소 어댑터는 툴이 아닙니다(레지스트리 40개 밖). `build_image`(CodeBuild가 push 토큰으로 push), `push_image`(digest 확인·기록), cd provider(태스크 정의 이미지·온프렘 pull)가 씁니다. 토큰 값은 어댑터가 다루지 않습니다(CodeBuild·ECS는 Secrets Manager 이름만, 온프렘은 호스트의 `docker login`).

## 3. P0 툴 (골든 패스 순서, 입출력은 💭 요약)

- 순서는 v2 로그인 배포 run(시크릿 장면 포함, ✅ 장부 32)에서 처음 쓰이는 순서입니다. v2는 새 SECRET_KEY 때문에 인프라 요구 해시가 바뀌어 인프라 툴 4개가 **v2 경로에도** 들어갑니다. 클라우드 트랙의 `ensure_tls`(확인)는 로컬 트랙과 동시에 돌고, 인프라 apply·시크릿 값 쓰기·태스크 정의 등록은 G1 뒤입니다(💭 N39, [02 §4-3](02_파이프라인과-계획.md#4-3-④⑤-클라우드-트랙)).

### 4-2. AI 출력 스키마 요약 (💭, 값·주소·명령을 담을 수 없는 enum 중심)

채팅 의도      {"action": "deploy_request|status_query|explain_last_run|unknown",
                "target": "both|local", "ref": "feature/login"}
분석 분류      {"keys": [{"key": "SECRET_KEY", "class": "secret|plain|address", "varies_by_env": true,
                          "policy": "generate_per_env|platform_ref|derive_from_public_url|
                                     derive_from_public_scheme|platform_profile|constant",
                          "evidence": [{"file": "flaskr/__init__.py", "line": 14}], "why": "세션 서명"}],

step 선택      PlanDraft (02 파이프라인 6-2)

### 4-3. AI가 절대 하지 않는 일

| 영역 | 누가 하나 |
|---|---|
| 빌드·배포·검증·롤백·잠금 실행 | 실행기(코드) |
| 인프라 apply, IAM 생성 | `apply_infra`(코드)가 검증·사람 승인 뒤. AI는 HCL 초안만(✅ 장부 4-a·23) |
| 인프라 검사 통과 판정 | `validate_infra`·`plan_infra`(코드). 생성기와 검사기는 import가 분리됨(계약 7) |
| Dockerfile 검사 통과 판정, 빌드 | `validate_dockerfile`(코드)·CodeBuild. 생성기와 검사기는 import가 분리됨(계약 5) |
| 툴 직접 호출 | 없음. LLM은 제안(JSON, HCL·Dockerfile 초안)만 돌려줌(CLI는 우리 함수를 모르고, 두 backend에서 같게 동작하려는 것) |
| 비밀값 열람·생성 | 없음. 키 이름만 봄. AI 입력 전 redact(하드코딩 비밀 리터럴 포함). SECRET_KEY 난수는 코드(`secrets`)가 만듦 |
| 도메인·IP·digest·시크릿 위치 생성 | 코드가 환경 정보(인벤토리·Terraform 출력·관리 페이지 설정·실행기 DB)에서 가져옴 |
| Terraform state·출력 원문 보기 | 없음. 가린 요약만(✅ 장부 27) |
| 필수 step 빼기, 순서·대기 지점 정하기 | 카탈로그 + `validate_plan` |
| 마이그레이션 파괴형 판정 | 규칙(lint) |
| 관문·롤백 판단, 보고 심각도 | 규칙·고정 표 |
| 승인(웹·Slack) | 사람. Slack 승인자는 허용 사용자 목록만(💭 장부 30) |

- 코드·diff·로그는 신뢰할 수 없는 입력입니다. `call_ai`가 `<untrusted_data>`로 감쌉니다(✅ 장부 4). 운영자 채팅 문장은 감싸지 않습니다(감싸면 모델이 지시를 거부함, [LLM 호출 검토](../../research/2026-09-30_웹-CLI-LLM호출-검토.md)).
- Jev는 diff 속 악의적 문장에 흔들릴 수 있다고 문서가 인정합니다. 그래서 Jev 답은 step을 늘리거나 경고하는 쪽으로만 반영합니다([Jev 조사](../../research/2026-09-30_Jev-사용처-검토.md)).
