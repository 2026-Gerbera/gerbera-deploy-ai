## 1. 5단계

| 단계 | 하는 일 | AI | 주 툴 | 결과물 |
|---|---|---|---|---|
| ① 플랜 | 요청 접수, 환경 정보 스냅샷, 바뀐 tier 계산, 환경 키 분류, 인프라 요구 도출, step 선택. (Dockerfile이 없으면) Dockerfile 초안. (인프라 요구가 바뀌었거나 부트스트랩이면) 기존 리소스 탐지와 Terraform 초안(개선 배포는 수정안) | 분류·step 선택(JSON), **Dockerfile 초안**, **HCL 초안** | `receive_deploy_request`, `detect_changed_tiers`, `analyze_project`, `generate_plan`, (Dockerfile) `generate_dockerfile`, (인프라) `discover_existing`, `generate_infra` | facts, 계획 초안(`PlanDraft`), Dockerfile 초안, 인프라 요구·HCL 초안 |
| ② 계획 검증 | 카탈로그 + facts + 초안으로 최종 계획을 조립하고 검사. (Dockerfile이 새로 생겼으면) 정적 검사 + 검증 빌드. (인프라가 있으면) 정적 게이트·validate·정책 검사 → plan(P1: 읽기 세션) → 요약·IAM diff·Access Analyzer | 없음(AI import 금지, 계약 5·7) | `validate_plan`, (Dockerfile) `validate_dockerfile`, (인프라) `validate_infra`, `plan_infra` | `plan.json` + `plan_hash`, (Dockerfile) 검사 결과 + sha256, (인프라) `tfplan` + sha256 + 요약 |
| ③ 빌드 | 바뀐 tier만 이미지 빌드 → **Docker Hub**(장부 28, ECR은 옵션), digest 확인·기록 | 없음 | `build_image`, (내장) `push_image` | manifest 초안, 신호 `images_ready` |
| ④ 배포 | 두 트랙 동시 시작. (있으면) 사람 승인된 인프라 apply, 설정·시크릿 값 주입, (부트스트랩) 앱 DB·계정 생성, DB 마이그레이션, tier 교체. 환경별 구현은 CD provider(aws·onprem) | 없음 | (인프라) `apply_infra`, `inject_env_config`, `sync_env_to_cloud`, `prepare_db`, `ensure_tls`, `deploy_tier` | 환경별 배포 결과, 환경 정보 갱신 |
| ⑤ 검증 및 보고 | 헬스·스모크·TLS, 교차 비교, 실패 원인 설명, 보고(💭 Slack 알림은 같은 보고 카드를 보냄, 장부 30) | 원인 설명·보고 요약(JSON) | `health_check`, `smoke_test`, `verify_tls`, `compare_env_results`, `diagnose_parity_gap`, `post_report` | 비교 표, 보고 카드 |

- 단계 번호는 논리 순서입니다. 트랙 안에서는 "배포 → 검증"이 반복됩니다. **로컬 트랙의 ⑤ 검증 통과가 클라우드 트랙 ④의 상태 변경을 여는 관문**입니다.
- 💭 인프라 apply는 ④ 배포에 속하는 클라우드 트랙 step(`deploy.infra.cloud`)입니다. 부트스트랩에서는 CodeBuild 프로젝트(ECR 옵션이면 ECR도)가 apply로 생기므로 빌드가 신호 `infra_ready`를 기다립니다. 5단계 이름과 순서는 그대로입니다(4-3절, 00: N25).
- 툴 40개 전체와 담당은 [04 툴 카탈로그](04_툴-카탈로그.md)에 있습니다. 모듈(💭 레지스트리 트리)과 단계는 1:1이 아닙니다.

## 2. 한 run의 흐름

```
[관리 페이지 채팅] "로그인 기능 배포해줘"
   │ call_ai → 의도 JSON {"action":"deploy_request","target":"both","ref":"feature/login"}      ← AI
   ▼
[입구 검사, 코드] action·target enum 확인, ref 존재 확인, 진행 중 run 없음, 두 환경 상태 정상
   │ receive_deploy_request → run_id, 소스 스냅샷(zip + sha256), 토글 상태 고정, 환경 정보 스냅샷
   ▼
① 분석
   detect_changed_tiers : tier별 build_inputs git 트리 해시를 마지막 성공과 비교 → facts
   analyze_project      : 규칙 스캐너(환경 키·마이그레이션·라우트·세션) → Jev/Claude 키 분류       ← AI(분류)
① 계획
   generate_plan        : Jev(step 필요 여부 묶음) / Claude(JSON 스키마) → PlanDraft                ← AI(선택)
   (tier의 Dockerfile이 없고 승인·저장된 것도 없을 때만, 4-0절)
   generate_dockerfile  : 분석 사실 → Dockerfile 초안                                             ← AI(Dockerfile)
   (인프라 요구 해시가 마지막 apply와 다르거나 부트스트랩일 때만 💭)
   discover_existing    : 기존 리소스 읽기 전용 탐지 → data source 후보
   generate_infra       : 인프라 요구(+ 개선 배포는 마지막 HCL·환경 정보 가린 요약) → HCL 초안·수정안 ← AI(HCL)
   ▼
② 계획 검증 (코드)
   validate_plan        : 카탈로그 + facts + PlanDraft → plan.json(+plan_hash)
   불합격 → 재지시 1회 → 그래도 불합격이면 규칙 계획(규칙 계획도 같은 검증을 통과해야 함)
   validate_dockerfile  : 정적 검사(hadolint + 보안 기본값) → 검증 빌드(push 없음). 실패 → 되먹임 → 사람
   validate_infra       : init 전 정적 게이트 → init(-lockfile=readonly, P1 미러) → validate → Checkov. 실패 → generate_infra에 첫 오류 되먹임(최대 3회) → 그래도 실패면 사람
   plan_infra           : plan -out(P0 테스트 프로필 / P1 읽기 세션) → 요약·IAM diff·Access Analyzer, plan sha256
   ▼
[관리 페이지] 계획 카드(필수 / 포함 / 제외 + 이유 / 무효화된 제외) + 환경별 설정 변환 표(비밀값 가림)
   (Dockerfile을 새로 만들었으면) Dockerfile·검사 결과 → 사람이 [Dockerfile 승인] (Dockerfile sha256에 묶음)
   (인프라가 있으면) plan 요약 · IAM diff · 검사 결과 → 사람이 [IAM·인프라 승인] (plan sha256에 묶음)
   │ 사람이 [배포] 클릭 = 승인 (request_approval)  ※ v2 시크릿 장면의 버튼 수는 N40(사용자 확인)
   ▼
③~⑤ 실행기 (코드, AI 없음)
   잠금(acquire_deploy_lock) → facts 재계산(V11)
   ├─ build    : (부트스트랩이면 infra_ready 대기) build.was ─→ (내장) push_image digest 확인 ─→ signal images_ready (G0)
   ├─ local    : (G0 대기) config → db → was → health → smoke ───→ signal local_verified (G1)
   └─ cloud    : 부트스트랩: infra(create뿐, G1 전) ──→ signal infra_ready → tls · secrets · dbinit · (G0 대기) config ─(G1)─→ db → app → 검증
                 v2(시크릿 장면): tls(확인) ──(G1 대기)──→ infra(앱 층 시크릿 + 권한 변경) → secrets(값 쓰기) → config → db → app → health · tls · smoke
                                                                  ───→ signal cloud_verified
   verify.compare (local_verified ∧ cloud_verified 대기 = G2)
   실패 → 그 환경만 규칙 롤백 → collect_diagnostics → diagnose_parity_gap(AI 설명)
   finally → verify.report = post_report(run=finally, 규칙 카드 + AI 요약 선택) → record_deploy_log(환경 정보 갱신) → 잠금 해제
```

### 2-1. 채팅 의도 JSON (✅ 장부 4, 스키마는 💭)

| 필드 | 값 | 비고 |
|---|---|---|
| `action` | `deploy_request` / `status_query` / `explain_last_run` / `unknown` | 부작용이 있는 것은 `deploy_request`뿐. 이것도 사람이 [배포]를 눌러야 실행 |
| `target` | `both` / `local` | 💭 `cloud` 단독은 로컬 검증을 건너뛰므로 받지 않음(V15) |
| `ref` | 브랜치·커밋 이름(예: `feature/login`) | 코드가 존재 여부를 확인. AI 말을 믿지 않음 |

- 채팅이 할 수 있는 것은 **조회와 "배포 요청(사람 승인)"뿐**입니다. 조회는 상태 DB를 읽어 코드가 답합니다.
- AI가 실패하면 한국어 키워드 규칙으로 대체합니다(Jev 조사: 규칙으로 충분).
- 채팅 의도 함수를 레지스트리 어디에 둘지는 남은 결정입니다([04 툴 카탈로그 4절](04_툴-카탈로그.md#4-ai-사용-툴)).

### 2-2. 입구 검사 (코드)

| # | 검사 | 위반 시 |
|---|---|---|
| E1 | `action`·`target` enum, `ref` 존재 | 거부 + 채팅에 이유 |
| E2 | 진행 중 run 없음(배포 잠금 조회) | 거부("run X 진행 중"). 대기열 없음 |
| E3 | 두 환경 `env_release.status`가 `DIVERGED`/`NEEDS_HUMAN`이 아님(V17) | 거부. 사람이 정리 |
| E4 | `target=cloud` 단독 아님(V15) 💭 | 거부 |
| E5 | 이전 성공 릴리스가 없으면 `mode=bootstrap`, 있으면 `update` | 코드가 결정 |
| E6 💭 | 기반 준비(상태 버킷·앱 경계, 9-3절)가 없으면 거부하고 "기반 준비 먼저"를 안내. 환경 정보에 Terraform 출력이 없으면 인프라 step 강제 + 부트스트랩 모드 관리자 자격 필요 표시. 있으면 인프라 요구 해시로 포함 여부 결정 | 거부 / 코드가 결정 |
| E7 💭 | `deploy.yaml`의 tier별 Dockerfile 경로에 파일이 없고 승인·저장된 생성본도 없으면 Dockerfile 생성(4-0절)을 켬. 생성본이 있으면 재사용 | 코드가 결정 |

## 3. step 층 (✅ 장부 5, 구체 배치는 💭)

| 층 | 계획에 보임 | AI가 넣기 | AI가 빼기 | 누가 강제 | 예 |
|---|---|---|---|---|---|
| **내장** | 아니오 | – | 불가 | 실행기 | 잠금, 상태 기록, 진행 이벤트, 빌드 뒤 digest 확인(`push_image` 💭), 실패 처리(롤백·진단 수집), 기록·잠금 해제 |

| **조건부** | 예 | 항상 허용 | 결정적 조건 `skip_allowed(facts)`가 참일 때만 | `validate_plan` | web 빌드, tier 배포, 설정 주입, DB 마이그레이션, 시크릿 생성, 💭 인프라 apply(`deploy.infra.cloud`), 앱 DB·계정 생성(`deploy.dbinit.cloud`) |
| **선택** | 예 | 허용 | 허용 | – | 배포 후 관찰(`watch_post_deploy`). 안전에 영향 없는 것만 |
| 계획 밖 | 아니오 | – | – | – | 입구·분석·계획·검증 툴(Dockerfile 생성·검사 `generate_dockerfile`·`validate_dockerfile`, 인프라 제안·검증 `discover_existing`·`generate_infra`·`validate_infra`·`plan_infra` 포함), 운영 툴(`preflight_check`, `reset_demo_state`, `cleanup`), 토글 전용 `patch_*` |

**effect (대기 지점 규칙의 근거, 💭)**

| effect | 뜻 | 예 | 클라우드에서 G1 전 실행 |
|---|---|---|---|
| `read` | 읽기만 | TLS 확인, 헬스, 스모크(테스트 데이터는 씀) | 허용 |
| `additive_prep` | 서비스 중인 동작을 바꾸지 않는 추가형 준비 | 값이 **없는** 시크릿에 값 쓰기(PutSecretValue), 태스크 정의 새 리비전 등록(서비스 미전환), 이미지 빌드, 💭 plan이 create뿐인 인프라 apply(부트스트랩), 앱 DB·계정 **없을 때만** 생성 | 💭 허용(W2) |
| `state_change` | 서비스 동작이나 공유 데이터를 바꿈 | DB 마이그레이션, 서비스 전환, 온프렘 `.env` 쓰기, 기존 시크릿 덮어쓰기, 💭 in-place update가 들어간 인프라 apply(예: v2 시크릿 장면의 실행 역할 정책 변경) | **금지**(W1) |

## 4. step 카탈로그 (flaskr v1 → v2 기준, 💭)

- **step ≠ 툴.** 같은 툴이 여러 step에 쓰입니다(예: `deploy_tier`가 tier·대상별로). step id 형식 💭 `<단계>.<대상물>.<트랙>`.
- 가정: ECS web·was는 한 태스크 2컨테이너(D3=(a), 남은 결정). (b) 서비스 2개면 4-6절.
- "빼도 되는 조건"은 코드가 facts로 평가합니다. AI의 판단이 아닙니다.
- 출처: [MySQL 조사 B4](../../research/2026-09-30_MySQL-계획구조-검토.md) + [docs/17 6절](../../docs/17_골든패스-시나리오.md)을 장부 기준으로 고친 것.

### 4-0. Dockerfile 생성 (Dockerfile이 없을 때만, 장부 26)

- 결정(✅ 장부 26): Dockerfile이 없으면 AI가 생성합니다("딸깍". CodeBuild도 Dockerfile이 필요). 흐름·툴 이름은 결정 문구대로이고 아래 세부(위치·횟수·저장)는 💭입니다(N36).
- 실행기 step이 **아닙니다**. ①② 단계(계획 밖)에서 사람 승인 **전**에 돕니다. plan.json의 빌드 step은 승인된 Dockerfile을 씁니다. 실행 경로에 AI가 들어가지 않습니다(장부 4-a).

| 순서 | 무엇을 | 누가 | 결과 |
|---|---|---|---|
| 1 | 조건 확인(E7): `deploy.yaml`의 tier별 Dockerfile 경로에 파일이 없고, 승인·저장된 생성본도 없음 | 코드 | 생성 필요 여부 |
| 2 | `generate_dockerfile`(uses_ai): 분석 사실(런타임·패키지 파일·진입점·포트·헬스 경로, 키 **이름**만)로 Dockerfile + `.dockerignore` 초안. 소스 원문·비밀값은 안 감 | AI(제안만) | 초안 + 가정 목록 |
| 3 | `validate_dockerfile` ① 정적 검사: hadolint(버전 고정) + 우리 규칙(**비root `USER`**, **베이스 이미지 버전·digest 고정**, `latest` 금지, **비밀값 `COPY`/`ADD` 금지**(`.env*`·`*.pem`·`*.key`·`.git`), URL `ADD` 금지, `curl … \| sh` 금지, 코드 소유 `.dockerignore` 규칙 포함) | 코드 | 합격/불합격 + 첫 오류 |
| 4 | `validate_dockerfile` ② **실제 빌드 성공 확인**: 💭 컨트롤 플레인 호스트에서 `docker build`(push 없음, 비밀값 없음, `--platform` = D4, 타임아웃). 부트스트랩 때는 CodeBuild 프로젝트가 아직 없으므로 로컬 빌드 | 코드 | 성공/실패 + 로그 요약(redact) |
| 5 | 실패하면 첫 오류 원문(redact)을 되먹여 다시(💭 최대 2회) → 그래도 실패면 사람에게. 자동 완화 없음 | 조정자(코드) | – |
| 6 | 관리 페이지에 Dockerfile 전문·정적 검사 결과·빌드 요약·sha256 → 사람 [Dockerfile 승인] | 사람 | 승인 기록(승인자·시각·Dockerfile sha256) |
| 7 | 저장·재사용: 💭 `var/dockerfiles/<project>/<tier>/<sha256>/`에 저장, 소스 스냅샷 zip에 `deploy.yaml` 경로로 넣어 빌드. `build_inputs` 해시에 Dockerfile sha256 포함. 다음 run은 AI 없이 재사용(앱에 Dockerfile이 생기면 그것을 씀). 관리 페이지에서 내려받아 사람이 앱 저장소에 커밋할 수 있음 | 코드 | 이후 run은 이 단계 없음 |

- 골든 패스: 샘플 앱(flaskr)은 장민영이 만든 **기준 Dockerfile**을 유지합니다(💭). 그래서 10/1 E2E는 이 경로를 기다리지 않습니다. 생성 경로는 Dockerfile을 뺀 사본으로 P1에서 확인하고, 부트스트랩 녹화에 넣을지는 팀 결정(N36).
- 보안: AI가 쓴 `RUN`은 검증 빌드에서 실행됩니다. 정적 검사가 빌드보다 **먼저**이고, 빌드 컨텍스트는 코드 소유 `.dockerignore`로 비밀 파일을 뺍니다([06 §4-8](06_보안-신뢰경계.md#4-8-ai-dockerfile-게이트-)).

### 4-1. ③ 빌드 (공통 트랙)

| step id | 툴(params) | 층 | effect | 빼도 되는 조건 | wait_for / signal | v2 | 부트스트랩 |
|---|---|---|---|---|---|---|---|
| `build.was` | `build_image(tier=was)` | 조건부 | additive_prep | was `build_inputs` 트리 해시(생성 Dockerfile이면 그 sha256 포함)가 **모든 대상**의 마지막 성공과 같고 그 digest가 이미지 저장소(Docker Hub)에 있음 | – (부트스트랩 💭 wait_for `infra_ready`) | **포함** | 포함(강제) |
| `build.web` | `build_image(tier=web)` | 조건부 | additive_prep | 같은 조건(web `build_inputs`) | – (부트스트랩 💭 wait_for `infra_ready`) | **제외**(rel-v1 digest 재사용) | 포함(강제) |
| (digest 확인·기록, S3 버전 ID, manifest 초안) | 실행기 + `push_image`(💭 내장) | 내장 | – | – | signal `images_ready`(G0) | 항상 | 항상 |

- 두 빌드 step이 모두 켜지면 실행기가 CodeBuild 1회로 묶습니다(`environmentVariablesOverride`의 `TIERS=web,was`). 프로비저닝 대기가 1회로 줄어듭니다.
- push 대상은 기본 Docker Hub입니다(✅ 장부 28). CodeBuild가 push 토큰 시크릿으로 로그인해 빌드 안에서 push하고, `push_image`는 저장소 API로 digest가 있는지 확인해 manifest에 `docker.io/<조직>/<이미지>@sha256:…`로 기록합니다(별도 CodeBuild 호출 없음). `push_image`를 따로 둘지 `build_image`에 합칠지는 N35.
- Dockerfile이 생성본이면(4-0) 빌드 입력에 그 sha256이 들어가고, 승인 기록이 있어야 합니다(V26).

- 로컬 트랙에는 `ensure_tls`·`verify_tls` step이 없습니다. 관리 페이지는 로컬 열에 "보류(해당 없음)"를 표시합니다(로컬 HTTPS ⏸, 장부 17).
- 💭 `deploy.infra.cloud`의 AI가 뺄 수 없는 조건: 인프라 요구 해시가 다르면 강제 포함(V22). 포함되면 `request_approval`이 [IAM·인프라 승인]을 따로 받아야 실행기가 시작합니다(V24, 버튼 수는 N40). 온프렘에는 인프라 step이 없습니다(온프렘 인프라는 김준석의 프로비저닝, 인벤토리 `platform.onprem.yaml`).
- **라이브 데모(v2) 시크릿 장면(✅ 장부 32)**: 분석이 새 키 SECRET_KEY와 개발 코드의 `'dev'` 하드코딩을 찾음 → AI(Jev)가 secret으로 분류 → 인프라 요구의 시크릿 키 이름이 늘어 해시가 바뀜 → `generate_infra`가 **앱 층**에 `aws_secretsmanager_secret`(`ddak/flaskr/SECRET_KEY`) + 실행 역할의 그 시크릿 읽기 권한 추가를 제안 → plan 요약 "+ 시크릿 1, IAM 정책 1 변경, 삭제 0" → 사람 승인 → (G1 뒤) `deploy.infra.cloud` apply → 환경 정보에 시크릿 ARN 기록 → `deploy.secrets.cloud`가 코드 난수를 PutSecretValue → `deploy.config.cloud`가 태스크 정의 `secrets` valueFrom에 그 ARN → `deploy.app.cloud` → 두 환경 로그인·세션 유지 확인(스모크 S5~S8). 온프렘은 `deploy.config.local`이 난수를 `.env`에 씁니다. 옛 "`sync_env_to_cloud`가 앱 접두사 안에 만들어 인프라 변경 없음"은 대체되었습니다(N31 해결).
- 💭 위치(N39): plan에 실행 역할 정책의 in-place update가 있으므로 V23대로 `state_change` → G1 뒤입니다(하네스 골든 plan). 대안은 AI Terraform 규칙으로 권한을 시크릿별 **새** 정책 리소스로 추가해 plan을 create만으로 만들고 G1 전에 돌리는 것입니다(빌드와 겹쳐 시간 절약). 리허설 실측을 보고 정합니다.
- ECS 서비스는 `lifecycle ignore_changes = [task_definition]`(장부 32)이라 앱 층 apply가 파이프라인이 등록한 태스크 정의를 되돌리지 않습니다. 💭 `desired_count`도 함께 두어야 앱 층 apply가 서비스를 0으로 되돌리지 않습니다(확인 필요).

### 4-6. 순서·결합 규칙과 변형

- **순서는 카탈로그 의존 그래프가 정합니다.** AI가 정하지 않습니다. `config < db < deploy.was < deploy.web`(WAS 먼저. 응답 필드 추가는 하위 호환 [docs/10 5절](../../docs/10_전체-흐름-초안.md)).
- **결합(V6):** `build.X` ⇒ 모든 대상의 `deploy.X` / `deploy.secrets.cloud` ⇒ `deploy.config.cloud` ⇒ `deploy.app.cloud` / `deploy.config.local` ⇒ `deploy.was.local` / `deploy.db.<t>`가 쓰는 이미지는 이번 manifest의 was digest. 💭 `deploy.infra.cloud` ∧ 부트스트랩 ⇒ 모든 `build.*`에 wait_for `infra_ready` / `deploy.dbinit.cloud` ⇒ `deploy.secrets.cloud`(DB 비밀) 먼저 / 인프라 plan에 시크릿 create가 있으면 ⇒ `deploy.secrets.cloud`(값 쓰기)를 인프라 step **뒤**에, 그리고 `deploy.config.cloud`·`deploy.app.cloud` 포함(ECS는 시작 때만 시크릿 주입) / 인프라 plan에 역할 변경이 있으면 ⇒ `deploy.config.cloud`·`deploy.app.cloud` 포함.
- **D3=(b)(서비스 2개)면:** `deploy.app.cloud` 대신 `deploy.was.cloud`·`deploy.web.cloud` 두 step(조건은 로컬과 같음). WAS 컨테이너에 `healthCheck(/health/live)`가 필요합니다. 없으면 RUNNING 뒤 40초 고정 대기가 생깁니다([docs/17 8-5](../../docs/17_골든패스-시나리오.md)).
- **온프렘 이미지 pull 위치(남은 결정):** `build_image(target=local)`을 `images_ready` 뒤 pre-pull step으로 둘지, `deploy_tier(local)` 안에서 digest로 pull할지 정해야 합니다.

### 4-7. AI의 실제 가치 (정직한 문장)

골든 패스에서 step 빼기는 규칙 재확인 수준입니다. AI의 값은 두 가지입니다.
1. 규칙이 못 보는 이유로 step·시나리오를 **넣는 것**. 예: `from_prefixed_env` 같은 간접 설정 읽기 → config step, auth 경로 변경 → 로그인 스모크 시나리오.
2. 포함·제외 이유의 **설명**.

근거: [MySQL 조사 결론](../../research/2026-09-30_MySQL-계획구조-검토.md), [Jev 조사 3·4절](../../research/2026-09-30_Jev-사용처-검토.md).

## 5. facts와 실행 컨텍스트

| 구분 | facts (AI가 읽음) | 실행 컨텍스트 `RunContext` (코드만 채움) |
|---|---|---|
| 누가 만듦 | 실행기가 결정적으로 계산. 계획에 `facts_hash`로 고정 | 실행기가 run 시작 때 **환경 정보**(원본 4곳, 장부 27)에서 조립 |
| AI에게 감 | 예(키 **이름**만, 값 없음) | **아니오**(가린 요약만: 리소스 종류·개수, 있음/없음) |
| 계획·툴 파라미터에 | 아니오(해시만) | 아니오 |
| 내용 | 변경 경로 목록 / tier별 `build_inputs` 트리 해시(`git rev-parse <sha>:<path>`) / 대상·tier별 마지막 성공 SHA·배포된 digest / 필요한 환경변수 키 이름(deploy.yaml ∪ 정적 스캔: `os.environ[...]`, `os.getenv`, `app.config[...] =`, `from_mapping`, `from_prefixed_env`) / 대상에 이미 있는 키 이름 / `migrations/` 트리 해시·대기 파일·lint 결과 / 라우트 목록(`/auth/*`), 세션 사용 여부 / TLS 상태(ISSUED 여부) / 토글 / `env_release.status` / 💭 인프라 요구(tier·포트·DB·시크릿 키 이름·헬스 경로)와 그 해시, 마지막 apply의 인프라 요구 해시 / 💭 tier별 Dockerfile 있음·생성본 승인 여부(`dockerfile_present`, `dockerfile_approved`) | `run_id`, `project`, `mode`, `source_sha`, `snapshot_sha256`, S3 버전 ID / 이미지 digest(manifest), 대상별 `previous_release` / `cloud_domain`·`dns_mode`·`hosted_zone_id`(관리 페이지 설정 스냅샷) / ALB·리스너 ARN, RDS 엔드포인트, 시크릿 ARN(앱 시크릿·Docker Hub pull 토큰), 역할 ARN(환경 정보의 Terraform 출력 = `terraform output -json`, `apply_infra` 뒤 갱신) / 💭 인프라 승인 기록(승인자, 시각, plan sha256), apply 세션 종류(부트스트랩 관리자 / 파이프라인 역할) / 온프렘 인벤토리(`platform.onprem.yaml`: tier별 docker 주소, DB 서버 IP, was upstream, `.env` 경로) / 토글, 어댑터 모드(real/fake), LLM backend, `lock_token` |

- 💭 `RunContext`는 메모리 객체로 두고 `var/runs/<run_id>/context.json`에 저장(재생·디버깅용, 비밀값 없음). 이것이 run 시점의 **환경 정보 스냅샷**입니다(N38).
- 도메인은 관리 페이지 설정 → run 시작 때 스냅샷 → `ctx.cloud_domain`으로만 흐릅니다. 툴 파라미터·계획·`deploy.yaml`·AI Terraform 입력·변수에는 없습니다(✅ 장부 17).
- AI Terraform(`generate_infra`)에 가는 것은 인프라 요구(키 **이름**, tier, 포트 등)와 코드 소유 틀·허용 목록·스키마 조각, 개선 배포면 마지막으로 apply된 앱 층 HCL과 환경 정보의 가린 요약뿐입니다. 비밀값·도메인·계정 ID·Terraform state·출력 원문은 가지 않습니다(계정 ID는 코드 소유 변수로 plan 때 코드가 채움 💭. 정책 ARN을 이름으로 조립하려면 plan 시점에 값이 있어야 함).

## 6. `plan.json` 스키마 (💭, 계약 문서가 확정)

### 6-1. 두 층: AI 초안 → 조립된 최종 계획

| 층 | 누가 만듦 | 담을 수 있는 것 | 담을 수 없는 것 |
|---|---|---|---|
| `PlanDraft` | `generate_plan`(AI) 또는 규칙 | 조건부·선택 step의 포함/제외와 이유, 스모크 시나리오 추가, 경고 | 필수·내장 step, 순서, `wait_for`/`signal`, 도메인·digest·명령 같은 값 |
| `Plan`(`plan.json`) | `validate_plan`(조립기, 순수 함수) | 카탈로그 + facts + 초안을 합친 최종 계획 | – |

- 실행기는 `Plan`만 실행합니다.
- [docs/18 B-7](../../docs/18_팀-합의요청-MCP-구조.md) 예시의 `{"step": "<툴 이름>"}`은 `id`(step id)와 `tool`(레지스트리 이름)로 나눴습니다 💭. 같은 툴이 여러 step에 쓰이기 때문입니다. 18 예시의 `db_migrate`는 카탈로그 이름 `prepare_db`로 씁니다.

### 6-2. `PlanDraft` (AI 출력)

```json
{
  "decisions": [
    {"step": "build.web",          "include": false, "reason": "web/·nginx/ 변경 없음"},
    {"step": "deploy.web.local",   "include": false, "reason": "web digest 동일"},
    {"step": "verify.watch.cloud", "include": false, "reason": "데모 시간"}
  ],
  "add_scenarios": ["auth"],
  "warnings": [{"code": "indirect_config", "message": "from_prefixed_env 사용 흔적"}]
}
```

| 필드 | 제약 |
|---|---|
| `decisions[].step` | 카탈로그의 **조건부·선택** step id enum. 필수 step id는 enum에 없음 |
| `decisions[].include` | bool |
| `decisions[].reason` | 200자 이하. 표시용 |
| `add_scenarios` | {`base`, `auth`} enum |
| `warnings[].code` | enum(예: `indirect_config`, `hardcoded_secret`, `unsupported_migration`) |

- Claude는 JSON 스키마 출력으로 받습니다. Jev는 질문별 확률을 코드가 모아 이 모양으로 조립합니다(형식이 깨질 일이 없음).

### 6-3. 필드 정의

| 필드 | 필수 | 누가 채움 | 설명 |
|---|---|---|---|
| `schema` | ✓ | 조립기 | `ddak.plan/v1`(접두어는 가칭 `ddak`) |
| `run_id` | ✓ | 실행기 | 패턴 `^[A-Za-z0-9][A-Za-z0-9._-]{0,63}$`(하네스). 💭 `run-YYYYMMDD-HHMM[-NN]` |
| `project` | ✓ | 코드 | `deploy.yaml`의 `project` |
| `mode` | ✓ | 코드 | `update` / `bootstrap`(이전 릴리스 없음) |
| `facts_hash` | ✓ | 코드 | facts 정규화 JSON의 sha256. 실행 시작 때 재계산, 다르면 재계획(V11) |
| `plan_hash` | ✓ | 조립기 | 켜진 step 목록·params·승인된 패치 해시의 정규화 JSON sha256. 매 step 직전 대조(V12) |
| `planner` | ✓ | 조립기 | `by`(ai/rule), `provider`(jev/claude-api/claude-cli/replay/rule), `model`, `source`, `attempts`, `fallback` |
| `toggles` | ✓ | 코드 | `{"code_patch": false}`(기본 OFF, 장부 16) |
| `build` / `deploy.local` / `deploy.cloud` / `verify` | ✓ | 조립기 | 각각 `steps[]`, `skipped[]`. 순서 = 배열 순서(카탈로그가 결정) |
| `build.signal` | ✓ | 조립기 | `images_ready` |
| step `id` · `tool` | ✓ | 조립기 | `id`는 카탈로그, `tool`은 레지스트리 이름 |
| step `target` · `tier` | 해당 시 | 조립기 | 트랙과 일치. `tier`는 `deploy.yaml`에 있어야 함 |
| step `params` | 선택 | AI/규칙 → 검증 | **step별 허용 키만**(예: `migrations`, `scenarios`, `mode`, `keys`). 값도 enum·존재 검사 |
| step `layer` | ✓ | 조립기 | `mandatory` / `conditional` / `optional`(내장은 계획에 없음) |
| step `effect` | ✓(기본 `read`) | **조립기(카탈로그)** | `read` / `additive_prep` / `state_change`. AI가 써도 덮어씀. 실행기가 W1 검사와 롤백 대상 판단에 씀(하네스 `PlanStep.effect`) |
| step `by` · `reason` · `evidence` | 선택 | AI/규칙 | 표시용. 판정에 쓰지 않음(V13) |
| step `wait_for` · `signal` | 해당 시 | **조립기(카탈로그)** | AI가 써도 무시하고 덮어씀. `wait_for`는 **항상 배열**(신호 하나도 `["images_ready"]`). 신호는 고정 4개: `infra_ready`(💭 인프라 apply 뒤), `images_ready`, `local_verified`, `cloud_verified`(하네스 `SignalName`) |
| step `run` | 해당 시 | 조립기 | `finally`만. verify 섹션에서만 쓰고 `wait_for`·`signal`을 두지 않음. 앞이 실패해도 실행하고, 실패해도 run 결과는 유지(하네스 실행기에 구현) |
| `skipped[]` | ✓ | 조립기 | `id`, `tool`, `target`·`tier`(해당 시), `layer`, `by`, `reason`, `skip_rule`(결정적 규칙 id) |
| `invalidated[]` | ✓ | 조립기 | AI가 빼려 했으나 무효화된 것. 예: `{"id":"deploy.db.cloud","attempt":"skip","by":"ai","result":"forced_include","why":"migrations_unchanged(cloud)=false"}` |
| `warnings[]` | 선택 | AI/규칙 | 보고 이슈로 올림 |

- `timeout_s`는 계획에 싣지 않고 실행기가 레지스트리 기본값·step 카탈로그에서 읽습니다 💭. `effect`는 계획에 싣습니다(위 표).
- step id 형식은 하네스 패턴 `^[a-z][a-z0-9_]*(\.[a-z0-9_]+){1,3}$`입니다. 점이 하나 이상 있어야 해서 보고 step은 `verify.report`입니다.
- 하네스 `Plan` 모델은 최소 예시라 `project`·`facts_hash`·`plan_hash`·`planner`를 아직 선택 필드로 둡니다. 계약 문서에서 필수로 바꿉니다 💭.

- `deploy.infra.cloud`가 `steps`에 있는 것은 v2(로그인)의 새 SECRET_KEY가 인프라 요구(시크릿 키 이름)를 바꾸기 때문입니다(✅ 장부 32). 그래서 이 run에서는 ①②에서 `generate_infra`(앱 층 수정안)·`validate_infra`·`plan_infra`가 돌고, [IAM·인프라 승인]이 들어갑니다(버튼 수는 N40). `discover_existing`은 새 계정이라 생략해도 됩니다(P1). `deploy.dbinit.cloud`는 부트스트랩에서 이미 앱 DB·계정을 만들어 `skipped`입니다.
- plan에 in-place update(실행 역할 정책)가 있어 `effect: state_change`, `wait_for: ["local_verified"]`입니다(V23, 위치는 N39). `signal: infra_ready`는 이 run에서 기다리는 step이 없지만 카탈로그 값이라 둡니다.

### 7-4. 위반 처리 분류 (💭)

| 분류 | 규칙 | 처리 |
|---|---|---|
| 형식 불합격 | V1·V2·V3·V16 | 재지시 1회 → 규칙 계획(✅ 장부 5) |
| 보정 | V4·V5·V6·V7·V14·V22 | 조립기가 고치고 `invalidated`/표시로 남김. 재지시 없음 |
| BLOCK | V10·V18·(V19, D12에 따라)·V21·V23·V24·V26 | 배포하지 않음. 보고 카드에 이유 |
| 거부 | V15·V17 | run을 만들지 않음 |

- "불합격 → 재지시"를 형식 위반에만 쓰고 안전 위반은 보정으로 처리하는 구분은 고려안입니다. 장부 5의 문구와 충돌하지 않지만 팀 확인이 필요합니다.
- 💭 Dockerfile 수정 루프(`generate_dockerfile` → `validate_dockerfile`, 최대 2회)도 따로 셉니다. 실패하면 run은 `FAILED_BEFORE_DEPLOY`(`DOCKERFILE_INVALID`)이고 사람에게 넘깁니다.
- 💭 인프라 수정 루프(`generate_infra` → `validate_infra` → 실패면 첫 오류 원문을 되먹여 다시, **최대 3회**, 매 회차 보안 검사 전체)는 계획 재지시(1회)와 따로 셉니다. 3회 안에 실패하면 자동 완화 없이 사람에게 넘기고 run은 `FAILED_BEFORE_DEPLOY`(`INFRA_INVALID`)입니다. 근거: 반복 수정 연구에서 3회차가 최적 중단점(arXiv 2608.13404, 프리프린트).
- 재지시 루프(`generate_plan` → `validate_plan` → 불합격이면 1회 더 → 규칙 계획)는 계획 흐름 조정자가 레지스트리 이름으로 두 툴을 불러 돌립니다 💭. `validate_plan`은 `generate_plan`을 import하지 않습니다(import-linter 계약, [07 개발 하네스](07_개발-하네스.md)). 조정자를 어느 모듈에 둘지는 [01 아키텍처](01_아키텍처.md)를 따릅니다.

| AI 호출 | Jev 2초·재시도 1회 / Claude API 20초·재시도 1회 / CLI 20초 | 설정 `DDAK_AI_TIMEOUT_S`=20, `DDAK_JEV_TIMEOUT_S`=2 | [Jev 조사](../../research/2026-09-30_Jev-사용처-검토.md)(SDK 기본 10초·재시도 2회를 줄임), [LLM 호출 검토](../../research/2026-09-30_웹-CLI-LLM호출-검토.md)(CLI 호출 4.5~9초 실측) |

- 하네스 실행기는 지금 레지스트리 기본값(툴마다 하나, 넉넉한 상한)만 씁니다. step·대상별 값은 step 카탈로그가 덮어쓰는 방식으로 넣습니다(TODO, 김준석·정준우) 💭.
- **주의(파이썬 동작):** `asyncio.wait_for`로 `asyncio.to_thread` 작업을 취소해도 **스레드 안의 boto3·docker 호출은 멈추지 않습니다.** 그래서 어댑터가 `ctx.deadline`을 스스로 지켜야 합니다(boto3 waiter 최대 횟수, subprocess kill, docker SDK timeout).
- 타임아웃 뒤에는 실제 상태를 모릅니다(예: `update_service`는 이미 나갔을 수 있음). 롤백은 **현재 상태를 조회한 뒤** 필요한 것만 하는 멱등 동작이어야 합니다 [판단].
- 💭 실행기는 `state_change` step을 자동 재시도하지 않습니다. 재시도는 툴 안의 읽기 폴링에서만 합니다.

### 8-3. 실패 처리와 롤백

**롤백 원칙 (✅ 장부 6)**
- **앱만, 해당 환경만.** 대상은 그 환경 `previous_release` manifest의 digest.
  - 온프렘: 바뀐 tier 컨테이너를 이전 digest로 다시 생성. 수 초 중단 허용(2~5초 [추정]).
  - 클라우드: `update_service(taskDefinition=이전 app 태스크 정의 ARN)`.
- **DB는 되돌리지 않습니다.** 추가형 마이그레이션만 허용하므로 v1 코드가 0002 스키마에서 그대로 동작합니다(v1식 `INSERT INTO post (title, body)`가 `author_id` NULL로 성공, 9/30 `mysql:8.4.11` 실험).
- **MySQL 주의:** DDL은 암묵 커밋입니다. 마이그레이션이 중간에 실패하면 앞 문장은 남습니다. 러너의 문장 단위 가드로 재실행을 안전하게 합니다([03 골든 패스 4-3](03_골든패스-시나리오.md)). 옛 문서의 "Postgres가 트랜잭션으로 되돌린다"는 해당하지 않습니다.
- 설정은 추가형 키만 늘어나는 것을 전제로 되돌리지 않습니다. 이전 앱이 새 `.env`로 떠도 동작해야 합니다 [판단]. 기존 키의 값을 바꾸는 배포는 이 전제를 깹니다(확인 필요).

**실패 위치별 처리**

### 8-4. 상태 머신

**run 수준**

```
CREATED → ANALYZED → PLANNED → VALIDATED → AWAITING_APPROVAL → APPROVED
        → BUILDING ∥ DEPLOYING(두 트랙) → COMPARING → REPORTED → (최종 상태)
```

- 💭 인프라 step이 있으면 `AWAITING_APPROVAL`에서 두 승인을 모두 받아야 `APPROVED`입니다: [IAM·인프라 승인](plan sha256) → [배포]. IAM 승인은 배포 클릭에 묻히지 않게 따로 받습니다(✅ 장부 23 "사람이 검증·승인"). 장부 32의 데모 문구는 "사람 '배포' 승인"이라 [배포] 한 번에 plan sha256까지 묶는 안도 선택지입니다(N40, 사용자 확인).
- 💭 Dockerfile을 새로 만들었으면 [Dockerfile 승인](Dockerfile sha256)도 받아야 합니다(V26).

| 최종 상태 | 뜻 |
|---|---|
| `SUCCEEDED` | 두 환경 배포·검증·비교 통과 |
| `FAILED_BEFORE_DEPLOY` | `VALIDATION_FAILED`·`BLOCKED`·`REJECTED`·`BUILD_FAILED`. 롤백할 것 없음 |
| `FAILED_LOCAL` | 온프렘 롤백, 클라우드 무변경 |
| `FAILED_CLOUD` | 클라우드 롤백, 온프렘 v2 유지 → `DIVERGED` |
| `PARITY_FAILED` | 교차 비교 불일치(D10) |
| `NEEDS_HUMAN` | 롤백 실패. 잠금 유지 |
| `CANCELLED` | 사람이 취소 |

**트랙 수준**

```
PENDING → RUNNING(step i) ⇄ WAITING(gate) → VERIFIED(signal) → DONE
실패:      FAILED → ROLLING_BACK → ROLLED_BACK | ROLLBACK_FAILED
클라우드:  ABORTED_AT_GATE (로컬 실패로 G1 fail, 롤백 불필요)
```

**step 수준:** `pending` / `waiting` / `running` / `succeeded` / `failed` / `skipped` / `aborted` 💭.

**환경 수준 `env_release` (대상별 1행)**

| 필드 | 뜻 |
|---|---|
| `current_release`, `previous_release` | 현재·직전 릴리스 id. 롤백 대상 |
| `status` | `SUCCEEDED` / `ROLLED_BACK` / `DIVERGED` / `NEEDS_HUMAN` |
| `last_success_sha` | skip 조건의 기준 |
| `updated_at` | – |

```python
class Gate:
    def __init__(self): self._ev, self.ok, self.why = asyncio.Event(), None, None
    def open(self): self.ok = True; self._ev.set()
    def fail(self, why): self.ok, self.why = False, why; self._ev.set()
    async def wait(self):
        await self._ev.wait()
        if not self.ok: raise GateFailed(self.why)

async def run_step(step, track, ctx):
    ctx.assert_plan_hash()                                   # V12 (하네스 TODO)
    for g in step.wait_for:                                  # 항상 배열

    inp = build_input(t, step, track.target, ctx)            # run_id·target·tier·lock_token은 실행기가 채움 → 스키마 재검증
    limit = t.spec.timeout_s                                 # 💭 step 카탈로그의 대상별 값은 TODO
    with tool_context(step.tool, ctx.run_id):                # call_ai 런타임 가드 기준
        out = await asyncio.wait_for(                        # 스레드는 안 멈춤 → 어댑터가 deadline 준수
            asyncio.to_thread(t.fn, inp, ctx), limit)
    ctx.record(step, out)                                    # 이벤트 + run 로그
    if getattr(out, "passed", True) is False:
        raise CheckFailed(step.id)
    if step.signal:
        ctx.gates[step.signal].open()

async def run_track(track, ctx):
    touched = False                                          # state_change를 시작했는가
    try:
        for step in track.steps:
            touched |= step.effect == "state_change"         # 시작만 해도(실패해도) 롤백 대상
            await run_step(step, track, ctx)
    except GateFailed:
        ctx.set_track(track, "ABORTED_AT_GATE")              # 바꾼 것 없음 → 롤백 없음
    except Exception:
        ctx.set_track(track, "FAILED")
        if touched: await ctx.rollback(track.target)         # 이 환경만, 앱만, 이전 digest
    finally:
        for s in track.own_signals: ctx.gates[s].fail(f"{track.name} ended")  # 못 연 신호는 실패로 닫음

async def run(plan, ctx):
    async with ctx.deploy_lock():                            # 내장: 잠금·하트비트·finally 해제
        try:
            ctx.assert_facts_unchanged()                     # V11
            await asyncio.gather(                            # W0: 세 트랙 동시 시작
                run_track(plan.build, ctx),                  # 끝나면 images_ready
                run_track(plan.deploy.local, ctx),           # 끝나면 local_verified
                run_track(plan.deploy.cloud, ctx))           # G1 뒤 state_change
            await run_track(plan.verify.main_steps(), ctx)   # verify.compare: G2 대기
            if ctx.any_failed() or ctx.unexpected_diff:
                await ctx.diagnose()                         # collect_diagnostics → diagnose_parity_gap
        finally:
            for step in plan.verify.finally_steps():         # verify.report(run=finally): 실패해도 결과 유지
                with suppress(StepFailed): await run_step(step, None, ctx)
            ctx.record_deploy_log()                          # env_release 갱신
```

- 실행기는 툴 모듈을 import하지 않고 `REGISTRY` 이름 조회만 씁니다. 그래야 "실행 경로에 AI 없음" import 계약이 간접 import로 깨지지 않습니다([04 툴 카탈로그 1절](04_툴-카탈로그.md#1-레지스트리-형식), [07 개발 하네스](07_개발-하네스.md)).
- 실행기는 ECS `COMPLETED`를 기다리지 않습니다. "새 대상 healthy + `/version` release_id 일치"로 다음 step에 들어갑니다(deregistration 기본 300초면 COMPLETED가 수 분 늦음).

## 9. 초기 배포(부트스트랩) vs 업데이트 배포 (✅ 장부 14·21·22, 세부 💭)

### 9-1. 차이

| 항목 | 업데이트(v2, 라이브 데모) | 초기 배포(v1, 부트스트랩) |
|---|---|---|
| `mode` | `update` | `bootstrap`(이전 성공 릴리스 없음) |
| 분석 입력 | 마지막 성공 이후 diff | 저장소 전체, baseline 없음 |
| 인프라 | 인프라 요구 해시가 같으면 **건너뜀**. 바뀌면 같은 흐름의 조건부 step(앱 층 수정안). **라이브 데모 v2는 새 SECRET_KEY로 포함**(장부 32) | **항상**: (기반 준비가 끝난 뒤, 9-3) 인프라 요구 → (탐지) → AI Terraform(플랫폼 층 + 앱 층) → 검증·정책 검사·Access Analyzer → plan 요약 → 사람 승인(관리자 자격) → apply |
| Dockerfile | 저장된 것 재사용(단계 없음) | 없으면 생성 → 검사·검증 빌드 → [Dockerfile 승인] → 저장(4-0). 샘플 앱은 기준 Dockerfile이 있어 보통 없음 |
| 조건부 step | skip 조건을 평가 | 비교 대상이 없어 **전부 강제 포함** |
| 빌드 | 바뀐 tier만(was) | web + was |
| DB | 대기 중 마이그레이션(0002)만 | 클라우드: 공유 RDS 안에 앱 DB·계정 생성(`deploy.dbinit.cloud`) → 0001부터. 대상 DB가 비었는지 검사(V18) |
| 사전 검증 | 계획 검증 | ① 인프라 검증(`validate_infra`·`plan_infra`, P0) + 온프렘 호스트 점검(`preflight_check(local)`, 💭) ② 계획 검증 ③ 런타임 위치 연결 검증(`migrate precheck`) |
| 설정 | 새 키 추가(SECRET_KEY, SESSION_COOKIE_SECURE). SECRET_KEY 값은 클라우드 = 새 시크릿에 PutSecretValue, 온프렘 = `.env` | 모든 키 첫 주입, 첫 태스크 정의 리비전. v1에는 SECRET_KEY 없음(장부 32) |
| 클라우드 전환 | `update_service(새 리비전)` | `update_service(desired=D23)`. AI Terraform은 서비스를 desired 0으로 만들어 둠(규칙 💭) |
| 스모크 | base + auth | base(v1: B1·B2) |
| `previous_release_id` | `rel-v1` | `null` |
| 실패 시 | 해당 환경만 앱 롤백 | 롤백 대상 없음 → **중지**(클라우드 desired 0, 온프렘 컨테이너 제거) |
| ECS circuit breaker | 이전 COMPLETED로 되돌림 | 되돌릴 대상이 없어 멈춤 |
| 결과 | `env_release` 둘 다 rel-v2 | 둘 다 rel-v1, `SUCCEEDED` |
| 시점 | 데모 당일 | 사전 준비(리허설로 확인). 발표에서는 녹화·사전 실행으로 보여 줌(인프라만 10~20분, 전체 15~30분 [추정]) |

### 9-2. 부트스트랩 run 순서

- 전제: 기반 준비(9-3, 상태 버킷·앱 경계, P1이면 파이프라인 역할·경계)가 끝나 있어야 합니다. `plan_infra`가 승인 **전**에 상태 버킷과 plan 자격을 쓰기 때문입니다.
- 💭 한 run으로 이어서 돕니다(아래 1~10). 다만 RDS 생성(최대 20분)과 ACM 검증 대기(최대 30분 Pending 가능) 때문에 리허설에서는 **두 단계 운용**도 허용합니다: 1차 run = 1~5(인프라 apply까지) + TLS(`ensure_tls` apply·`verify_tls`), 2차 run = 6~10(2차 run에서는 인프라 요구 해시가 1차 apply와 같아 `deploy.infra.cloud`가 skipped). 둘 다 같은 파이프라인·같은 잠금이라 "파이프라인이 다 한다"(장부 14)는 그대로입니다. 1차 run의 plan 모양(인프라·TLS만)은 N25와 함께 정합니다.

1. **분석 → 인프라 요구:** 전체 저장소(`deploy.yaml`, tier·포트·DB·시크릿 키 이름·헬스 경로) → 인프라 요구 JSON과 해시. 환경 정보에 Terraform 출력이 없으므로 부트스트랩 모드(E6).
1-1. **(Dockerfile이 없을 때만) Dockerfile:** `generate_dockerfile` → `validate_dockerfile`(정적 검사 + 로컬 검증 빌드) → 4번 승인 때 [Dockerfile 승인]. 샘플 앱은 기준 Dockerfile이 있어 보통 건너뜀(4-0).
2. **AI Terraform:** `discover_existing`(P1, 새 계정이라 사실상 빈 결과) → `generate_infra`(HCL 초안) → `validate_infra`(init 전 정적 게이트 → `init -lockfile=readonly` → validate → Checkov, 실패면 최대 3회 되먹임) → `plan_infra`(P0 테스트 프로필 / P1 읽기 세션으로 plan → 요약·IAM diff·Access Analyzer). 상태 백엔드는 기반 준비의 버킷.
3. **[사전 검증] 계획 검증:** DB가 비었는지(V18), 0001 lint, V22~V24.
4. **사람 승인:** ([Dockerfile 승인]) → [IAM·인프라 승인](plan sha256, 관리자가 이 시점에만 단기 관리자 자격 제공) → [배포].
5. **cloud 첫 step `deploy.infra.cloud`:** 승인 기록 sha256 대조(V25) → `apply <run>.tfplan`(관리자 단기 키를 terraform 자식 env로만, 플랫폼 층 → 앱 층 순서) → 플랫폼·앱 역할·플랫폼 역할 생성 → `terraform output -json`으로 환경 정보 기록 → `infra_ready`. 상태 버킷·경계·파이프라인 역할은 기반 준비에서 이미 만들어져 있음. Docker Hub 토큰 시크릿 값은 사람이 넣어 둠(💭 절차 확인 필요).
6. build web + was(`infra_ready` 대기) → manifest(`previous_release_id: null`). 동시에 cloud: TLS(한 run이면 apply) → DB 비밀 생성 → **앱 DB·계정 생성(`deploy.dbinit.cloud`)** → 첫 태스크 정의 리비전(G0 대기).
7. **[사전 검증] 런타임 위치 연결 검증:** 각 환경의 실제 런타임 위치에서 `migrate precheck`(온프렘 was 호스트의 일회성 컨테이너 / 클라우드 일회성 태스크. TLS·time_zone·버전 확인).
8. local: config → migrate 0001 → verify schema → was → web 기동 → v1 스모크(B1·B2) → `local_verified`.
9. cloud(G1 뒤): migrate 0001 → `update_service(desired=D23)` → verify + TLS.
10. compare → `env_release` 둘 다 rel-v1.

### 9-3. 파이프라인 밖과 별도 run

| 구분 | 내용 | 누가 |
|---|---|---|
| 새 계정 준비(사람, 파이프라인 밖) | 💭 Paid plan 계정, 관리자 신원(IAM Identity Center 또는 MFA 사용자, root 사용 금지), Route 53 영역(R3), Budgets, 할당량 확인(Fargate vCPU, CodeBuild 동시 빌드). HCL은 쓰지 않음 | 유상준 |
| 💭 기반 준비(별도, AI 없음, 계정당 한 번) | `apply_infra(stage=foundation)`: 코드 고정 템플릿으로 상태 버킷(버저닝·암호화·PAB) + `ddak-app-boundary`(+ P1: `ddak-pipeline-boundary`·파이프라인 역할·서비스 연결 역할)를 boto3로 생성. Terraform 상태 밖. IAM 생성이라 [기반 승인](템플릿 JSON 전체·sha256 표시, 관리자 자격)을 거침(✅ 장부 23). 부트스트랩 run의 `plan_infra`가 이 버킷·자격을 씀. 장부 21~23과의 관계(상태 버킷도 AI 범위, IAM은 AI 설계)는 사용자 확인 필요(N27) | `apply_infra`(승인은 사람) |
| 클라우드 플랫폼(인프라) | **파이프라인 안**(9-2의 1~5). 옛 "Terraform 사전 구축(파이프라인 밖)"을 대체(✅ 장부 21·22). AI HCL로 만듦 | `apply_infra`(승인은 사람) |
| 온프렘 셋업(파이프라인 밖) | DB 서버/컨테이너 `mysql:8.4.11`, was·web 호스트, 네트워크, 인벤토리 `platform.onprem.yaml`(환경 정보 원본 ③), 각 호스트 Docker Hub **읽기 전용 토큰** `docker login`(AWS 자격 불필요). 초기화 스크립트는 DB·사용자만, 스키마는 마이그레이션 경로로 | 김준석 |
| Docker Hub 준비(사람, 파이프라인 밖) | 💭 조직·비공개 저장소, 읽기·쓰기 토큰(CodeBuild용)과 읽기 전용 토큰(ECS·온프렘용)을 따로 발급 → 시크릿 컨테이너(AI Terraform이 만든 `ddak-platform/*`)에 사람이 값 입력. 무료 플랜 제한 확인(N37) | 안승환 |
| "도메인 연결" run(별도, AI 없음) | `[ensure_tls(cloud, mode=apply), verify_tls(cloud)]`만. 같은 배포 잠금. ALB가 인프라 apply로 생긴 뒤에만 가능. 한 run 부트스트랩이면 9-2 6에 포함. 사전 발급 마감 10/1(남은 결정) | 유상준(입력은 사람) |

- 발표 문구 💭: "인프라도 AI가 Terraform으로 짭니다. IAM과 인프라 변경은 사람이 plan 요약을 승인해야 만들어지고, 권한 경계가 AI 설계의 상한입니다. 초기 배포와 업데이트는 같은 파이프라인입니다." 옛 문구 "플랫폼은 Terraform으로 미리 만들었다"는 더 이상 사실이 아니므로 쓰지 않습니다. SQLite → MySQL 포팅은 "팀이 손으로 포팅한 기준 앱"이라고 말합니다. 부트스트랩이 변환했다고 하면 과장입니다.
- 리허설 초기화는 `reset_demo_state`(가드 스크립트, `ALLOW_DEMO_RESET=1`)로 합니다. 앱을 rel-v1로, DB를 0001로 되돌리는 파괴형이라 리허설 전용입니다. 인프라는 되돌리지 않습니다(부트스트랩 재연습은 새 계정 또는 `cleanup` 뒤, 사람만).
