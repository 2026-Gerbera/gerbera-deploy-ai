## 2. v1 사전 준비 (담당 장민영, SQLAlchemy·MySQL 호환·`users`)

### 2-0. v1 준비 체크리스트 (✅ 장부 32, 담당 장민영 O3)

- v1은 로그인 기능이 **아예 없고** SECRET_KEY도 없습니다. 그래야 v2에서 "새 비밀 키 → 시크릿·권한 추가(인프라 변경) → 난수 주입" 장면이 생깁니다.
- 아래는 10/1 E2E 전에 확인할 목록입니다. 항목 문구는 💭(체크 방법은 담당이 바꿀 수 있음).

| # | 확인 | 방법 💭 |
|---|---|---|
| V1-1 | `create_app`에 `SECRET_KEY` 설정이 없음(`from_mapping`·`config[...]`·`from_prefixed_env` 포함) | `grep -rn SECRET_KEY flaskr/` 결과 0줄 |
| V1-2 | `flash()`·`get_flashed_messages()` 호출이 없음(템플릿 포함). 오류는 템플릿 변수로 | `grep -rn "flash" flaskr/` 결과 0줄 |

## 4. 마이그레이션 DDL (MySQL 8.4, 추가형만)

### 4-1. 파일

```sql
-- migrations/0001_init_v1.sql
CREATE TABLE IF NOT EXISTS post (
  id INT UNSIGNED NOT NULL AUTO_INCREMENT PRIMARY KEY,
  created TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
  title VARCHAR(200) NOT NULL,
  body TEXT NOT NULL
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci;

-- migrations/0002_v2_users.sql  (users에 created를 넣지 않음: 목록 쿼리 1052 모호성 회피)
CREATE TABLE IF NOT EXISTS users (
  id INT UNSIGNED NOT NULL AUTO_INCREMENT PRIMARY KEY,
  username VARCHAR(50) NOT NULL,
  password VARCHAR(255) NOT NULL,          -- werkzeug scrypt 해시 약 162자
  UNIQUE KEY uq_users_username (username)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci;
ALTER TABLE post ADD COLUMN author_id INT UNSIGNED NULL AFTER id;
ALTER TABLE post ADD CONSTRAINT fk_post_author FOREIGN KEY (author_id) REFERENCES users (id) ON DELETE SET NULL;

-- 러너가 만드는 표 (파일에 넣지 않음)
CREATE TABLE IF NOT EXISTS schema_migrations (
  version    VARCHAR(16)  NOT NULL PRIMARY KEY,
  name       VARCHAR(100) NOT NULL,
  checksum   CHAR(64)     NOT NULL,
  applied_at TIMESTAMP    NOT NULL DEFAULT CURRENT_TIMESTAMP,
  release_id VARCHAR(64)  NULL
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci;
```

- 파일 이름 4자리(`0001_…`)와 러너 방식은 남은 결정입니다 💭.

### 4-2. [실험 9/30] `mysql:8.4.11`에서 확인한 것

| 확인 | 결과 |
|---|---|
| 0001 → 0002 순서 적용 | 성공 |
| 적용 뒤 v1식 `INSERT INTO post (title, body)` | 성공(`author_id` NULL) |
| `ALTER TABLE … ADD COLUMN IF NOT EXISTS` | **ERROR 1064**(MySQL 미지원) |
| `CREATE INDEX IF NOT EXISTS` | **ERROR 1064** |
| 같은 `ADD COLUMN` 재실행 | ERROR 1060 Duplicate column |
| 같은 `ADD CONSTRAINT` 재실행 | ERROR 1826 Duplicate foreign key constraint name |
| FK 생성 | InnoDB가 `fk_post_author` 인덱스 자동 생성 → 별도 인덱스 불필요 |
| 같은 초에 넣은 두 글 | `created` 같음 → `id DESC` 보조 정렬 필요 |
| 문자셋 미지정 `mysql` CLI | 한글이 `?`로 보임 → 연결마다 `charset=utf8mb4` |
| 컨테이너 기본값 | `sql_mode`에 `STRICT_TRANS_TABLES` 포함, `require_secure_transport=0`, `time_zone=SYSTEM` |

- **MySQL DDL은 암묵 커밋입니다.** 파일 중간에서 실패하면 앞 문장은 남습니다. 트랜잭션으로 되돌려지지 않습니다.

### 4-3. 러너 `python -m flaskr.migrate {precheck|up|verify} --json` (장민영)

| 단계 | 하는 일 |
|---|---|
| `precheck` | 연결(클라우드는 CA 검증 TLS), `VERSION()`·`@@sql_mode`·`@@collation_server`·`@@time_zone`·`@@require_secure_transport`, `Ssl_version`, 대기 파일 목록, 대기 파일 lint(추가형만), 적용된 파일 checksum 드리프트. `mode=bootstrap`이면 DB가 비었는지 |
| `up` | `GET_LOCK('flaskr_migrate', 10)` → 드리프트 재확인 → 문장 분리(`;` + 줄끝) → **문장 단위 가드**(`information_schema.COLUMNS`·`TABLE_CONSTRAINTS`·`STATISTICS`로 이미 있으면 건너뜀) → 파일 끝에 `schema_migrations` 기록 → `RELEASE_LOCK` |
| `verify` | 기대 버전 = 최대 버전, 스키마 서명(정렬한 `information_schema` sha256), DB 지문(VERSION, sql_mode, collation, time_zone, Ssl_version) |
| 출력 | 한 줄 `MIGRATE_RESULT {"phase":…, "ok":…, "current":"0002", "expected":"0002", "signature":"sha256:…", …}` + exit code |
| 실행 위치 | 온프렘 = was 호스트의 일회성 컨테이너(같은 was 이미지) / 클라우드 = ECS RunTask(migrate 태스크 정의, 같은 was digest). 클라우드는 CloudWatch 로그에서 결과 줄을 읽음 |

- 파이프라인은 `init-db`를 절대 부르지 않습니다(명령 자체 삭제).
- 💭 대안: 앱 시작 때 `GET_LOCK`을 잡고 마이그레이션(일회성 태스크 25~45초 절약 [추정]). 계획에 step으로 안 보이는 단점이 있어 권장은 명시적 step입니다.

- **개발값 표시** 💭: 개발값은 저장소에 있는 개발용 더미라 그대로 보여줍니다(`SECRET_KEY=dev`가 바뀌는 장면이 요점). 배포 값은 가립니다.
- **개발값 유출 검사** 💭(V21, [02](02_파이프라인과-계획.md)): 대상 값이 개발값과 같거나(`dev`, `sqlite:`, 클라우드의 `localhost`) 두 환경 SECRET_KEY 참조가 같으면 배포 전에 멈추고 보고합니다.
- **`DATABASE_URL`과 RDS 비밀번호**: RDS가 생성하는 비밀번호는 문장부호가 들어가 URL을 깨뜨립니다. ECS는 시크릿 JSON 키로 URL을 조립할 수 없습니다. 장부 문구(`DATABASE_URL`)를 지키려면 💭 **DB 초기화 step(코드)이 앱 계정 비밀번호를 난수로 만들고 URL 인코딩한 완성 URL을 시크릿 값으로 씁니다**(값은 즉시 버림). AI Terraform이 비밀번호를 만들면 상태 파일에 평문으로 남으므로 쓰지 않습니다(대안: 앱이 `DB_*` 개별 변수로 조립, N17).
- 클라우드 DB 계정: **앱 전용 계정, 최소 권한**(✅ 장부 23: DML만, `REQUIRE SSL`). 💭 장부 35: 마이그레이션 계정(DDL, `ddak/flaskr/DATABASE_URL_MIGRATOR`)을 분리하고 비밀번호는 Secrets Manager, RDS IAM 인증은 P2. 💭 교체 안 되는 시크릿(D17). RDS 관리형 마스터 시크릿은 기본 7일마다 교체되므로 마스터는 DB 초기화 step에서만 씁니다.
- 왜 SECRET_KEY 시크릿을 코드가 아니라 AI Terraform이 만드나(✅ 장부 32): Terraform이 시크릿의 존재를 알아야 드리프트·정리·재현이 되고, 실행 역할 권한 변경도 같은 plan에서 사람이 승인하기 때문입니다. 값만 코드가 씁니다(대안 write-only `secret_string_wo`는 Terraform·provider 버전 확인 뒤, N41).
- 온프렘 SECRET_KEY 생성 주체(실행기 vs 대상 호스트 안 헬퍼 컨테이너)는 남은 결정입니다. `.env`/컨테이너 env는 `docker inspect`로 보입니다(한계로 명시).

- ECS `secrets`는 컨테이너 시작 때만 주입됩니다. 시크릿을 새로 만들면 새 태스크 정의·배포가 필요합니다(계획 검증 V6 결합의 근거).

## 7. 실행 타임라인 (병렬 + 대기 지점, 초는 전부 [추정])

### 7-1. 그림

```
[배포] 클릭 전(승인 전, 약 28~145초)
  의도·분석·step 선택·계획 검증 ─→ generate_infra(앱 층 수정안) → validate_infra → plan_infra ─→ [IAM·인프라 승인] [배포]

t(초, [배포] 클릭 기준)   0              40~85                  52~110          64~170                         129~297  130~300
빌드(공통)   [잠금][CodeBuild: 프로비저닝 → was 빌드 → Docker Hub push]──▶ G0 images_ready
local 트랙                                   [config(.env 난수) → db 0002 → was 교체 → health → smoke]──▶ G1 local_verified
cloud 트랙   [TLS 확인]··············대기(G1)··············[인프라 apply(시크릿 1 + 정책 1) → PutSecretValue → 태스크 정의 등록]
                                                                     → [db 0002 RunTask → ECS 롤링 → health·TLS·smoke]──▶ cloud_verified
공통                                                                                                           [compare → report]
```

- 두 트랙은 빌드와 **동시에** 시작합니다. 이미지가 필요한 step만 G0를 기다립니다([장부 1·6]).
- 클라우드의 상태 변경 step(인프라 apply의 실행 역할 정책 변경, DB 마이그레이션, 서비스 전환)은 G1(`local_verified`) 뒤입니다([장부 6] 예시, V23). 💭 N39.
- v2는 시크릿 컨테이너가 인프라 apply로 생기므로 시크릿 값 쓰기와 태스크 정의 등록(시크릿 ARN 필요)도 인프라 apply 뒤로 밀립니다. 그래서 G1 전에 클라우드가 하는 일은 TLS 확인(읽기)뿐입니다.
- 💭 G1 전 허용(W2)의 다른 쓰임: 인프라 step이 없는 개선 배포에서는 추가형 준비(없을 때만 시크릿 값 쓰기, 태스크 정의 새 리비전 등록 — 서비스는 전환 안 함)를 G1 전에 합니다. 더 엄격한 안은 "모든 쓰기를 G1 뒤로"이고 차이는 1~4초입니다. 팀 결정.
- 💭 N39 대안: AI Terraform 규칙으로 권한을 시크릿별 **새** 정책 리소스로 추가해 plan을 create만으로 만들면(→ `additive_prep`) 인프라 apply·값 쓰기·태스크 정의 등록을 G1 전에 빌드와 겹쳐 돌릴 수 있습니다(약 12~60초 절약 [추정]). 사용자 문구 "IAM 정책 1 변경"과 달라지므로 리허설 실측을 보고 정합니다.
- 태스크 정의 등록은 이미지 digest가 필요하므로 G0 뒤입니다 [판단].
- 로컬이 실패하면 G1이 fail → 클라우드는 대기 지점에서 멈춥니다(`ABORTED_AT_GATE`). v2에서는 인프라 apply도 G1 뒤라 실행되지 않습니다(승인된 plan은 다음 run에서 stale이면 다시 plan·승인).

- 남은 수단: 설계 설명 시작 때 트리거(D15, 운영진 확인 필요), 리허설에서 승인된 AI Terraform 수정안을 캐시로 재사용(`source=cache` 라벨, 20~110초 중 생성 시간 절약), 앱 층 state를 작게(장부 32), 인프라 step을 G1 전으로(N39: create만으로 만들 때), 승인 버튼 1개(N40), ALB·ECS 값 조정(이미 가정), 최신 CodeBuild 기본 이미지, 앱 시작 때 마이그레이션(4-3 대안).
- 병렬로 버는 시간은 작습니다. 클라우드 시간 대부분이 G1 뒤에 있습니다. 줄이려면 트래픽 없이 새 태스크를 미리 띄우는 블루/그린이 필요하고, 이는 나중 옵션입니다.
- 실행기는 ECS `COMPLETED`를 기다리지 않습니다. "새 대상 healthy + `/version` release_id 일치"로 넘어갑니다(드레이닝 기본 300초).
- 발표에서는 **실측 p50/p95만** 말합니다.

- 왜 이 장면인가: 앱 변경(로그인)이 인프라 변경(시크릿·권한)을 부르는 가장 작은 실제 예이고, "AI 제안 → 검증 → 사람 승인 → 코드 실행"(장부 4-b)과 "비밀값은 누구도 보지 않음"(장부 4-a)을 한 번에 보여 줍니다. 차별점 설명(환경 차이 흡수·교차 검증)의 한 부분이지 중심은 아닙니다.
- 💭 N39 대안(G1 전): 권한을 시크릿별 새 정책 리소스로 만들어 plan을 create만으로 하면 7~9를 빌드와 겹쳐 약 12초(하한) 이상 줄입니다. 화면 문구는 "+ 시크릿 1, + IAM 정책 1, 삭제 0"으로 바뀝니다.
- 💭 N40 대안(버튼 1개): 계획 카드에 plan 요약·IAM diff를 보이고 [배포] 한 번으로 plan sha256·`plan_hash`를 같이 승인합니다(사용자 문구 "사람 '배포' 승인"에 가까움). IAM 승인이 배포 클릭에 묻히지 않게 IAM diff를 카드 맨 위에 둡니다.
- AI Terraform 생성이 실패·지연하면 리허설에서 승인된 같은 입력 해시의 수정안을 캐시로 씁니다(`source=cache` 라벨, 정적 게이트·plan·승인은 매번 다시).

**💭 초기 배포(부트스트랩) 녹화**

- 결선 5분 중 설계 설명(약 2분) 때 녹화를 보여 줍니다: 새 계정 → 기반 준비(고정 템플릿, [기반 승인]) → (넣는다면 💭) Dockerfile 없는 사본의 AI Dockerfile 초안 → 검사·검증 빌드 → [Dockerfile 승인] → AI HCL 초안 → 정적 게이트·Checkov 결과 → plan 요약(전부 create) → IAM diff(경계 부착 확인) → [IAM·인프라 승인] → apply 진행 → 환경 정보 기록 → 두 환경 v1. 인프라 생성만 10~20분이 걸리므로 라이브로 하지 않습니다. 녹화는 녹화라고 밝힙니다(킥오프 요구). Dockerfile 장면을 녹화에 넣을지는 팀 결정(N36).

**비상 대응**

| 상황 | 대응 |
|---|---|
| 클라우드가 늦음 | manifest·롤백 규칙·설정 변환 표·시크릿 장면 세부 표를 설명하며 시간을 씀 |
| AI 호출 실패·지연 | 규칙 계획으로 진행("규칙 대체" 배지). replay면 "저장된 응답" 라벨 |
| AI Terraform 수정안 실패·지연 | 리허설에서 승인된 같은 입력 해시의 수정안을 캐시로(`source=cache` 라벨). 검사·plan·승인은 그대로. 캐시도 없으면 사람에게 넘기고 그렇다고 말함(사람이 HCL을 대신 쓰지 않음) |
| 새 태스크가 새 시크릿을 못 읽음(IAM 전파) | 규칙 시그니처 `ResourceInitializationError` → 클라우드만 롤백 + 원인 설명 화면. 리허설에서 전파 대기 시간을 실측해 재시도 규칙에 반영 💭 |
| Docker Hub pull 실패·한도 | `CannotPullContainerError` 원인 설명. 데모 전 `preflight_check`로 로그인·한도 확인, 막히면 ECR 어댑터로 전환(N37) |
| 배포 실패 | 자동 롤백 화면을 그대로 보여주고 정직하게 설명 |
| 실패 → 원인 설명 장면이 필요 | 사전 녹화나 직전 run 결과로 보여주고 그렇다고 말함 |

**목업 고지 대상:** 컨테이너 온프렘(11절 문구), replay 응답, 이전 run 화면, 녹화(부트스트랩 포함), 캐시된 AI Terraform·Dockerfile 생성물을 재사용했다면 `source=cache` 라벨, Slack 알림을 켰다면 그것이 창구일 뿐이라는 점(💭 장부 30).
