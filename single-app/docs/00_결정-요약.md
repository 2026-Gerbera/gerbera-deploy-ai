**주의: 주제 문구의 "AI가 고친다"와 장부 16의 관계 [판단]**
- 장부 16으로 코드 패치 토글은 기본 OFF, AI 패치는 나중입니다.
- 그래서 지금 범위에서 "환경 차이를 고친다"는 다음 뜻입니다. AI가 어떤 키가 환경마다 달라야 하는지 분류하고(장부 13), 코드가 대상 값으로 바꾸고, 실패하면 AI가 원인을 설명합니다.
- 발표 문구가 "AI가 코드를 고친다"로 들리지 않게 맞춰야 합니다. 문구 결정은 팀 몫입니다.

**주의: "딸깍"과 사람 승인의 관계 [판단]**
- 장부 23으로 IAM은 사람이 승인해야 만들어집니다. 그래서 초기 배포(플랫폼 생성)에는 사람 승인이 더 들어갑니다: 💭 [기반 승인](상태 버킷·경계, 계정당 한 번, N27)과 [IAM·인프라 승인].
- 개선 배포는 인프라 요구가 바뀔 때만 인프라 step이 있습니다(장부 27). 라이브 데모 v2는 새 SECRET_KEY 때문에 앱 층에 시크릿 1개 + 실행 역할 읽기 권한 변경이 생겨 인프라 step과 승인이 들어갑니다(✅ 장부 32). 승인 버튼을 [IAM·인프라 승인] + [배포] 둘로 둘지, 계획 카드의 [배포] 하나로 plan sha256까지 묶을지는 💭 결정 필요(N40, 사용자 문구는 "배포 승인"). 인프라 변경이 없는 개선 배포는 [배포] 하나입니다.
- Dockerfile이 없는 앱의 초기 배포에는 [Dockerfile 승인](💭)이 하나 더 들어갑니다(장부 26). 승인된 Dockerfile은 저장·재사용하므로 다음 run부터는 없습니다.
- 발표에서는 "사람은 Terraform을 쓰지 않는다. 사람은 AI가 짠 인프라의 plan 요약과 IAM diff를 보고 승인만 한다"로 설명합니다. 문구 결정은 팀 몫입니다.
- 같은 기수(Term1) Team Daisy가 "AI Terraform 생성 → 검증 → 승인"을 공개했습니다. AI Terraform은 수단이고, 발표의 중심은 환경 차이 흡수와 교차 검증입니다. 차별점은 권한 경계 + 사람 승인 + 정책 검사입니다(💭, [06 §13](06_보안-신뢰경계.md#13-심사위원-예상-보안-질문과-답)).

## 5. 확인 필요 (요약)

- RDS MySQL 8.4 서울 마이너 목록, 기본 `sql_mode`·`character_set_server`. 유상준.
- CodeBuild 프로비저닝·Fargate 기동·일회성 태스크 소요, ECS 배포 3회 이상 실측. 유상준·안승환.
- CodeBuild ARM의 서울 지원. 안승환.
- ECS circuit breaker `thresholdConfiguration type=COUNT`의 boto3·Terraform 지원. 안승환.
- 원격 도커 데몬(`ssh://`)으로 Docker Hub pull할 때 읽기 전용 토큰 로그인 위치(각 tier 호스트의 `docker login` vs SDK `auth_config`), 소켓 프록시에서 pull. 정준우.
- Jev 실제 추론 지연(키로 측정). 김준석.
- API 키·Bedrock 사용료 환급 여부, 현장 외부 LLM 호출 허용. 운영진 질문.
- 새 계정 할당량(Fargate On-Demand vCPU 기본 6이고 새 계정은 더 낮을 수 있음, CodeBuild 동시 빌드 컴퓨트 타입별 1)과 계정 플랜(Free/Paid). 유상준, 9/30 밤.
- AI Terraform 생성 성공률 실측(연구 수치: IaC-Eval GPT-4 pass@1 19.36%, 반복 수정 시 GPT-4o 84.4% — 프리프린트). 수정 루프 3회 안 성공률을 10/1 정오까지 기록. 유상준.
- Terraform이 역할을 만들고 지울 때 실제로 부르는 IAM 읽기·보조 액션(파이프라인 역할 정책 확정용, 테스트 계정 CloudTrail). 유상준.
- 권한 경계 정책 초안([research/IAM 13절](../../research/2026-09-30_IAM-최소권한-설계.md))이 정상 apply를 막지 않는지(양성 스모크). 유상준·안승환.
- **사용자 확인:** 기반 준비의 권한 경계·파이프라인 역할(코드 고정 템플릿, AI가 설계하지 않는 IAM)과 코드가 만드는 상태 버킷이 장부 22·23("상태 버킷도 AI 범위", "IAM은 AI가 설계")과 맞는지. 사람 승인은 똑같이 거침(N27). 💭 우리 권고는 장부 34(고정 틀 = 제품 코드라 "딸깍" 취지에 맞음). 정준우.
- ~~RDS IAM DB 인증 해석~~ → 💭 장부 35로 정리: MySQL 계정(앱 DML / 마이그레이션 DDL) + 비밀번호는 Secrets Manager, RDS IAM 인증은 P2. 사용자 확인만 남음. 정준우.
- 이름 통일(장부 36 권고, N44)을 **기반 준비 전에** 확정. 앱 경계의 리소스 패턴은 만든 뒤 못 고치므로(Deny) 실제 이름과 다르면 정상 태스크 시작이 거부됨. 문서는 `ddak/<앱>/<KEY>`로 맞췄고 역할 경로는 `/ddak/app/` 유지안(N44). 유상준.
- **사용자 확인:** 데모 시크릿 장면의 승인 버튼 수(N40). 장부 32는 "사람 '배포' 승인"이고, 이전 문서는 IAM 승인을 [배포]와 따로 받는 안이었음. 정준우.
