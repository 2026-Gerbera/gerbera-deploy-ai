## 맥락

- 계획 카탈로그(`core/contracts/step_catalog.py` `_env_steps`)는 `deploy.<tier>.<env>`를 deploy.yaml `tiers` 순서대로 만들었다. 데모 앱(2026-Gerbera/gerbera-application) deploy.yaml은 `web, was` 순서라서 계획도 web → was였다.
- 10/3 데스크탑 WSL 온프렘 풀체인의 첫 실패는 web 준비 확인에서 났다. nginx 기본 ready 경로 `/health/ready`가 WAS로 프록시되는데, 새 WAS를 배포하기 전이라 옛 WAS(첫 배포에서는 아직 없는 WAS)를 확인했다. 인벤토리의 web ready path를 `/nginx-health`로 바꿔 우회했고, 그 뒤 v1 첫 배포(run-20261002-175023-84a6)와 v2 PR merge 자동 감지(run-20261002-180550-2d12, WAS만 재빌드)가 성공했다.
- 설계 문서는 이미 was → web 순서다. `single-app/docs/02_파이프라인과-계획.md` 806행, `single-app/docs/03_골든패스-시나리오.md` 509행, `single-app/dev-docs/00_공통-개요.md` 16-c("최초 배포 db→was→web"), `single-app/dev-docs/01_공통-계약.md` 404행. 10/2 실 VM 검증 스크립트 `harness/scripts/o1_onprem.py`의 `deployment_plan`도 db → migrate → was → web 순서로 실측했다. 제품 카탈로그만 deploy.yaml 순서를 따라 설계와 어긋나 있었다.

## 필요성 판단: 필요하다

| 관점 | web 먼저(기존) | WAS 먼저(이번) |
|---|---|---|
| 호환성 | 새 web이 옛 WAS를 부르는 구간이 생긴다. 새 화면이 새 API에 기대면 깨진다. | web을 바꿀 때 새 WAS가 이미 준비돼 있다. 옛 web → 새 WAS 구간만 남는데, API를 추가만 하는 변경이면 유지하기 쉽다. |
| 준비 확인 | web `/health/ready`가 옛 WAS나 없는 WAS를 보고 실패한다(10/3 첫 실패). | web 준비 확인이 새 WAS까지 실제로 확인한다. `/nginx-health` 우회를 유지해도 되고 `/health/ready`로 되돌려도 통과한다. |
| 실패 시 영향 | WAS가 실패하면 web은 이미 바뀌어 있다. | WAS가 실패하면 web `deploy_tier`를 호출하지 않는다. 사용자 접점(web)은 그대로다. |
| 롤백 범위 | WAS가 실패해도 web과 was를 모두 되돌린다. | WAS가 실패하면 was만 되돌린다. web이 실패하면 web → was 순서로 되돌린다. |

## 다른 규칙과의 관계

- **실행기 신호**: 모든 `deploy_tier`는 `wait_for=images_ready` 하나만 기다린다. 이 신호는 빌드 섹션 신호라 tier 순서와 무관하다. 한 트랙 안의 step은 계획 순서대로 차례로 실행된다(`executor/engine.py` `_track`). `check_signals`에는 영향이 없다.
- **롤백 순서**: `executor/service.py`의 `rollback()`은 실제로 호출한 tier 목록을 역순(`reversed`)으로 되돌린다. 그래서 순서를 바꾸면 롤백은 자동으로 web → was가 된다. 실행기 코드는 바꾸지 않았다. `prepare_db`는 기존처럼 롤백 tier `was`로 묶인다(DB 역마이그레이션은 없다).
- **이월 tier**: `executor/images.py` `carried_images`는 tier 집합만 보며 순서와 무관하다. v2(WAS만 빌드)에서 web은 `digest_deployed`로 빠지므로 deploy.was만 실행된다. 공용 새 env 키가 있어 web도 다시 배포하면 순서는 was → web이고, web은 이전 성공 digest를 이월한다.
- **계획 검증(plan/validate, 준석 소유)**: tier끼리의 순서 검사는 없다. 조립 순서는 카탈로그를 그대로 따른다. R-migration은 migrate가 모든 `deploy_tier`보다 앞서야 한다는 규칙이다. 카탈로그에서 migrate가 tier 배포보다 앞이라 그대로 통과한다. **plan/validate 코드는 바꾸지 않았다.**
- **AI 계획(Jev·Claude)**: AI는 OPTIONAL step을 넣을지만 고르고 순서는 정하지 않는다. `deploy_tier`는 CONDITIONAL이라 AI가 결정하는 대상이 아니다.
- **클라우드**: 카탈로그는 두 환경이 함께 쓰므로 `deploy.was.cloud` → `deploy.web.cloud` 순서도 바뀐다. ECS는 web·was가 한 태스크에 있어서, 첫 deploy step이 이번 run의 이미지를 한 리비전으로 한꺼번에 전환한다(`cloud/deploy/entry.py`). 그래서 달라지는 것은 어느 step이 전환하는지(이제 `deploy.was.cloud`)뿐이다. 실 AWS 검증은 하지 않았다.
- **빌드 순서**: `build.<tier>`는 deploy.yaml 순서를 유지한다. 빌드는 모두 images_ready 하나로 모이므로 서로 의존하지 않는다.
- **승인 해시**: `plan_hash`가 step 순서를 포함한다. 바꾸기 전에 만든 승인 대기 계획은 만들어진 순서대로 실행되고, 새 계획부터 이번 순서가 적용된다.

## 결정

- `step_catalog._env_steps`가 만드는 `deploy.<tier>.<env>`는 고정 의존 순서 **db → was → web**을 따른다. 그 밖의 tier는 deploy.yaml 순서대로 뒤에 둔다.
- 공유 계약 파일을 바꿨다. 툴 이름·파라미터·스키마·step id·layer·target·skip_rule·deploy.yaml 키는 바꾸지 않았다. `make -C harness contracts-update`를 실행했고 JSON 스키마 변경은 없었다.

## 범위 밖과 남은 것

- **3계층 DB**: `deploy.db.<env>`는 아직 dbinit/migrate 뒤에 있다(카탈로그의 공통 블록 순서). DB 컨테이너는 migrate보다 먼저 떠 있어야 하므로 3계층 자동 계획은 아직 순서가 틀리다. db를 앞으로 옮기려면 R-migration(`plan/validate/rules.py` `check_migrations`)이 db tier를 예외로 두도록 같이 고쳐야 한다. 10/3 O2 남은 요청 "DB tier 자동 계획 순서"와 같은 건이다. 데모 앱 tiers는 web, was라 이번 데모에는 영향이 없다.
- **인벤토리 web ready path**: 데모 직전이라 `/nginx-health` 우회를 유지한다. WAS 먼저로 v1·v2 리허설을 통과한 뒤 `/health/ready`로 되돌릴지 정한다. 인벤토리는 이 변경에 포함하지 않았다.
- **클라우드**: 실 AWS에서 was → web 순서를 확인하는 일은 사용자 지시를 기다린다.

## 준석님 확인 필요

- plan/validate·planner 코드는 바꾸지 않았다. 카탈로그 순서가 바뀌어서 조립된 계획의 deploy 섹션이 was → web이 된다. 골든(`fixtures/plans/golden_v2_update.json`) 비교는 집합 비교라 영향이 없다.
- DB tier 자동 계획 순서(db → dbinit/migrate → was → web)는 R-migration 예외와 함께 정해야 한다.
