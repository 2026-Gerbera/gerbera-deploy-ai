# O1 착수 기준: 승인·스냅샷·이미지·로컬 환경

> 9/30 구현 착수 갱신: 사용자가 O1 실행 계획을 승인했다. 교차 검증 실패는 클라우드만
> 롤백하고 로컬 v2를 유지한다. 기존 FastAPI 골격과 프레임워크 독립 코어를 유지한다.
> SQLite·승인·실행기·온프렘 구현의 현행 연결 방법은 [O1 가이드](../guides/O1.md)를 따른다.

- 상태: 최신 사용자 결정 반영 + 사용자 위임에 따른 O1 우선 기준. 다른 역할과 연결되는 필드·반환 형식은 팀 통합 전 합의한다.
- 적용: 저장소 최상위의 `harness/` 디렉토리. 구형 MCP 하네스는 삭제했고 최신 하네스만 이 폴더에 둔다.
- 우선순위: 최신 사용자 결정 → 이 문서와 `docs/contracts/` → 역할 가이드 → 코드. 이전 결정 장부의 상충하는 문구는 현재 기준이 아니다.

## 확정된 제품 방향

단일 파이썬 앱과 함수 레지스트리를 사용한다. AWS와 온프렘은 CD 공통 인터페이스 뒤의 provider로 나눈다. AI 코드 수정은 P0이며 데모에서는 ON이다. 일반 실행의 토글 기본 OFF는 유지한다. 지원 패턴은 로그인 시나리오의 하드코딩 설정 2~3종이며 임의 버그 수정으로 확장하지 않는다.

환경별 이미지를 따로 만들지 않는다. tier별 공통 이미지 index에 `linux/amd64`와 `linux/arm64`를 포함한다. 서로 다른 플랫폼의 이미지 바이트가 같다는 뜻은 아니다. MySQL·Docker Hub 기준을 유지한다.

관리 웹 프레임워크는 FastAPI/Django 중 미정이다. 현재 FastAPI 골격과 설치 의존성은 최종 선택이 아니다. 실행기·계약은 프레임워크와 분리한다. 데모는 프로젝트 등록, 연결 설정, v1 배포가 완료된 관리 페이지에서 시작한다. 초기 설정 과정은 라이브 데모에 넣지 않는다.

## 승인: 한 화면·한 번 클릭

사용자가 선택한 방식은 코드 diff·배포 계획·인프라 plan/IAM 변경을 한 화면에서 확인하고 한 번 승인하는 것이다. `approval_id` 하나로 묶되 `patch`, `deploy`, `infra`, 필요한 경우 `dockerfile`·`foundation` 기록을 따로 남긴다. 항목을 숨긴 포괄 승인은 하지 않는다.

- 각 기록은 프로젝트·run·종류·대상 해시·승인자·시각·결과를 가진다. O1 저장·실행 API는 구현했고 승인 UI 연결은 C3 통합 대상이다.
- 패치는 원본 스냅샷 해시, diff 해시, 수정본 스냅샷 해시에 묶는다. 승인 전 임시 검사 사본에서 수정본의 예상 해시를 계산하고, 승인 후 빌드용 사본이 그 해시와 같은지 다시 확인한다. 승인 전 S3 업로드·빌드는 하지 않는다.
- 이전 패치는 프로젝트와 세 해시가 모두 같고 이전 기록이 승인인 경우에만 재사용한다. run이 달라도 가능하지만 다른 소스·diff·결과에는 승계하지 않는다. 화면에 재사용 사실을 표시한다.
- 배포·인프라 승인은 이전 run에서 자동 재사용하지 않는다. 어느 대상이든 내용이 바뀌면 그 대상에 대한 새 승인이 필요하다.
- 계약 모델은 데이터 검증용이다. 모델을 만들었다는 사실만으로 사람이 승인했거나 실행 권한이 생기지 않는다. 저장소·승인 API가 기록의 출처를 보장해야 한다.

## 스냅샷과 환경별 상태

변경 탐지는 커밋 유무와 무관하게 원본 소스의 파일별 내용 해시를 사용한다. 대상 환경의 마지막 성공 배포에 기록된 **원본 소스 해시 목록**과 현재 원본을 비교한다. AI 적용본을 원본과 비교해 매번 변경으로 판단하지 않는다.

`SnapshotBinding`은 원본·수정본 해시와 선택적 패치 해시를 보관한다. 패치가 없으면 원본과 수정본 해시가 같아야 한다. 원본 파일별 해시 목록·zip 생성과 제외 목록은 O2 구현 계약으로 별도 맞춘다. S3에는 승인 후 수정본만 올린다.

O1 상태 저장은 SQLite와 표준 `sqlite3`를 사용한다. 웹 프레임워크 ORM에 실행기를 결합하지 않는다. `runs`, `steps`, `approvals`, `env_release`, `locks`, `releases`를 구현했다. UI 프로젝트 설정 저장은 C3와 합의한다.

환경별 성공 기록은 독립적이다. 온프렘 성공·클라우드 실패이면 온프렘만 새 기준으로 갱신한다. 실패 환경의 마지막 성공 기록은 유지한다. DB 마이그레이션 자동 역변환은 하지 않는다.

## 이미지 계약

`ImageArtifact`는 digest로 고정한 이미지 참조, index digest, 두 플랫폼의 하위 digest를 가진다. 참조의 digest는 index와 같아야 한다. `ImageObservation`은 대상 환경에서 관측한 플랫폼과 그 플랫폼의 실제 digest를 가진다.

`ReleaseArtifacts`의 관측값은 같은 tier의 index에 포함된 해당 플랫폼 digest와 일치해야 한다. 요청한 index 참조가 같다는 것만으로 실제 실행 이미지 일치를 판정하지 않는다. ECS 응답이 index인지 하위 manifest인지 확인·정규화하는 책임은 C2/C3에 있다.

관측값이 없는 빌드 산출물도 계약상 표현할 수 있다. 관측이 없으면 미검증이며 배포 성공이 아니다. 실제 완료 판정에는 양쪽 이미지 관측과 독립 기능 검증이 필요하다. 전체 릴리스 이력 모델을 대신하는 계약은 아니다.

`RunContext.release_artifacts`는 선택 필드로 추가해 기존 실행기 예시와 호환한다. 기존 `images`와 같은 tier를 함께 제공하면 참조가 일치해야 한다. O1 실행기는 빌드 산출물 갱신·해시 재검증을 구현했다. 인프라 apply 후 새 컨텍스트를 반환하는 `refresh`는 C1이 연결하며, 연결이 없으면 apply 전에 차단한다.

## O1부터 시작할 범위

- 기존 `Plan`, 신호 4개, 진행 이벤트, CD 함수 이름은 유지한다. O2/C2/C3가 읽는 입출력 변경은 팀 통합 계약으로 검토한다.
- 로컬 검증을 통과하기 전 클라우드 `state_change`는 금지한다. 실패 환경의 앱만 이전 digest로 되돌리고, 반대 환경은 유지한다.
- 온프렘 런타임 첫 검증은 컨테이너 모드로 한다. tier별 서버 배포 설계를 폐기하는 결정은 아니다.
- 실행기 잠금은 단일 제어 프로세스/SQLite 기준이다. 여러 노트북을 아우르는 분산 잠금으로 주장하지 않는다.
- 로컬 시크릿은 우선 대상 호스트의 env 파일에 보관하고, 기존 값은 재사용한다. 새 값은 환경별로 생성한다. 비밀값은 컨텍스트·로그·승인 기록에 저장하지 않는다. 원격 호스트 생성/전달 상세는 온프렘 구현에서 검증한다.

## 개발환경과 남은 팀 연결

Git 저장소가 아닌 템플릿에서는 `make setup-local`로 의존성만 준비하고 `make ci`로 로컬 품질 검사를 실행한다. `make setup`과 `make check`의 Git 신원·훅 검사는 팀 저장소 도입 후 그대로 적용한다. 상위 저장소에 잘못 훅을 설치하지 않는다.

남은 팀 항목은 웹 프레임워크(C3), 실제 CD 결과와 마이그레이션 러너 반환(C2/O3), Terraform 출력 허용 목록과 기반 준비 방식(C1), 소스 파일 해시 목록·계획 조립(O2), GitHub ID/계약 승인자 지정이다. O1 우선 기준을 팀 전체의 승인 완료로 표시하지 않는다.
