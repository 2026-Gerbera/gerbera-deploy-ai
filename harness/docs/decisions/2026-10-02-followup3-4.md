# 10/2 후속 수정 3·4 — 승인 기반 첫 배포와 운영자 진단

기준: 정준우 후속3 결정과 온프렘 리허설 추가 요청. 후속3 우선 순서 0→0-2→1→2→3.
Git 기준 afc3031의 깨끗한 작업 트리에서 시작. 커밋·push·PR 및 실제 AWS 호출 없음.
Claude가 리허설 중인 데스크톱 WSL 클론·VM은 접근하지 않는다. 사용량 잔여 21% 이하에서 안전 지점 정리 후 PAUSED.

## 인프라 실행 경계

개발 에이전트가 실제 Terraform apply/destroy를 실행하는 것은 금지다. 제품은 **검증된 계획을 사람이 승인한 뒤 코드로 실행**한다.
초기 기반과 플랫폼을 사람이 터미널에서 적용하던 안은 폐기한다. 사전 준비는 AWS 자격증명·권한과 도메인 구매다.
LLM은 생성기 입력/제안 단계에만 있고, 검증·승인 대조·적용·state 이전에는 없다.

- 플랫폼 BOOTSTRAP binding의 validate는 대상 계정·버킷 존재를 읽고 backend를 확정한다. 403/계정 불일치는 부재로 처리하지 않는다.
- 버킷이 없으면 **실제 local backend 선언**으로 플랫폼 plan을 저장한다. infra 승인 대상은 saved-plan 바이트 해시·기반 템플릿 해시·backend 대상/이전 여부를 묶은 해시다.
- C-18 요약의 기존 iam_diff와 headline에 버킷·기반 템플릿 해시·앱/빌드 권한 경계 및 state 이전 여부를 표시한다. TLS 강제·암호화·버전 관리는 해시에 묶인 고정 기반 템플릿에 포함된다. 별도 승인 클릭이나 허위 승인 레코드는 만들지 않는다.
- apply_infra에서 동일 승인·잠금을 확인한 다음 SDK 기반 생성 → 저장된 플랫폼 plan 적용 → S3 state 이전 → 출력 확인 순으로 실행한다. 기존 기반은 소유 태그·정책 일치 시 재사용한다.
- state 이전은 Terraform과 동일한 S3 `.tflock`을 조건부 생성한 뒤 대상 key 부재를 검사한다. 그 잠금 아래 비대화형 이전을 수행하고 성공 때만 본인 ETag로 잠금 객체를 해제한다. state 원문은 읽거나 파싱하지 않는다.
- 부분 생성·apply·migration 실패는 NEEDS_HUMAN, 상태/marker/잠금을 보존하며 자동 재적용하지 않는다.
- 승인 전 app 조립에서 플랫폼 apply를 cloud 첫 단계로 이동하고 build에 infra_ready 의존을 넣는다. 따라서 CodeBuild/ALB/ACM이 생기기 전에 빌드/TLS 검사를 실행하지 않는다. 실행 중 wait_for를 무시하지 않는다.

**연결 한계:** generate_infra의 실제 번들/세션 binding은 준석 소유다. 없으면 기존 명시 오류로 중단한다.
생성기나 DNS 자동화 없이 전체 AWS 플랫폼/ACM 구축이 끝났다고 보고하지 않는다. `dns_mode=external`의 DNS API 연결은 별도 통합 필요.

## 앱 저장소·후보

- ddak.app이 승인 입력의 repo_url로 제품 전용 checkout을 만들고 prepare/실행/재시작에 동일 factory를 주입한다.
- 실제 origin fetch URL과 모든 push URL이 승인 화면의 repo_url과 정확히 같아야 한다. pushurl·다중 URL·Git URL 재작성 불일치는 거부한다. 기존 checkout의 origin을 자동 변경하지 않는다.
- app 조립은 공개 설정 목록의 repo_url/watch_branch/auto_detect/default_targets로 O2 Watcher를 구성하고 설정 변경을 반영한다. O2 watch.py 단독 기본 main→prod 정정 요청은 유지한다.
- 과거 ai-prod deploy.yaml의 CONFIG_INVALID는 prod 템플릿 경로로 대체해 승인 트리를 만든다. 기타 파일/안전 오류를 무시하지 않는다.
- 일반 제외 경로는 원래 대소문자 규칙을 유지한다. 비밀 이름과 .env 계열 경로만 대소문자를 접어 검사한다.
- 후보 merge 커밋의 트리는 승인 트리와 같아야 한다. 패치 OFF 시 이전 AI 패치는 빠진다(**정준우 확인 대기**).

## 후속4 결정 기록

`deployed/onprem`, `deployed/cloud`는 **실제로 배포된 상태**를 가리킨다. 비교 툴 오류인 FAILED_VERIFY에서는
배포를 롤백하지 않으므로 성공한 환경의 태그는 이동한다. main 승격은 보류한다. 이 항목은 기록만 정리하며 코드 정책은 변경하지 않는다.

## 후속4 구현과 제한

- annotated v* 태그는 O1 AppRepository가 peeled commit SHA를 우선해 고정한다. O2 fetch.py 자체는 그대로이며 peel 순서·TLS 오류 분류·ref 오류 진단을 담당자 요청으로 남겼다.
- app 준비 실패 기록에 생성된 plan.json, 당시 project_settings와 version, phase/code/detail/missing_tool을 보존한다. 등록 누락은 CONFIG_INVALID다. 실패 run 승인 조회는 PRECONDITION_FAILED로 거절한다.
- 소스 복사 실패/준비 실패/취소에서 이번 요청이 만든 소스 사본만 지운다. 취소된 to_thread가 뒤늦게 다시 파일을 만드는 것을 막기 위해 복사 완료 후 정리한다. 기존 소스와 승인·실행 기록은 보존한다.
- prepare_db(dbinit)와 prepare_db(migrations=[0001])는 둘 다 precheck/verify를 수행한다. precheck current==expected이면 up을 생략하여 같은 이미지를 연속 적용해도 up은 한 번만 실행한다. 기존 데이터가 있는 새 컨트롤러에서도 precheck가 이미 적용된 버전이면 DB를 재생성하지 않는다. precheck 실패/잘못된 결과는 up 이전에 중단한다.
- 이 보장은 규약을 지키는 승인된 마이그레이터 기준이다. 임의 앱 코드의 모든 SQL을 검사하거나 실제 MySQL DB를 검증한 것은 아니다. O2의 db_initialized 성공 이력 기반 판단은 실제 DB/버전 확인과 조합하도록 요청했다.

**NEEDS_CONTEXT — 혼합 초기 상태:** 선택한 단일 환경의 기록으로 BOOTSTRAP/UPDATE를 판정한다. 온프렘 성공 뒤 cloud만 선택하면 첫 cloud도 BOOTSTRAP이 된다. both인데 한 환경만 기존 상태인 경우 현재 전역 RunMode로 둘을 다르게 표현할 수 없다. 임의로 기존 환경을 BOOTSTRAP하지 않고 ‘미배포 대상만 선택’ 오류로 안내한다. 두 환경의 서로 다른 모드를 한 run에 표현할지는 O2와 공유 계약 합의 후 진행한다. 다른 작업은 완료했다.
