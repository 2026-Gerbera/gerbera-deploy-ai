# 10/3 수정 8 — 온프렘 로컬 실행 구성

정준우의 수정8 대체본과 추가 1b·2·3, 후속 Store 시그니처 결정을 따른다. 폐기된 최초 수정8(Groq 제거·analyze Claude fallback)은 구현하지 않았다. 커밋·push·PR은 하지 않는다.

- AI 역할과 빌드 backend는 설정이 선택한다. Groq 키는 DDAK_GROQ_*로 분리, TypeSafe DDAK_JEV_API_KEY는 외부 전송하지 않는다. 판단은 groq/claude-cli, 생성은 기존 cli/api/replay다. Claude 기본 Sonnet 5.5/low, 선택 medium. --effort와 --model은 CLI 도움말에서 확인했고 실제 호출은 하지 않았다.
- CodeBuild 기본 유지, local은 온프렘 리허설·개발용. 같은 패키지 buildspec의 phase를 실행한다. 로컬에서 login/QEMU설치/builder생성/bootstrap 명령을 생략하고 사전 준비된 builder를 검사한다. 고정 /tmp 메타데이터 경로만 run 임시 경로로 바꾸며 소스 SHA·cache·라벨·digest 형식은 같다.
- RunContext에 선택 필드 build_backend/image_repository/preparation_failures/source_checks를 추가했다. 승인 컨텍스트 해시에 묶으며 refresh에서 식별자 변경을 거부한다. EnvKey.provider/model 출처 선택 필드와 분석/계획 스키마 3개를 contracts-update로 갱신했다.
- 준비가 끝난 자동 run만 supersede_awaiting을 마지막 호출한다. 같은 project/ref의 다른 source_sha 자동 AWAITING_APPROVAL을 SUPERSEDED로 닫는다. manual/tag 보존은 사용자가 확인한 최신 Store 계약이다. SUPERSEDED의 approve/acquire는 명시 거부한다.
- 컨트롤러 lease를 먼저 확보한 뒤 재시작 복구한다. 고아 lock은 삭제하고 RUNNING은 선택한 환경만 NEEDS_HUMAN 차단으로 기록한다. 정상 종료 lock 해제, 만료 terminal lock 재획득, 실행 중 수동 unlock 거부를 유지한다.
- unlock은 DB RUNNING과 살아 있는 service task를 거부한다. lock 삭제 및 감사/차단 면제만 기록한다. run/env NEEDS_HUMAN과 current/previous/release는 보존하며 recovery_verified=false다. 차단 여부는 blocked_targets로 읽는다. 이후 실패는 다시 차단한다.
- source preflight는 승인 전에 prod 트리/비밀값을 검사한다. 원본 .gitleaksignore의 정확한 fingerprint만 허용하며 wildcard는 거부한다. 승인 패치/원본과 달라진 후보 파일은 예외 없이 재검사한다. 구현은 변경된 파일 전체를 엄격 검사하므로 줄 단위 정책보다 보수적이다. 예외 요약에는 개수·규칙·경로만 넣는다.
- `/ops`와 새 템플릿에 설정·재계획·잠금 해제·대체됨·승인 메타를 모았다. 기존 C3 라우트/템플릿은 수정하지 않았다. 설정 변경은 조립부 watcher supervisor가 감지한다. sync_env_to_cloud 구현은 따로 만들지 않았다.
- O1↔O2 연결분은 `.worktrees/o1-o2-link`에 먼저 분리했다. 이 트리의 같은 변경은 추후 main 반영분을 기준으로 중복을 정리한다.

미확정은 [인계서](../guides/O1-exec-fix8-handoff-2026-10-03.md), 사람 실행은 [런북](../guides/onprem-fullchain-runbook.md)을 따른다. 실제 온프렘 성공과 3분 데모는 아직 실측하지 않았다.

## 추가 5 — cloud 브랜치 합치기 전 O1 보완

- both 요청의 인프라 준비 DdakToolError는 cloud에 격리한다. 미등록 여부와 무관하며 RunContext.preparation_errors(phase/code/detail) 선택 필드로 원인을 보존하고 승인 컨텍스트 해시에 묶는다. 실행은 cloud 준비 실패를 기록하고 local은 계속한다. cloud 단독이면 요청 준비를 실패시킨다.
- DeployRequest.target 비교를 local로 수정했다. 온프렘 단독·이전 cloud 출력 없음이면 가짜 cloud platform을 만들지 않는다.
- enqueue_deployment는 HTTP 수명 밖 준비 task를 만든다. 같은 project·ref·대상의 준비 또는 AWAITING_APPROVAL만 재사용한다. 다른 ref/대상이나 자동 준비 중 수동 요청은 LOCK_HELD로 명시 거절한다. 자동 준비끼리는 프로젝트별 비동기 잠금에서 기다려 감시 재시도 횟수를 소비하지 않는다. 기존 request_deployment는 비동기 완료까지 기다리는 내부 API로 유지한다. get_preparation/list_preparations로 상태를 공개한다. task 종료/취소는 서비스 shutdown이 회수한다. 준비 중 메모리 요청 표는 재시작 이후 유지되지 않으므로 완료 전 종료됐다면 운영자가 재요청한다. 이미 만들어진 run 기록은 Store에 보존된다.
- /ops/plan은 JSON 202 또는 목록 redirect, /ops/preparations/{request_id}는 진행 조회다. 기존 C3 웹 파일은 수정하지 않았다.
- generate_infra 직접 호출은 tool_context로 감싸 AI 관문이 동작하게 했다. contracts-update는 실행했고 기존 JSON 스키마 3개 외 추가 변경은 없다(RunContext는 dataclass 컨텍스트다).

## 추가6 — Docker 로그인 메타데이터는 경고

정준우 위임의 추가6에 따라 Username 누락·중복·이미지 namespace 불일치를 차단하지 않는다. preflight는 비밀값 없는 문자열 경고 목록을 반환하며 RunContext.preparation_warnings 선택 필드(기본 빈 목록)에 저장한다. 경고는 승인 컨텍스트 해시에 묶고 approval_view 및 ops 승인 화면에 노출한다. 기존 None 반환 preflight 주입도 빈 경고로 호환한다. buildx/QEMU 검사·실제 push 실패 판정은 그대로 유지한다.

빌드 인증·권한 오류에는 상수 `docker login 필요` 안내를 더하며 원문 stderr는 저장·출력하지 않는다. 제품 subprocess 메모리에서 인증 패턴만 검사한다. 계정과 조직 namespace가 다를 수 있으므로 불일치는 경고일 뿐이다. `contracts-update`를 실행한다(RunContext는 dataclass이므로 별도 JSON 스키마 없음). 기존 C3 화면 수정 대신 인계서에 preparation_warnings 표시 연결점을 남긴다.
