## 호출 순서와 경계

제품은 `validate_infra` → `plan_infra` → 한 화면의 infra 승인 → foundation(state bucket + app/build 권한 경계) → platform apply 순서로 실행합니다. bucket이 없으면 local backend plan을 승인한 뒤 코드가 SDK로 bucket을 만들고 platform local apply 후 remote backend로 state를 이전합니다. 사람이 미리 foundation/platform을 apply하는 전제는 폐기합니다. 사람의 사전 준비는 AWS 자격증명과 도메인 구매입니다. AI 개발 에이전트는 Terraform을 직접 실행하지 않으며, 승인 뒤 제품 코드가 실행하는 경로와 구분합니다. 실제 생성기의 O2 연결은 아직 미완이고 AWS 전체 완료를 의미하지 않습니다.

`bind_infra(InfraBinding(...))`로 운영자가 run별 runtime·입력 HCL·세션 factory·Analyzer를 연결한다.
validate/plan은 승인 전 호출이다. plan 결과의 `plan_sha256`을
`prepare(subjects={"infra": sha}, infra_summary=summary)`에 전달한다.
사용자 승인 뒤 `apply_infra`가 실행되면 `refresh_infra_context`가 허용된 출력만 반영한다.
적용 성공은 refresh보다 먼저 infra_changes에 남긴다. 이후 빌드가 실패해도 적용 기록을 보존하며,
앱 배포 미시작 환경에 rollback_tier를 호출하지 않는다. 인프라를 자동 원복했다는 뜻은 아니다.
C-18 없음/다른 해시로는 승인되지 않는다. 자격증명은 컨텍스트·DB·툴 인자에 넣지 않는다.
FAKE는 명시적 fixture runner만 허용하며 source=fixture로 표시한다.

실 연결자는 영속 runtime root, 실제 잠금 검사, 서비스의 최신 승인 읽기 함수를 제공해야 한다.
해당 run 연결이 없으면 툴은 INFRA_MISSING으로 실패한다. fixture로 자동 대체하지 않는다.
초기 foundation + platform은 한 화면 infra 승인 뒤 제품 코드가 적용하는 흐름이다. 앱 개선 배포 run은 따로 검증·승인한다. 기존 run당 infra 슬롯/생성기 연결 조립은 아직 미완이다. 카탈로그의 TLS→apply 순서는
이미 플랫폼이 있는 개선 배포 기준이다. 첫 플랫폼은 ddak.app이 승인 전에 apply→infra_ready→build/TLS로 조립하며 생성기 binding 통합이 남았다.

출력 기준은 `core/contracts/infra_outputs.py`다. 플랫폼 ARN/도메인/서브넷 등과 앱 역할 ARN을
구분한다. 신규 앱 시크릿은 `app_secret_arn_<KEY>`(대문자 env 키)이며 `secret_arn`은 이전 연결
호환용이다. 임의 출력 이름·민감 출력·시크릿 값은 통과하지 않는다. ARN은 시크릿 값이 아니다.

`ensure_tls`는 `ddak.app`→CD 콜백 주입으로 연결했다. C2의 AwsProvider 직접 메서드는 여전히
미구현이므로 제품 호출은 레지스트리 경로를 사용한다. 모드 apply는 거절한다. 기존 카탈로그의
STATE_CHANGE/lock/2700초 메타 정리는 공유 검토 대상이며 현재 값은 유지했다. 별도 443 probe는
DNS를 포함해 monotonic 기준 min(10초, 남은 시간)으로 제한한다. 시간 초과는 검사 불합격이며
ADAPTER_TIMEOUT/NEEDS_HUMAN으로 승격하지 않는다. 응답이 503이어도 TLS
연결은 성공할 수 있다. 앱 성공은 health/smoke/verify_tls에서 별도로 확인한다.

### 10/1 사용자 후속 확정

- CodeBuild는 `ai-prod` 후보 커밋 SHA를 `sourceVersion`에 고정한다. S3는 대체 경로다. C2 빌드 연결은 이 기준을 따른다.
- TLS 담당은 정준우다. ACM·443·리다이렉트·HSTS는 플랫폼 Terraform이 만들고 `ensure_tls`는 발급 완료·443 동작을 확인하며 불충족 시 실패한다. `ensure_tls`에서 직접 발급·변경하지 않는다.
- 트랙 대기 지점(`local_verified` 게이트·`ABORTED_AT_GATE`)은 제거하고 두 트랙을 독립 진행하며, 교차 검증은 둘 다 성공했을 때만 수행한다. **이 변경과 `prod` 감시·`ai-prod` 갱신·`deployed/*` 태그·`main` 갱신은 별도 브랜치 착수 지시 전까지 구현하지 않는다.**
- 이번 후속 반영은 결정 기록이다. 현재 TLS 코드는 AWS 설정 조회까지이며 실제 443 접속 동작을 확인한 것으로 보지 않는다. 기존 실행기·트리거 코드도 변경하지 않았다.

### 취합 때 필요한 결정

1. 생성기는 리소스 HCL만 넘기고 provider/backend/variable/output은 코드가 만들지(C-20), bundle SHA·저장 위치.
2. 플랫폼·앱 별도 run/승인. 현재 O1 저장소는 run당 infra 기록 하나다.
3. C-03 출력 이름·타입·필수 키와 생성 리소스 주소. C3 기존 ALB/ACM 이름, C2 ECS/CodeBuild/시크릿을 맞춘다.
