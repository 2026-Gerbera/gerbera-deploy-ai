## 10/2 야간: 현재 개발 상태

독립 트랙·대상 선택·Git 후보/배포 기록·WP11 내부 API·C1 툴 연결을 구현했다.
최신 범위/담당자 요청은 [아침 인계](O1-night-handoff-2026-10-02.md), 계약 추가는
[야간 결정](../decisions/2026-10-02-night-development.md)에 정리했다.
수정 전 야간 전체 CI는 **1,015 passed, 1 skipped, 4 deselected / 45.7초**였다. 수정 라운드의 최종 검증은
[아침 인계](O1-night-handoff-2026-10-02.md)의 마감 검증을 따른다. 아래 VM 수치는
**야간 변경 전 코드**의 결과다. 야간 변경 후 VM·AWS·원격 Git을 다시 실행하지 않았다.

- `targets=onprem/cloud/both`는 승인 전에 계획에 반영한다. 생략하면 기존 계획 대상을 유지한다.
  제외된 환경은 N/A이고 기존 환경 기록은 보존한다. `trigger=manual/auto`를 run에 남긴다.
- 카탈로그의 환경 간 대기를 제거했다. local_verified/cloud_verified 값은 완료 신호로 유지한다.
  구형 대기 계획은 거부하므로 재계획·재승인이 필요하다. 실패한 환경만 복구하고 다른 환경은 계속한다.
  둘 다 성공해야 compare가 실행되며 불일치 때는 cloud만 복구한다. 건너뛴 검증은 STEP_SKIPPED로 남긴다.
  rollback은 이번 run의 deploy_tier/prepare_db 호출 tier만 대상으로 한다. 빌드 실패 시 앱 배포 전 환경은
  SKIPPED, run은 FAILED_BEFORE_DEPLOY이며 이미 적용한 인프라는 infra_changes로 별도 보존한다.
  환경별 verify 실패는 해당 환경 실패이고 compare/diagnose 실패만 PARITY_FAILED다. 공통 검증 실패는 FAILED_VERIFY다.
- `source_sha`는 승인한 prod 원본, `candidate_sha`는 실제 ai-prod 후보다. 운영자가 연결한
  `repositories={project: AppRepository(app_checkout)}`가 있을 때만 후보 생성/게시를 수행한다.
  기본 app factory에는 이 매핑이 아직 없다. repo_url 설정만으로 clone/push가 켜지지 않는다.
- 후보는 기존 ai-prod에 prod를 merge한 뒤 관리 대상 파일을 승인된 build_files와 정확히 맞춰
  merge 커밋을 만든다. 충돌 파일은 기록만 하며 승인된 트리로 해결한다. 패치 OFF의 의미는 10/3에
  "OFF = 새 AI 제안 없음, 이전 승인 패치를 유지할 수 없으면 승인 전에 멈춤"으로 정했다("OFF면 이전 AI 패치가 제거된다"는 폐기, 구현은 수정 11 진행 중, [10/3 결정 따라잡기](../decisions/2026-10-03-decisions-catch-up.md) 결정 12). 패치 재사용 불일치의 재제안은 O3 연결 대상이다.
  `.env.example`·`.env.sample` 및 prod deploy.yaml의 env_example 경로는 prod 내용을 유지하고 후보 관리 트리 비교에서 제외하지만 비밀검사에는 포함한다.
  `.env`·PEM·KEY는 대소문자를 무시하고 차단한다. 일반 경로 템플릿이 승인 원본/수정본에서 prod와
  다르거나 prod에 없는 파일을 추가하면 후보 생성·검사를 거부한다. 충돌 목록은 get_release의 merge_conflicts로 조회한다. 전체 사본 비밀검사·manifest 검사를 통과해야 고정 SHA를 일반 push한다.
  Gitleaks 미설치는 실패다. 이 Mac의 8.30.1 실제 CLI 검증과 scanner fixture 검증을 구분한다.
- 성공 환경의 deployed/onprem·deployed/cloud 태그만 갱신한다. 선택한 대상 전체 성공 때만 main을
  fast-forward한다. Git 실패는 배포 결과를 지우지 않고 별도 git.status로 남긴다.
- WP11 공개 조회: `get_run/list_runs/get_release/get_environments/get_approvals`,
  설정: `get_project_settings/save_project_settings(expected_version=...)`. 승인 메타는 `approval_view`.
  실제 저장한 설정/버전만 prepare에서 스냅샷한다. targets=None은 계획 대상을 유지한다. default_targets는
  O2/C3 요청 접수 때만 적용한다. 기존 웹의 일부 키 저장도 나머지 값을 보존하나 공개 API 교체는 C3 몫이다.
- C1 validate/plan/apply 등록·refresh·CD TLS 검사를 연결했다. Terraform 부분 실패/출력 확인 실패는
  NEEDS_HUMAN과 잠금을 유지하며 앱 롤백으로 인프라 복구 완료를 기록하지 않는다. 실 세션 생성은 미연결이다.

## 10/2: flaskr 온프렘 첫 배포 구현 당시

최신 실행 절차는 [3티어 WSL2 가이드](O1-three-tier.md), 범위 정정은
[10/2 결정](../decisions/2026-10-02-onprem-three-tier-bootstrap.md)을 따른다.
아래 10/1 기록은 당시 상태다. 현재 temp-box는 SQLAlchemy 기반 flaskr 최종형이며,
web·DB 최초 생성도 승인된 배포 계획에 포함한다. 기존 테스트 fixture는 유지했다.

- `scripts/o1_onprem.py`: 오프라인 인벤토리·0600 env 생성, 멀티 아키텍처 빌드·digest 산출물,
  tier별 preflight, 승인·잠금·장부를 거치는 bootstrap/update. WAS 단독과 3티어 상태를 분리한다.
- DB → 마이그레이션 → WAS 3개 순차 교체 → web → health·HTTP smoke.
  기존 DB는 재생성하지 않고, 고아 볼륨·정지·다른 이미지·소유권 불일치는 수동 확인으로 멈춘다.
  DB rollback은 보존이며 DB 포함 demo reset은 거부한다.
- web은 이미지·인벤토리 공개 설정이 같으면 새 RELEASE_ID에도 유지한다.
  build의 `--reuse-web`으로 static/nginx 입력이 같을 때 이전 web 산출물을 재사용한다.
  web 설정은 인벤토리 `public_env`에서 관리한다.
- 실 로컬 Docker에서 SQLite WAS 단독을 먼저, MySQL·Traefik·nginx 3티어를 다음에 검증했다.
  WAS는 각각 3복제본, `ports=[]`; HTTP 경로·migration·digest·종료 코드 0 확인.
  업데이트 시 DB·web 컨테이너 ID가 보존된다. 상세 실측과 preflight는
  `var/validation/flaskr-three-tier-runtime.json`, 실행 로그는 `flaskr-docker-test.log`.
- 앱 전용 검증은 `var/validation/flaskr-app-tests.log`, 전체 CI는
  `var/validation/onprem-three-tier-ci.log`. 전용 앱 의존성 환경은 루트와 분리했다.
- WSL2 실제 VM·SSH, Docker Hub push, Cloudflare HTTPS/실제 IP·Secure 쿠키 확인은 사용자가
  준비한 환경에서 이어서 실행한다. 로컬 성공은 VM 성공이나 3분 성공률 보장이 아니다.
- 트리거 개편·트랙 독립화·C3 웹 조립·클라우드 통합은 이번 변경에 포함하지 않는다.

실행 진입점은 `ddak.executor.service.DeploymentService`다. `Executor`만 직접 호출하면
승인·프로젝트 잠금·영속 기록이 연결되지 않으므로 제품 진입점으로 쓰지 않는다.
웹 기동 시 `app.state.deployment`에 동일 서비스가 들어간다. 승인 화면·인증·CSRF·SSE
HTTP 라우트는 C3 구현이며, 이 내부 Python API를 인증 없이 외부에 노출하지 않는다.

```python
run_id = service.prepare(
    plan,
    context,
    source_path,
    patch=proposed_diff,
    facts_reader=recompute_facts,
    subjects={"infra": plan_sha256},
    infra_summary=c18_summary,  # plan_sha256과 아래 C-18 필드가 있는 가린 요약
    patch_meta={"reason": "개발 URL 설정 교체", "reuse": False, "source": "live"},
)
view = service.approval_view(run_id)  # diff, 계획, 대상별 해시를 한 화면에서 표시
service.approve(run_id, approver="operator")  # 실제 사용자 승인 시에만 호출
service.start(run_id)  # 브라우저 연결 종료와 독립적인 task
result = await service.wait(run_id)
events = service.events(run_id, after=last_seq)
```

인프라 변경이 없으면 `subjects`·`infra_summary`를 생략한다. 패치가 없으면 `patch_meta`도 생략한다.
`prepare`는 임시 사본 검사만 하고,
실제 사용자 승인 이후 `start`가 빌드 사본을 만든다. 승인 호출을 자동 승인 로직으로 쓰지 않는다.

### WP10 승인 메타 (10/1 후속 지시)

- 새 `approval_view` 키는 `patch_meta`, `infra_summary`이며 기본값은 각각 `None`. 기존 키는 유지한다.
- `patch_meta`: `reason`(1~200자), `reuse`(bool), `source`(`live/cache/fixture/replay`). 표시용이며 `reuse=True`도 새 run의 승인을 생략하지 않는다. 호출자가 출처·재사용 사실을 확인해 전달한다.
- `infra_summary`: `layer`(`app/platform`), `plan_sha256`, `exit_code`(0/2), `headline`, `counts`(`create/update/delete/replace`), `destructive`, `iam_diff`, `access_analyzer`(`errors/security_warnings`), `checkov`(`passed/failed`), `sensitive_masked=true`. 01 공통 계약의 C-18과 C1/C3 역할 문서 예시를 사용한 **임시 구조**이며 실행기 내부 모델이다. 정책 안전성 판정·요약 생성은 C1/O2 책임이다.
- 메타 각각 정규화 JSON UTF-8 **8KiB 이하**(감사 파일의 들여쓰기·두 메타를 감싸는 키는 제외). 원문 자격증명·가리지 않은 계정 ARN 등 redact 변화가 있으면 입력을 거부한다. 원문 검증 오류를 출력하지 않는다. C-18의 이미 가린 Secrets Manager ARN은 허용한다.
- 인프라 대상은 있으나 요약이 없거나 해시가 다르면 `prepare`로 검토 상태를 만들 수 있지만 `approve(approved=True)`·`start`는 거부한다. 거절 기록은 남길 수 있다. 대상 없는 메타와 잘못된 모양은 `prepare`에서 거부한다.
- `runs/<run_id>/approval-meta.json`에 보관한다. 입력·조회 결과를 바꿔도 준비된 메타는 변하지 않는다. 저장 JSON의 값·타입이 바뀌면 승인/시작/step 전에 중단한다(키 순서·들여쓰기만 바뀐 동일 데이터는 허용). UI의 HTML 이스케이프·표시·버튼 상태 연결은 C3가 담당한다.

## 로컬과 기록

- Docker CLI·buildx와 로컬 Unix 소켓(컨테이너 모드), pinned SSH를 통한 was VM Docker를 지원한다.
  app-1..3 순차 교체·Traefik 라벨·준비 확인·부분 롤백을 구현했다. 컨테이너 모드는 실제 Docker로,
  VM은 위 10/2 새벽 리허설로 검증했다. 야간 실행기 변경 후 VM 재검증은 하지 않았다.
- `ctx.platform.onprem.tiers`의 `name`, `platform`, `ports`, `network`, `volumes`,
  `env_file`을 사용한다. 상세 허용값은 `onprem/deploy/provider.py`의 입력 모델에 있다.
  공개 설정은 `public_env`로 주입하고 비밀값은 노트북 env 파일에 둔다(A안).
- `ctx.images`는 digest 고정 참조다. 이미지와 플랫폼 manifest 검증이 끝나야 기존
  컨테이너를 멈춘다. 소유 프로젝트/tier 라벨이 다른 컨테이너는 건드리지 않는다.
- `var/ddak.sqlite`가 실행·승인·환경별 성공 기록의 기준이다. `var/runs/<run_id>/`에는
  계획, diff, 빌드 사본, 가린 컨텍스트, JSONL 이벤트, 최종 릴리스 export가 있다.
- 최초 실배포는 `mode=bootstrap`으로 성공 기록을 만든다. 실환경 update는 해당
  환경의 실제 성공 기록이 있어야 한다. fixture 기록은 실환경 복구 기준으로 쓰지 않는다.
- 성공한 환경은 `SUCCEEDED`를 유지한다. 복구 실패·종료 미확인 타임아웃·인프라 부분 실패이면 `NEEDS_HUMAN`으로
  다음 실행을 막는다. 실행 중(RUNNING) run의 잠금은 TTL 만료만으로 빼앗지 않고, 종료된 run의 만료 잠금은 다시 획득한다(10/3). DB/인프라는 역변환하지 않는다.
- 롤백 제한 시간은 등록된 툴의 tier별 제한 시간을 합산한다. 잠금 갱신의 일시적 SQLite
  경합은 재시도하고, 연속 3회 실패하거나 잠금이 무효이면 실행을 중단하고 잠금을 남긴다.
- 한 상태 디렉토리에는 컨트롤러 하나만 실행한다. 재시작 시 실행 중 작업은 `NEEDS_HUMAN`,
  미실행 계획은 `CANCELLED`로 표시하고 새 run으로 준비한다. 자동 재개는 없다.
- 실패 복구 확인은 실제 Docker 상태와 DB 이력을 대조해야 한다. 잠금·차단은 운영자가 `/ops`의
  잠금·차단 해제 버튼이나 `make -C harness unlock`으로 쉽게 푼다(10/3 결정, 이전 "강제 해제 미제공" 대체).
  실행 중 run은 해제를 거부하고, 해제는 감사 기록만 남기며(`recovery_verified=false`) 복구 확인이 아니다.
  임의 DB 초기화 명령은 제공하지 않는다. 리허설은 전용 데모 상태/자원으로 분리한다.

## 10/1 독립 검토 반영

- 롤백 동일성은 이미지 참조·플랫폼/config digest·config/release_id spec으로 판정한다. `ddak.envkeys`는 reset 전용 비교다. v1→SECRET_KEY 주입→v2 app-2 실패에서 복구 [1,2], app-3 ID·마지막 성공 장부 불변을 DeploymentService 경유로 검증한다. 이전 release_id가 없으면 작업 전에 거부한다.
- 인벤토리 ready 포트·경로로 Docker healthcheck를 생성하고 healthy까지 확인한다. 준비 실패 replica는 stop 후 ADAPTER_FAILED를 반환한다. [Docker health 옵션](https://docs.docker.com/reference/cli/docker/container/run/)과 [Traefik Docker provider의 healthy 필터](https://github.com/traefik/traefik/blob/master/pkg/provider/docker/config.go)를 기준으로 구현했다. 실제 Traefik 경로 검증은 VM 준비 뒤 수행한다.
- local health는 registry를 조회하지 않는다. 컨테이너의 native manifest descriptor를 대조하고 classic store는 배포 때 검증해 저장한 manifest/config 라벨과 컨테이너 Image를 대조한다. config ID를 플랫폼 manifest digest로 대신 기록하지 않는다. 관측 실패는 passed=False, 접속/CLI 실패는 예외다.
- reset 인벤토리 오류는 원문 대신 고정 메시지를 반환한다. cloud DIVERGED만 해제하며, 변경 전 실패는 장부를 보존한다. 성공 장부 커밋 후 감사 기록 실패는 경고로 반환한다. 변경 중 복구 실패의 NEEDS_HUMAN은 유지한다. 사람은 감사 기록·실제 replica/env·장부를 대조해 복구 여부를 확인한 뒤 정상 릴리스를 다시 준비한다. 자동 재개 기능은 제공하지 않는다(잠금 해제는 10/3부터 `/ops` 버튼·`make -C harness unlock`으로 한다. reset 스크립트는 잠금을 풀지 않는다).
- SSH jump/대상은 다른 지문으로 검증하며 jump 불일치 시 대상 스캔 전에 중단한다. key_path의 `$`는 금지한다. 컨테이너 모드 `docker_host=ssh://...` 허용은 사용자 요청으로 유지한다.
- **알려진 위험: container 모드 ssh://는 지문 고정 없이 사용자 ssh 설정을 쓴다. 데모는 vm 모드 인벤토리 사용.** P1 제한 작업은 O1-completion.md에 기록했다.

- 최종 확인: `make -C harness ci` **487 passed, 2 deselected**. PR #1 `0b1751c`와 조합한 사본 CI는 **500 passed, 2 deselected**, 공통 health 툴·reset 설정 보존의 별도 검사도 2 passed다. PR 파일·공유 계약은 수정하지 않았다. PR #1의 기존 기능 지적은 위 표대로 남아 있다.
- 이번 구현 파일: `onprem/deploy/{replicas,health,containers,provider,demo,ssh,migrate,__init__}.py`; 검증 파일: `tests/unit/onprem/deploy/{test_service_vm,test_onprem_vm,test_onprem,test_demo}.py`, `tests/docker/{service_rehearsal,test_onprem_runtime,test_onprem_vm}.py`, `tests/docker/fixture/server.py`.
- 검토 항목별 판정은 로컬 전용 `var/validation/o1-review-fixes-resolution.json`에 기록한다. 변경 없음이 확인된 reset 오류만 기존 장부를 보존하며, env 쓰기 도중 실패·복구 중단은 NEEDS_HUMAN으로 막는다.
- reset 실패의 수동 복구: 컨트롤러를 멈춘 뒤 감사 JSON의 before/기준 release와 모든 replica의 소유 라벨·이미지·RELEASE_ID·env 키 이름·DB 마이그레이션 상태를 대조한다. 혼합 상태면 먼저 동일한 검증된 release로 복구한다. 실제 상태와 장부가 일치함을 확인한 사람이 해당 프로젝트의 local 환경 장부를 검증된 release/status로 복구하고 감사 기록을 남긴 뒤 새 run을 준비한다. 상태 확인 없이 NEEDS_HUMAN만 지우지 않는다. 이 작업을 자동 수행하는 스크립트는 제공하지 않는다.
