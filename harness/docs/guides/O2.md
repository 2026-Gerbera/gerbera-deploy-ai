# O2 플랜·검증 연결: 접수에서 검증된 Plan까지

> **📌 10/3 연결분, 준석 확인 필요:** 판단용 Groq 셸 설정을 `DDAK_GROQ_API_KEY`·`DDAK_GROQ_MODEL`로 옮깁니다. 감시 기본값은 `flaskr/local/prod`로 변경했습니다. 변경 목록과 검증은 [O1↔O2 연결 결정](../decisions/2026-10-03-o1-o2-link.md)을 봅니다.
> 💭 v2 기능은 미정이며 로그인은 후보입니다. 정준우의 10/2 검증은 1차 Flask 기본 앱에 이미지·박스를 추가한 파이프라인 E2E, 2차 실제 로직의 LLM 분석·패치·인프라 생성 검증으로 나눕니다. 1차 결과로 실제 LLM·AWS 전체 완료를 주장하지 않습니다.

> 기준: 앱 1개 구조(✅ 9/30 최신 개발자 문서 기준)

- 상태: O1↔O2 연결분 반영 (2026-10-03, 준석 확인 필요)
- 담당: O2 김준석 · 소비자: O1(실행기), C3(승인 화면), O3(패치·Dockerfile)
- 관련 계약: `src/ddak/core/contracts/{plan,plan_draft,plan_facts,deploy_request,deploy_config}.py`

## 1. 범위와 비범위

- 범위: GitHub URL 접수, 변경 탐지, 분석, 계획 초안(AI 제안), 계획 검증(코드), 저장소 감시(폴링), 온프렘 인벤토리 읽기.
- 비범위: 승인 UI(C3), 배포 실행·롤백(O1), 패치·Dockerfile 생성(O3), 마이그레이션 실행.
- AI는 제안만 한다. 검증은 결정적 코드다. 키·digest·도메인은 계획과 AI 입력에 없다.

## 2. 공개 API (`ddak.plan`, 각 디렉토리 `__init__.py`)

| 이름 | 위치 | 용도 |
|---|---|---|
| `plan_deployment(request, *, run_id, settings, strict_ai_check=False, previous_manifests, cloud_domain=None, platform=None, fetch_policy=None, fetcher=None, jev_client=None, provider=None) -> PlanBundle` | `plan/flow.py` | 접수 -> 탐지 -> 분석 -> 계획 -> 검증을 한 번에 |
| `PlanBundle(plan, context, facts, source)` | `plan/flow.py` | `prepare` 입력 묶음. `to_json_dict()`로 직렬화 |
| `new_run_id(now=None)` | `plan/flow.py` | `run-YYYYMMDD-HHMMSS-<4hex>` |
| `receive_deploy_request`, `cleanup_stale_sources`, `FetchPolicy` | `plan/intake` | 접수(툴 `receive_deploy_request`) |
| `WatchTarget`, `Watcher`, `load_watch_targets`, `resolve_head`, `warm_cache` | `plan/intake` | 10초 폴링 감시 |
| `detect_changed_tiers`, `facts_reader` | `plan/detect` | 변경 탐지, `prepare`용 facts 해시 |
| `analyze_project` | `plan/analyze` | tier·환경 키 분류(Jev) |
| `generate_plan` | `plan/planner` | 선택 step 초안(Jev -> Claude -> 규칙) |
| `validate_plan` | `plan/validate` | 검증·조립(AI 금지) |
| `load_inventory` | `onprem/inventory` | `RunContext.platform["onprem"]` |

툴 이름은 `receive_deploy_request`, `detect_changed_tiers`, `analyze_project`, `generate_plan`, `validate_plan`(모두 계획 밖 단계).

## 3. `prepare`에 넘기는 법

```python
bundle = plan_deployment(
    request, run_id=new_run_id(), settings=settings,
    previous_manifests=lambda project: {"local": ..., "cloud": ...},  # Store의 source_files, 없으면 None
)
run_id = service.prepare(
    bundle.plan, bundle.context, bundle.source, facts_reader=facts_reader,  # ddak.plan.detect
)
```

- `previous_manifests`: `store.environments(project)[env]["current"]["source_files"]`를 `FileMeta`로 바꿔 돌려준다. 성공 기록이 없으면 `None`(그 환경은 전부 변경으로 본다). Store 읽기는 호출자 몫이다.
- `facts_reader`는 번들에 넣지 않는다. 실행기가 시작 전 `plan.facts_hash`와 대조한다.
- 넘어가지 않는 것: 도메인·호스트·이미지 digest·시크릿 값·AI 원문 응답·소스 내용. 마이그레이션은 id 목록만.
- `source`는 run 전용 checkout. 실패하면 flow가 지우고, 성공하면 남긴다. 오래된 사본은 `plan_deployment` 시작 때 `cleanup_stale_sources(root, 3600, keep=(run_id,))`로 정리한다.
- `patch`·`subjects`는 O2 범위 밖(None).

## 4. 검사 모드

`strict_ai_check`(기본 False)를 `RunContext.toggles`·`Plan.toggles`에 같은 값으로 넣는다.

- 기본 검사: 재지시 없음. 초안이 구조 위반이면 곧바로 규칙 계획(`planner.fallback=True`).
- 엄격 검사: 위반 사유를 `feedback`으로 `generate_plan`을 1회 더 부르고, 그래도 안 되면 규칙 계획.
- 끌 수 없는 최소선: 금지 파라미터, 필수 step, 카탈로그 조립, 마이그레이션 누락 검사.

## 5. 저장소 감시(`ddak.app`)

앱 조립부는 저장된 project_settings의 `auto_detect`·`repo_url`로 감시 대상을 만들고 `watch_branch`를 `Watcher`에 공급한다(기본 prod). `DDAK_WATCH_REPO_URL`은 저장 설정이 없는 프로젝트의 보조 입력이다. 새 커밋은 계획·승인 흐름으로 연결하며 배포는 사람 승인 뒤 실행기가 한다. standalone 기본값도 `flaskr/local/prod`다. 저장 설정이 우선이고 환경변수는 저장 설정이 없는 프로젝트에 적용한다. `flaskr` 설정이 없고 `demo` 설정만 있으면 기존 `demo` 장부를 그대로 쓴다. 성공 기록이 없으면 `mode=bootstrap`, 있으면 `update`.

## 6. 환경변수

| 변수 | 뜻 | 기본 |
|---|---|---|
| `DDAK_WATCH_REPO_URL` | 감시할 GitHub URL. 설정해야 감시 시작 | 없음(감시 꺼짐) |
| `DDAK_WATCH_PROJECT` / `DDAK_WATCH_TARGETS` / `DDAK_WATCH_BRANCH` | 저장 설정이 없는 감시 대상의 프로젝트·대상·브랜치 (`onprem`은 `local` 별칭) | flaskr / local / prod |
| `DDAK_WATCH_INTERVAL_S` | 폴링 간격(초) | 10 |
| `DDAK_GITHUB_TOKEN` | 비공개 저장소용 읽기 전용 토큰(선택). 로그·repr에 나오지 않는다 | 없음 |
| `DDAK_GIT_ALLOWED_HOSTS` | 허용 호스트(쉼표) | github.com |
| `DDAK_GIT_TIMEOUT_S` / `DDAK_GIT_MAX_MB` / `DDAK_GIT_MAX_FILES` | 접수 제한 | 120 / 200 / 20000 |

| `DDAK_SOURCES_DIR` | 접수 사본·감시 상태 루트 | `var/sources` |
| `DDAK_LLM_BACKEND` | 생성 역할 `call_ai`: cli / api(현재 Groq) / replay | replay |
| `DDAK_LLM_API_KEY` / `DDAK_LLM_MODEL` | 생성 역할 api 키 / 모델. cli 모델은 판단 역할 cli와 공유 | cli는 claude-sonnet-5-5 |

| `DDAK_JEV_API_KEY` / `DDAK_JEV_MODEL` / `DDAK_JEV_TIMEOUT_S` | 실제 TypeSafe 연결용 예약. 현재 어떤 경로에도 키를 보내지 않음 | 미연결 |

키는 파일에 쓰지 않고 셸 환경변수로만 주입한다.

## 6-1. AI 호출부 교체 방법

판단 역할은 `get_jev_client(Settings)`가 `GroqJevClient` 또는 `ClaudeJevClient`를 선택한다. AI가 backend를 선택하지 않는다. `JevClient`는 TypeSafe 미연결 자리이며 `AI_UNAVAILABLE`로 끝난다. Groq는 `DDAK_JEV_API_KEY`를 대체 키로 사용하지 않는다.

Claude 판단은 기존 CLI의 제한된 argv·환경을 재사용한다. 생성 역할도 cli이면 `DDAK_LLM_MODEL`을 함께 쓰고, 생성 역할이 api/replay이면 판단 모델은 `claude-sonnet-5-5`다. `--effort` 지원은 읽기 전용 `claude --help`로 확인했다. 실제 모델 사용 가능 여부·로그인은 운영자가 확인한다. cli 사용 시 컨테이너·원격/CI 표식·비 loopback 또는 불명확한 웹 바인딩을 거부한다. 공식 `make run` 진입점은 127.0.0.1이다.

분석 `EnvKey.provider/model`과 계획 `Planner.provider/model`에 실제 판단 경로(groq / claude-cli)를 남긴다. fixture/replay 출처도 유지한다. 생성 역할 api의 실제 Groq·claude-api 라벨 불일치는 별도 결정 항목이다.

### 수동 확인(실호출, 에이전트는 실행하지 않는다)

1. 셸에서 생성 역할의 `DDAK_LLM_API_KEY`·`DDAK_LLM_MODEL`, 판단 역할의 `DDAK_GROQ_API_KEY`·`DDAK_GROQ_MODEL`을 준비한다. 키 값은 문서·로그에 쓰지 않는다. 비공개 저장소 읽기는 `DDAK_GITHUB_TOKEN`을 쓴다.
2. AI 스모크: `cd harness && DDAK_LLM_BACKEND=api DDAK_JEV_BACKEND=groq python -m pytest -m llm -q`.
3. 감시 스모크: `DDAK_WATCH_REPO_URL=https://github.com/<owner>/<repo> DDAK_SOURCES_DIR=/tmp/ddak-src python -m ddak` 후 감시 브랜치를 prod로 설정하고 해당 저장소의 PR을 prod에 merge한다(prod 직접 push 금지). 약 10초 안에 로그 `새 커밋 계획 생성, 승인 대기`가 나오고 단계별 `ms`가 찍혀야 한다(AI 지연 제외 단일 자릿수 초).
4. 키가 대화·로그에 노출됐다면 폐기·재발급한다.

## 8. 연결 규칙

- `core.env_keys.is_migration_key`의 대소문자 무시 `*_MIGRATOR` 규칙을 분석·온프렘·Fake가 공유한다. 이 키는 앱 런타임 `env_keys`에서 제외하고 마이그레이션 전용 경로로만 공급한다.
- BOOTSTRAP의 env_example 키는 신규다. UPDATE 신규 판정 개선은 별도다.
- `validate_plan(..., registered_tools=set[str])` / `assemble`은 미등록 OPTIONAL step을 제외하고 `unregistered_optional_tool` 경고와 `forced_skip` 사유를 남긴다. 생략하면 조립 시점 레지스트리를 읽는다.
- 필수 환경 툴 미등록은 `RunContext.preparation_failures`에 기록한다. 다른 환경은 승인·실행할 수 있다. 공통 빌드 툴 미등록 또는 선택한 모든 환경이 준비 불가면 요청 전체를 거부한다.
- 현재 감시는 첫 HEAD를 기준선으로만 저장한다. 컨트롤러 시작 후 PR을 prod로 merge한다. 첫 HEAD 수동 계획·잠금 해제 등 수정 8의 나머지는 이 연결분에 포함하지 않는다.
