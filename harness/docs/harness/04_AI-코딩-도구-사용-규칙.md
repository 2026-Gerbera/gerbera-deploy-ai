# 04. AI 코딩 도구 사용 규칙

> 기준: 앱 1개 구조(✅ 9/30 최신 개발자 문서 기준)

개발 과정에서 쓰는 AI 코딩 도구(Claude Code, Codex 등)의 규칙입니다. 제품이 실행 중에 쓰는 AI(`call_ai`)와는 별개입니다.

## F-1. AGENTS.md 해설

[AGENTS.md](../../AGENTS.md)는 사람과 모든 AI 도구가 같이 읽는 규칙입니다. 150줄 이내, 명령형으로 씁니다. 하네스 소유자(@TL, 지정 대기) 소유이고 `harness` scope 전용 PR로만 고칩니다.

| 절 | 내용 | 설계 이유 |
|---|---|---|
| 1. 적용 범위와 우선순위 | 공통 계약 > 역할 가이드 > 코드. 권위 문서는 인덱스 링크 한 줄. 충돌하면 30분 안에 하네스 소유자에게 `NEEDS_CONTEXT` | devpi-guardian에서 권위 문서 목록이 갱신되지 않은 교훈. "중단"을 3일 일정에 맞게 "30분 안에 질문"으로 바꿈 |
| 2. 확정 사항 | ✅/🟡 표(언어, AI 컨트리뷰터 금지, 앱 1개 구조 ✅, 파이프라인·대기 지점, AI 경계, 계획 층, LLM backend, TLS, DB·샘플 앱, AI 설정 패치 P0·데모 ON/일반 OFF) | 에이전트가 확정·합의 대기·고려안을 섞지 않게 |
| 3. 금지 | 소유 밖 수정, 공유 파일, 새 의존성·LangChain, 비밀 파일 읽기, AI attribution, 훅 우회·force push·git config, terraform apply, 실행 경로·웹의 AI import, 툴 모듈끼리 import, `print`, 로컬 검증 건너뛰기, 구독 CLI 외부 사용, 데모용 개발값 수정, 계약 임의 변경 | 각 항목이 훅·CI·import-linter·ruff·레지스트리 등록 검사 중 하나로도 막힘(문서는 1차 방어) |
| 4. 작업 방식 | worktree 하나에 에이전트 하나, 모듈이 다르면 병렬 허용, 짧은 브랜치, `make check`, 새로 실행해 검증 | devpi는 "구현 에이전트 동시 실행 금지"였지만 5명 병렬에는 반대로 적용 |
| 5. 보고 형식 | `DONE` / `NEEDS_CONTEXT` / `BLOCKED` | 구현자는 설계 결정을 하지 않음 |
| 6. 불변 조건 | AI 경계 (a)~(h) | devpi의 Engineering constraints 형식 |
| 7. 명령 | `make <타깃>`만 | 명령이 여러 곳에서 달라지는 문제를 막는 단일 진입점 |
| 8. AI 활용 기록 | `docs/ai-usage/<역할>.md` | F-4 |

[CLAUDE.md](../../CLAUDE.md)는 `@AGENTS.md`로 같은 규칙을 불러오고, Claude Code 전용 주의 4줄만 더합니다(LangChain·MCP SDK 코드를 만들지 말고 ping 템플릿을 복사). CLAUDE.md의 attribution 지시는 Claude Code 내장 지침보다 우선합니다.

## F-2. 도구별 설정

### Claude Code

커밋하는 `.claude/settings.json`:

- `attribution`: `{"commit": "", "pr": "", "sessionUrl": false}` — 세 키를 모두 명시합니다.
- `permissions.deny`: `Read(.env)`, `Read(.env.*)`, `Read(*.pem)`, `Read(*.key)`, `Read(*.tfstate)`, `Read(*.tfstate.*)`, `Read(*.tfvars)`, `Read(.terraform/**)`, `Read(.secrets/**)`, `Read(~/.claude/.credentials.json)`, `Read(~/.aws/**)`, `Read(~/.ssh/**)`, `Read(~/.mcp-inspector/**)`, `Bash(git push --force *)`, `Bash(git push -f *)`, `Bash(git push --force-with-lease *)`, `Bash(terraform apply *)`, `Bash(terraform destroy *)`. 파일 이름만 쓴 패턴(`.env`, `*.pem`)은 gitignore 규칙대로 모든 깊이에 적용됩니다(permissions 문서, 9/30 확인).
- (💭) PreToolUse 훅: `matcher: "Bash"` → `python3 "$CLAUDE_PROJECT_DIR/.claude/hooks/guard_bash.py"`. 막을 명령이면 종료 코드 2와 사유를 돌려주고, 입력을 해석하지 못하면 경고만 쓰고 통과시킵니다.

한계:

- Bash deny 규칙은 앞부분 일치라 인자 순서를 바꾸면 우회됩니다. 그래서 훅을 함께 둡니다. 훅도 문자열 패턴이라 완전하지 않습니다.
- `cat`·`grep` 같은 셸 명령과 파이썬 하위 프로세스는 Read deny의 적용 대상이 아닙니다. 그래서 Bash 가드 훅이 명령에 `.env`, `.secrets/`, tfstate, `~/.aws/credentials`, `~/.ssh/id_*`, `~/.claude/.credentials.json`, `~/.mcp-inspector` 경로가 나오면 막습니다(따옴표로 감싸거나 파이썬으로 열면 여전히 우회됨). OS 수준 차단(sandbox의 파일 읽기 차단)은 Docker·AWS 작업과 충돌할 수 있어 **개인 선택**으로 둡니다.
- `.claude/settings.local.json`은 `attribution` 같은 단일 값을 덮을 수 있습니다. `permissions` 목록은 파일끼리 병합되고 deny가 allow보다 먼저라, local 파일로 공유 deny를 지울 수는 없습니다(settings·permissions 문서, 9/30 확인). 규칙상 local 파일에서 attribution을 다시 켜지 않고 `disableAllHooks`도 쓰지 않습니다.
- 각자 Claude Code 버전을 확인하고, 본인 `~/.claude/settings.json`에도 attribution 세 키를 넣습니다(`make setup`이 없으면 경고).
- 권한 규칙은 문서 표준형인 공백 + `*`(`Bash(git push --force *)`)로 씁니다. `:*` 접미사도 같은 뜻입니다(permissions 문서, 9/30 확인). 훅이 실제로 막는지는 첫 커밋 담당이 한 번 확인합니다.

### Codex

- AGENTS.md를 기본으로 읽습니다.
- 프로젝트 설정 파일은 키 이름을 확인하지 못해 **만들지 않았습니다.** 각자 `~/.codex/config.toml`에서 파일 읽기 차단 프로필과 셸 환경변수 정책(키·토큰 변수 제외)을 쓸 수 있습니다. 키 이름은 설치한 버전의 문서로 확인합니다.
- 커밋 트레일러를 로컬에서 끄는 설정은 없습니다(기본은 없음, 워크스페이스 관리자가 켤 수 있음). 방어는 git 훅과 CI가 합니다.
- Codex cloud로 팀 저장소에 직접 PR을 만들지 않습니다.

### Superpowers 등 외부 스킬

선택입니다. 하네스 문서는 외부 플러그인 없이도 이해되게 썼습니다. 계획 문서를 남기려면 이슈 템플릿(`task.md`) 수준으로 짧게 쓰고, 구현 코드를 미리 적지 않습니다.

## F-3. 병렬 작업 요령

- 에이전트 하나는 worktree 하나(`.worktrees/<브랜치>`)에서만 일합니다. 같은 모듈이나 공유 파일에 두 에이전트를 동시에 붙이지 않습니다.
- 에이전트에게 툴을 맡길 때 넘길 것: 역할 가이드, 계약 문서 경로, `src/ddak/core/tools/ping/` 템플릿, 카탈로그의 해당 행(모듈·층·대상), 완료 기준(`@tool` 등록, 정상 1 + 실패 1 테스트, 스냅샷, `make boundary`), "계약을 바꿔야 하면 NEEDS_CONTEXT".
- 에이전트가 "통과했다"고 해도 사람이 `make check`를 새로 돌리고 PR에 출력 요약을 붙입니다.
- 보안 민감 PR(`security-sensitive`)은 새 에이전트 리뷰 1회, 수정 반복 최대 2회. 그 이상은 사람이 판단합니다.

## F-4. 개발 과정 AI 활용 기록 (AI 10점·팀 개발 20점 대비, 점수 반영 여부는 미확인)

- `docs/ai-usage/<역할>.md`에 사람별로 append만 합니다(충돌 없음). 형식은 [docs/ai-usage/README.md](../ai-usage/README.md).
- PR 템플릿의 "AI 사용" 칸에 도구, 범위, 사람이 검증한 부분을 적습니다.
- README의 "개발 과정의 AI 사용" 절이 이 기록을 가리킵니다. **git 메타데이터에서 AI를 빼는 것은 컨트리뷰터 목록 문제이지 AI 사용 사실을 숨기는 것이 아닙니다.** 해커톤 규정에 AI 사용 공개 조항이 있는지 확인합니다 [I-22].
- 제품 런타임의 AI 호출 비용은 이것과 별개입니다. `call_ai`가 기록해 결과 카드에 표시합니다.

## F-5. 개발 도구와 제품 런타임 AI를 섞지 않기

- 개발 과정의 AI 코딩 도구(이 문서)와 제품이 실행 중에 부르는 AI(`call_ai`, [02](02_툴-작성-규약.md) C-7)는 별개입니다.
- 제품의 `cli` backend는 운영자 본인 로컬의 구독 CLI를 `claude -p`로 부르지만 도구를 전부 끄고 JSON만 받습니다. 코딩 에이전트처럼 파일을 고치거나 명령을 실행하지 않습니다.
- 구독 로그인 정보를 저장소·컨테이너·CI에 넣지 않습니다. 외부 공개 데모는 API 키(`api` backend)로 합니다.
