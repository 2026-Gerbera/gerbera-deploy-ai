# 02. 툴 작성 규약

> 기준: 앱 1개 구조(✅ 9/30 최신 개발자 문서 기준)
>
> 역할 코드: O1 정준우 · O2 김준석 · O3 장민영 · C2 안승환 · C3 양서윤 · C1 = 유상준 하차(10/1), C1은 정준우·김준석 분담(분담 ✅, 세부 🟡 김준석 확인) · TL = 하네스·계약 승인자(미지정, 결정 필요).

✅ 원칙: "툴 하나 + 환경별 어댑터(local/cloud)". 어댑터는 코드가 실행 컨텍스트와 모드로 고릅니다(AI가 고르지 않음). 파라미터는 좁게 받습니다. 툴은 MCP 서버가 아니라 코드 안 레지스트리에 등록하는 파이썬 함수입니다(🟡 장부 3). 아래 형식은 💭 하네스 기본값입니다.

## C-1. 툴 하나의 구성

```
src/ddak/<module>/tools/<tool_name>/
├── __init__.py  # 비워 둔다(로직·import 없음). import-linter 와일드카드 계약과 자동 등록 때문
├── tool.py      # @tool("<tool_name>"): 입력 모델 → 어댑터 선택 → 호출 → 출력 모델. 로직 없음
├── logic.py     # (선택) 환경 무관 공통 로직, 툴별 어댑터 Protocol
├── local.py     # 온프렘 어댑터   (target이 있는 툴만)
├── cloud.py     # 클라우드 어댑터 (target이 있는 툴만)
├── fake.py      # Fake 어댑터: 결정적 정상/실패 시나리오(테스트·드라이런·UI 개발)
└── prompt.md    # AI 툴만: 프롬프트. 머리말에 버전·담당·변경일
src/ddak/core/contracts/tools/<tool_name>.py   # <ToolName>Input / <ToolName>Output (계약 파일)
tests/unit/test_<tool_name>.py
```

`<module>`은 카탈로그의 모듈(💭 레지스트리 트리 9/30: `plan` / `infra` / `ci` / `cd` / `verify` / `ops`)입니다. 다른 모듈에 두면 앱 기동이 실패합니다.

**cd 모듈은 예외(✅ 9/30, 공통 인터페이스 + provider 모듈):** cd 툴은 툴마다 `local.py`·`cloud.py`를 두지 않습니다. 환경별 구현은 `src/ddak/cd/providers/{aws,onprem}.py`(테스트는 `fake.py`)에 모으고, `tool.py`는 `select_provider(inp.target, ctx.adapter_mode)`로 provider를 골라 인터페이스 함수(`src/ddak/cd/interface.py`: deploy·rollback·health_check·migrate_db·inject_config·ensure_tls)를 부릅니다. 온프렘 `ensure_tls`는 실패가 아니라 `applicable=False`("해당 없음")를 돌려줍니다. GCP·Azure provider는 후순위라 코드가 없습니다. 공통 설정값(💭 Helm values처럼)은 deploy.yaml 공통 키 + provider별 덮어쓰기 + 환경 정보(코드가 채움)를 코드가 합쳐 넘깁니다.

```python
# src/ddak/cd/tools/deploy_tier/tool.py 의 모양(💭)
from ddak.cd.dispatch import select_provider


@tool("deploy_tier")
def deploy_tier(inp: DeployTierInput, ctx: RunContext) -> DeployTierOutput:
    provider = select_provider(inp.target, ctx.adapter_mode)  # AI가 고르지 않음
    result = provider.deploy(inp.tier, ctx)  # digest·주소는 ctx(환경 정보)에서
    return DeployTierOutput(run_id=inp.run_id, target=inp.target, result=result)  # 필드는 계약 문서
```

시작 방법: `src/ddak/core/tools/ping/`을 복사해 이름을 바꿉니다. 등록 목록 파일은 없습니다. `ddak.app.load_tools()`가 각 모듈 `tools/` 아래 디렉토리의 `tool.py`를 이름순으로 import하고, import 시점에 `@tool`이 등록합니다(이름이 `_`로 시작하면 제외).

```python
# tools/<tool_name>/tool.py 의 모양 (ping 기준)
from ddak.core.adapters import AdapterSet, select_adapter
from ddak.core.contracts.context import RunContext  # 모듈 최상단에서 import(TYPE_CHECKING 금지)
from ddak.core.contracts.tools.ping import PingInput, PingOutput
from ddak.core.registry import PING, tool

ADAPTERS = AdapterSet(local=LocalPingAdapter, cloud=CloudPingAdapter, fake=FakePingAdapter)


@tool(PING)  # 카탈로그에 있는 이름만. 다른 모듈에 있거나 시그니처가 다르면 기동 실패
def ping(inp: PingInput, ctx: RunContext) -> PingOutput:
    """대상 환경 어댑터가 응답하는지 확인한다."""
    adapter = select_adapter(ADAPTERS, inp.target, ctx.deploy_config, ctx.adapter_mode)
    return PingOutput(run_id=inp.run_id, target=inp.target, adapter=adapter.name, ok=adapter.ping())
```

## C-2. 입출력 모델 규칙

1. 모든 툴은 `contracts/tools/<tool>.py`의 pydantic 모델만 받고 반환합니다. 원시값이나 dict 반환은 금지합니다.
2. 시그니처는 `def <tool>(inp: <Tool>Input, ctx: RunContext) -> <Tool>Output`입니다(동기 또는 `async def`). 인자 이름도 `inp`, `ctx`로 고정합니다.
3. 모델은 `ContractModel`(extra="forbid", frozen=True)을 상속합니다. 입력은 `ToolInput`(run_id 필수)을 상속합니다.
4. 입력은 좁게 받습니다. 실행기가 plan.json step으로 입력을 만들고 스키마로 한 번 더 검증합니다.
   - `run_id`는 모든 툴의 필수 입력입니다(`RunId`).
   - `target: Target`(local|cloud)은 target이 있는 툴의 입력입니다. 실행기가 트랙에서 채웁니다. 카탈로그 대상에 없는 target이면 실행기가 거부합니다(예: `ensure_tls`·`verify_tls`는 cloud만).
   - `tier`는 `TierName`(패턴 `^[a-z][a-z0-9_-]{0,31}$`)으로 받습니다. 실행 시 deploy.yaml과 대조합니다.
   - ④ 툴은 `lock_token: LockToken`을 받습니다(실행기가 채움).
   - step `params`로 `run_id`·`target`·`tier`·`lock_token`을 바꿀 수 없습니다(실행기가 거부).
   - 자유 문자열 명령, 빌드 명령 재정의, IAM 역할 재정의, **도메인·호스트·URL·zone·이미지·digest·ARN** 입력은 열지 않습니다. 이 값들은 `RunContext`(코드가 채움)에서 읽습니다(✅ 장부 6·17).
5. 비밀값이 들어가는 필드는 `SecretStr`로 둡니다. 로그, 이벤트, run 로그, plan.json, AI 입력 어디에도 남기지 않습니다. SECRET_KEY는 툴 안에서 시스템 난수로 만들고 값을 바로 버립니다(참조만 기록).
6. AI 툴 출력에는 `ai_usage`(`AIUsage`)와 `source`(`Source`: live | cache | fixture | replay)를 넣습니다. 관리 페이지는 `source != live`이면 라벨을 표시합니다.
7. 필드 정의 자체는 `TODO(contract)`입니다. 공통 계약 문서가 정합니다.

## C-3. 메타정보와 레지스트리

`src/ddak/core/registry.py`에 두 층이 있습니다.

1. **카탈로그(`CATALOG`)**: 40개 툴의 `ToolSpec`(pydantic). 계약 파일이라 계약 변경 PR로만 고칩니다. `contracts/schemas/tool_catalog.json`으로 스냅샷합니다.
2. **등록(`@tool`)**: 구현 함수를 카탈로그 이름에 붙입니다. LangChain `@tool`과 비슷하지만 LangChain 패키지는 쓰지 않습니다.

```python
class ToolSpec(ContractModel):
    name: str
    module: Module        # plan | infra | ci | cd | verify | core | ops (💭 트리 9/30)
    stage: Stage          # plan | validate | build | deploy | verify_report | common | ops
    kind: ToolKind        # tool_fn(@tool 등록) | library(call_ai) | executor_fn
    uses_ai: bool         # call_ai·Jev를 부를 수 있는가(런타임 가드 기준)
    layer: Layer          # builtin | mandatory | conditional | optional | outside (step 층 기본값)
    targets: tuple[Target, ...]   # () = target 없음
    effect: Effect        # read | additive_prep | state_change (대기 지점 규칙의 근거, 💭)
    owners: dict[str, str]        # {"logic": "O2", "local": "O1", "cloud": "C2", "ui": "C3"} (실명은 ROLES)
    destructive / read_only / requires_lock / requires_approval: bool
    timeout_s: int        # 💭 실측 전 값
    canonical: bool       # False = 40개 밖(예시 ping)
```

- `@tool(name)`이 검사하는 것: 카탈로그에 있는 이름인가, `tool_fn` 종류인가, 함수가 `ddak.<카탈로그 모듈>.` 아래에 있는가, 시그니처가 `(inp: ToolInput 하위, ctx: RunContext) -> ContractModel 하위`인가, 두 번 등록하지 않았는가. 어긋나면 앱 기동(import)에서 `RegistryError`로 실패합니다.
- `REGISTRY.get(name)`이 실행기의 유일한 호출 경로입니다. `REGISTRY.missing()`은 아직 구현하지 않은 툴 목록(구현 진행 상황)이고 `make contract-smoke`가 보여 줍니다.
- 테스트는 `Registry(CATALOG)`나 테스트용 카탈로그로 레지스트리를 따로 만들어 씁니다(전역 REGISTRY를 더럽히지 않음).

## C-4. 실패 보고 규약 (💭)

| 상황 | 방법 | 실행기 동작 |
|---|---|---|
| 작업을 수행할 수 없음(잠금 실패, 어댑터 타임아웃, 입력과 deploy.yaml 불일치, 인프라 없음) | `raise DdakToolError(ErrorCode.X, "메시지")` | step 실패 기록(`X: 메시지`, redact) → 그 트랙 중단 → 상태를 바꾸는 step을 시작했으면 그 환경만 규칙 롤백 |
| 검사 결과 불합격(스모크 실패, 헬스 실패, TLS 불합격) | 정상 반환 + `passed=False` + 상세 | `check_failed` 기록 → 위와 같음 |
| 예상하지 못한 예외 | 그대로 둠 | `INTERNAL`로 기록(메시지 redact) → 위와 같음 |
| 타임아웃(카탈로그 `timeout_s`) | – | `ADAPTER_TIMEOUT`. 동기 툴은 스레드를 죽일 수 없으므로 boto3·subprocess에 자체 타임아웃을 둔다 |

- ErrorCode 초기안(💭, 확정은 계약 문서): `PLAN_INVALID`, `LOCK_HELD`, `LOCK_INVALID`, `CONFIG_INVALID`, `INFRA_MISSING`, `ADAPTER_TIMEOUT`, `ADAPTER_FAILED`, `PRECONDITION_FAILED`, `APPROVAL_REQUIRED`, `APPROVAL_DENIED`, `TOGGLE_OFF`, `AI_NOT_ALLOWED`, `AI_UNAVAILABLE`, `AI_OUTPUT_INVALID`, `INTERNAL`.
- 에러 메시지에 비밀값, 절대 경로, 계정 ID를 넣지 않습니다. 이 메시지는 관리 페이지와 LLM(원인 설명)으로 흘러갑니다.

## C-5. 실행 규칙 (실행기·대기 지점)

- 실행기(`src/ddak/executor/engine.py`)는 빌드·로컬 트랙·클라우드 트랙을 **동시에 시작**합니다. step의 `wait_for` 신호가 열릴 때까지 기다리고, `signal`이 있는 step이 성공하면 그 신호를 엽니다. 신호 이름은 고정 3개: `images_ready`, `local_verified`, `cloud_verified`.
- 로컬이 실패하면 `local_verified`가 실패로 닫혀 클라우드는 대기 지점에서 멈춥니다(`ABORTED_AT_GATE`). 검증 섹션(compare)은 두 트랙이 끝난 뒤 실행합니다.
- `run: "finally"` step(보고 `verify.report` = `post_report`)은 verify 섹션에만 두고 신호를 기다리거나 열지 않습니다. 앞이 실패해도 마지막에 실행하고, 실패해도 run 결과를 바꾸지 않습니다.
- plan.json의 `wait_for`는 항상 배열이고, step `effect`는 조립기가 step 카탈로그에서 채웁니다(AI 값은 덮어씀). 골든 예시: `fixtures/plans/golden_v2_update.json`(`tests/contract/test_plan_example.py`).
- 실행기가 계획 모양을 한 번 더 검사합니다(1차 관문은 validate_plan): 아무도 열지 않는 신호를 기다리는 step, 같은 트랙의 뒤 신호를 기다리는 step(교착), 로컬이 클라우드 신호를 기다리는 것(W3), 클라우드 상태 변경 step이 `local_verified` 대기 앞에 오는 것(W1), verify 밖이나 신호를 쓰는 `run: finally` step을 거부합니다.
- 툴은 상태를 들고 있지 않습니다. 실행 컨텍스트(`RunContext`: run_id, 어댑터 모드, deploy.yaml, lock_token, cloud_domain, 이미지 digest, 인벤토리·Terraform 출력)는 읽기만 합니다.
- boto3와 Docker 호출은 blocking입니다. 툴을 동기 함수로 두면 실행기가 워커 스레드에서 돌립니다(contextvar 복사됨). Docker는 `subprocess`에 리스트 인자로 호출합니다(`shell=True` 금지, ruff S602).
- 로그는 `ddak.core.logging.JsonLogger`로 stderr에 JSON 한 줄(`ts, level, run_id, component, tool, target, msg`)을 남깁니다. `print`는 쓰지 않습니다(ruff T20).
- 40개 툴 이름은 앱 전체에서 유일합니다(테스트로 강제).

## C-6. AI 경계 강제 (네 겹, 한 프로세스판)

| 겹 | 수단 | 잡는 것 | 한계 |
|---|---|---|---|
| 1 정적 | import-linter 계약 7개(`pyproject.toml`) | 실행 경로·웹에서 AI 관문·LLM SDK import(간접 포함), AI 툴 밖에서 AI 관문 직접 import, 툴 모듈끼리 import | 동적 import는 못 잡음 |
| 2 정적 | ruff TID251 banned-api | `anthropic`, `openai`, Jev SDK(`typesafe`, 이름 확인 필요), `langchain` import(`ddak/core/ai/providers/**`만 예외) | 같음 |
| 3 런타임 | `call_ai`·`ask_jev` 가드: contextvar `current_tool`이 카탈로그의 AI 툴 9개가 아니면 `AI_NOT_ALLOWED` | 허용되지 않은 툴에서 호출 | – |
| 4 구조 | LLM은 툴을 호출하지 않고 제안(JSON, Terraform HCL 초안, Dockerfile 초안)만 돌려준다. JSON은 계획 검증(목록에 없는 step, 필수 step 누락, 허용 안 된 params, domain·host·url·zone 키)을, HCL은 `validate_infra`(init 전 정적 게이트·정책 검사)·`plan_infra`(Access Analyzer)와 **사람 승인**을 통과해야 실행에 반영된다(✅ 장부 21·23, 흐름 💭) | AI가 실행을 바꾸는 경로 | AI HCL은 init·plan만 해도 코드를 실행할 수 있어 정적 게이트가 init보다 먼저다 |
| (물리) | 한 프로세스라 **없음**(LLM 자격과 AWS 자격이 같은 프로세스). 💭 컨테이너 모드에서 웹/실행기 두 컨테이너로 자격증명을 나누는 안. CLI subprocess에는 env 허용목록(`PATH HOME USER LANG`)만 넘김 | – | 발표에서 "프로세스 격리"라고 말하지 않는다 |

import-linter 계약(타입과 키는 import-linter 2.15 소스로 확인, 스크래치에서 실행 확인):

1. **forbidden**: `ddak.ci`, `ddak.cd`, `ddak.executor`, `ddak.ops`, `ddak.web` → `ddak.core.ai`, `anthropic`, `openai`, `typesafe`(`include_external_packages = true`). 설치 전인 외부 패키지는 그래프에 없어서 건너뜁니다.
2. **protected**: `ddak.core.ai`는 AI 툴 9개(`ddak.plan.tools.{analyze_project,generate_plan,generate_dockerfile,patch_db_access,patch_storage,patch_config}.**`, `ddak.infra.tools.generate_infra.**`, `ddak.verify.tools.{diagnose_parity_gap,post_report}.**`)와 `ddak.app`(LLM 상태 함수 주입용)만 import합니다. 와일드카드는 패키지 자신(`__init__.py`)을 빼므로 `__init__.py`에는 로직을 두지 않습니다.
3. **independence**: `ddak.plan`, `ddak.infra`, `ddak.ci`, `ddak.cd`, `ddak.verify`, `ddak.ops`는 서로 import하지 않습니다.
4. **forbidden**: `ddak.core`, `ddak.executor`, `ddak.web` → 툴 모듈 6개 금지(툴 조립은 `ddak.app`만, 동적 import).
5. **forbidden**: `ddak.plan.tools.{validate_plan,validate_dockerfile}.**` → `ddak.core.ai`, `generate_plan`, `generate_dockerfile` 금지(생성기·검사기 분리). 디렉토리가 생기기 전에도 깨지지 않게 와일드카드로 적었습니다.
6. **forbidden**: `ddak.executor` → `ddak.web`, `ddak.app` 금지(웹 → 실행기 방향만).
7. **forbidden**: `ddak.infra.tools.{discover_existing,validate_infra,plan_infra,apply_infra}.**`, `ddak.infra.providers` → `ddak.core.ai`, `generate_infra` 금지(계약 5와 같은 생성기·검사기 분리. `apply_infra`가 같은 infra 모듈로 옮겨 와서 여기서 막음).

테스트(`tests/contract/`): AI 툴 집합이 정확히 9개인지(스냅샷), 인프라 툴 중 AI는 `generate_infra` 하나이고 `apply_infra`는 사람 승인 플래그가 있는지, Dockerfile 툴 중 AI는 `generate_dockerfile` 하나인지, 실행 경로 모듈에 AI 툴이 없는지, 허용되지 않은 툴 문맥에서 call_ai·ask_jev를 부르면 예외가 나는지, AI 툴에서 부를 때 비밀값이 provider에 가기 전에 가려지는지, 운영자 채팅 문장은 untrusted로 감싸지 않는지, CLI 인자에 도구가 모두 꺼져 있고 env 허용목록에 API 키·AWS 키가 없는지. 발표 때 "실행 경로에 AI 없음"을 CI 결과로 보여 줄 수 있습니다.

## C-7. call_ai backend (✅ 장부 7)

| backend | 용도 | 방식 | 코드 |
|---|---|---|---|
| `cli` | 개발(운영자 본인 로컬만) | `claude -p`를 도구 전부 끄고 인자 배열로. 프롬프트는 stdin, 빈 임시 cwd, env 허용목록, 타임아웃 시 프로세스 그룹 종료 | `providers/cli.py`(플래그·결과 키는 CLI 2.1.284 실측 기준, 확인 필요) |
| `api` | 데모(외부 공개 포함) | Anthropic SDK `messages.create` + `output_config.format` json_schema, `max_retries=0`(재시도는 call_ai), refusal이면 `AI_UNAVAILABLE` | `providers/api.py`(anthropic 미설치, O2가 `uv add`) |
| `replay` | 테스트·비상(기본값) | `fixtures/ai_replay/<툴>/<입력 해시>.json`, `source=replay` 라벨 | `providers/replay.py` |
| Jev | ① step 선택·환경 키 분류(규칙이 바닥, Jev는 추가·경고) | 타임아웃 2초·재시도 1회, 실패하면 규칙/Claude 대체 | `providers/jev.py`(호출 미구현, TODO(O2)) |

- 공통 처리는 `gateway.call_ai`가 합니다: 허용 툴 확인 → redact → untrusted_data 감싸기(운영자 채팅 문장은 감싸지 않음) → provider 호출(타임아웃, `AI_UNAVAILABLE`이면 재시도 1회) → pydantic 파싱(실패 `AI_OUTPUT_INVALID`) → `AIResult(value, source, usage)`. backend를 바꿔도 앱 동작이 같습니다.
- 재지시 1회 → 규칙 계획은 호출한 툴(generate_plan 등)이 처리합니다(✅ 장부 5).
- 약관: 구독 CLI는 운영자 본인 로컬 용도만입니다. 외부에 연 관리 페이지, 서버·ECS·컨테이너의 구독 토큰, 웹 Claude 로그인은 금지 패턴입니다. 관리 페이지는 "LLM 연결" 카드(`/api/llm-status`)로 backend와 로그인·키 상태만 보여 줍니다(값·이메일은 가림).

## C-8. 신뢰하지 않는 입력 처리

- 코드·diff·로그·설정은 프롬프트에 **데이터**로만 넣습니다. `call_ai`가 redact 후 `<untrusted_data>` 구분자로 감싸고(데이터 안의 닫는 태그 제거), 그 안의 문장을 지시로 따르지 말라는 시스템 지시를 붙입니다.
- LLM 출력은 항상 pydantic으로 파싱합니다. AI 출력은 enum 중심으로 값·주소·명령을 담을 수 없게 설계합니다.
- 관리 웹은 LLM 출력을 이스케이프한 텍스트로만 렌더링합니다(마크다운 이미지·링크 자동 로드 금지).
- 코드 수정 토글은 기본 OFF입니다(✅ 장부 16). 패치는 코드로 바로 실행하지 않고, 토글 ON일 때도 데모 작업 사본에 적용하고 사람 승인 뒤에만 반영합니다. OFF이면 계획 검증이 patch_* step을 거부합니다.

## C-9. 스키마 스냅샷과 완료 기준(DoD)

- `make contracts`가 하는 일:
  - `contracts/schemas/<tool>.input.json|output.json`, `plan.json`, `events.json`, `deploy_config.json`(모델이 정의된 것만), `tool_catalog.json`을 메모리에서 다시 만듭니다.
  - 커밋된 파일과 비교합니다. 없는 파일, 다른 파일, 남는 파일이 있으면 실패합니다. CI도 같은 검사를 합니다.
- 첫 도입과 계약 변경 PR에서는 `make contracts-update`로 파일을 갱신해 같은 PR에 커밋합니다.
- **툴별 DoD:** `@tool` 등록, Fake 어댑터로 정상 1개·실패 1개 테스트(C-4의 두 실패 유형 중 해당하는 것), 스키마 스냅샷 커밋, `make boundary` 통과. 예시: `tests/unit/test_ping.py`.
- **테스트가 반드시 있어야 하는 영역(작성 순서·TDD 여부는 자유):** validate_plan, 계약 모델·카탈로그, AI 경계, redact, git_guard, 실행기 대기 지점·롤백. 나머지는 스모크 위주입니다.
- 커버리지 수치 게이트는 두지 않습니다.
