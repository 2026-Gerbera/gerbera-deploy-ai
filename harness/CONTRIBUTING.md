# 개발 시작

3일 해커톤 기준으로 협업 규칙을 최소화합니다. 팀원 이메일 수집, 커밋 제목 형식, 브랜치 이름, 필수 PR 승인, main 직접 push 금지를 강제하지 않습니다.

## 로컬 준비

uv >=0.12.20,<0.13과 Python 3.13을 사용합니다.

```sh
make setup-local
make ci
make run-fake
```

Git 저장소에서는 `make setup`으로 로컬 훅을 설치할 수 있습니다. Git의 `user.name`과 `user.email`은 각자 설정하고, 개인정보를 공개하고 싶지 않으면 GitHub noreply 주소를 사용합니다. 팀에 제출하거나 허용목록에 등록할 필요는 없습니다.

## 코드 올리기

하네스는 저장소의 `harness/`에 있습니다. 이 폴더에서 개발 명령을 실행합니다. GitHub 워크플로는 저장소 루트의 `.github/workflows/ci.yml`에 있고 `harness/`를 검사합니다.

- main 직접 push 또는 짧은 브랜치·PR 중 편한 방식을 사용합니다. 공유 파일을 동시에 수정할 때만 담당자끼리 조율합니다.
- 커밋 제목과 브랜치 이름은 자유입니다. 필수 리뷰어·승인 대기는 두지 않습니다.
- CI는 main push와 PR 생성·수정 때 자동 실행됩니다. 일반 브랜치에 push만 하고 PR을 열지 않으면 실행되지 않습니다.
- CI는 코드 품질·테스트, AI 작성자 표시, 비밀키 유출을 검사합니다. Docker 이미지 빌드나 AWS 배포는 하지 않습니다.
- 비밀값을 올리지 않고, AI 공동 작성자·봇 작성자 표시를 넣지 않습니다. 로컬 훅은 AI 트레일러를 제거하고 CI는 남은 표시를 거부합니다.
- 계약 모델 변경 시 `make contracts-update`, 코드 수정 후 `make ci`를 실행합니다. 원격 CI의 실패는 확인하고 고칩니다.

`CODEOWNERS`의 역할은 담당자 참고용입니다. GitHub ID 치환이나 브랜치 보호 설정은 이번 개발을 시작하기 위한 필수 작업이 아닙니다. Git 업로드와 저장소 설정 변경은 사용자가 직접 진행합니다.

실제 배포, 승인 UI, 프로젝트별 툴은 아직 구현 대상입니다. 관리 API가 켜졌다는 사실을 배포 성공으로 해석하지 않습니다.
