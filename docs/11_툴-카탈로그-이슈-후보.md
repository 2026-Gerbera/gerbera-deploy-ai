## 1. 결론 요약

1. **이슈 선택보다 먼저 기본 파이프라인이 끝까지 돌아야 합니다.** 챗봇 요청에서 로컬·클라우드 공개 URL, 데이터 유지까지 한 번에 도는 게 우선입니다. 2025 탈락 사례가 바로 "버튼→배포" 연결을 못 한 팀이었습니다.
2. **점수로는 이슈 하나를 고를 수 없습니다.** 상위 6개가 3.14~3.37로 0.23점 안에 몰려 있어서, 서로 약점을 메우는 **조합**으로 판단했습니다.
3. **고려안 A "고치는 배포" (1순위):** 이식성 패치(I2 업로드 한정 + I1 패치 엔진) + 클라우드 계약 리허설(I5) + 설정 계약(I4).
   - 장점: 주제 문구 "코드를 자동으로 변경하면서"에 정면으로 답하고, 2025 수상 기준(데이터 유지·이중화·실제 서빙)을 라이브로 증명합니다.
4. **고려안 B "증명하는 배포" (2순위):** 변경 맞춤 판별 프로브 + 로컬↔클라우드 교차 비교(I7) + 설정 계약(I4).
   - 장점: 코드를 고치지 않고 클라우드 배포도 1회라 라이브 위험이 낮습니다.
   - 단점: 찾기만 하고 흡수하지는 못해 클라우드 30점 기여가 A보다 약합니다.
5. **결정 게이트(제안): 10/1 정오.** 샘플 변형 10개 중 8개 이상에서 LLM 패치가 20초 안에 테스트를 통과하면 A, 아니면 B로 갑니다. 기본 툴은 두 안이 공유하므로 버려지는 작업이 없습니다.
6. **클라우드 배포 시간 D ≤ 60초 실측이 모든 결정보다 먼저입니다.**

## 2. 기본 툴 카탈로그 (무조건 있어야 하는 것, 25개)

원칙:
- AI는 계획 JSON과 좁은 분류·생성만 맡습니다. 실행은 고정 실행기가 합니다.
- AI는 IaC를 생성하지 않고(Daisy와 겹침 회피), 클라우드 API를 직접 호출하지 않습니다.
- 한 번 빌드한 같은 이미지(digest)를 두 환경에 배포합니다.

| 컴포넌트 | 툴 | 하는 일 (요약) | 데모 초(추정) |
|---|---|---|---|
| 입구 | `receive_deploy_request` | 챗봇 "배포해줘" → 실행 ID·대상 환경·코드 수정 토글 확정 | <1 |
| 입구 | `stream_progress` | 로컬·클라우드 2열 실시간 타임라인(단계별 초, by rule/ai, 캐시·이전 기록 라벨). D를 기다리는 동안 보여줄 화면 | 상시 |
| 공통 | `call_ai` | 모든 Jev·LLM 호출의 관문: 비밀값 마스킹, 타임아웃, 재시도 1회, 규칙 폴백, 토큰·비용 기록 | 0 |
| 공통 | `request_approval` | 대화창 승인 버튼(타임아웃이면 거절, 승인자·시각 기록) | 클릭 2~5 |
| 계획 | `detect_changed_tiers` | tier별 마지막 성공 SHA 대비 git diff + 경로 규칙 → 바뀐 tier, 규칙 기본 계획 | 1~2 |
| 계획 | `generate_plan` | AI가 계획 JSON 생성(허용 툴만, 단계는 추가만) | 3~8 |
| 계획 | `validate_plan` | 스키마·허용 툴·필수 단계·토글 검사. 불합격이면 재지시 1회 후 규칙 계획으로 대체 | <1 |
| 빌드 | `build_image` | 바뀐 tier만 빌드, SHA 태그 + digest 기록, 같은 digest를 두 환경에 사용 | 20~45 + push 5~20 |
| 테스트 | `run_unit_tests` | 빌드한 이미지 안에서 단위 테스트(push와 병렬) | 5~20 (핵심 경로 +0) |
| 테스트 | `run_integration_tests` | `smoke_test`와 같은 스크립트를 일회용 스택(WAS+임시 DB)에서 먼저 실행 | 10~30 (병렬) |
| 배포 | `acquire_deploy_lock` | 환경×tier 잠금 + FIFO 대기열 + TTL (킥오프 예시 "동시 안전 배포") | <1 |
| 배포 | `ensure_infra` | 고정 IaC 모듈로 환경 보장(ALB·80 리스너까지, 2 AZ, desired 2, 최소 권한, 관리형 DB 설정. HTTPS 연결(443·인증서·DNS)은 `ensure_tls`). **데모 핵심 경로에서 제외**(발표 전 점검과 infra 변경 시만) | 데모 중 0 |
| 배포 | `inject_env_config` | 설정·시크릿 **참조**와 APP_VERSION 주입. 필수 키 목록과 이름만 대조(값은 읽지 않음) | 2~5 |
| 배포 | `prepare_db` | DB 도달성·스키마 버전 확인. 조건부 마이그레이션을 택하면 직전 덤프 + 추가형만 | 1~5 |
| 배포 | `deploy_tier` | 계획 순서대로 반영, 안정화 대기. 로컬·클라우드 병렬(느린 쪽이 D). 클라우드는 3~5초 간격 직접 폴링 + 헬스체크·드레이닝 단축 | 로컬 5~10 / 클라우드 40~60 목표 |
| 배포 | `rollback_tier` | 자체 판정으로 실패한 환경·tier만 직전 성공 digest로 복귀(규칙 전용) → 헬스체크 재실행 | 로컬 5~10 / 클라우드 30~60 |
| 검증 | `health_check` | Web 버전 메타 + WAS `/health`(DB 포함) + `X-App-Version`==SHA (유령 배포 방지) | 5~15 |
| 검증 | `smoke_test` | 고정 시나리오(Web 경유 쓰기→읽기, 데이터 유지)를 같은 스크립트로 로컬·클라우드에서 실행. 실패하면 롤백 트리거 | 5~15 |
| 검증 | `watch_post_deploy` | 배포 후 30~60초 5xx·재시작·지연 관찰, 임계 초과 시 롤백 (킥오프 예시 "모니터링") | 백그라운드 |
| 검증 | `collect_diagnostics` | 실패 자료(로그 끝, 종료 코드, 중지 사유, 설정 키 목록) 한 묶음. AI 전달 시 마스킹 | 2~5 |
| 보고 | `record_deploy_log` | 작업 로그(누가·언제·SHA·결과·단계별 초·by rule/ai·AI 호출·토큰·비용), last_success_sha 갱신 | <1 |
| 보고 | `post_report` | 결과 카드(공개 URL 2개, 단계별 초, 건너뛴 단계와 이유, AI 추가 단계, AI 비용). 데모 중 LLM 요약은 끔 | 1~3 |
| 운영 | `preflight_check` | 발표 직전 점검(자격증명, 캐시 예열, 서비스 안정, AI 지연, 업로드 속도) | 카드 5 |
| 운영 | `reset_demo_state` | 리허설마다 기준 상태로 복원(last_success_sha, DB 시드, 리비전, 결함 브랜치) | 무대 밖 |
| 운영 | `cleanup` | 일회용 스택·오래된 이미지 정리, 데모 후 클라우드 중지(비용) | 무대 밖 |

**기본 경로 합계(추정): 약 120~140초.** 강조 이슈에 쓸 수 있는 시간은 약 40~60초입니다.

**조건부·권장 툴**

| 툴 | 언제 |
|---|---|
| `expose_local_url` | 운영진이 로컬 배포에도 공개 접근을 요구할 때 |
| `upload_static` + `invalidate_cdn` | Web을 객체 스토리지 + CDN에 둘 때 (무효화를 빠뜨리면 유령 배포) |

| `estimate_infra_cost` | 권장. 시간당 비용 카드 (2025 수상작 모두 비용 고려로 칭찬) |
| `load_probe` | 권장. "배포 중 요청 오류 0건"을 수치로 |

**하위 후보는 버리지 않고 기본 툴로 흡수합니다.**

- I9 → `prepare_db`의 직전 덤프
- I10 → `acquire_deploy_lock`
- I8 → `validate_plan`의 "DB→WAS→Web 순서" 규칙
- I11 → 컴퓨트를 고른 뒤 옵션으로 검토

## 4. 3분 데모 조합안 (요약)

공통:
- D ≤ 60초
- 발표 전 `reset_demo_state` → `preflight_check`
- 캐시·이전 기록은 화면 라벨과 말로 밝힘
- Orange 대본 구조(상황 선언 → 준비 확인 → 단계 전환 + 내레이션 → 모니터링 → 한 줄 메시지)

**A "고치는 배포"**

| 시각 | 장면 |
|---|---|
| 0:00–0:15 | 사진 업로드 커밋, 토글 ON, "배포해줘" → preflight 카드 |
| 0:15–0:25 | 계획: WAS만 변경 → Jev가 `uploads/` 쓰기를 "영속 데이터"로 분류, AI가 리허설·이식성 스캔 단계 추가 |
| 0:25–0:45 | 로컬 리허설(읽기 전용 + 복제본 2개): A에서 올린 사진이 B에서 404 → **빨간불, 클라우드 차단** ∥ LLM 패치 생성 |
| 0:45–0:58 | 패치 diff + 설정 계약 카드(`S3_BUCKET` 자동 등록) → 승인 |
| 0:58–1:25 | 패치 빌드·테스트, 리허설 재실행 **초록불** |
| 1:25–2:25 | 로컬 배포·시연 ∥ 클라우드 배포(D). 기다리는 동안 신뢰 경계 설명 |
| 2:25–2:45 | 심사위원 휴대폰으로 공개 URL 접속 → 응답 태스크가 바뀌어도 사진 유지. 패치 전후 증거 표 |
| 2:45–3:00 | 관찰 창·작업 로그(AI 비용) → "로컬에서만 되던 코드를 AI가 고치고, 두 환경에서 증명한 뒤 배포했습니다" |

**B "증명하는 배포"**
