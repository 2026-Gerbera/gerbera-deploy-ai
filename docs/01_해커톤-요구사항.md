## 2. 주제

> **One Action, Infinite Clouds.**
> 로컬에서 개발한 웹 애플리케이션을 원터치로 배포. AI를 전적으로 활용해 Google Cloud, AWS 같은 하이퍼스케일러나 온프레미스(로컬) 환경으로 쉽게 배포할 수 있는 시스템.
> "코드를 자동으로 변경하면서 적절하게 인프라 환경까지 구축해 주는 시스템을 만들어 보세요!"

**운영진의 힌트 질문**
- 코드를 어디에 배포해서 동작시키나? (Lambda/Cloud Functions, Fargate/Cloud Run, EC2/GCE)
- 로컬과 클라우드에서 데이터를 어떻게 관리하나?
- 클라우드와 온프레미스의 격차를 어떻게 메우나?
- CI/CD와 어떻게 연동하나? 마이그레이션은 어떻게 하나?
  - 일본어 원문은 "どうマイグレーションする？"로 DB를 특정하지 않습니다.

**"간단한 배포"의 예시** (정답이 아니라 예시)
- 다양한 환경(온프레미스, 각 회사 환경)과 다양한 규모의 앱에 대응
- 대충 만든 앱도 프로덕션 품질 인프라로 배포 (예: SQLite → 적절히 설정된 RDS)
- 모니터링 도입과 시각화
- 배포 관련 작업 로그 기록
- 롤백, 블루그린, 카나리 대응
- 비용 효율: AI 기능 비용에 걸맞은 효과
- 여러 명이 동시에 안전하게 배포

## 2-1. 해석 노트 (2026-09-29, 원문 대조)

- **"로컬"은 두 가지 뜻으로 쓰입니다.**
  - 출발점: 「ローカルで作成した Web アプリケーション」(로컬에서 만든 앱)
  - 배포 대상: 「オンプレ環境（ローカル）へ」(온프레미스=로컬로 배포)
  - 심사 기준 「ローカルとクラウドの両方へのデプロイ」의 "로컬"은 **배포 대상**입니다. 즉 요구는 "로컬을 클라우드로 포팅"이 아니라 **"같은 앱을 로컬(온프레미스)과 클라우드 양쪽에 배포하는 시스템"**입니다.
- **입력:** 「ローカルで動作する」 샘플 웹앱(로컬에서 돌아가는 상태가 전제)을 「アップロードし」(업로드해서) 배포합니다. 입력은 코드나 앱 묶음에 가깝습니다.
- **명시되지 않은 것:**
  - 트리거(버튼 / push / CLI)
  - 초기 조건(첫 배포인지 업데이트인지, 인프라가 이미 있는지)
  - 로컬 배포와 클라우드 배포의 관계(병렬인지 순차인지)
  - → 모두 우리가 설계로 정하면 됩니다.
- **SQLite→RDS는 "간단한 배포"의 예시 하나**입니다(「一例であり、これに限ったものではありません」). 필수는 아니지만 "환경 차이를 시스템이 흡수하는 것"을 좋게 본다는 신호이고, 클라우드 30점 문구(환경 차이 흡수·포터빌리티)와 같은 방향입니다.
- **SQLite→RDS 예시의 범위:** 원문은 "대충 만든 앱도 운영 품질 인프라로 쉽게 배포 — SQLite → 적절히 설정된 RDS" 한 줄뿐입니다(118~122행).
  - 읽을 수 있는 것: 출발점은 로컬 개발에서 SQLite로 만든 앱, 도착점은 **운영급으로 설정된** RDS. 힌트 질문(101행)은 로컬 개발과 클라우드의 데이터 보관을 따로 묻습니다.
  - 명시되지 않은 것: 처음부터 각각 따로 배포하는 방식, 로컬 데이터를 RDS로 옮겨야 하는지, 1회인지 매 배포인지, 로컬(온프레미스) 배포에서도 SQLite를 유지하는지.
- **시사점:** 데모 오프닝에서 "로컬에서 만든 앱을 올리면 로컬(온프레미스)과 클라우드에 배포된다"가 보여야 안전합니다. 로컬 Compose 배포는 "개발용 실행"이 아니라 "온프레미스 배포 대상"으로 설명합니다.

## 3. 제약과 기대

- 클라우드는 자유롭게 선택합니다. 개인 PC나 VM을 온프레미스 배포 대상으로 쓰는 것도 권장합니다.
- AI 도구도 자유입니다.
- **평가 대상은 배포 시스템의 품질입니다. 배포되는 앱의 품질은 평가하지 않습니다.** 샘플 앱은 데모에 필요한 최소 기능이면 충분합니다.
- 기대하는 제작물은 두 가지입니다.
  - ① 로컬에서 동작하는 샘플 웹앱
  - ② 그 앱을 업로드해 클라우드·온프레미스에 배포하는 서비스
- 인프라 비용은 팀당 ₩300,000을 지원합니다. 팀 대표가 최종일 설문의 폼으로 신청하고, 초과분은 자비입니다.
