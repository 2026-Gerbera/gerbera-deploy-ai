# 14. 역할 분담 (💭 초안, 2026-09-30)

> **확정 주제 (✅ 2026-09-30):** "로컬에서 만든 앱을 딸깍 한 번으로 로컬(온프레미스)과 클라우드에 동시에 배포하면서, 환경 차이로 깨지는 부분은 AI가 고치고, 두 환경이 똑같이 동작하는지 교차 검증까지 끝내는 파이프라인"
> 전제: 6명, 클라우드 3명 + 온프레미스 3명. 여기에 공용 모듈(트리거·분석, AI 계획·패치, 실행기, 교차 검증, 관리 페이지)을 부 담당으로 나눕니다.

## 1. 구성 원칙
- 온프레미스(Compose)는 클라우드(Terraform·CodeBuild·ECS·RDS)보다 작업량이 적습니다. 공용 모듈은 어느 환경에도 속하지 않습니다. → **온프레미스 팀이 공용 모듈을 더 많이 맡습니다.**
- 툴은 "툴 하나 + 환경별 어댑터(local / cloud)" 구조입니다. 클라우드·온프레미스 담당이 같은 툴의 서로 다른 구현을 맡습니다.

## 2. 역할표

| 사람 | 소속 | 주 담당 | 부 담당 (공용) | 성공 기준 |
|---|---|---|---|---|
| C1 클라우드 인프라 | 클라우드 | Terraform 전체(VPC·ALB·ECS·RDS·ECR·S3·시크릿 저장소·CodeBuild 프로젝트·IAM), **SSL: Terraform(ALB·대상 그룹·보안 그룹 80/443·80 리스너 `ignore_changes`·허용 호스팅 영역 IAM, RDS TLS), `ensure_tls`(cloud)**, 비용·정리 | 신뢰 경계: IAM 최소 권한(실행기 역할 포함), CodeBuild 위험 옵션 Deny | 클라우드 배포 시간 D ≤ 60초 |
| C2 클라우드 빌드·배포 | 클라우드 | 클라우드 어댑터: CodeBuild(S3 소스, ECR 캐시), ECS 배포·롤백, 시크릿 주입, RDS 스키마·이관(VPC 안 일회성 태스크) | – | 같은 이미지가 ECS에 뜨고 RDS에 연결 |
| C3 클라우드 검증 + 관리 페이지 | 클라우드 | 공개 HTTPS URL 헬스·스모크, **`verify_tls`(cloud) 합격 기준**, 배포 후 관찰(CloudWatch), 실패 자료 수집 | 관리 페이지: 챗봇 "배포해줘", 계획 화면(규칙/AI), 2열 진행 화면, 승인, 결과 카드·AI 비용, **도메인 설정 화면(입력·형식 검증·DNS 방식·검증 CNAME 안내·인증서 상태)** ([15](15_파이프라인-단계별-개발-매핑.md) 5절) | 심사위원이 한 화면에서 흐름을 이해 |
| O1 온프레미스 런타임 + 실행기 | 온프레미스 | 온프레미스 어댑터: Compose 배포·롤백, .env 주입, DB 컨테이너, ECR에서 같은 이미지 받기, **SSL: 로컬 어댑터가 `ensure_tls`·`verify_tls`에 "보류(해당 없음)" 반환·표시**, 로컬 스테이징 게이트 | 실행기: 계획 JSON → 툴 호출, 배포 잠금, 롤백 트리거, 진행 이벤트, 작업 로그, **실행 시작 때 프로젝트 설정 스냅샷 → 실행 컨텍스트 `cloud_domain` 주입** | 계획 JSON 하나로 양쪽 배포가 끝까지 돎 |
| O2 입구·분석 + AI 계획 | 온프레미스 | 트리거·분석: 로컬 디렉토리 / 깃 주소 / zip → 코드 읽기 → tier 구성, 환경변수 추출·분류, SQLite 인지, 로컬 파일 저장·localhost 인지 → `deploy.yaml` 초안 + 분석 결과 | AI 계획·검증: 계획 JSON 생성, 계획 검증 스크립트(`domain`·`host`·`url`·`zone` 키 거부 포함), AI 호출 관문(`call_ai`), Jev 연동 | 새 프로젝트를 넣으면 분석과 계획이 나옴 |
| O3 AI 패치 + 샘플 앱 + 교차 검증 | 온프레미스 | 샘플 앱(로컬 전용 패턴 포함: SQLite raw SQL, 로컬 업로드, localhost 하드코딩, 검색) + AI 이식성 패치(SQLite → 공용 SQL·`DATABASE_URL`, localhost → 환경변수, 업로드 → S3, HTTPS 대응: 클라우드 전용 `ProxyFix`·쿠키 `Secure`(환경 플래그), `http://` 하드코딩) | 교차 검증: 같은 스모크를 두 환경에서 실행·비교, 예상된 차이(스킴·`Secure`·HSTS·DB SSL)는 비교에서 제외, 불일치 원인 분석(Jev + LLM) | 불일치를 잡고 AI 수정 후 양쪽 일치 |
| **테크 리드·문서 총괄** (6명 중 1명 겸임, 정준우 추천) | – | 툴 스키마·계획 JSON 최종 확정, Notion 설계문서·회의록, 3분 데모 대본, 중간보고 | 신뢰 경계 설계(C1과 함께) | 대안·결정 기록이 쌓인 설계문서 |

- 문서·발표는 전원이 자기 담당 부분을 쓰고, 테크 리드가 총괄합니다.
- 테크 리드는 구현 부담이 가벼운 자리와 겸하는 걸 권합니다.

## 3. 주제 → 모듈 매핑

| 주제 문구 | 모듈 | 담당 |
|---|---|---|
| 로컬에서 만든 앱을 | 트리거·분석 (로컬 디렉토리 / 깃 주소 / zip) | O2 |
| 딸깍 한 번으로 | 관리 페이지(챗봇) + 실행기 | C3, O1 |
| 로컬(온프레미스)과 클라우드에 동시에 배포 | 온프레미스 어댑터 + 클라우드 인프라·어댑터 | O1, C1, C2 |
| 환경 차이로 깨지는 부분은 AI가 고치고 | 분석(인지) + AI 계획 + AI 이식성 패치 | O2, O3 |
| 두 환경이 똑같이 동작하는지 교차 검증 | 스모크 + 교차 비교 + 원인 분석 | C3, O3 |

| 약속 | 내용 | 담당 |

| 1. 툴 목록·파라미터 | 공용 툴 이름, 좁은 파라미터(`tier`, `target`), 반환 형식 | 테크 리드 + O1 |

| 4. 어댑터 규약 | 툴 하나당 local / cloud 구현, 입력·출력 동일 | O1 + C2 |
