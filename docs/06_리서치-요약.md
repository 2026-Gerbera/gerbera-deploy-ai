## 3. 실무자 불만 (커뮤니티 정성 조사, 업계 통계 아님)

1. **"한 줄 고쳤는데 확인하려면 커밋하고 몇 분씩 기다린다."** push → 대기 → 실패 → 수정이 반복됩니다. 로컬 실행 도구(act)에서는 되는데 CI에서는 안 되는 경우도 있습니다.
2. **"코드가 문제인지 실행 환경이 문제인지 모르겠다."** OpenStack 지침도 이유 없는 재실행을 피하고 테스트 실패와 환경 실패를 구분하라고 합니다.
3. **"앱 배포는 자동인데 DB까지 바뀌면 사람이 순서를 챙긴다."** 코드를 되돌려도 DB 변경은 남습니다.
4. **"파이프라인은 초록불인데 기능은 안 된다."** 배포 성공과 기능 성공이 어긋납니다.
5. **"불편해도 기존 도구를 계속 쓴다."** 교체 비용이 크기 때문입니다. 기존 파이프라인에 붙여 쓸 수 있어야 유리합니다.

## 4. 이중화·배포 전략 관련 확인 사항

- 이중화·LB·오토스케일링은 보통 **플랫폼(IaC) 층**이 만듭니다(AWS Well-Architected 복원력 공유책임모델).
- 파이프라인은 배포 전략·배포 후 검증·자동 롤백을 맡고, **배포 중 가용성을 깨지 않을** 책임이 있습니다.
  - 한 번에 일부만 교체해 최소 용량 유지
  - 여러 AZ를 동시에 건드리지 않음
  - 오토스케일 대수를 덮어쓰지 않음
- 블루그린·카나리 + 배포 후 검증은 CD의 정석입니다. 롤백을 촉발하는 것은 보통 결정적 규칙(임계값·알람·통계 검정)이고, AI는 원인 분석·권고 중심입니다.
- ECS 내장 블루그린(2025-07), 카나리·리니어(2025-10)가 있습니다. 다만 기본 설정 그대로면 한 사이클이 약 9~13분(외부 실측)이라 데모에서는 설정 튜닝이 필수입니다.

## 5. SoftBank 관련 공개 사실

- 주최는 **SoftBank Corp.**(통신 법인)입니다. "프로덕트 개발팀 주최"는 공개 근거가 없어 **미확인**입니다.
- 인프라 엔지니어 직무 설명이 共通プラットフォーム開発本部(공통 플랫폼 개발본부)의 법인 게이트웨이 채용 공고와 거의 같습니다. 해당 본부가 주관한다는 것은 **추론**입니다.
- 발표에 인용할 수 있는 공개 사실:
  - 통신사의 중대 사고 보고 의무(총무성)
  - 2023-11 고정전화 장애: DB **전환 작업**이 발단
  - 멀티 AI 에이전트 자율 운용 검증(2026-03)
  - 자체 쿠버네티스 플랫폼 CNAP(GitOps, 멀티클라우드 차이 흡수)
- 표현 수위: "통신사급 변경관리를 구현"(✕) → "통신사 운영 원칙에서 착안"(○). 특정 본부를 단정해 언급하지 않습니다.
- 배점표에 "고객사 맞춤" 항목은 없습니다. 맞춤 스토리는 **기능으로 보여야** 점수가 됩니다.
