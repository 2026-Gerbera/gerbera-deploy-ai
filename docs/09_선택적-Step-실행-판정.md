## 1. 판정 요약

| 질문 | 판정 |
|---|---|
| "웹 변경에 WAS급 검증을 돌리는 과잉 실행이 병목"은 실제 개발자 이슈인가? | **조건부로 맞습니다.** 모노레포, 긴 테스트, 재배포 때 다운타임이 생기는 구성에서는 강한 이슈입니다. 소규모 앱, tier별 저장소, 몇 분짜리 파이프라인에서는 약합니다 |
| AI 파이프라인이라면 핵심 기능이어야 하는가? | **넣는 것은 맞지만 "AI라서 핵심"은 아닙니다.** 업계의 표준 해법은 규칙·의존성 그래프·해시입니다. **바닥층**으로 넣는 게 맞습니다 |
| 차별점이 될 수 있는가? | "바뀐 tier만 재배포 / 시간 단축" → **낮음.** "변경의 의미를 보고 단계 추가 + 배포 순서 + 환경 반영까지 판단" → **중(가설)** |

## 2. 근거 요약

**맞다는 근거**
- **3tier에 가장 가까운 직접 사례:** [atama+](https://zenn.dev/atamaplus/articles/79579a242b64d4)는 프론트만 바꿔도 백엔드(Lambda)가 재배포되어 API가 수 분간 멈췄습니다. 경로 필터를 적용한 뒤 프론트 변경은 10분에서 2분으로 줄었습니다. **문제의 핵심은 시간보다 위험 노출이었습니다.**
- **대규모 조직:** Google·Meta·Shopify·Slack·PR TIMES·토스 모두 선택 실행이나 병렬화로 큰 폭을 줄였습니다. 다만 모두 대형 모노레포 사례입니다.

**약하다는 근거**
- **CI 워크플로 시간 중앙값은 2분 43초입니다**(CircleCI 2025, 벤더 데이터). 대부분 이미 권장 기준인 10분 안쪽이고, 문제는 긴 꼬리에 몰려 있습니다.
- **워크플로 단위 경로 필터의 절감액은 저장소당 연 $2.20입니다**(ICSE 2024, 952개 저장소).
- **개발자가 꼽는 CI 1순위 장벽은 느린 빌드가 아니라 실패 원인 디버깅입니다**(Hilton 2017: 실패 디버깅 50/64%, 긴 빌드 38/50%).
- 로컬 Docker Compose는 원래 바뀐 서비스만 다시 만듭니다.

**선택 실행 자체의 위험**
- 비용을 많이 줄일수록 놓치는 실패가 늘어납니다(ICSE 2021).
- 공유 라이브러리가 경로 목록에서 빠져 테스트가 돌지 않았고, 운영 장애로 이어진 사례가 있습니다.

**3tier에서 실제로 장애를 내는 것**
- 과잉 검증보다 **배포 순서와 버전 호환**입니다.
- 근거: [GitLab 다중 버전 호환 문서](https://docs.gitlab.com/development/multi_version_compatibility/)의 실제 사례, Vercel이 Skew Protection을 따로 제품화한 것.

→ 3tier 논거는 **"속도"보다 "불필요한 재배포는 위험 노출이고, 순서가 틀리면 장애가 난다"**로 세우는 편이 강합니다.

## 3. 규칙으로 되는 것 vs AI가 필요한 것

| 변경 유형 | 규칙으로 판별 가능? | AI가 더하는 가치 |
|---|---|---|
| 문서만 | 가능 | 없음 |
| Web(화면·정적) | 가능 | 없음 (단, Web이 호출하는 API가 바뀌었다면 아래 API 행) |
| WAS 로직 | 경로는 가능. API 계약이 정말 안 바뀌었는지는 불가 | 낮음~중 |
| **WAS API 계약** | API 스펙(OpenAPI)이 있으면 가능, 없으면 불가 | **중:** 추가형/파괴형 분류, 영향받는 Web 호출 지점, 배포 순서 제안 |
| **DB 스키마** | 마이그레이션 도구를 알면 린터로 대부분 가능 | **중:** 도구를 모르는 임의 앱에서 확장형/파괴형(expand/contract) 분류와 순서 설명 |
| **환경변수·설정** | 일부만 가능 | **중 (클라우드 30점과 직결):** 어느 tier가 읽는지, 런타임에 읽는지 빌드 시점에 굽는지, 클라우드 시크릿에 빠져 있는지 |
| **의존성 잠금 파일(lockfile)** | 가능 (보수적으로 전체 실행) | 낮음 |
| Dockerfile·IaC | 가능 | 낮음~중 (변경 위험 요약) |

- **경로만으로 판정할 수 없는 칸은 네 개입니다:** API 추가형/파괴형, 마이그레이션 확장형/파괴형, 환경변수를 읽는 tier와 시점, lockfile의 런타임 영향.
- **샘플 앱 선택이 AI의 역할 크기를 정합니다.** API 스펙이나 마이그레이션 도구가 있으면 이 칸들도 결정적 도구로 대체됩니다. Flask·Express처럼 스펙이 기본으로 없는 스택이면 AI의 여지가 커지고, FastAPI처럼 스펙을 자동 생성하면 줄어듭니다(추정).

## 4. tier별 배포 순서

| 변경 | 순서 |
|---|---|
| Web만 / WAS 로직만 | 해당 tier만 |
| API 필드 추가 | WAS → Web |
| API 제거·변경 | Web이 먼저 사용 중단 → WAS |
| 추가형 스키마 | DB → WAS (→ Web) |
| 파괴형 스키마 (컬럼 삭제·이름 변경) | WAS가 먼저 사용 중단 → **다음 릴리스**에 DB |
| 복합 변경 (컬럼 + API 필드 + 화면) | DB → WAS → Web |

순서를 지키는 도구(Argo CD sync wave, Heroku release phase)는 이미 표준입니다. 차별점은 **"변경의 의미를 보고 어떤 순서가 필요한지 판단해 설명하는 것"**이어야 합니다.

## 5. 해커톤 적용 고려안 (💭)

| 고려안 | 내용 | 장점 | 단점 |
|---|---|---|---|
| **A. 바닥층 + 07 문서 안 1·2의 입구** | 규칙 기반 선택 실행을 깔고, AI(1회 호출)가 영향 tier·순서·환경 차이·이식성 위험을 분류해 계획에 단계를 **추가** | AI 호출 한 번이 여러 가치로 이어짐. 클라우드 30점과 연결 | 안 1·2의 구현 부담 |
| **B. 이 기능을 주력으로 재정의** | "변경 의미 기반 tier 순서·환경 반영 계획기". 시간 단축 서사는 쓰지 않음 | 3tier 전제를 가장 잘 활용. 데모 장면이 선명 | 기존 도구·경쟁팀(shift-deploy)과 겹침. LLM이 규칙보다 낫다는 직접 근거 없음 |
| C. 규칙만 | AI 없이 경로·해시로 선택. AI 점수는 다른 기능에서 확보 | 비용·위험이 가장 작음 | AI·독창성 기여 없음 |

**어느 안이든 공통 안전장치**
1. **AI는 단계를 추가만 합니다.** 규칙이 요구한 단계는 뺄 수 없습니다. 조작을 당해도 최악의 결과는 과잉 실행입니다.
2. AI가 실패하거나 시간이 초과되거나 확신도가 낮으면 **전체를 실행**합니다.
3. 변경은 있는데 선택된 단계가 비어 있으면 **전체를 실행**합니다.
4. 비교 기준은 tier별 "마지막으로 배포에 성공한 커밋"입니다.
5. 배포 후 **전 tier 헬스체크·스모크는 항상** 돌립니다. 건너뛴 검증은 배포 후 비동기로 실행합니다.
6. 수동 "전체 실행" 버튼을 둡니다.
7. 판정 로그(규칙 판정, AI 추가 판정, 근거)를 저장합니다.
8. 캐시한 AI 결과를 데모에 쓰면 발표에서 밝힙니다.

**3분 데모 장면 예시 (A·B 공통)**

| 시간 | 장면 |
|---|---|
| 0:00–0:15 | "한 커밋에 DB 컬럼 추가 + API 응답 필드 + 화면 표시 + 새 환경변수" |
| 0:15–0:40 | **계획 화면.** 규칙 판정 옆에 AI 추가 판정 3개: ① 추가형 스키마라 DB 먼저 ② 새 환경변수가 클라우드 시크릿에 없어 반영 단계 추가 ③ 응답 필드 추가는 하위 호환이라 WAS → Web |
| 0:40–2:10 | 로컬·클라우드 병렬 실행. 기다리는 동안 "화면만 바꾼 커밋" 실행 기록을 보여줌(Web만 배포, WAS 재시작 0회, DB 접촉 0회, 건너뛴 단계는 이유와 함께 회색) |
| 2:10–2:40 | 공개 URL에서 새 필드 확인 + 전 tier 스모크 결과 |
| 2:40–3:00 | 한 줄 메시지 + 변경 유형별 사전 측정 표 |

**Q&A 대비**
- "경로 필터로 되지 않나요?" → "됩니다. 그래서 그 부분은 규칙으로 했습니다. AI는 경로로 알 수 없는 네 가지에만 씁니다."
- "몇 초 아꼈나요?" → 측정 표로 정직하게 답합니다. "이 규모에서는 절감이 작습니다. 핵심은 불필요한 WAS 재시작과 DB 접촉을 0으로 만든 것, 그리고 배포 순서입니다."
- "AI가 검증을 빼먹으면요?" → "AI에게는 빼는 권한이 없습니다. 추가만 합니다."

## 7. 남은 확인 사항

1. **실측:** tier별 배포 시간, 전체 재배포 대비 선택 재배포의 차이, 클라우드 배포 시간 D ≤ 약 60초인지
2. **샘플 앱 스택:** API 스펙을 자동 생성하는지, 마이그레이션 도구가 있는지 (AI 역할의 크기를 정함)
3. **저장소 구조:** 모노레포(web/was/db 디렉터리)인지 폴리레포인지
4. **LLM 정확도 자체 측정:** tier를 넘나드는 샘플 커밋 10~20개로 "규칙만"과 "규칙+AI"의 누락·과잉 선택을 비교합니다. AI 10점의 가장 강한 증거가 됩니다
5. **운영진 질문:** 규칙과 AI를 섞은 구조가 AI 10점으로 인정되는가, 캐시한 AI 결과는 목업으로 보는가
