# 07. 2025 수상작 분석과 "AI 에이전트 파이프라인" 판정

> 전문(출처·검증 표 포함): [../research/2026-09-29_2025수상작-분석-AI에이전트-판정.md](../research/2026-09-29_2025수상작-분석-AI에이전트-판정.md)
> 수상 정보는 모두 참가자가 GitHub에 직접 올린 기록입니다. SoftBank·Progate·KOREC의 공식 수상자 발표는 찾지 못했습니다.

## 1. 판정

**"AI 에이전트가 파이프라인을 자동 실행·관리한다"는 그것만으로 주력 차별점이 되지 않습니다.** 2026에는 출발선(바닥층)입니다.

| 근거 | 내용 |
|---|---|
| 같은 Term1 경쟁팀 | [Team Daisy](https://github.com/Softbank-Hackathon-2026-Team-Daisy/daisy)가 거의 같은 구조를 공개했습니다. AI가 Terraform 생성 → 검증 실패 시 AI가 최대 3회 수정 → 승인 → 온프레미스·AWS·GCP 병렬 배포. 9/29 기준 설계만 있고 코드는 없습니다 |
| 2025 예선 | AI 중심작이 최소 7개 있었고, 그중 수상 기록이 있는 작품은 없습니다. 에이전트가 실제로 실행까지 한 사례도 있습니다([Kube Garden](https://github.com/term2-bear/kube-garden-ai): LangGraph Planner→Executor→Verifier, EKS 카나리). 단, 2025에는 AI 배점이 없었으므로 그대로 옮기면 안 됩니다 |
| 상용 시장 | 2026년 1~7월에 GitLab Duo Agent Platform(GA), GitHub Agentic Workflows(프리뷰), AWS DevOps Agent(GA), Azure SRE Agent, Vercel Agent, Terraform MCP 1.0(GA) 등이 나왔습니다 |
| 본질적 문제 | 에이전트는 해결 수단이지 문제 정의가 아닙니다. 2025 본선 최우수 Team Blue가 심사평에서 가장 먼저 칭찬받은 것이 "명확한 문제 정의"였습니다 |

**배점별로 보면 ("에이전트가 파이프라인을 돌린다"만 있을 때)**
- 데모 30: 점수는 실제 배포에서 나옵니다. LLM의 비결정성은 오히려 라이브 실패 위험을 키웁니다.
- 클라우드 30: 누가 오케스트레이션하느냐가 아니라 **무엇을 흡수하느냐**를 봅니다.
- 독창성 10: 낮습니다(Daisy, 2025 사례, 상용 제품과 겹침).
- AI 10: "규칙 몇 줄로 되는 거 아니에요?"에 답할 수 있을 때만 점수가 됩니다. 경쟁팀 spillway는 이 질문을 Q&A 대비로 미리 적어 뒀습니다.

→ **팀이 세운 두 번째 경로로 가야 합니다.** AI 에이전트 기반 파이프라인을 깔고, 그 안에 "AI 없이는 풀기 어려운 이슈"를 문제로 정의해 얹습니다.

**점수로 이어지려면 네 가지 조건이 모두 필요합니다.**
1. AI 없이는 풀 수 없는 판단 지점 하나를 **문제로 정의**한다.
2. AI의 출력을 결정적 검증(빌드·테스트·정책 검사·스모크)으로 닫는다.
3. 로컬과 클라우드에서 3분 안에 안정적으로 뜬다. 폴백과 캐시를 준비한다.
4. 수치를 현장에서 측정해 보여준다.

## 2. 2025 수상작이 실제로 한 것

| 작품 | 단계·수상 | 무엇을 | 핵심 | AI |
|---|---|---|---|---|
| Team Orange | 1차 예선 최우수 | Slack 제어 CI/CD, Blue/Green, 관측 대시보드 | 필요한 Step만 골라 배포 시간 단축, Well-Architected로 설계 설명, 부하 테스트 수치 | 없음 |
| Yoitang Auto Deploy | 2차 예선 최우수 | Git URL만 넣으면 빌드→스캔→k3s 배포→HTTPS 도메인→비용 대시보드 | **이슈 하나가 아니라 기능 전체를 끝까지 만듦.** 심사평은 편의성·이중화·비용·완성도·신뢰 경계 결정(사용자 계정 없는 배포, 비root 빌드)을 칭찬 | 없음 |
| Team Blue | 본선 최우수 | WASM 기반 자체 FaaS | 콜드스타트·격리 문제 정의, 반대 의견과 PoC를 거친 결정, HA·보안·비용 고려 | 제품에는 없음(개발에 Claude Code 등 많이 사용) |
| Team Green (Cutty-X) | 본선 2위 | k3s + Knative FaaS, gVisor 격리 | 개발자 편의 + 운영 효율 번들형 | gpt-4o-mini 코드 점검(선택 기능) |

**팀원 가설("파이프라인을 깔고 그 안의 이슈 하나를 개선")은 부분적으로만 맞습니다.**
- **맞는 부분:** 수상작은 모두 기본 파이프라인을 완성한 뒤 그 위에 무언가를 얹었습니다. 파이프라인 자체를 차별점으로 내세운 수상작은 없습니다.
- **틀린 부분:** "이슈 하나" 구조는 수상 기록이 없는 작품에도 흔했습니다(WhaleRay, Deploy Land, Penguin, Mango). 반대로 2차 예선 최우수 Yoitang과 본선 2위 Green은 여러 기능을 묶은 번들형이었습니다.
- **수상작 공통점(추정):**
  1. 공개 URL과 데이터 유지까지 끝까지 실제로 동작하는 배포
  2. HA·보안(신뢰 경계)·비용을 함께 고려한 흔적
  3. 세부 기능까지 끝까지 만든 완성도
  4. 설계 결정을 설명하는 능력
- 결론: 실제로 이긴 작품은 **완성된 파이프라인 위에 날카로운 결정 몇 개를 얹은 형태**였습니다.

## 3. 2025 → 2026에서 달라진 것

| 항목 | 2025 예선 | 2026 예선 |
|---|---|---|
| 배포 대상 | 클라우드 1곳 (수상작은 전부 AWS 단일) | **로컬 + 클라우드 양쪽** |
| 배점 | 클라우드 30 / 완성도 30 / 재미 10 / 팀 30 / **AI 없음** | 완성도 30 / 클라우드 30 / 팀 20 / 독창성 10 / **AI 10** |
| 클라우드 활용의 의미 | 한 클라우드 안의 확장성·보안·비용 | **환경 간 차이 흡수·포터빌리티** (2025에 선례 없음) |
| 발표 | 슬라이드 사용 흔적 | 슬라이드 금지 |
| 준비 기간 | 킥오프 후 약 8일 | 약 5일 |

**옮길 것**
- 끝까지 실제로 동작하는 배포
- 신뢰 경계 결정 (2026에는 "AI에게 인프라 권한을 어디까지 줄 것인가")
- HA·보안·비용을 고려한 한두 줄
- 대안 → 반대 의견 → PoC → 결정 기록
- 현장에서 측정 가능한 수치만 주장
- "시간이 더 있다면?"에 대한 답 (2025에 실제로 나온 질문)
- 개인별 기여 표시

**옮기면 안 될 것**
- 게이미피케이션 (2026에는 재미 배점 없음)
- AWS 하나만 깊게 파기
- 자체 K8s 구축 (Blue는 여기에 여러 날을 씀)
- 본선 수준의 플랫폼 깊이
- README 과장 (수상작도 코드와 README가 어긋남)

## 4. 에이전트 파이프라인 위에 얹을 "내부 이슈" 고려안 (💭 후보, 결정 아님)

| 안 | 해결하는 이슈 | 규칙이 아닌 AI가 필요한 정도 | 3분 데모 | 겹침 위험 | 4일 난이도 | 주 배점 |
|---|---|---|---|---|---|---|
| **1. 앱 코드 이식성 자동 변경** | 로컬에서 되는 앱이 클라우드에서 깨지는 원인(하드코딩 주소·자격증명, 로컬 파일 저장, 인메모리 세션, 헬스체크 부재)을 코드 수준에서 고침 | 높음 (의미 수준의 수정은 규칙으로 불가) | 중 (AI 결과 캐시 필요) | 낮음~중 (**공개 경쟁작은 이 부분을 사용자 책임으로 넘김**) | 중~상 (지원 패턴 4~5개로 좁혀야) | 클라우드 30, AI 10, 독창성 10. 주제 문구 "코드를 자동으로 변경"에 직접 대응 |
| **2. 배포 후 환경 간 동등성 검증 + AI 진단·수정** | 파이프라인은 성공했는데 로컬과 클라우드의 동작이 다름(타임존, DB 버전, 프록시 헤더, 시크릿 누락 등) | 중~높음 (탐지는 테스트로, 원인 연결·수정은 AI) | 높음 (60~90초) | 중 (차별점은 반드시 "교차 환경 비교"여야 함) | 중 | 데모 30, 클라우드 30, AI 10 |
| 3. 환경별 등가 서비스 매핑 + 선택 근거 | 로컬 Postgres ↔ RDS ↔ Cloud SQL 같은 대응과 근거 | 낮음~중 (매핑은 규칙으로 충분) | 낮음 | 높음 | 중 | 클라우드 30, 팀 20 (설계문서 재료로 적합) |
| 4. AI 인프라 변경의 권한·안전 게이트 | AI가 만드는 과도한 권한·위험 설정 차단 | 중 | 중 (장면 1개) | 높음 | 하~중 | **차별점이 아니라 필수 바닥층** (Q&A에서 거의 확실히 나올 질문, 추정) |
| 5. DB 상태 이식 | 스키마·데이터를 환경 간에 옮김 | 낮음~중 | 낮음 | 중~높음 | 상 | 완성도·클라우드 |
| 6. 변경 영향 분석 기반 증분 재배포 | 바뀐 tier만 재배포해 시간 절약 | 단계 생략은 낮음. 의미 영향·순서·환경 차이 판정은 중 ([09](09_선택적-Step-실행-판정.md)) | 조건부 높음 | 시간 단축 서사는 높음, tier 순서·환경 반영은 중 | 하~중 | 바닥층으로 필요. 재정의하면 데모 30·클라우드 30 ([09](09_선택적-Step-실행-판정.md) 5절) |

**안들 사이의 관계**
- 1과 2는 하나의 루프로 묶입니다: 고치고 → 배포하고 → 비교하고 → 다시 고친다.
- 4는 어느 안을 고르든 필요한 바닥층입니다.
- 3은 설계문서 재료, 6은 데모 시간 확보용 보조 수단으로 가치가 있습니다.
- 5는 3tier라면 최소 수준(쓰기 → 읽기로 데이터 유지)은 필수지만, 주력으로 삼기에는 무겁습니다.

**고를 때 물어볼 네 가지**
1. 클라우드 30점을 어디서 딸 것인가?
2. "AI가 없으면 여기서 막힌다"를 한 문장으로 말할 수 있는가?
3. 그 장면이 3분 안에 화면으로 보이는가?
4. 샘플 앱 하나로 4일 안에 끝까지 완성할 수 있는가?

## 5. 운영진·멘토에게 추가로 물을 것

1. 로컬 배포의 "공개 접근"은 어떤 방식까지 인정하나? (터널 서비스, 현장 inbound 접속 가능 여부)
2. 클라우드는 1곳으로 충분한가, 2곳 이상이면 가점이 있나? 계정은 누가 주나?
3. AI 활용 10점은 제품 안의 AI만 보나, 개발 과정의 AI 활용도 포함하나?
4. 사전 프로비저닝이 허용되나? 캐시해 둔 AI 결과를 재사용하면 목업으로 보나?
5. 배포 대상 웹앱은 팀이 준비하나, 운영진이 주나?
6. 현장에서 외부 LLM API를 호출할 수 있나?
7. 공식 MCP 서버나 관리형 에이전트를 가져다 쓰면 어떻게 평가하나?
