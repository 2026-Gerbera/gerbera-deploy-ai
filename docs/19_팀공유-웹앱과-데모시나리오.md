# 19. 팀 공유: 데모 웹앱과 시나리오 (2026-09-30)

> 채팅방에 그대로 붙일 수 있는 공유문입니다. 상세 설계는 `single-app/docs/`(작성·검토 중)에 있습니다.

---

**[공유] 데모 웹앱과 시나리오 + 어제 논의 정리**

**1. 데모 웹앱: flaskr (Flask 공식 튜토리얼)**
- 원본: https://github.com/pallets/flask/tree/main/examples/tutorial (BSD-3, 저작권 고지 유지)
- 게시판 + 회원가입/로그인이 있는 작은 Flask 앱입니다. 원래는 SQLite를 `sqlite3`로 직접 씁니다.
- 구성: nginx(web) + Flask(was) + MySQL(db)
- 담당: 장민영(O3)

**2. v1 / v2**
- **v1 = 초기 코드.** 로그인 기능이 아예 없는 익명 게시판입니다. 데모 전에 온프렘·클라우드 양쪽에 이미 배포되어 있어야 합니다. 이 배포도 우리 파이프라인의 초기 배포로 합니다.
  - DB 접근은 SQLAlchemy(`DATABASE_URL`)로 바꿔서 개발은 SQLite, 배포는 MySQL로 동작하게 합니다.
  - **로그인이 없으니 `SECRET_KEY`도 없어야 합니다.** 원본은 `flash()` 메시지 때문에 세션을 쓰므로 v1에서 `flash()`·세션 사용을 빼야 합니다.
- **v2 = 로그인 페이지 추가.** 개발자가 로컬에서 로그인 기능을 붙인 상태입니다. 라이브 데모는 이 v2를 딸깍 한 번으로 배포하는 장면입니다.
  - 로그인 화면은 WAS 템플릿(nginx 설정 변경 없음)
  - `users` 테이블 추가(추가형 마이그레이션), 글 작성자는 NULL 허용, 목록은 LEFT JOIN
  - 세션 서명용 `SECRET_KEY`가 새로 필요해짐. 개발 코드에는 `'dev'`로 하드코딩되어 있음

**3. 라이브 데모에서 보여줄 것**
- 로컬·클라우드 배포를 동시에 시작해 병렬로 진행하고, 로컬 검증이 필요한 지점(클라우드 DB 마이그레이션·배포)에서만 대기합니다.
- **환경별 설정 변환:** 개발 환경에 일부러 둔 개발용 값이 배포 환경에 맞게 바뀝니다.

| 키 | 개발 PC | 온프렘 | 클라우드 |
|---|---|---|---|
| `DATABASE_URL` | `sqlite:///...` | 온프렘 DB 서버 IP의 MySQL | RDS MySQL (TLS) |
| `APP_BASE_URL` | `http://localhost:5000` | 온프렘 web 주소 | `https://<관리 페이지에 입력한 도메인>` |
| `SECRET_KEY` | `'dev'` 하드코딩 | 시스템 난수 → `.env` | 시스템 난수 → **Secrets Manager 새 시크릿** |
| 쿠키 `Secure`·ProxyFix | 끔 | 끔(http) | 켬(HTTPS) |

- **Secrets Manager 생성 장면 (AI Terraform + 승인):**
  1. 분석이 v2 diff에서 새 키 `SECRET_KEY`와 하드코딩된 `'dev'`를 찾습니다. AI(Jev)가 "비밀값"으로 분류합니다.
  2. AI가 Terraform 앱 층에 **시크릿 리소스 + 실행 역할 읽기 권한**을 추가하는 수정안을 만듭니다.
  3. plan 요약("+ 시크릿 1, IAM 정책 1 변경, 삭제 0")을 보고 사람이 "배포"를 승인하면 apply합니다.
  4. 파이프라인 코드가 난수를 만들어 시크릿에 값을 넣습니다. 온프렘은 같은 방식으로 난수를 `.env`에 넣습니다.
  5. 태스크 정의에 시크릿 ARN(Terraform 출력)을 연결하고 ECS를 배포한 뒤, 두 환경에서 로그인과 세션 유지를 확인합니다.
- Terraform이 시크릿을 관리하므로 존재를 인지하고(드리프트 탐지, 정리, 재현 가능), 권한 변경도 같은 plan에서 승인됩니다.
- **값은 Terraform state·AI·화면에 남지 않습니다.** Terraform은 시크릿 틀과 IAM만 관리하고 값은 코드가 넣습니다(대안: write-only 인자, 확인 중).
- state는 플랫폼 층과 앱 층으로 나눠 앱 층 plan을 짧게 합니다. 시간은 리허설에서 잽니다.
- 마지막에 두 환경의 동작을 교차 검증합니다: 로그인 페이지, 틀린 비밀번호, 로그인 후 글쓰기, `users` 테이블, 배포 버전.

**4. 어제 논의 정리 (답변 감사합니다)**
- ✅ **앱 1개 + 툴 레지스트리.** LLM은 JSON(의도·계획)만 반환하고, 검증 후 미리 짠 코드를 실행합니다(준석·서윤 동의).
- ✅ **CD는 공통 인터페이스 + provider 모듈**(서윤 안). 공통 설정값은 Helm처럼 공유합니다(준석 안).
  - 구현: `aws.py` + `onprem.py`. GCP·Azure는 후순위라 인터페이스만 둡니다.
  - 인터페이스: deploy, rollback, health_check + DB 마이그레이션, 설정·시크릿 주입, HTTPS(클라우드만)
- ✅ **CSP:** AWS 1순위, 나머지는 후순위
- ✅ **이미지 저장소:** Docker Hub 기본(클라우드 의존 감소), ECR은 옵션
- ✅ **테스트 step:** 제외
- ✅ **Dockerfile:** 없으면 AI가 생성합니다. 흐름은 검사 + 실제 빌드 확인 → 사람 승인입니다.
- ✅ **Terraform도 AI가 작성**(플랫폼까지). 흐름은 AI 작성 → 검증·정책 검사 → plan 요약 → 사람 승인 → apply이고, 자동 apply는 없습니다.
  - IAM은 AI 설계 → 사람 승인 → 생성합니다. 권한 경계를 붙여서 설계가 과해도 실제 권한이 경계를 넘지 못합니다.
- ✅ **LLM이 정하는 값은 초기 배포 때만.** 이후 개선 배포는 초기 배포 때 기록한 환경 정보(Terraform 출력, 온프렘 인벤토리, 관리 페이지 설정)를 코드가 읽어서 씁니다.
- 💭 **Slack 연동(제안):** P0는 Webhook으로 진행·결과 알림, P1은 Slack 앱(Socket Mode)으로 채팅·승인 버튼. 담당은 정해야 합니다.
- ⏸ **기존 레거시 시스템 편입:** 후순위입니다. 확장 경로만 설계해 둡니다.

**5. 역할별로 관련된 부분**
- 장민영(O3): v1 준비(SQLAlchemy 전환, `flash()`·세션 제거), v2 로그인 diff 작성
- 김준석(O2): 분석에서 새 설정 키 탐지·비밀값 분류, 계획에 시크릿 step 추가
- 안승환(C2): 시크릿 값 저장(난수, `sync_env_to_cloud`), 태스크 정의에 시크릿 ARN 연결
- 유상준(C1): AI Terraform 앱 층(시크릿 리소스·IAM 추가 → plan 요약 → 승인 → apply), state 층 분리, 권한 경계
- 정준우(O1): 온프렘 `.env` 주입, 실행기 대기 지점
- 양서윤(C3): 관리 페이지의 계획 승인 화면과 "환경별 설정 변환" 표(비밀값 가림)

역할별 상세 개발 문서는 설계 검토를 마친 뒤 따로 공유하겠습니다.
