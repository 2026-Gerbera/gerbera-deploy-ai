# CodeBuild를 MCP 툴로 감쌀 때의 사실 검증 (2026-09-29)

## [codebuild-api] [confirmed] [1] StartBuild API에 sourceVersion, environmentVariablesOverride, buildspecOverride, imageOverride, privilegedModeOverride, serviceRoleOverride, computeTypeOverride 같은 재정의(override) 파라미터가 실제로 있는가?
7개 모두 실재합니다. 공식 StartBuild 레퍼런스(2026-09-29 조회)의 요청 파라미터: projectName(필수), sourceVersion, environmentVariablesOverride(name/type/value 배열), buildspecOverride, imageOverride, privilegedModeOverride, serviceRoleOverride, computeTypeOverride(BUILD_GENERAL1_* / BUILD_LAMBDA_* / ATTRIBUTE_BASED_COMPUTE / CUSTOM_INSTANCE_TYPE). 그 밖에도 environmentTypeOverride, cacheOverride, fleetOverride, timeoutInMinutesOverride(5~2160), queuedTimeoutInMinutesOverride(5~480), sourceLocationOverride, sourceTypeOverride, sourceAuthOverride, artifactsOverride, logsConfigOverride, hostKernelOverride, imagePullCredentialsTypeOverride, registryCredentialOverride, encryptionKeyOverride, gitCloneDepthOverride, debugSessionEnabled, autoRetryLimitOverride, secondarySources*Override, idempotencyToken(유효 5분) 등이 있습니다. 오버라이드는 해당 빌드 1회에만 적용되고 프로젝트 설정은 바뀌지 않습니다. sourceVersion 형식은 GitHub이면 커밋ID/브랜치/태그/PR(pr/25), S3이면 객체 버전 ID입니다. boto3에도 client.start_build로 동일 파라미터가 노출되어 있습니다(boto3 문서 확인). 설계 시사점: 이 목록 전체가 'LLM이 채울 수 있는 표면'이 되므로 MCP 툴 스키마에는 필요한 것만 노출해야 합니다(항목 2, 3 참고).
SRC: https://docs.aws.amazon.com/codebuild/latest/APIReference/API_StartBuild.html, https://docs.aws.amazon.com/boto3/latest/reference/services/codebuild/client/start_build.html

## [codebuild-api] [confirmed] [1-보안] buildspecOverride로 임의 명령 실행이 가능한가?
가능합니다. buildspecOverride는 인라인 buildspec 본문, 소스 내 대체 buildspec 경로, 또는 S3 ARN을 받고, 프로젝트에 정의된 buildspec을 그 빌드에 한해 대체합니다. AWS 공식 문서 스스로 이 속성이 컨테이너에서 실행될 빌드 명령을 바꿀 수 있으므로, StartBuild 호출과 이 파라미터 설정 권한이 있는 IAM 주체는 기본 설정을 덮어쓸 수 있다고 경고하고, 소스 저장소 파일이나 S3 같은 신뢰 가능한 위치를 쓰거나 조건 키로 override를 막으라고 권고합니다. 빌드 컨테이너는 프로젝트 서비스 역할 자격증명으로 동작합니다(트러블슈팅 문서에 컨테이너 안에서 AWS_CONTAINER_CREDENTIALS_RELATIVE_URI로 자격증명을 받는다는 예시가 있음). 따라서 LLM이 buildspecOverride에 인라인 YAML을 넣을 수 있으면 곧 서비스 역할 권한으로 임의 셸 명령을 실행하는 것과 같습니다(이 부분은 문서 내용에서 제가 추론한 결론). 같은 맥락에서 privilegedModeOverride(컨테이너가 모든 디바이스 접근), imageOverride(임의 이미지 실행), serviceRoleOverride(다른 역할로 실행), environmentVariablesOverride(type에 PARAMETER_STORE/SECRETS_MANAGER 지정 가능, Terraform 문서 기준)도 위험 표면입니다. 또 sourceVersion은 임의 브랜치/커밋의 buildspec.yml과 Dockerfile을 실행하게 만드는 간접 경로입니다. 권장: MCP 툴 스키마에서 위 override들을 아예 제외하고, sourceVersion은 정규식/허용 목록으로 검증하며, IAM에서도 Deny를 겁니다.
SRC: https://docs.aws.amazon.com/codebuild/latest/APIReference/API_StartBuild.html, https://docs.aws.amazon.com/codebuild/latest/userguide/action-context-keys.html, https://docs.aws.amazon.com/codebuild/latest/userguide/troubleshooting.html, https://docs.aws.amazon.com/codebuild/latest/userguide/caching-local.html

## [codebuild-api] [partially] [1-보안2] IAM 정책으로 StartBuild의 override를 제한할 수 있는가?
대부분 가능하지만 전부는 아닙니다. 공식 문서 예제: Deny StartBuild + Condition Null {codebuild:source.buildspec: false} 로 buildspecOverride 사용을 통째로 차단할 수 있습니다. 단, 이 키는 Null 연산자만 지원하며 buildspec 내용은 평가하지 못한다고 명시되어 있습니다. AWS 공식 Service Reference JSON(codebuild.json)의 StartBuild 조건 키에는 codebuild:source.buildspec, source.location, environment.image, environment.privilegedMode, environment.computeType, environment.imagePullCredentialsType, environment.fleet.fleetArn, environment.environmentVariables(.name/.value, /NAME.value), serviceRole, cache.type/modes/location, artifacts.*, logsConfig.s3Logs.* 등이 있어(총 64개) image/privileged/serviceRole/env var/cache 오버라이드도 Null 또는 값 조건으로 막을 수 있습니다. 반면 같은 목록에서 sourceVersion, timeout(build/queued), debugSessionEnabled, hostKernel에 해당하는 키는 확인되지 않았습니다. 그래서 이들은 IAM이 아니라 툴 코드(파라미터 검증)에서 통제해야 합니다. 참고: AWS Service Authorization Reference 웹 페이지는 동적 렌더링이라 직접 파싱이 안 되어, 같은 데이터의 공식 JSON 배포본을 사용했습니다.
SRC: https://docs.aws.amazon.com/codebuild/latest/userguide/action-context-keys.html, https://servicereference.us-east-1.amazonaws.com/v1/codebuild/codebuild.json, https://docs.aws.amazon.com/service-authorization/latest/reference/list_awscodebuild.html

## [codebuild-api] [confirmed] [2] 빌드 상태·로그 조회: BatchGetBuilds의 phases(PROVISIONING, DOWNLOAD_SOURCE, BUILD 등)와 CloudWatch Logs 연동이 실제로 되는가?
BatchGetBuilds는 ids(1~100개)를 받아 builds[]와 buildsNotFound[]를 반환합니다. 각 Build에는 buildStatus(SUCCEEDED|FAILED|FAULT|TIMED_OUT|IN_PROGRESS|STOPPED), buildComplete(bool), currentPhase, phases[], logs, startTime/endTime 등이 있습니다. phases[] 각 항목은 phaseType, phaseStatus, startTime, endTime, durationInSeconds, contexts(실패 원인 메시지)를 가지며 phaseType 값은 SUBMITTED | QUEUED | PROVISIONING | DOWNLOAD_SOURCE | INSTALL | PRE_BUILD | BUILD | POST_BUILD | UPLOAD_ARTIFACTS | FINALIZING | COMPLETED 입니다(질문에 든 3개 모두 포함). 로그: Build.logs(LogsLocation)에 groupName, streamName, deepLink, cloudWatchLogsArn(및 S3 로그 사용 시 s3DeepLink/s3LogsArn)이 들어오며, CloudWatch 로그 스트림은 PROVISIONING 단계에서 생성되어 그 전에는 deepLink/ARN이 유효하지 않습니다. 공식 알림 예제 JSON에는 로그 그룹이 /aws/codebuild/<프로젝트명>, 스트림명이 빌드 UUID 형태로 나옵니다(프로젝트 logsConfig로 그룹/스트림 접두어 지정도 가능). 툴 구현 시 흐름: start_build -> batch_get_builds 폴링(또는 EventBridge의 'CodeBuild Build State Change'/'CodeBuild Build Phase Change' 이벤트) -> 로그가 필요하면 반환된 groupName/streamName으로 CloudWatch Logs를 읽기(이 마지막 조회 방식은 표준 CloudWatch Logs API 사용을 제안하는 것으로, 이 조사에서 별도 문서 검증은 하지 않음).
SRC: https://docs.aws.amazon.com/codebuild/latest/APIReference/API_BatchGetBuilds.html, https://docs.aws.amazon.com/codebuild/latest/APIReference/API_Build.html, https://docs.aws.amazon.com/codebuild/latest/APIReference/API_BuildPhase.html, https://docs.aws.amazon.com/codebuild/latest/APIReference/API_LogsLocation.html

## [codebuild-api] [confirmed] [3] CodeBuild 프로젝트를 Terraform(aws_codebuild_project)·CloudFormation으로 완전히 정의할 수 있는가? (소스, 환경 이미지, privileged mode, 서비스 역할, 캐시)
네, 질문의 5개 항목 모두 IaC로 정의됩니다. Terraform aws_codebuild_project: source{type,location,buildspec,git_clone_depth}, environment{image,type,compute_type,privileged_mode,image_pull_credentials_type,fleet{fleet_arn},docker_server,environment_variable}, service_role(필수), cache{type(NO_CACHE|LOCAL|S3),modes,location,cache_namespace}, logs_config, vpc_config, build_timeout, queued_timeout, concurrent_build_limit, source_version 등. CloudFormation AWS::CodeBuild::Project도 Source, Environment(Image, PrivilegedMode, ComputeType, Fleet, DockerServer...), ServiceRole, Cache(Type, Modes, Location, CacheNamespace), LogsConfig, VpcConfig, ConcurrentBuildLimit 등을 지원하고, 예약 용량 fleet은 aws_codebuild_fleet / AWS::CodeBuild::Fleet로 정의합니다. 따라서 '콘솔로 설정하는 게 코드로는 힘들다'는 전제는 성립하지 않습니다(반박). 주의할 점 3가지: (a) GitHub을 CodeConnections로 연결하면 aws_codestarconnections_connection이 PENDING으로 생성되어 최초 인증은 콘솔에서 사람이 완료해야 합니다(Terraform 문서 명시). PAT 방식은 aws_codebuild_source_credential로 코드화되지만 토큰 시크릿 관리가 필요합니다. (b) Terraform 문서의 LOCAL_DOCKER_LAYER_CACHE 예제는 privileged_mode를 설정하지 않지만, AWS 문서는 Docker 레이어 캐시에 privileged 플래그가 필수라고 하므로 직접 true로 지정해야 합니다. (c) 'StartBuild(빌드 실행)'는 리소스가 아니라 런타임 API이므로 IaC가 아닌 boto3 호출 대상입니다.
SRC: https://registry.terraform.io/providers/hashicorp/aws/latest/docs/resources/codebuild_project, https://registry.terraform.io/providers/hashicorp/aws/latest/docs/resources/codebuild_fleet, https://registry.terraform.io/providers/hashicorp/aws/latest/docs/resources/codestarconnections_connection, https://registry.terraform.io/providers/hashicorp/aws/latest/docs/resources/codebuild_source_credential

## [codebuild-api] [partially] [4a] 로컬 캐시 모드(LOCAL_DOCKER_LAYER_CACHE 등)는 같은 호스트일 때만 적중하는 best-effort인가? 한계는?
'같은 호스트에서만 사용 가능'은 공식 문서로 확인됩니다. 로컬 캐시는 빌드 호스트에 저장되며 해당 호스트에서만 쓸 수 있고, 빌드가 드문 경우에는 좋은 선택이 아니라고 문서가 밝힙니다. 반면 'best-effort'라는 표현은 공식 사용자 가이드가 아니라 AWS DevOps 블로그(로컬 캐시는 호스트에서 best effort로 유지되어 적중이 자주 안 될 수 있음)에 나옵니다. 커뮤니티 정리(OneUptime, 2026-02)도 자주 빌드하면 같은 호스트가 재사용되어 잘 맞고, 다른 호스트에 배정되면 miss라고 설명합니다. 즉 적중 보장은 없다고 봐야 하며, 이 조사에서 적중률의 정량 수치는 찾지 못했습니다. 문서상 한계: Docker 레이어 캐시는 Linux 환경 전용, privileged 필수(모든 디바이스 접근 권한 부여, 보안 영향 검토 필요), LINUX_GPU_CONTAINER와 BUILD_GENERAL1_2XLARGE에서는 로컬 캐시 미지원, VPC 구성 시 로컬 캐시 미지원(caching-local 페이지의 노트), Lambda 컴퓨트는 캐시 자체를 지원하지 않음. 예약 용량 fleet에서는 문서가 Docker 레이어 캐시를 권장하고, fleet 인스턴스에 캐시된 소스/도커 레이어가 같은 계정의 다른 프로젝트에서도 접근 가능하다고 경고합니다(프로젝트 간 격리 없음).
SRC: https://docs.aws.amazon.com/codebuild/latest/userguide/caching-local.html, https://docs.aws.amazon.com/codebuild/latest/APIReference/API_ProjectCache.html, https://aws.amazon.com/blogs/devops/reducing-docker-image-build-time-on-aws-codebuild-using-an-external-cache, https://aws.amazon.com/blogs/devops/reduce-docker-image-build-time-on-aws-codebuild-using-amazon-ecr-as-a-remote-cache

## [codebuild-api] [confirmed] [4b] S3 캐시와 buildx 레지스트리 캐시(ECR)를 도커 이미지 빌드 캐시로 쓸 수 있는가?
S3 캐시: 사용 가능하지만 용도가 다릅니다. 여러 빌드 호스트가 공유하는 캐시이고 buildspec의 cache.paths(디렉터리/파일 glob)를 저장하며, 중소 규모 산출물(의존성 등)에 적합하다고 문서가 설명합니다. Docker 레이어 캐시 모드(LOCAL_DOCKER_LAYER_CACHE)는 API 문서상 LOCAL 타입에서만 쓰이는 modes 값이므로, S3 캐시로 도커 레이어를 네이티브하게 캐시하는 옵션은 없습니다(문서에서 제가 추론한 결론). buildx 레지스트리 캐시(ECR): 가능합니다. Amazon ECR은 2023-10-24 발표로 BuildKit 0.12+ 클라이언트의 원격 캐시(OCI 캐시 매니페스트)를 지원하고, 권장 플래그는 --cache-to type=registry,ref=<ECR URI>,mode=max,image-manifest=true,oci-mediatypes=true 및 --cache-from type=registry,ref=<ECR URI> 입니다. CodeBuild에서의 적용은 AWS DevOps 블로그(2025-10-03)가 다루며, 기본 docker 드라이버만으로는 부족해 docker-container 드라이버(또는 containerd 이미지 스토어 활성화)를 만들어야 한다고 설명합니다. 그 글의 예시는 캐시 없이 약 10분, Dockerfile 소폭 수정 후 약 6분(최대 25% 단축 주장)이며, 구형 블로그의 --cache-from 이미지 pull 방식 예시는 약 39분에서 약 6분입니다(둘 다 특정 조건의 예시). 이 방식은 로컬 캐시와 달리 호스트가 달라도 적중하므로 온디맨드(임시 호스트)에 적합하지만, 캐시 pull/push 네트워크 비용이 듭니다. 또한 docker 빌드 자체에 도커 데몬이 필요하므로 일반 온디맨드에서는 privileged 모드가 필요합니다(트러블슈팅 문서: privileged가 아니면 Cannot connect to the Docker daemon).
SRC: https://docs.aws.amazon.com/codebuild/latest/userguide/caching-s3.html, https://docs.aws.amazon.com/codebuild/latest/APIReference/API_ProjectCache.html, https://aws.amazon.com/blogs/containers/announcing-remote-cache-support-in-amazon-ecr-for-buildkit-clients/, https://aws.amazon.com/blogs/devops/reduce-docker-image-build-time-on-aws-codebuild-using-amazon-ecr-as-a-remote-cache

## [codebuild-api] [confirmed] [4c-보너스] CodeBuild의 Docker Server(원격 도커 서버) 기능으로 지속 캐시를 얻을 수 있는가?
네. 2025-05 발표된 기능으로, 프로젝트에 전용·지속형 Docker 서버를 두어 레이어 캐시를 빌드 간 공유하고 동시 빌드도 같은 캐시를 씁니다. 공식 샘플 문서: 프로비저닝된 인스턴스는 빌드가 돌 때 활성 상태이고 빌드가 없으면 중지되며, 최대 한 달간 보관 후 재생성됩니다. 보안 그룹은 프로젝트에 설정된 VPC로부터 포트 9876 ingress를 허용해야 합니다(VPC 구성 전제). AWS 블로그는 x86 Linux 전용(ARM 미지원)이라고 하고, 예시 벤치마크는 24분 54초에서 16초(코드 변경 없는 재빌드, 최선 사례)입니다. IaC: Terraform environment.docker_server{compute_type, security_group_ids}, CloudFormation Environment.DockerServer. 추가 비용이 있으므로 가격 페이지 확인이 필요합니다(이번 조사에서 금액은 확인하지 못함).

## [codebuild-api] [partially] [5a] 온디맨드 빌드의 시작 대기(PROVISIONING) 시간은 보통 얼마인가? (공식 수치가 없으면 커뮤니티 실측)
공식 SLA/전형적 수치는 찾지 못했습니다(확인 결과 '없음'). 공식 문서가 말하는 것은 (1) 지원되는 최신 curated 이미지는 머신 AMI에 캐싱되어 프로비저닝이 최적화되므로 'Always use the latest image'를 쓰라는 것, (2) 로그 스트림이 PROVISIONING 중 생성된다는 것입니다. 공식 알림 포맷 예제 JSON에 PROVISIONING 36초가 나오지만 2017년 날짜의 예시 데이터라 실측으로 보기 어렵습니다. 커뮤니티 보고(조건 편차 큼): aws-cdk 이슈 #23096은 구형 aws/codebuild/standard:1.0에서 약 166초, STANDARD_4_0으로 바꾸자 30초 미만; aws-codebuild-docker-images 이슈 #296은 AL2 standard:1.0에서 3~5분(AWS 지원이 내부 변경 때문이라고 답변, 이미지 지원 중단 예정); 이슈 #526은 회당 90초 초과; 일본어 블로그(tsukaby)는 181초에서 튜닝 후 40~80초, 다른 프로젝트는 10초 미만이었고 Amazon Linux를 Ubuntu 이미지로 바꾸자 크게 개선; dev.to 사례는 커스텀 이미지를 ECR에 두어 프로비저닝 최대 1분 단축. 정리하면 최신 curated 이미지의 온디맨드는 대략 수십 초, 구형/큰 커스텀 이미지·환경에 따라 1.5~5분까지 관측됩니다(개별 사례이며 통계가 아님). ## [mcp-params] [confirmed] 2. 도구 입력 JSON Schema(inputSchema)로 enum·pattern 같은 제약을 걸 수 있는가?
inputSchema는 JSON Schema 객체입니다. $schema가 없으면 2020-12가 기본이고, 구현체는 2020-12를 반드시 지원해야 합니다(MUST). enum과 pattern은 2020-12의 표준 키워드라서 그대로 쓸 수 있습니다. 다만 사양이 enum/pattern을 직접 예시로 들지는 않습니다. tools 페이지 예시는 type, properties, required, additionalProperties 정도이고, basic 페이지 예시에 minimum이 나옵니다. 그래서 '쓸 수 있다'는 것은 JSON Schema 표준에서 나온 추론입니다. 파라미터가 없는 도구는 {type: object, additionalProperties: false}를 권장합니다. ToolAnnotations(readOnlyHint, destructiveHint 등)는 힌트일 뿐이고 신뢰하지 말라고 사양이 명시합니다. 이 값으로 권한을 통제하면 안 됩니다.

## [mcp-params] [refuted] 3. 스키마 제약(enum·pattern)만 걸어두면 LLM이 알아서 지키므로 충분한가?
충분하지 않습니다. MCP 사양은 서버가 모든 도구 입력을 검증해야 하고(MUST), 접근 제어와 rate limit을 구현하며 출력도 sanitize해야 한다고 규정합니다. 클라이언트는 민감한 작업에서 사용자 확인을 받고 도구 입력을 사용자에게 보여줘야 합니다(SHOULD). 입력 검증 실패는 isError:true인 tool execution error로 돌려주고, LLM이 그걸 보고 스스로 고쳐 재시도하도록 설계돼 있습니다. LLM 쪽 강제력은 사업자마다 다릅니다. Anthropic API 문서에 따르면 기본 모드에서는 타입 불일치나 필수 필드 누락이 생길 수 있습니다. strict:true를 켜면 grammar-constrained sampling으로 스키마 준수를 보장합니다. 하지만 지원 범위는 enum/const까지이고, pattern, minLength, maxLength, minimum, maximum은 미지원입니다. SDK가 이 제약들을 스키마에서 빼고 설명문에 덧붙인 뒤 로컬에서 검증합니다. 따라서 enum은 모델 측에서도 강제할 수 있어도 pattern은 서버 검증이 필수입니다. enum 안의 값 중 무엇을 고를지는 여전히 모델이 정하므로, 프롬프트 인젝션으로 다른 유효 값이 선택될 수 있습니다. 이는 Anthropic API 사양이며 다른 LLM이나 클라이언트는 다를 수 있습니다.

## [mcp-params] [confirmed] 7. 범용 서버(aws-api-mcp-server, 매니지드 AWS MCP Server)로 CodeBuild·CodePipeline·ECR·ECS API를 호출할 수 있는가? 어떤 도구와 통제 수단이 있는가?
aws-api-mcp-server는 call_aws(AWS CLI 명령 실행), suggest_aws_commands, get_execution_plan(실험적) 세 도구를 노출합니다. README가 '최신 AWS CLI의 모든 명령을 지원'한다고 하므로 codebuild, codepipeline, ecr, ecs 명령도 기술적으로 포함됩니다. 이 서비스들을 이름으로 열거한 문구는 못 찾았고, 지원 여부는 CLI 전체 지원이라는 문구에서 추론했습니다. 일부 위험 명령(deploy install/uninstall, emr ssh 등)은 denylist입니다. 통제 수단은 READ_OPERATIONS_ONLY, REQUIRE_MUTATION_CONSENT(elicitation으로 동의 요청), 그리고 ~/.aws/aws-api-mcp/mcp-security-policy.json의 denyList/elicitList입니다. 목록은 정확한 문자열 일치만 지원하고 와일드카드는 없습니다. 매니지드 AWS MCP Server는 2025-11-30 프리뷰였고 2026-05-06 GA 블로그가 나왔습니다. 인증은 IAM(SigV4)이고 CloudTrail로 감사합니다. 이 블로그는 call_aws, search_documentation, read_documentation, run_script를 핵심 도구로 소개합니다. 현재 문서의 도구 페이지에는 aws___run_script, aws___get_presigned_url, aws___get_tasks와 지식 도구들이 나오고 call_aws는 보이지 않아 블로그와 문서 사이에 불일치가 있습니다(문서 갱신 가능성, 미확정). IAM 통제는 컨텍스트 키 aws:ViaAWSMCPService와 aws:CalledViaAWSMCP로 하고, 예전 aws-mcp:InvokeMcp 등 액션은 더 이상 필요 없다고 안내됩니다. 예를 들어 에이전트 경유 호출에만 삭제를 Deny하는 정책을 만들 수 있습니다. call_aws는 CLI 문자열 전체를 LLM이 채우므로 LLM 재량이 가장 넓은 표면입니다.
SRC: https://raw.githubusercontent.com/awslabs/mcp/main/src/aws-api-mcp-server/README.md, https://docs.aws.amazon.com/aws-mcp/latest/userguide/understanding-mcp-server-tools.html, https://aws.amazon.com/blogs/aws/the-aws-mcp-server-is-now-generally-available/, https://aws.amazon.com/about-aws/whats-new/2025/11/aws-mcp-server/

## [mcp-params] [confirmed] 8. '툴은 파이썬으로 작성하고 boto 기반으로 만든다'는 구현 방식이 AWS 자체 MCP 서버와 같은 패턴인가?

LLM이 채운 인자를 boto3에 그대로 넘기는 얇은 래퍼는 이 패턴의 안전한 구현이 아닙니다.

## [mcp-params] [confirmed] 9. LLM이 도구 인자를 자유롭게 채울 때의 위험(환각된 인자, 프롬프트 인젝션으로 주입된 위험 인자)은 공식·신뢰 자료로 뒷받침되는가?

'악의적 또는 우발적'이라는 표현이 인젝션과 환각을 모두 포괄합니다. (5) 환각형 오류는 Anthropic 문서가 인정합니다. strict 모드가 아니면 타입이 틀리거나 필수 필드가 빠질 수 있다고 합니다. (6) OWASP MCP Top 10은 MCP03 Tool Poisoning, MCP05 Command Injection & Execution, MCP06 Intent Flow Subversion 등을 나열하지만 v0.1 베타 단계의 살아있는 문서입니다. ## [mcp-params] [confirmed] 10. CodeBuild StartBuild API에서 LLM이 채우면 특히 위험한 인자는 무엇인가? (구체 사례)
StartBuild의 필수 인자는 projectName 하나뿐이고, 나머지는 프로젝트 설정을 이번 빌드에 한해 덮어쓰는 *Override 계열입니다. 위험한 것은 다음과 같습니다. buildspecOverride는 컨테이너에서 실행될 빌드 명령을 바꿀 수 있고, 공식 문서가 직접 경고하며 신뢰할 수 있는 위치만 쓰라고 권합니다. imageOverride(이미지 교체), serviceRoleOverride(서비스 역할 교체), privilegedModeOverride, environmentVariablesOverride, sourceLocationOverride와 sourceVersion(빌드할 소스 교체), artifactsOverride(산출물 위치)도 같은 부류입니다. timeoutInMinutesOverride는 최대 2160분, computeTypeOverride는 비용에 영향을 줍니다. 서버 측 완화도 공식 문서에 있습니다. IAM 조건 키 codebuild:source.buildspec에 Null 연산자를 걸어 buildspecOverride 사용을 통째로 Deny할 수 있습니다. 이 키는 필드 존재 여부만 검사하고 내용은 검사하지 못합니다. 환경변수도 codebuild:environment.environmentVariables/이름.value 형태 키로 값을 제한할 수 있습니다. 설계상 도구는 projectName(enum)과 sourceVersion(pattern 제한) 정도만 노출하고 나머지 override는 서버 코드가 고정하는 것이 안전합니다. serviceRoleOverride의 iam:PassRole 요건 등은 이번에 확인하지 못했습니다.
SRC: https://docs.aws.amazon.com/codebuild/latest/APIReference/API_StartBuild.html, https://docs.aws.amazon.com/codebuild/latest/userguide/action-context-keys.html

## [mcp-params] [confirmed] 11. 권장 완화책(스키마 제약, 서버 측 검증, 허용 목록, 사람 승인, 최소 권한)은 공식·신뢰 자료에 있는가?
각 항목의 출처는 다음과 같습니다. 스키마 제약과 서버 검증은 MCP 사양의 서버 MUST(모든 도구 입력 검증, 접근 제어, rate limit, 출력 sanitize)이고, OWASP MCP Cheat Sheet는 additionalProperties:false와 문자열 pattern 사용을 권합니다. 허용 목록은 OWASP Cheat Sheet의 URL 허용 목록 검증과 OWASP LLM06의 열린 도구(셸, URL fetch) 회피이며, aws-api-mcp-server는 denyList/elicitList로 구현합니다. 사람 승인은 MCP 사양의 SHOULD(확인 프롬프트, 입력 표시), OWASP LLM01과 LLM06의 고위험 작업 승인, OWASP Cheat Sheet의 전체 파라미터 표시와 자동 승인 금지이며, 제품 수준에서는 aws-api-mcp-server의 REQUIRE_MUTATION_CONSENT, ECS 서버의 ALLOW_WRITE 잠금이 있습니다. 최소 권한은 OWASP LLM06의 권한 최소화와 하위 시스템 권한 검증, MCP 보안 모범사례의 scope minimization, AWS 보안 블로그의 aws:ViaAWSMCPService 기반 Deny 패턴입니다. 그 밖에 모든 호출과 파라미터 로깅, CloudTrail 감사도 권고됩니다. OWASP Cheat Sheet 항목은 요약 도구를 거쳐 확인했으므로 인용 문구보다 취지 위주로 읽어야 합니다.

## [mcp-params] [refuted] 12. 사용자 전제 확인: '웹 콘솔로 CodeBuild를 설정하는 것은 코드로 하기 힘들다'
