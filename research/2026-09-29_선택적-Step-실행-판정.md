> 작성일: 2026-09-29
> 근거: 조사 스트림 3개(과잉 실행 병목 / 기존 해결책 / tier별 파이프라인)와 그 검증 결과를 합쳤습니다.

> - **(추정)** 근거에서 끌어낸 판단

## 0. 한 줄 결론

팀원 주장은 절반만 맞습니다.
- **"과잉 실행이 병목"은 조건부 사실입니다.** 대형 모노레포, 긴 테스트, 재배포 시 다운타임이 생기는 구성에서만 해당합니다.
- **"AI 파이프라인이니 당연히 핵심 기능"은 근거가 없습니다.** 업계 표준 해법은 규칙, 의존성 그래프, 해시입니다.
- 제안: 이 기능은 **바닥층**으로 넣습니다. AI는 경로만으로는 판단할 수 없는 네 가지(API 계약, 스키마 expand/contract, 환경변수를 어느 tier가 언제 읽는지, lockfile 영향)에서 **단계 추가, 순서 제안, 이유 설명만** 맡깁니다.

## 1. 판정

### (a) "웹 변경에 WAS급 검증을 돌리는 과잉 실행이 병목"인가

| 조건 | 판정 | 근거 |
|---|---|---|
| 모노레포, 여러 팀, 테스트 10분 이상, 공유 라이브러리 | **강한 실제 이슈** | Google, Meta, Shopify, Slack, PostHog† |
| 프론트만 바꿨는데 백엔드·인프라까지 재배포되고, 재배포 때 다운타임이 생기는 구성 | **강한 실제 이슈.** 문제는 시간보다 **위험** | atama+: 프론트 변경에도 Lambda가 재배포되어 API가 수 분간 멈춤 |
| 폴리레포(tier별 저장소), 소규모, 몇 분짜리 파이프라인 | **약함** | CircleCI 워크플로 중앙값 2분 43초. 경로 필터 절감액은 저장소당 연 $2.20† |
| 선언형 배포와 캐시를 갖춘 로컬 3tier(Compose) | **거의 없음** | compose는 바뀐 서비스만 다시 만들고, 레이어 캐시가 적용됨 |

짚어야 할 점이 세 가지 있습니다.

1. **"Web/WAS/DB 구도에서 웹 변경에 WAS급 과정이 돈다"를 정확히 다룬 1차 자료는 atama+ 한 건뿐입니다.** 그마저 Next.js / FastAPI+Lambda / CDK 구성이라 비슷할 뿐 같지는 않습니다. 나머지 사례는 프론트 모노레포입니다. 따라서 "개발자들의 실제 이슈"라는 말은 이렇게 나눠 봐야 합니다.
   - 모노레포 CI 과잉 실행이라는 인접 문제로는 **입증됨**
   - 3tier에 특화된 문제로는 **단일 사례에 기댄 유추**
2. **개발자가 꼽는 1순위 CI 장벽은 느린 빌드가 아니라 실패 원인 디버깅입니다.**
   - Hilton 2017: 실패 디버깅 50/64%, 긴 빌드 38/50%
   - CircleCI 2026도 병목을 실패와 복구로 봅니다(main 브랜치 성공률 70.8%, 복구 72분). 벤더의 해석입니다.
3. **tier 사이에서 실제로 장애를 내는 것은 과잉 검증보다 배포 순서와 버전 호환입니다.**
   - 근거: GitLab 다중 버전 호환 문서의 실제 사례, Vercel이 Skew Protection을 따로 제품화한 것, "장애의 약 70%는 라이브 시스템 변경에서 비롯된다"(Google SRE 책†)
   - 그래서 3tier 논거는 "속도"보다 **"불필요한 재배포는 위험 노출이고, 순서가 틀리면 장애가 난다"**로 세우는 편이 강합니다.

### (b) "필요한 Step만 선택"이 AI 파이프라인의 핵심 기능이어야 하는가

**파이프라인 기능으로는 넣는 것이 맞습니다.** 성숙한 도구는 모두 기본으로 갖추고 있고, 구현 비용이 낮으며(0.5~1시간 추정, 04 문서), 3분 데모 시간을 확보하는 데 도움이 됩니다.

**그러나 "AI 기반이니 당연히 핵심"이라는 논리는 성립하지 않습니다.**
- **실무의 선택 로직은 거의 전부 결정적입니다.**
  - 경로 규칙: GitLab rules:changes, paths-filter
  - 의존성 그래프: Nx affected, Turborepo, Bazel, Pants, Google TAP
  - 콘텐츠 해시: Docker·Gradle 캐시
  - 선언형 diff: compose, K8s, terraform plan
  - GitLab 공식 효율화 문서도 "프론트만 바뀌면 백엔드 테스트 생략"을 **규칙 예시**로 듭니다.
- **ML 기반 선택은 이력이 없으면 못 씁니다.** Meta PTS, Develocity, CloudBees Smart Tests처럼 상용화된 것은 있지만, 고르는 대상이 '테스트'이고 약 1주 이상의 이력이 필요합니다. 해커톤의 신규 앱에는 이력이 없습니다.
- **LLM이 혼자 단계를 고르는 제품은 찾지 못했습니다.** 2026-09 최신 사례도 두 가지뿐입니다.
  - Trunk Dynamic CI†: 통계 신호를 결정적으로 조합(LLM 없음)
  - juju PR†: 정적 점수에 LLM 가산점을 얹어 섀도 모드로만 운영
  - Nx조차 선택은 결정적으로 두고, AI는 실패한 뒤(Self-Healing CI)에만 씁니다.
- **결론:** 이 기능은 **바닥층(필수 인프라)이지 AI 핵심 기능이 아닙니다.** AI 10점의 근거로 쓰려면 "경로로는 안 보이는 판단"으로 범위를 좁혀야 합니다.

### (c) 차별점이 될 수 있는가

| 무엇을 내세우나 | 차별 가능성 | 이유 |
|---|---|---|
| 바뀐 tier만 재배포 / 시간 단축 | **낮음** | 규칙, 빌드 그래프, 캐시로 이미 해결됨. 2025 Mango(캐시로 7초), 2026 Daisy(재사용 시 AI 호출 0회), 상용 도구 다수 |
| AI가 테스트를 골라 줌 | **낮음** | CircleCI·Harness·Datadog·CloudBees·Develocity가 이미 제품화. 이력 없이 LLM만으로 고를 때의 정확도 근거가 없음 |
| tier 간 의미 영향 판정 → 단계 추가 + 배포 순서 + 근거 설명 | **중 (가설)** | 커버리지 도구는 기본적으로 tier 간(HTTP) 영향을 못 봄(Azure TIA 멀티머신 미지원, Datadog external services 미감지. 모든 도구로 일반화한 것은 추론). 다만 DB 순서는 shift-deploy(규칙 기반, Django 한정)가 이미 구현했고, LLM이 그래프 도구보다 낫다는 직접 근거는 없음 |
| 같은 변경 계획을 로컬·클라우드 실행 단계로 번역 + 환경 차이(env·시크릿) 누락 감지 | **중 (가설)** | 클라우드 30점(환경 차이 흡수)과 직결. 선례는 찾지 못함[미확인]. 대상 환경이 고정이면 번역 자체는 결정적 매핑 |

### 이전 평가 재검토

| 항목 | 이전 | 수정 | 이유 |
|---|---|---|---|
| AI 필요도 | 낮음~중 | **유지하되 세분화.** 단계 생략은 낮음, 의미 영향·순서·환경 차이 판정은 중 | 성공 사례는 전부 규칙·그래프 기반. AI의 가치는 "스펙도 도구도 없는 임의의 앱"이라는 전제에서만 생김 |
| 겹침 위험 | 중~높음 | **세분화.** 단계 생략·시간 단축 서사는 **높음**, tier 순서·호환은 **중**, 환경 차이 감지는 낮음~중(추정) | 상용 제품, 2025·2026 팀, shift-deploy |
| 데모 적합성 | 매우 높음 | **조건부 높음** | 생략은 '안 일어난 일'이라 화면에 보이게 만들어야 함. 건너뛸 단계가 무거워야 대비가 생김. 클라우드 소요 시간은 테스트보다 배포 방식(ECS 드레이닝 등)이 좌우함. 실행 계획(dry-run) 화면으로 보여주면 두 번 돌릴 필요는 없음(추정) |

## 2. 근거

### 2-1. 과잉 실행이 실제로 비싸다는 근거 (지지)

| 출처 | 내용 | 주의 |
|---|---|---|
| [Google TAP 2017](https://static.googleusercontent.com/media/research.google.com/en//pubs/archive/45861.pdf) | 역의존성으로 골라낸 테스트 550만 개 중 한 번이라도 실패한 것은 6.3만 개. 실제로 파손이나 수정을 발견한 실행은 1.23% | 이미 그래프 규칙으로 고른 뒤의 수치. 논문 결론(의존 거리 10을 넘는 테스트는 거의 안 깨짐)은 **규칙을 지지**함 |

| [atama+ 2025-06](https://zenn.dev/atamaplus/articles/79579a242b64d4) | 프론트만 바꿔도 backend·infra가 배포되고 Lambda 재배포로 API가 수 분간 정지. 경로 필터 적용 후 프론트 변경 10→2분, 백엔드 변경 10→8분 | **3tier에 가장 가까운 직접 사례.** 규칙만 사용. 비교 기준이 '직전 실행'이라 실패한 구성요소가 이후 배포에서 빠지는 문제가 있었음 |
| [Slack 2025-04](https://slack.engineering/speedup-e2e-testing/) | 프론트 변경이 없으면 git diff로 빌드를 건너뛰어 프론트 빌드 약 5→2분, 빌드 빈도 60% 감소 | 줄인 것은 테스트가 아니라 빌드. 원문 헤드라인(50%)과 본문 수치(계산하면 60%)가 서로 어긋남 |
| [PR TIMES 2024-02](https://developers.prtimes.com/2024/02/16/github-actions-frontend/) | 프론트 모노레포가 GitHub Actions 월 사용 시간의 약 70%를 차지. 월 약 25,000분 절감 | 경로 필터, 캐시, 동시성 취소, Renovate 조정을 합친 효과. 항목별 기여는 분리돼 있지 않음 |
| [토스 2024-06](https://toss.tech/article/monorepo-pipeline) | 200여 서비스 모노레포에서 서비스 2개 배포 30→6분 | 개선폭의 원천은 **병렬화**. 가장 큰 절감은 체크아웃(36분→22초) |
| [Hilton 2017](https://mir.cs.illinois.edu/marinov/publications/HiltonETAL17TradeOffsInCI.pdf) | '너무 긴 빌드'를 장벽으로 꼽은 비율 38%(n=523) / 50%(51명). 허용 가능한 빌드 시간의 최빈값 10분 | 1위 장벽은 실패 트러블슈팅(50/64%) |
| [Jaspan & Green 2023](https://newsletter.getdx.com/p/build-times-and-developer-productivity) | 빌드가 몇 초 빠른 머신을 받은 쪽의 생산성 자가 평가가 '약간' 높았고, 3개월째 작은·중간 변경을 11~14% 빨리 끝냄. 마법의 임계값은 없음 | 로컬 빌드 대상. 벤더(DX)의 2차 요약이며 통계적 유의성은 미확인 |

### 2-2. 규모가 작으면 효과도 작고, 더 큰 병목이 따로 있다 (반대)

- **[CircleCI 2025](https://circleci.com/landing-pages/assets/2025-state-of-software-delivery-report.pdf)** (필터 적용 후 1,414만 워크플로, 벤더 데이터)
  - p25 38초, **중앙값 2분 43초**, p75 8분 7초, 평균 11분 2초, p95 25분 이상
  - 대부분은 이미 권장 기준(10분) 안쪽이고, 문제는 긴 꼬리에 몰려 있습니다.
- **[ICSE 2024 Bouzenia & Pradel](https://software-lab.org/publications/icse2024_workflows.pdf)†**
  - 워크플로 단위 경로 필터의 절감액은 **저장소당 연 $2.20**입니다(952개 저장소, 실행 130만 건).
  - 잡 단위 선택은 측정하지 않았습니다.
- **[Atlassian·DX 2024](https://newsletter.getdx.com/p/state-of-developer-experience-2024)**
  - 시간 손실의 원인은 기술부채 59%, 문서 부족 41%, 빌드 프로세스 27% 순입니다.
- **[Atlassian 2025](https://www.atlassian.com/blog/developer/developer-experience-report-2025)**
  - 상위 마찰 요인에 CI 대기가 없습니다. 다만 "조사해 보니 낮았다"가 아니라 "언급되지 않았다"는 부재 증거입니다.
- **소규모 파이프라인의 오버헤드†**
  - GitHub Actions는 잡마다 1분 단위로 올림해 과금합니다. 그래서 잡을 잘게 나누면 비용이 오히려 늘 수 있습니다.

### 2-3. 선택 실행 자체의 위험 (반대)

- **[Jin & Servant, ICSE 2021](https://arxiv.org/abs/2102.06666)**
  - **대부분의 기법**에서 비용을 많이 줄일수록 놓치는 실패가 늘었습니다.
  - '안전해 보이는' 스킵(코드 변경이 없는 빌드 등)도 설정·컴파일 오류를 놓쳤습니다. 이런 오류는 실패 빌드의 약 35%였습니다(저자가 간략히 확인한 수치).
- **[Shinder, dev.to 2026-09](https://dev.to/sergey_shinder_ab2d943365/the-path-filter-that-skipped-the-tests-for-the-code-we-changed-l2)** (1인 자기보고)
  - 경로 목록에 공유 라이브러리가 빠져 billing 테스트가 돌지 않았고, NPE가 운영까지 나갔습니다.
  - 점검해 보니 트리거되지 않는 서비스가 11개였습니다.
  - 해법은 의존 그래프 도입과 "diff는 있는데 선택된 대상이 비면 전체 실행" 가드였습니다.
- **[Nx #37218](https://github.com/nrwl/nx/issues/37218)** (2026-09-28, 미해결, 보고자 1명)
  - 버전 카탈로그 변경을 affected가 놓쳐, 캐시된 오래된 빌드가 그대로 나갔습니다.
- **[GitHub 경로 필터](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax)**
  - 워크플로 단위로 건너뛰면 필수 체크가 Pending으로 남아 머지가 막힙니다([#44490](https://github.com/orgs/community/discussions/44490) 👍125 미해결, [#26251](https://github.com/orgs/community/discussions/26251) 2019년부터).
  - 잡 단위 `if`로 건너뛰면 Success로 보고됩니다.
  - 변경 파일이 3,000개를 넘으면 조용히 실행되지 않을 수 있습니다.
- **보안**
  - AI CI/CD의 판단을 조작하는 공격 클래스 11개가 제시됐고, 테스트한 제공자 4곳이 모두 기본 설정에서 하나 이상에 취약했습니다([GitInject](https://arxiv.org/abs/2606.09935)†).
  - 변경 감지 액션 tj-actions/changed-files는 태그 변조로 시크릿이 노출됐습니다([CVE-2025-30066](https://www.cisa.gov/news-events/alerts/2025/03/18/supply-chain-compromise-third-party-tj-actionschanged-files-cve-2025-30066-and-reviewdogaction)).
- **LLM 정확도**
  - GPT-5의 코드 엔티티 단위 변경 영향 분석은 지표 중앙값이 0이었습니다([arXiv 2512.19481](https://arxiv.org/abs/2512.19481)†).
  - tier 단위 분류는 이보다 쉬울 수 있지만, 벤치마크가 없습니다(추정).

### 2-4. tier 순서·호환 장애 (3tier 특화 근거)

- **[GitLab 다중 버전 호환 문서](https://docs.gitlab.com/development/multi_version_compatibility/)**
  - 배포는 원자적이지 않아서 신·구 코드가 몇 시간씩 공존합니다.
  - 실제 사례: NOT NULL 제약을 추가한 뒤에도 구버전 서버가 null을 넣어 CI 아티팩트 업로드가 실패했습니다. GraphQL 타입을 바꾸자 사이드바가 로드되지 않았습니다.
- **[Vercel Skew Protection](https://vercel.com/docs/skew-protection)**
  - 프론트와 백엔드의 버전 불일치를 막는 기능을 따로 제품화했습니다.
- **정정: [corvmc #1350](https://github.com/corvmc/corvmc.org/issues/1350)은 실제 장애가 아닙니다.** 배포 스크립트를 읽고 추론한 잠재 위험이며, 본문에 "Not observed in production"이라고 적혀 있습니다. '설계상 위험 사례'로만 인용해야 합니다.
- **유사 사례** (데이터·설정 변경이 코드의 가정과 충돌한 경우로, 3tier 순서 문제는 아님)
  - [Cloudflare 2025-11-18](https://blog.cloudflare.com/18-november-2025-outage/): 전체 정상화까지 약 5시간 46분
  - [Google Cloud 2025-06-12](https://status.cloud.google.com/incidents/ow5i3PPK96RduMcb1SsW): 약 7시간 27분

## 3. 규칙으로 되는 것 vs AI가 필요한 것

| 변경 유형 | 필요한 단계 | 규칙으로 판별 가능한가 | 결정적 도구 | AI가 더하는 가치 |
|---|---|---|---|---|
| 문서만 | 전부 생략. GitHub Actions라면 잡 단위 `if`로 Success 보고 | 가능 | paths-ignore, paths-filter | 없음 |
| Web(CSS·화면·정적) | Web 빌드·린트·단위 테스트 → 정적 배포 → index.html 무효화(해시 파일명 전제) → 화면 스모크. WAS·DB 생략 | 가능 | 경로 필터, compose, 레이어 캐시 | 없음. 단 Web이 **호출하는 API가 바뀌었다면** 아래 계약 행으로 |
| WAS 로직(계약 불변) | WAS 빌드·단위·통합 테스트 → 이미지 → 롤링 → `/health`(DB 연결) + API 스모크. Web·DB 생략 | 경로는 가능. **계약이 정말 안 바뀌었는지는 불가** | — | 낮음~중. 계약 불변 여부 확인 |
| WAS API 계약 | 계약 검사. 추가형이면 WAS → Web. 파괴형이면 v1·v2 병행 또는 두 릴리스로 분리 | OpenAPI 스펙이 있으면 가능, 없으면 불가 | [oasdiff](https://github.com/oasdiff/oasdiff), [Pact can-i-deploy](https://docs.pact.io/pact_broker/can_i_deploy) | **중.** 스펙이 없는 앱에서 추가형/파괴형 분류, 영향받는 Web 호출 지점 지목, 순서 제안 |
| DB 스키마 | 추가형: 마이그레이션 린트 → DB 먼저 → WAS(스냅샷은 선택, default 없는 NOT NULL은 차단). 파괴형: 스냅샷 필수, 코드 먼저 → **다음 릴리스**에 DB | 파일이 있는지는 가능. expand/contract 분류는 **ORM과 도구를 알면** 린터로 대부분 가능 | [Atlas lint](https://atlasgo.io/lint/analyzers), [squawk](https://squawkhq.com/docs/safe_migrations), strong_migrations, `makemigrations --check`†, `prisma migrate diff --exit-code`† | **중.** 도구를 모르는 임의 앱에서 감지 방법 선택, raw SQL 분류, 순서 설명. 규칙 기반 구현은 [shift-deploy](https://github.com/hyunsuhahaha/shift-deploy)에 이미 있음 |
| 환경변수·설정 | 런타임 변수: 빌드·테스트 생략, 해당 tier 재시작 + 헬스체크·스모크. **빌드 시점에 치환되는 변수(Vite `VITE_` 등): Web 재빌드 필요.** 클라우드 시크릿·설정 반영 | `.env.example` diff와 grep으로 일부 가능 | — | **중(클라우드 30점과 직결).** 어느 tier가 읽는지, 런타임인지 빌드 시점인지, 시크릿인지, 클라우드에 빠져 있는지 |
| lockfile | 해당 tier 전체 빌드·전체 테스트. 루트에서 공유하면 영향받는 tier 전부 | 가능(보수적으로 전체) | Nx(기본 all, auto로 정밀화), Pants | 낮음. 런타임 영향 여부 설명 정도 |
| Dockerfile·베이스 이미지 | 해당 tier를 캐시 없이 빌드 → 배포 → 헬스체크 | 가능 | Docker 캐시 무효화 | 낮음 |
| IaC·compose 파일 | plan → 승인 → apply(별도 파이프라인 권장) → 전 tier 스모크 | 가능 | `terraform plan -detailed-exitcode` | 낮음~중. plan 결과의 위험 요약(Meta DRS 방식) |
| 공유 코드(DTO 등) | 의존성 그래프로 영향받는 tier 전부 | 그래프가 있으면 가능. 수동 경로 목록은 누락 위험 | Nx, TS project references | 낮음~중. 매핑이 낡은 것 감지 |

**요약:**
- 경로만으로 판정할 수 없는 칸은 네 개입니다.
  1. API 변경이 추가형인가 파괴형인가
  2. 마이그레이션이 expand인가 contract인가
  3. 환경변수를 어느 tier가 언제 읽는가
  4. lockfile 변경이 런타임에 영향을 주는가
- 이 네 칸도 스펙이나 마이그레이션 도구가 있으면 결정적 도구로 대체됩니다.
- 그래서 **샘플 앱 선택이 AI의 가치를 좌우합니다.** 03 문서 후보 중 Flask·Express는 OpenAPI가 기본으로 없어 AI의 여지가 큽니다. FastAPI·Spring처럼 스펙을 자동 생성하는 스택이면 이 논리는 약해집니다(추정).

## 4. 3tier별 파이프라인 차이와 배포 순서

### 4-1. tier별 과정

| 항목 | Web | WAS | DB |
|---|---|---|---|
| 빌드·검증 | 번들 빌드, 린트, 단위 테스트 | 빌드, 단위·통합 테스트 → 태그 붙인 이미지 | 마이그레이션 린트, 파괴형이면 스냅샷 |
| 로컬(Compose) | nginx 컨테이너 재생성 | 앱 컨테이너 재생성 | `compose run --rm`으로 마이그레이션, `pg_dump` |
| 클라우드(💭 AWS 예시) | S3 sync + CloudFront 무효화, 또는 ECS nginx | ECS 롤링(서킷 브레이커) | ECS RunTask로 마이그레이션, RDS 스냅샷(소요 시간 [미측정]) |
| 배포 후 확인 | 화면 스모크 | `/health`(DB 연결) + API 스모크 | WAS 헬스체크로 간접 확인 |
| 롤백 | 이전 아티팩트 재배포 | 서킷 브레이커 / 이전 태그 | 사실상 어려움. expand-contract로 회피 |
| 시간을 좌우하는 것 | 무효화 P95 기준 반영 5초 미만, 완료 25초 미만(AWS 주장) | ALB 드레이닝 기본 300초, 헬스체크 기본 30초 간격. **튜닝 필수**(드레이닝 5초, 5초×2회) | DDL 잠금, 데이터 크기 |
| 표준 근거 | [DPRA](https://aws-samples.github.io/aws-deployment-pipeline-reference-architecture/application-pipeline/) Source의 정적 자산, CloudFront의 파일 버전 권장 | DPRA Build(10분 미만), Beta(30분 이내) | DPRA: DB 배포가 소프트웨어 배포보다 앞(권장 수준). [Heroku release phase](https://devcenter.heroku.com/articles/release-phase): 실패하면 새 릴리스를 배포하지 않음 |

주의: DPRA Build 단계의 필수 항목에는 시크릿 탐지, SAST, SCA, SBOM도 들어 있습니다. 팀은 보안 컴포넌트를 보류했으므로(02 문서), "Web 변경이니 무거운 검증은 전부 생략"할 때 보안 스캔을 남길지 따로 판단해야 합니다.

### 4-2. 배포 순서

| 변경 | 순서 | 근거 |
|---|---|---|
| Web만 / WAS 로직만 | 해당 tier만 | — |
| API 필드 추가 | WAS → Web | 하위 호환 원칙에서 끌어낸 추론. GitLab 문서는 "아직 배포되지 않은 API를 프론트가 호출하는" 위험을 경고함 |
| API 제거·변경 | Web이 먼저 사용 중단 → WAS | 추론 |
| 추가형 스키마 | DB → WAS (→ Web) | DPRA, [PlanetScale](https://planetscale.com/blog/backward-compatible-databases-changes) |
| 파괴형 스키마(drop·rename) | WAS 코드가 먼저 사용 중단 → **다음 릴리스**에 DB | [GitLab post-deployment migration](https://docs.gitlab.com/development/database/post_deployment_migrations), expand-contract |
| 런타임 환경변수 | 해당 tier 설정 반영 → 재시작 | 12-factor |
| 복합 변경(컬럼 추가 + API 필드 + 화면) | DB → WAS → Web | 위 규칙의 조합 |

결정적으로 순서를 제어하는 도구는 이미 표준입니다. Argo CD PreSync·sync wave, Heroku release phase가 그 예입니다. 차별점은 "순서를 지킨다"가 아니라, **변경의 의미를 보고 어떤 순서가 필요한지 판단해 설명하는 것**이어야 합니다.

### 5-1. 위치: 세 가지 고려안

| 고려안 | 내용 | 장점 | 단점 |
|---|---|---|---|
| **A. 바닥층 + 안 1·2 루프의 입구** (권장 후보) | 규칙 기반 선택 실행을 깔고, 변경 분석(LLM 1회 호출)이 영향 tier·순서·환경 차이·이식성 위험을 분류해 계획에 단계를 **추가**. 주력 스토리는 07 문서의 안 1+2 | AI 호출 한 번이 여러 가치로 이어짐. 클라우드 30점과 연결 | 안 1·2의 구현 부담 |
| B. 이 기능을 주력으로 삼되 재정의 | "변경 의미 기반 tier 순서·환경 반영 계획기". 시간 단축 서사는 쓰지 않음 | 3tier 전제를 가장 잘 활용. 데모 장면이 선명 | shift-deploy·상용 도구와 겹침. LLM이 규칙보다 낫다는 근거 없음 |

### 5-2. 점수로 이어지는 형태

| 배점 | 점수가 되는 형태 | 점수가 안 되는 형태 |
|---|---|---|
| 데모 30 | 계획 → 실행이 로컬·클라우드에서 실제로 동작하고, 건너뛴 이유와 추가한 이유가 화면에 보임. 사전 측정 표 | "Web만 다시 떴다"(compose 기본 동작) |
| 클라우드 30 | 같은 계획이 환경별 실행 단계로 번역됨(nginx 재생성 ↔ S3+CloudFront, compose run ↔ ECS RunTask, pg_dump ↔ RDS 스냅샷). 새 환경변수·시크릿의 클라우드 누락 감지 | 로컬에서만 선택 실행 |
| AI 10 | 규칙 판정과 AI 추가 판정을 나란히 보여줌. AI가 잡은 '경로로는 안 보이는 영향'을 1건 이상 라이브로 | "AI가 단계를 골랐다"(규칙으로 되는 일) |
| 독창성 10 | tier 순서 + 환경 번역 + 안전 폴백의 조합 | 시간 단축 |
| 팀 20 | "규칙으로 충분한 부분과 AI가 필요한 부분을 나눠 검토했다"는 결정 기록. 반대 근거 포함 | — |

### 5-3. 안전장치 (모든 고려안 공통)

1. **AI는 단계를 추가만 합니다.** 규칙이 요구한 단계는 뺄 수 없습니다. 프롬프트 인젝션을 당해도 최악의 결과가 과잉 실행에 그칩니다.
2. **판단이 없으면 실행합니다.** LLM이 실패하거나, 시간이 초과되거나, 확신도가 낮으면 전체를 실행합니다. 조건식도 `== true`가 아니라 `!= false`로 씁니다(Trunk†의 원칙).
3. **diff는 있는데 선택된 대상이 비면 전체 실행**합니다(Shinder 사례).
4. **비교 기준은 tier별 '마지막으로 배포에 성공한 커밋'**으로 둡니다(atama+ 교훈).
5. **배포 후에는 모든 tier의 헬스체크·스모크를 항상 돌립니다.** 건너뛴 검증은 배포 후 비동기로 실행해 결과를 보여줍니다(Shopify·Develocity 방식).
6. 수동 **'전체 실행' 버튼**을 둡니다.
7. 판정 로그(규칙 판정, AI 추가 판정, 근거, 확신도)를 저장합니다. 팀 20점의 재료가 됩니다.
8. GitHub Actions를 쓴다면 워크플로 단위 `paths` 대신 잡 단위 `if`를 씁니다. tj-actions 대신 dorny/paths-filter나 직접 `git diff`를 쓰고, 커밋 SHA로 고정합니다.
9. 데모용 LLM 결과를 캐시해 둘 경우, 캐시를 썼다고 발표에서 밝힙니다(목업 공개 규칙).

### 5-4. 3분 데모 장면 (최종 발표 5분 = 설계문서 약 2분 + 데모 약 3분, 01 문서)

| 시간 | 장면 |
|---|---|
| 0:00–0:15 | 상황 선언: "한 커밋에 DB 컬럼 추가 + API 응답 필드 + 화면 표시 + 새 환경변수" |
| 0:15–0:40 | **계획 화면(DAG).** 규칙 판정(경로: db/·was/·web/) 옆에 AI 추가 판정 3가지를 보여줌. ① 추가형 마이그레이션이므로 DB 먼저 ② 새 환경변수는 WAS가 런타임에 읽는데 클라우드 시크릿에 없으므로 반영 단계 추가 ③ 응답 필드 추가는 하위 호환이므로 WAS → Web. 확신도와 "불확실하면 전체 실행" 규칙도 표시 |
| 0:40–2:10 | 로컬·클라우드 병렬 실행. 로컬은 compose run 마이그레이션 → WAS → nginx, 클라우드는 RunTask → ECS 롤링 → S3+CloudFront. 기다리는 동안 CSS 변경 실행 기록을 보여줌: Web만 배포, WAS 재시작 0회, DB 접촉 0회, 건너뛴 단계는 회색 + 이유. 이전 기록이면 그렇다고 밝힘 |
| 2:10–2:40 | 공개 URL 두 곳에 접속해 새 필드가 보이는지 확인. 전 tier 스모크 결과(안 2와 결합하면 교차 환경 비교 결과) |
| 2:40–3:00 | 한 줄 메시지 + 변경 유형별 사전 측정 표(측정 스크립트는 저장소에 커밋) |

- 시간 전제: 파이프라인 약 85초 + 배포 시간 D ≤ 150초(04 문서). 따라서 **D가 약 60초 이하여야 하고 ECS 튜닝이 필수**입니다.
- 설계문서 발표 중에 파이프라인을 미리 트리거해도 되는지는 운영진 확인 전까지 전제하지 않습니다.
- 파괴형 변경(컬럼 drop)을 차단하거나 두 릴리스로 나누는 장면(15초)은 시간이 남을 때만 넣습니다. 차단은 린터 규칙으로, 설명은 AI로 합니다.

## 6. 남은 확인 사항

1. **실측(개발 1일차)**
   - tier별 경로 시간: Web(빌드 + S3 sync + 무효화), WAS(이미지 빌드·푸시 + 튜닝 후 ECS 롤링), DB(RunTask 마이그레이션 + RDS 스냅샷)
   - 캐시와 compose를 켠 상태에서 전체 재배포와 선택 재배포의 차이
   - D가 약 60초 이하인지
2. **샘플 앱 스택:** OpenAPI를 자동 생성하는지, ORM 마이그레이션 도구를 쓰는지. 이것이 AI 역할의 크기를 정합니다.
3. **저장소 구조:** 모노레포(web/was/db 디렉터리)인지 폴리레포인지. 폴리레포면 과잉 실행 문제가 애초에 약해집니다.
4. **클라우드 Web tier:** S3+CloudFront인지 ECS nginx인지. ECS nginx면 tier별 배포 경로의 차이가 줄어듭니다.
5. **LLM 정확도 자체 측정:** tier를 넘나드는 샘플 커밋 10~20개로 "규칙만"과 "규칙+LLM"의 누락·과잉 선택을 비교합니다. AI 10점의 가장 강한 증거가 됩니다.
6. **운영진 질문**

7. **상용 제품의 범위:** 배포 단계(tier별 재배포, DB 백업·마이그레이션 순서) 선택까지 다루는지 [미확인]
