# 파이프라인 컴포넌트 결정 보고서: 무엇을 넣을지, 시간 안에 되는지

- 기준일: 2026-09-29
- 대상: SoftBank Hackathon 2026 Term1 예선. 3분 라이브 데모와 약 4일 개발, 현장 3.5시간+4시간 조건.
- 확정된 것은 "빌드·배포는 CI/CD로 기본 탑재" 하나뿐입니다. 배포 방식, 컴퓨트 전환, 클라우드 종류, AI 모델은 모두 전제하지 않았습니다.
- 표기 규칙
  - [벤더 주장]: 판매사가 낸 수치
  - [추정]: 공개 근거 없이 경험·문서로 추론한 값
  - [미확인]: 검증 단계에서 확인하지 못함
  - [정정]: 조사 초안의 내용을 검증에서 고침
  - 시간 수치는 대부분 [추정]이나 단일 사례입니다. 실측 전에는 방향을 잡는 용도로만 쓰세요.

---

## 먼저 볼 판단 재료 5개

1. **3분 예산을 가장 많이 쓰는 것은 보안이 아니라 기본 CI/CD입니다.** 러너 할당, 빌드, 배포가 대부분을 차지합니다. 정적 보안 스캔(시크릿·SAST·SCA·IaC)은 빌드와 병렬로 돌리면 핵심 경로에 거의 더해지지 않습니다(+0~30초 [추정]). 그래서 가장 먼저 잴 값은 **타깃별 배포 시간(D)**입니다.
2. **DAST는 차단 게이트로 줄 세우면 3분 안에 들어가지 않습니다([추정]).** ZAP baseline은 공식 기본값만으로 스파이더 최대 1분에 패시브 분석 대기가 붙고, 약 1.2GB 이미지를 받고 기동하는 시간이 더해집니다. 현실적인 선택지는 비동기 실행, 이전 실행 결과 보여주기, 트래픽을 받기 전 버전에 병렬 스캔입니다. 이 중 무엇을 쓸지는 배포 방식에 묶입니다.
3. **배점에 "보안" 항목이 따로 없습니다.** 보안은 배포 안전성과 포터빌리티 서사에 연결될 때만 점수로 이어질 가능성이 큽니다([추정]). 보안 컴포넌트 중에서 "클라우드 활용 30"과 직접 이어질 여지가 있는 것은 서명·프로비넌스와 결과 정규화 정도입니다.
4. **AI로 스캔 결과를 거르고 수정 PR을 만드는 기능은 이미 흔합니다.** GitHub, GitLab, Datadog, Semgrep, Snyk 등이 제품으로 내놨고, 공개 레포는 무료인 경우도 있습니다. 차별 여지는 "스캔 결과를 대상별 배포 결정과 근거 로그로 연결하는 방식"에 있습니다.
5. **"컴포넌트 먼저, 배포 방식은 나중" 순서는 대체로 타당합니다.** 단, 배포 방식보다 먼저 정해야 할 상위 전제가 4개 있습니다: 컨테이너 이미지로 통일할지, 인프라를 사전 프로비저닝할지, 레포를 공개할지, 어떤 CI 플랫폼을 쓸지. DAST 위치, 배포 후 검증과 롤백, 서명 검증 강제 지점은 입력과 출력만 먼저 고정하고 실행 위치와 시점은 미뤄야 합니다.

- **배포 전 정적 계열은 거의 전부 배포 방식과 무관**하고, 병렬로 가릴 수 있습니다.
- **배포 방식에 강하게 묶이는 것은 소수**입니다: 배포 후 계열(스모크, 롤백, DAST)과 서명 검증 강제 지점.
- 킥오프 예시(작업 로그, 롤백, 모니터링, 동시 배포)에 직접 대응하는 것은 **비보안 컴포넌트**입니다.

## 2. 보안 컴포넌트별 판단

공통 전제가 하나 있습니다. **대부분의 게이트는 기본값이 "실패하지 않음"입니다.**
- `semgrep scan`은 `--error` 없이 exit 0으로 끝납니다.
- trivy-action은 `exit-code`를 설정하지 않으면 실패하지 않고, `trivy config`의 기본 exit code도 0입니다.
- zaproxy/action-baseline은 `fail_action` 기본값이 false이고, zap-baseline.py는 모든 알림을 WARN으로 취급합니다.
- 반대로 anchore/scan-action은 `fail-build` 기본값이 true이고 severity cutoff가 medium이라 **예상하지 못한 차단**이 날 수 있습니다([scan-action](https://github.com/anchore/scan-action), [trivy-action](https://github.com/aquasecurity/trivy-action)).

"막는 장면"을 보여주려면 이 옵션들을 명시적으로 설정해야 하고, "막히지 않는 데모"를 원하면 임계치를 미리 설계해야 합니다.

### 2.1 파이프라인 자체 하드닝(스캐너 선택과 별개로 먼저 검토)
- **넣는 이유**
  - 멀티클라우드 원터치 파이프라인에는 AWS/GCP/Azure 자격증명이 한곳에 모입니다.
  - 2026-03-19에 trivy-action 태그 77개 중 76개가 악성 커밋으로 강제 푸시됐습니다(약 12시간 노출). setup-trivy 태그 7개도 전부 교체됐고, 악성 Trivy v0.69.4가 배포됐으며, 03-22에는 Docker Hub 전용 악성 이미지 v0.69.5/0.69.6이 올라왔습니다([GHSA-69fq-xp46-6x23](https://github.com/aquasecurity/trivy/security/advisories/GHSA-69fq-xp46-6x23), CVE-2026-33634).
  - 탈취 방식은 두 가지였습니다. 호스티드 러너에서는 러너 프로세스 메모리를 덤프해 시크릿을, 셀프호스티드 러너에서는 파일시스템을 훑어 클라우드 자격증명과 K8s 토큰을 가져갔습니다([CrowdStrike](https://www.crowdstrike.com/en-us/blog/from-scanner-to-stealer-inside-the-trivy-action-supply-chain-compromise/), [Microsoft](https://www.microsoft.com/en-us/security/blog/2026/03/24/detecting-investigating-defending-against-trivy-supply-chain-compromise/)).
  - [정정] 일부 기사의 "75/76"이 아니라 공식 권고의 76/77을 인용하세요. "1만 개 이상"은 레포 수가 아니라 이 액션을 참조한 워크플로 파일 수입니다(Socket 집계).
  - 2026-03~04에는 Checkmarx KICS의 GitHub Action, Docker 이미지, VS Code 확장도 침해됐습니다. "보안 스캐너 자체가 공급망 공격면"이라는 논지를 설계문서의 대안 논의 소재로 쓸 수 있습니다.
- **내용**
  - 액션은 전체 커밋 SHA로 고정합니다. GitHub 문서는 이것이 액션을 불변 릴리스로 쓰는 유일한 방법이라고 하고, repo/org 수준 강제 정책도 있습니다.
  - `GITHUB_TOKEN`은 최소 권한으로 둡니다.
  - 클라우드 인증은 OIDC 단기 토큰으로 하고, `pull_request_target`은 피합니다([GitHub 보안 사용 가이드](https://docs.github.com/en/actions/security-for-github-actions/security-guides/security-hardening-for-github-actions)).
  - 스캔 잡과 배포 자격증명을 가진 잡을 분리합니다.
- **주의**
  - Dependabot은 SHA로 고정된 액션에 대해 알림을 만들지 않습니다. 업데이트는 수동으로 확인해야 합니다.
  - Trivy를 쓴다면 안전 버전은 trivy v0.69.3 이하 또는 이후 정상 릴리스(현재 v0.74.0), trivy-action 0.35.0 이상(현재 v0.36.0), setup-trivy v0.2.6입니다.
  - Microsoft 블로그 요약에는 같은 캠페인이 LiteLLM으로 번졌다는 내용이 있습니다. 팀이 LiteLLM을 AI 라우터로 쓸 계획이라면 확인하세요 [미확인].
- **시간**: 파이프라인 실행 시간은 0초이고, 설정은 1~2시간입니다 [추정].

### 2.2 시크릿 스캔
- **넣는 이유**
  - 비용이 가장 낮고, 신호 대비 잡음이 적은 편입니다. OWASP, AWS DPRA, GitLab Auto DevOps, OpenSSF가 모두 기본 항목으로 둡니다.
  - 공개 레포라면 GitHub secret scanning과 push protection을 무료로 쓸 수 있습니다(3자 요약, medium).
- **안 넣는 이유**
  - 차별성이 거의 없습니다.
  - OIDC로 장기 키를 없애면 유출될 대상 자체가 줄어듭니다.
- **주의**
  - Gitleaks는 "feature complete, 보안 패치만" 상태이고, 메인테이너는 후속작 Betterleaks(드롭인 대체는 아님)에 집중하고 있습니다([gitleaks](https://github.com/gitleaks/gitleaks)).
  - **gitleaks-action@v2는 2026-09-16 호스티드 러너에서 Node 20이 제거되면서 동작을 멈췄습니다.** v3를 쓰거나 CLI를 직접 실행하세요. 조직 계정 레포에서는 무료 라이선스 키(폼 제출 후 메일 수신)가 필요하므로, 조직 레포라면 CLI 직접 실행이 마찰이 적습니다([gitleaks-action](https://github.com/gitleaks/gitleaks-action)).
  - "TruffleHog보다 4~5배 빠르다"는 수치는 인용 출처에 없고, 벤더 블로그의 실험 1건(9초 대 41초)에서 나온 값입니다(low).
- **시간**: 변경분 기준 1초 미만~수 초이고, 전체 히스토리 스캔은 더 걸립니다([appsecsanta](https://appsecsanta.com/secret-scanning-tools/gitleaks-vs-trufflehog)).

### 2.3 SAST
- **경량(Semgrep CE)**
  - [정정] "diff-aware 중앙값 10초"는 원문 표현이 아닙니다. Semgrep 2023 블로그는 OSS CI 스캔 "평균 10초 미만", 전체 스캔 평균 약 20초라고 쓰고 있고, 저장소 크기 조건은 밝히지 않았습니다([벤더 주장], [Semgrep 블로그](https://semgrep.dev/blog/2023/semgrep-speed/)).
  - [정정] `p/default` 같은 레지스트리 룰셋을 써도 메트릭이 전송됩니다. 끄려면 `--metrics=off`와 명시적 룰셋(또는 로컬 룰 파일)을 같이 씁니다. `--config auto`와 `--metrics=off`를 함께 쓰면 오류가 납니다([Semgrep metrics](https://semgrep.dev/docs/metrics)).
  - **라이선스 주의**: 레지스트리 룰은 Semgrep Rules License v1.0이 적용되고, 요약하면 내부 업무 사용만 허용하며 배포나 서비스 제공은 허용하지 않습니다([rules license](https://semgrep.dev/legal/rules-license)). 팀 CI에서 쓰는 것은 문제없어 보입니다. 하지만 "배포 플랫폼이 사용자 앱을 대신 스캔해 준다"는 식으로 제품화하면 충돌할 수 있습니다. 법률 판단은 아니므로 원문을 확인하세요.
  - 대안으로 LGPL 포크인 Opengrep이 있습니다.
- **심층(CodeQL)**
  - 증분 분석은 PR, 기본 쿼리 스위트, build mode none 조건에서만 적용됩니다([GitHub changelog](https://github.blog/changelog/2026-03-24-faster-incremental-analysis-with-codeql-in-pull-requests/)). main에 직접 push하는 해커톤 흐름이면 매번 전체 스캔입니다.
  - PHP, Scala 등은 지원하지 않습니다.
  - 비공개 레포는 Code Security가 필요합니다.
  - 데모 경로에서는 빼고 비동기로 두는 쪽이 합리적입니다. 설계문서에는 "CodeQL을 검토했지만 속도와 라이선스 때문에 비동기로 뺐다"는 대안 논의 소재가 됩니다.
- **넣는 이유**: SSDF PW.7과 OpenSSF 등이 코드 분석을 권고합니다.
- **안 넣는 이유**
  - 샘플이 외부 오픈소스라면 발견의 대부분이 upstream 코드일 것입니다.
  - 첫 도입 때 범위 밖 규칙에 막히는 사례가 있습니다. Qiita 후기에서는 12건 전부가 `github-actions-mutable-action-tag` 규칙에 걸려 PR이 막혔습니다([Qiita](https://qiita.com/takudon/items/20ffe2ad44b1c32f08de)).
  - 그래서 "신규 finding만 차단"하고 나머지는 리포트 모드로 두는 쪽이 현실적입니다.
- [정정] NIST SSDF(SP 800-218 v1.1)는 SAST/DAST를 특정해 강제하지 않습니다. 조직 정책에 따라 선택하라는 권고입니다. v1.2는 2025-12-17에 초안(IPD)으로 공개됐고 최종본은 아직 없으니, 인용은 v1.1 기준으로 하세요([NIST](https://www.nist.gov/news-events/news/2025/12/secure-software-development-framework-ssdf-version-12-available-public)).

### 2.4 SCA
- **넣는 이유**: 소규모 팀 최소 세트로 "시크릿 + SCA"를 먼저 두라는 권고가 흔합니다(블로그·벤더 일반론, medium).
- **안 넣는 이유(실무 불만의 중심)**
  - 버전만 보고 판정하므로 호출하지 않는 함수의 CVE까지 알립니다(7장 참조).
  - 무료 도달 가능성 분석은 OSV-Scanner 기준 Go(기본)와 Rust(실험적)뿐이고, Java(JAR) 분석이 실험적으로 추가됐다는 서드파티 글이 있습니다. JS/Python은 확인한 자료 범위에서 근거가 없습니다([OSV-Scanner](https://google.github.io/osv-scanner/usage/scan-source)).
- **고려안**: "수정 버전이 있는가 + 공개 노출 타깃인가"로 WARN과 BLOCK을 나누는 정도가 현실적입니다. 데모 당일 새 CVE로 게이트가 깨지지 않도록 `--ignore-unfixed`, HIGH/CRITICAL 한정, `.trivyignore`/VEX 허용 목록을 준비합니다.
- **도구**: Trivy fs, OSV-Scanner, npm audit/pip-audit, dependency-review-action. dependency-review-action은 공개 레포면 무료이고, severity 임계치와 라이선스 allow/deny를 지원합니다.
- **시간**: Trivy DB 콜드 다운로드 약 108MiB에 약 35초였습니다(프로젝트 1건 실측, [issue #405](https://github.com/adorsys/status-list-server/issues/405)). **trivy-action의 캐시 키는 날짜 단위라서 그날 첫 실행은 콜드**입니다. 데모 당일 아침에 한 번 돌려 두는 절차가 필요합니다.

### 2.5 IaC 스캔
- **의존성**: 배포 방식이 아니라 **인프라를 사전 프로비저닝하느냐**에 달려 있습니다.
  - 사전 프로비저닝이면 데모 경로 밖에서 한 번만 돌고, 설계·개발 기간에만 가치가 있습니다.
  - AI가 배포마다 IaC를 생성하거나 바꾸는 구조라면 핵심 경로의 게이트가 됩니다. 이 경우 "AI 산출물을 검증한다"는 서사와 연결됩니다.
- **도구 현황**
  - [정정] tfsec은 아카이브된 것이 아니라 Trivy로 통합되어 사실상 유지보수 모드입니다(마지막 릴리스 v1.28.14, 2025-05-02). 대체는 `trivy config`이고, 빌드를 실패시키려면 `--exit-code 1`이 필요합니다.
  - Terrascan은 2025-11-20에 아카이브됐습니다.
  - 활발히 유지되는 도구는 Checkov, Trivy, KICS인데, KICS는 2026년 침해 이력이 있습니다.
- **시간**: .tf 87개 기준 Trivy 13.4초, Checkov 58.3초였습니다(로컬 Apple Silicon 벤치마크 1건, [appsecsanta](https://appsecsanta.com/iac-security-tools/checkov-vs-trivy)). 해커톤 규모의 Terraform이면 수 초일 가능성이 높습니다 [추정].

### 2.6 컨테이너 이미지 스캔(CI 내부)
- **넣는 이유**
  - "한 번 빌드한 digest를 모든 타깃에 배포"하는 구조를 택하면 스캔 한 번으로 로컬과 모든 클라우드를 커버합니다.
  - AWS DPRA도 "아티팩트는 한 번만 빌드해 각 환경에 그대로 배포하고 재빌드하지 않는다"고 명시합니다([AWS DPRA](https://aws-samples.github.io/aws-deployment-pipeline-reference-architecture/application-pipeline/)).
- **안 넣는 이유**
  - 아티팩트가 컨테이너가 아니면(zip, VM) 해당하지 않습니다.
  - 오픈소스 샘플의 베이스 이미지에는 High/Critical 취약점이 이미 있을 가능성이 커서, 임계치 설계 없이 켜면 데모 배포가 막힙니다.
- **도구**
  - Trivy와 Grype 중 하나로 통일하는 편이 좋습니다(속도 우위는 벤치마크마다 엇갈림).
  - Grype DB v6은 약 65MB입니다([벤더 주장]). scan-action의 `cache-db`는 기본으로 꺼져 있습니다.
  - Trivy DB 기본 저장소는 레이트리밋 문제 때문에 mirror.gcr.io가 1순위이고 ghcr.io가 폴백입니다([trivy discussion](https://github.com/aquasecurity/trivy/discussions/8009)).
- **시간**: 캐시가 있으면 스캔 자체는 1초 미만~10초(low)이고, 잡 단위는 10~40초입니다 [미확인]. 빌드된 로컬 이미지를 스캔하는 동안 push를 병렬로 돌리면 직렬 추가분이 줄어듭니다.

### 2.7 SBOM
- 단독으로는 데모에서 보이지 않습니다. 서명·어테스테이션과 묶어 "배포된 것이 무엇인지 증명"하는 흐름에서만 의미가 생깁니다.
- 시간은 2~30초(블로그, low)이고, 이미지 스캔과 병렬로 돌릴 수 있습니다.
- 포맷: CycloneDX(ECMA-424), SPDX(ISO/IEC 5962:2021).

### 2.8 서명·프로비넌스와 검증
- **생성 측(쉬움)**
  - GitHub `actions/attest@v4`만 써도 SLSA v1.0 Build L2이고, reusable workflow와 결합하면 L3입니다.
  - **Free/Pro/Team 플랜에서는 공개 레포만** 쓸 수 있습니다. 공개 레포는 Sigstore Public Good 인스턴스를 쓰므로 투명성 로그에 신원이 기록됩니다([GitHub attestations](https://docs.github.com/en/actions/concepts/security/artifact-attestations)).
  - cosign keyless도 공개 Rekor에 워크플로 신원이 남습니다.
  - 온프레미스를 오프라인으로 가정한다면 키 기반 서명과 키 관리 설명이 추가로 필요합니다.
  - SLSA v1.2(2025-11-24)에서 Source Track이 추가됐습니다.
- **검증·강제 측(어렵고 클라우드마다 다름)**: 5장 표를 참조하세요.
  - 파이프라인 안에서만 검증하면 "파이프라인을 우회한 배포는 못 막는다"는 반론을 받습니다.
  - 모든 클라우드와 로컬에 네이티브 강제를 구현하면 4일을 넘길 위험이 큽니다 [추정].
- **고려안(선택지)**
  - (a) 모든 타깃에서 배포 스크립트 안에 `cosign verify` 또는 `gh attestation verify`를 넣고 통일합니다.
  - (b) 한 곳만 네이티브로 강제하고 나머지는 (a)로 둡니다. 예를 들어 Cloud Run의 Binary Authorization은 무료입니다.
  - (c) 서명은 생성만 하고 검증은 설계문서의 확장안으로 둡니다.

### 2.9 DAST: 배치 옵션과 3분 안 가능 여부

**사실관계(공식 문서)**
- ZAP baseline은 스파이더를 기본 최대 1분 돌리고(크롤이 먼저 끝나면 조기 종료), 패시브 스캔이 끝날 때까지 기다립니다. 공격은 하지 않으며 "길어야 수 분"입니다([ZAP baseline](https://www.zaproxy.org/docs/docker/baseline-scan/)).
- 공식 이미지 zap-stable 2.17.0은 amd64 압축 기준 약 1.2GB입니다. 작은 bare 이미지(약 505MB)에는 baseline 스크립트가 없습니다.
- [정정] `-T` 기본값 0이 "무제한"인 것은 패시브 대기뿐입니다. ZAP 기동 대기는 600초로 대체됩니다.
- `-silent`를 주지 않으면 기동할 때 애드온 업데이트가 돌아서 네트워크 의존과 시간이 늘어납니다.
- SPA는 `-j` 없이 전통 스파이더만 돕니다.
- zaproxy/action-baseline(v0.15.0)은 기본으로 GitHub Issue를 만듭니다(`allow_issue_writing: false`로 끔). `fail_action` 기본값은 false입니다.
- **벤더 관점 충돌**
  - GitLab은 "운영 서버에 DAST를 돌리지 말라"고 하고, 패시브 스캔조차 일반 사용자처럼 삭제 같은 파괴적 동작을 할 수 있다고 경고합니다([GitLab DAST](https://docs.gitlab.com/user/application_security/dast/browser/)).
  - ZAP은 baseline이 "운영 사이트에도 적합하다"고 합니다.
  - 공개 데모 인스턴스에 돌린다면 일회용 데이터로 분리하는 편이 안전합니다.

**배치 옵션**

| 옵션 | 방식 | 핵심 경로 영향 | 3분 안 가능? | 배포 방식 의존 |
|---|---|---|---|---|
| (a) 직렬 차단 게이트 | 배포 후 스캔 → 통과 시 완료 | +90~240초 [추정] | **불가** | 중간 |
| (b) 러너 내 임시 컨테이너 병렬 | CI 러너에서 앱을 띄워 ZAP을 돌리고, 클라우드 배포와 동시에 진행해 둘 다 통과하면 승격 | +max(0, ZAP 시간 − 배포 시간) | 배포가 길 때만 가능성이 있음. 실측 필요 | "승격" 단계가 필요하므로 의존 |
| (c) 트래픽 받기 전 버전 대상 | Cloud Run `--no-traffic --tag` URL, ECS 블루그린 테스트 리스너와 POST_TEST_TRAFFIC_SHIFT 훅, ACA revision label FQDN | (b)와 비슷 | 조건부 | **강함**(해당 전략·컴퓨트를 골랐을 때만 가능) |
| (d) 배포 후 비동기 리포트 | 배포 완료 후 스캔 결과를 작업 로그에 첨부(선택적으로 FAIL 시 롤백 트리거) | 0초 | **가능**(결과가 데모 중에 도착하지 않을 수 있음) | 약함(롤백을 연동하면 강해짐) |
| (e) 이전 실행 결과 표시·야간 스케줄 | 미리 돌린 결과 화면을 보여줌 | 0초 | **가능** | 없음 |

- 비동기 방식에는 "취약한 버전이 잠깐이라도 노출된다"는 반론이 나올 수 있습니다. (c)는 이 문제를 해소하지만 배포 방식 결정에 종속됩니다.
- 공유 staging에 스캔하다 다른 팀의 테스트를 깬 사례가 있습니다([HackerNoon](https://hackernoon.com/what-went-wrong-when-we-bolted-security-scanning-onto-our-github-pipeline)). "여러 명 동시 배포" 시나리오와 같은 환경을 쓰면 간섭할 수 있습니다.
- GCP 네이티브 DAST(Web Security Scanner)는 Cloud Run을 지원하지 않고, 2026-02-11 개편 이후 새 Standard 티어에서는 custom scan도 안 됩니다. 선택지에서 빠집니다([GCP 문서](https://docs.cloud.google.com/security-command-center/docs/concepts-web-security-scanner-overview)).
- **판정**: 직렬 차단형 DAST는 3분 데모에서 제외하는 쪽이 합리적입니다. (d)나 (e)는 시간 부담 없이 가능합니다. (b)/(c)는 배포 방식이 정해지고 실측한 뒤에 판단할 항목입니다.

### 2.10 클라우드 네이티브 스캔과 런타임 보안
- 네이티브 레지스트리 스캔은 결과가 비동기로 옵니다. AWS/GCP는 공식 지연 수치가 없고, Azure는 "보통 수 시간 안"입니다. 과금과 설정도 제각각이라 동기 게이트로 쓰기에는 부적합합니다. "대기 중 → 도착" 형태의 보강 신호로 두는 선택지가 있습니다(5장).
- 런타임 보안(GuardDuty Runtime Monitoring, Defender sensor, Falco)은 파이프라인 시간은 0이지만 3분 데모에서 보여주기 어렵습니다. 설계문서의 확장안 수준이 현실적입니다.

## 3. 비보안 컴포넌트: 가치 대비 비용이 좋은 것

근거: Google SRE 책은 장애의 약 70%가 라이브 시스템의 변경에서 온다고 합니다([SRE book](https://sre.google/sre-book/introduction/)). 킥오프 예시(작업 로그, 롤백, 블루그린/카나리, 모니터링, 여러 명 동시 배포)도 모두 이쪽입니다. 아래 순서는 제 판단이고 확정안이 아닙니다.

1. **스모크 + 공개 접근 확인**
   - 배점 조건("클라우드 배포 앱 공개 접근")을 직접 확인하고, 롤백 트리거로도 씁니다.
   - curl 수 초, k6 스모크 10~30초입니다. k6는 threshold를 위반하면 0이 아닌 exit code(주로 99)를 냅니다([k6](https://grafana.com/docs/learning-paths/automate-k6-cicd/handle-exit-code/)).
   - 대상 URL과 시점은 배포 방식에 따라 다르지만, "URL을 받아 pass/fail을 돌려준다"는 계약은 지금 정할 수 있습니다.
2. **동시 배포 잠금(GitHub Actions concurrency)**
   - 설정 몇 줄이면 됩니다. 단, **기본값은 대기 중인 이전 실행을 취소**하고 새 실행으로 교체합니다.
   - 여러 명이 순서대로 배포해야 하면 `queue: max`(최대 100개 FIFO)를 명시해야 하고, 이 옵션은 `cancel-in-progress: true`와 함께 쓸 수 없습니다([GitHub concurrency](https://docs.github.com/en/actions/writing-workflows/choosing-what-your-workflow-does/control-the-concurrency-of-workflows-and-jobs)).
   - 여러 타깃에 배포한다면 타깃별로 그룹을 나눌지 설계해야 합니다.
3. **작업 로그·감사**
   - OWASP CICD-SEC-10(로깅·가시성 부족)에 대응합니다.
   - 게이트 판정(PASS/WARN/BLOCK과 근거, 도구 버전), 배포 대상, digest를 한 줄씩 남기면, 보안 컴포넌트를 데모에서 보여주는 가장 싼 방법이 됩니다.
   - 쓸 수단: GitHub deployments 이력, `$GITHUB_STEP_SUMMARY`, 아티팩트, 자체 JSONL/SQLite.
4. **최소형 롤백**
   - "스모크 실패 시 이전 digest 재배포"는 배포 방식과 무관하게 자리만 먼저 잡을 수 있습니다.
   - 플랫폼 네이티브 롤백(ECS 블루그린 훅, Cloud Run revision, ACA revision)은 배포 방식이 정해진 뒤에 고도화합니다.
5. **digest 태깅 + 빌드 캐시**
   - git SHA 태그와 digest 고정 배포는 모든 롤백 방식의 전제입니다.
   - buildx `type=gha` 캐시는 레포당 기본 10GB이고, 7일간 쓰지 않으면 제거됩니다([Docker docs](https://docs.docker.com/build/cache/backends/gha/)).
   - 레지스트리를 단일(GHCR 등)로 둘지 클라우드별로 둘지는 서명·스캔 결과의 포터빌리티와 직결됩니다.
6. **알림(Slack/Discord webhook)**: 30분 수준의 작업이고 [추정], 데모 화면에서 진행 상황을 보여주는 보조 수단입니다.
7. **배포 마커·모니터링**: 킥오프 예시 "모니터링"에 대응합니다. 카나리 분석이나 알람 기반 롤백을 택하면 필수 입력이 되므로 배포 방식과 함께 정하세요.
8. **선택 사항**
   - 비용 추정(Infracost): 무료 API 키가 필요하고, 비용 정책으로 PR을 실패시키는 기능은 유료입니다. 킥오프의 "AI 비용 대비 효과"와는 다른 축입니다.
   - 드리프트 검사: `terraform plan -refresh-only -detailed-exitcode`에서 exit 2가 변경 있음입니다.
   - 단위 테스트: 샘플 앱에 이미 있다면 넣습니다.
   - E2E/부하: 데모에는 스모크로 충분할 가능성이 큽니다.
9. **피하거나 미룰 것**
   - 수동 승인: "원터치" 컨셉과 충돌합니다. GitHub Free 플랜은 공개 레포에서만 environments를 쓸 수 있습니다.
   - DB 마이그레이션: 블루그린·카나리·롤링처럼 두 버전이 공존하면 expand-contract가 필요합니다. 샘플 앱을 stateless로 고르면 통째로 제외할 수 있습니다.

### 4.3 이 표에서 읽히는 것
- **보안을 하나도 넣지 않아도, 배포가 1분을 넘으면 3분 데모가 빠듯해집니다.** 보안 컴포넌트를 논의하기 전에 D(타깃별 배포 시간)와 Q(러너 할당)를 재야 합니다.
- A는 배포가 1분 안쪽이면 들어갑니다. B는 배포가 30초대이거나 낙관 조건일 때만 들어갑니다. C는 비동기 변형만 B와 같은 비용입니다.
- 트래픽을 받기 전 버전을 검증할 수 있는 배포 방식(4.2의 C-병렬, 2.9의 (c))을 고르면 스캔과 배포 시간을 겹칠 수 있습니다. 이 점을 **배포 방식을 고를 때 평가 기준 중 하나로** 넣을 가치가 있습니다.
- 3분 안에서 쓸 수 있는 레버
  - 캐시 사전 준비: Trivy는 날짜 단위 캐시 키라 당일 아침에 한 번 돌립니다. ZAP과 Semgrep 이미지를 미리 받아 둡니다.
  - ECS를 고른다면 등록 해제 지연과 헬스체크를 튜닝합니다.
  - 셀프호스티드 웜 러너: Q가 5초 미만이라는 수치는 [벤더 주장, 미확인]입니다. 다만 공개 레포에서 셀프호스티드 러너를 쓰는 것은 GitHub 공식 문서가 강하게 비권고합니다([GitHub secure use](https://docs.github.com/en/actions/reference/security/secure-use)).
  - "게이트가 막는 장면"은 30~60초가 추가로 들 수 있으므로 [추정], 이전 실행 결과 화면으로 대체하는 방법이 있습니다.
  - [규칙 확인 필요] 설계문서 2분 발표를 시작할 때 원터치를 눌러 두는 것이 허용되면 가용 시간이 크게 늘어납니다. 대회 규칙 해석 문제이므로 전제하지 마세요.

### 4.4 4일 개발 예산(모두 [추정], 신뢰도 낮음)
- A안(정적 5종, 병렬, 게이트, 임계치 튜닝): 0.5~1인일
- B안 추가분(이미지 스캔, SBOM, 서명, 파이프라인 내 verify): +0.5인일. 클라우드 네이티브 검증을 넣으면 +0.5인일 이상.
- DAST 비동기 연동(대상 기동, 룰 파일, 결과 첨부): +0.5~1인일
- 결과 정규화 스키마와 작업 로그 연동: +0.5인일
- AI 요약이나 판단: +0.5~1인일
- 합계는 대략 1.5~3인일입니다. 백엔드 배포 경험이 적은 팀이라면 늘어날 수 있습니다. 멀티클라우드 배포 본작업과 인력을 나눠 써야 한다는 점이 핵심 제약입니다.

## 5. 클라우드 활용 30점과의 연결

### 5.1 "공통 인터페이스 + 환경별 구현" 패턴은 설득력이 있는가
- **강점(사실 기반)**
  - 벤더 서비스가 이미 표준 형식을 입출력으로 씁니다.
    - Amazon Inspector CI 스캔은 CycloneDX SBOM을 받습니다([Inspector CI/CD](https://docs.aws.amazon.com/inspector/latest/user/scanning-cicd.html)).
    - Defender CLI는 SARIF를 출력합니다([Defender CLI](https://learn.microsoft.com/en-us/azure/defender-for-cloud/ci-cd-pipeline-scanning-with-defender-cli)).
    - 새 Security Hub는 OCSF 1.6을 씁니다([Security Hub OCSF](https://docs.aws.amazon.com/securityhub/latest/userguide/securityhub-ocsf.html)).
    - Cloud Build는 SLSA in-toto 프로비넌스를 만듭니다([Cloud Build provenance](https://docs.cloud.google.com/build/docs/securing-builds/generate-validate-build-provenance)).
  - 그래서 "정책은 하나, 구현은 환경별" 구도의 어댑터 경계가 자연스럽게 나뉩니다. "한 번 빌드한 digest를 모든 환경에"라는 원칙도 AWS DPRA가 뒷받침합니다.
- **약점과 반론**
  - SARIF는 코드 위치 중심 포맷이라 이미지 CVE의 패키지명이나 수정 버전을 담기 어색합니다. 스키마 하나로 모두 정규화하겠다는 주장은 반박당할 수 있습니다. 대신 세 층으로 나누는 편이 정확합니다 [추론].
    - 코드 결과(SAST, IaC, 시크릿): SARIF
    - 의존성·이미지 CVE: CycloneDX(+VEX) 또는 OCSF Vulnerability Finding
    - 증명: in-toto
  - 네이티브 스캔은 비동기라 데모의 동기 게이트로 쓸 수 없습니다.
  - 파이프라인 안에서만 검증하면 우회 배포를 막지 못합니다.
  - 네이티브 기능 없이 OSS만 감싸면 "래퍼일 뿐"으로 보일 수 있으니, 각 클라우드 특유 기능 한두 개를 실제로 연동해야 설득력이 생깁니다 [추정].

### 5.2 후보 클라우드별 대응(선택을 전제하지 않은 비교)

| 기능 | 로컬(OSS) | AWS | GCP | Azure |
|---|---|---|---|---|
| 이미지 스캔(동기 게이트 가능?) | Trivy/Grype, Harbor(scan-on-push, 취약 이미지 pull 차단) | Inspector ScanSbom API: CI에서 동기로 호출 가능. $0.03/건, 계정당 1회 25건 무료, 서울 엔드포인트 있음 | On-Demand Scanning: push 전 로컬 이미지를 스캔하고 severity로 빌드 실패시키는 공식 튜토리얼 있음. $0.26/이미지 | Defender CLI(`defender scan image`, SARIF). **Defender CSPM(유료)이 전제** |
| 레지스트리 스캔 결과 지연 | 즉시 | ECR enhanced: 공식 수치 없음(커뮤니티 2~5분, low). EventBridge `INITIAL_SCAN_COMPLETE` 이벤트 | 공식 수치 없음(블로그 1~5분, low) | "보통 수 시간 안"(공식) |
| 서명 | cosign(v3 bundle 기본) | ECR managed signing(2025-11): push 시 AWS Signer로 자동 서명(Notation). Signer는 ECR과 함께 쓰면 무료. 크로스 리전 불가 | Cloud Build SLSA 프로비넌스(`requestedVerifyOption: VERIFIED` + `images` 필드 필수) | Notation + Artifact Signing/Key Vault, ACR referrer |
| 배포 시 검증 강제 | 배포 스크립트의 `cosign verify`, K8s라면 Kyverno | ECS: 네이티브 강제 없음(2023 자료 기준, 2026 현재는 [미확인]). 블루그린 PRE_SCALE_UP Lambda 훅으로 사전 차단 가능. EventBridge 사후 검증은 감사용이라 막지 못함 | **Cloud Run Binary Authorization 무료**. built-by-cloud-build attestor는 Cloud Run에서 **Preview**. org policy가 없으면 개발자가 끌 수 있음 | AKS 1.31 이상 + ACR의 gated deployment. **Container Apps 네이티브 강제는 확인 못 함** |
| 트래픽 전 검증 대상(DAST·스모크 삽입) | 새 컨테이너를 띄운 뒤 교체 | ECS 블루그린 테스트 리스너와 훅 8단계(Lambda 반환값은 **SUCCEEDED**/FAILED/IN_PROGRESS) | Cloud Run `--no-traffic --tag` URL, Cloud Deploy verify(카나리 단계마다) | ACA revision label별 FQDN |
| 네이티브 DAST | ZAP | 확인 못 함 | Web Security Scanner는 Cloud Run 미지원 | 확인 못 함 |
| 결과 집계 | SARIF/CycloneDX 파일, GitHub code scanning | Security Hub(OCSF 1.6). 서드파티 finding은 CSPM BatchImportFindings(ASFF, 배치 100건·6MB)로 입력 | SCC 연동은 확인 못 함 | Defender for Cloud로 업로드 |

[정정]
- ECS 블루그린 Lambda 훅의 반환값은 SUCCESSFUL이 아니라 **SUCCEEDED**입니다. 잘못 쓰면 ECS가 롤백합니다([ECS lifecycle hooks](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/lambda-lifecycle-hooks.html)). 현재 훅 단계는 8개이고 pause hook도 있습니다.
- GCP Artifact Analysis의 지속 분석은 "푸시 후 30일"이 아니라 **최근 30일 안에 pull된 이미지**에만 적용됩니다([GCP 문서](https://docs.cloud.google.com/artifact-analysis/docs/container-scanning-overview)).
- ECR의 Clair 기반 스캐닝 중단은 2026-02-02 ECR 릴리스 노트 기준으로 완료됐습니다.

### 5.3 비용·지연 제약
- **종량제 항목**
  - Inspector ECR enhanced: 최초 $0.09, 재스캔 $0.01, 신규 계정 15일 무료
  - Inspector CI 스캔: $0.03/건
  - GCP 스캔: $0.26/이미지
  - Cloud Run BinAuthz, Signer, 대상이 하나인 Cloud Deploy: 무료
  - 이미지 수십 장 기준으로 합쳐도 몇 달러 수준입니다 [추정].
- **리소스 단위 과금 항목**: Defender for Containers(vCore당 월 $7, low), Defender CSPM, GuardDuty Runtime(첫 500 vCPU까지 vCPU당 월 $1.50, 30일 체험), Config(평가당 $0.001 + recorder 기록 건당 $0.003). 무료 체험 안에서만 쓰고 **대회가 끝나면 끄는 체크리스트**가 필요합니다.
- **함정**
  - GCP: 공식 ODS 튜토리얼처럼 별도 `docker push` 단계로 올리면 Cloud Build 프로비넌스와 built-by-cloud-build 어테스테이션이 생기지 않습니다. 스캔은 push 앞에 두고 push는 `images` 필드에만 맡기는 구성이 필요해 보입니다 [추론, 미검증].
  - GCP: Artifact Analysis API가 켜져 있으면 ODS와 자동 스캔이 각각 과금될 수 있습니다 [추론]. 자동 스캔의 digest 중복 제거는 자동 스캔에만 명시돼 있습니다.
  - AWS: Inspector Code Security(SAST/SCA/IaC, 스캔 유형당 $0.15)는 **서울 리전에서 지원하지 않습니다**(도쿄는 지원). ECR 스캐닝과 Inspector CI 스캔은 서울에서 됩니다([Inspector 리전](https://docs.aws.amazon.com/inspector/latest/user/inspector_regions.html)).
  - AWS: enhanced 스캔 이벤트의 `finding-severity-counts`는 해당 심각도가 있을 때만 키가 나옵니다. 게이트 로직에서 누락된 키를 0으로 처리해야 합니다.
  - AWS: CodeGuru Security는 2025-11-20에 지원이 끝났습니다.
  - Inspector는 Azure ACR 이미지 스캔($0.09)도 요금표에 있어 클라우드 중립 스캐너 후보가 될 수 있습니다. 다만 이 대회 환경에서 가능한지는 [미확인]입니다.
  - 대회 제공 계정에 GCP org policy나 Defender 플랜을 켤 권한이 있는지 모릅니다. 없으면 "강제"라는 주장이 약해집니다.

### 5.4 고려안(선택지)
- **(가) 전부 파이프라인 안에서 판정**: CI 안의 OSS 게이트로 모든 타깃을 판정하고, 네이티브 스캔은 비동기로 "대기 중 → 도착" 표시만 합니다. 데모가 안정적이고, 클라우드 특유 기능 점수는 약합니다.
- **(나) 한 클라우드만 네이티브로 강제**: 예를 들어 Cloud Run이라면 BinAuthz로 강제하고, 나머지는 파이프라인 verify로 둡니다. 클라우드별 차이를 비교표로 설계문서에 넣기 좋습니다. 해당 클라우드를 고른다는 전제가 붙습니다.
- **(다) 보안 네이티브 연동은 설계문서의 비교표로만**: 구현 시간은 0이지만 "대안 논의"(팀 20점)용입니다.

## 6. AI가 들어갈 자리와 차별성

### 6.1 이미 제품화돼서 겹치는 것
| 기능 | 기존 제품(근거) | 해커톤 차별성 |
|---|---|---|
| 취약점 수정 제안·PR | GitHub Copilot Autofix는 **공개 레포 무료**이고, CodeQL을 쓰는 레포에서 기본 활성(CodeQL 스캔 자체는 켜야 함, [GitHub docs](https://docs.github.com/en/code-security/concepts/code-scanning/copilot-autofix-for-code-scanning)). agentic autofix는 2026-07-10 공개 프리뷰로 GHAS + Copilot 라이선스와 AI Credits 필요. GitLab 18.11(2026-04) 에이전트형 SAST 수정 GA(Ultimate + Duo). Snyk Agent Fix(2026-05 에이전트형, "정확도 80%"는 [미확인]). Datadog Bits Code | 낮음 |
| 오탐 트리아지·설명 | GitLab 18.10(2026-03-19) SAST 오탐 판정 GA([GitLab 블로그](https://about.gitlab.com/blog/gitlab-18-10-brings-ai-native-triage-and-remediation/)). Datadog Bits AI agentic evaluation GA. Semgrep Assistant/Multimodal(동의율 95%, 초기 백로그 약 60% 감소는 [벤더 주장]). Aikido, Checkmarx Triage Assist | 낮음 |
| 도달 가능성 | Snyk(Java/JS/TS/Python GA). Endor Labs(코드~컨테이너, [벤더 주장]). Socket(Coana 인수와 "90% 감소"는 [미확인]). OSV-Scanner(Go) | 낮음(무료 OSS는 언어가 제한적) |

결론적으로 "SAST/SCA/DAST를 넣었다"와 "AI로 스캔 결과를 걸렀다"는 둘 다 독창성 점수에 유리하지 않습니다.

### 6.2 차별 가능성이 있는 판단 지점(모두 추측, 고려안)
- **배포 대상별 노출도 정책**: 같은 finding이라도 공개 클라우드 URL로 나가는 타깃은 BLOCK, 로컬(온프레미스) 타깃은 WARN으로 처리합니다. "환경 차이 흡수" 서사와 맞습니다.
- **좁은 질문으로 분해한 판단 + 규칙이 최종 권한**
  - 예시 질문: "공개 노출 타깃인가", "수정 버전이 있는가", "신규 finding인가", "런타임 이미지에 실제로 포함되는가"
  - 규칙이 결정하고, AI는 설명과 우선순위를 맡습니다.
- **AI가 만든 산출물을 게이트로 검증**: AI가 Dockerfile, IaC, 매니페스트를 생성·수정한다면, 그것을 IaC 스캔과 정책 게이트로 검증하는 구조입니다. 주제("AI 활용 원터치 배포")와 보안 배경이 동시에 연결됩니다.
- **판단 근거와 AI 호출 비용·지연 기록**: 킥오프 예시 "AI 비용 대비 효과"에 대응합니다.
- **클라우드별로 이질적인 결과를 한 줄로 설명**: 비동기로 도착하는 네이티브 신호를 공통 스키마로 맞춘 뒤 요약합니다.

### 6.3 위험
- **조작 가능성**: LLM 리뷰어는 검사 대상인 코드와 주석을 입력으로 읽습니다. Checkmarx는 페이로드를 여러 파일로 나눠 Claude Code 보안 리뷰를 우회한 사례를 공개했습니다([Checkmarx](https://checkmarx.com/zero-post/bypassing-claude-code-how-easy-is-it-to-trick-an-ai-security-reviewer/)). AI에 통과·차단의 최종 권한을 주면 미탐 경로가 되고, 보안 엔지니어 관점에서는 오히려 약점으로 지적받을 수 있습니다.
- **시간**: AI 호출 지연(수 초~수십 초 [추정])을 4장 예산에 넣어야 합니다.
- **분류형 결정 모델(Jev 등)**
  - 조사 스트림은 지연 70~500ms, 선택지 밖 답변 불가, 좁은 질문으로 분해하면 정확도가 오른다는 제3자 테스트를 제시했습니다.
  - 검증 단계에서는 출처를 확인하지 못했습니다(jev.ai는 주차 도메인). 관련 수치는 모두 [미확인]입니다.
  - 후보로 남긴다면 질문 분해, 보정, shadow 평가를 전제로 두세요. AI 모델은 아직 미정이므로 이 보고서는 특정 모델을 전제하지 않습니다.
- **DORA 2025 요약(제3자)**: AI 도입은 처리량과는 양의 상관, 안정성(변경 실패율 등)과는 음의 상관이었습니다. "AI가 배포를 빠르게 한다"만 강조하면 반론을 받습니다.

## 7. 실무자 불만 근거

- **SAST 노이즈와 개발자 반발**

  - 해법은 주간 트리아지 당번, 룰 파일의 코드화, PR마다 baseline + 야간 풀스캔이었고, "DAST는 먼저 advisory로" 돌리라고 권합니다.
  - 9인 팀이 2개월간 겪은 단일 사례입니다([HackerNoon](https://hackernoon.com/what-went-wrong-when-we-bolted-security-scanning-onto-our-github-pipeline)).

- **DAST 운용 부담**
  - 인증 이후 화면, SPA, API 전용 백엔드는 추가 설정이 필요합니다([Zenn](https://zenn.dev/mapellion/articles/cb03f335bb6684)).

## 8. "컴포넌트 먼저, 배포 방식은 나중" 순서에 대한 평가

### 동의하는 점
- 네 조사 스트림 모두 같은 결론입니다. 배포 전 컴포넌트(하드닝, 시크릿, SAST, SCA, IaC, 이미지 스캔, SBOM, 서명 생성, 결과 정규화, 잠금, 작업 로그, 알림)는 블루그린·카나리·롤링과 무관합니다.
- OWASP DevSecOps Guideline도 모든 단계를 일률 적용하지 말고 SDLC에 맞춰 커스터마이즈하며 점진적으로 자동화하라고 합니다. 일부만 고르는 결정의 공식 근거로 쓸 수 있습니다.
- [정정] 다만 "빌드/테스트/런타임" 단계 구분은 원문이 아니라 해석입니다([OWASP](https://owasp.org/www-project-devsecops-guideline/)).

### 함께 묶어 정해야 하는 의존성
| 항목 | 왜 배포 방식에 묶이나 | 지금 고정할 것(인터페이스) | 나중에 정할 것 |
|---|---|---|---|
| DAST 배치 | 트래픽 전 대상이 있는지, 승격 훅이 어디 있는지 | 넣을지 말지, 차단형인지 비차단형인지. 입력(대상 URL), 출력(결과 스키마) | 실행 위치·시점, (b)/(c) 옵션 채택 여부 |
| 시간 예산 | D가 예산을 좌우하고, 배포 방식에 따라 스캔과 배포를 겹칠 수 있는지가 달라짐 | 4장 예산식과 실측 계획. "트래픽 전 검증 가능 여부"를 배포 방식 평가 기준에 넣기 | 배포 방식 선택 |
| 배포 후 검증·롤백 | 검증 시점과 롤백 메커니즘이 전략·플랫폼마다 다름 | 스모크 계약(URL → pass/fail), 최소형 롤백(이전 digest 재배포) | 플랫폼 네이티브 롤백(ECS 훅, Cloud Run·ACA revision 등) |
| WARN일 때의 동작 | 점진 배포면 "제한 배포"가 가능하고, 일괄 전환이면 PASS/BLOCK 둘뿐 | 판정 스키마에 WARN을 포함할지 | WARN의 실제 동작 |
| 서명 검증 강제 지점 | 컴퓨트마다 BinAuthz, Lambda 훅, Kyverno 등으로 다름 | 서명을 생성할지, 검증 결과를 로그에 남길지 | 네이티브로 강제할지 파이프라인에서 할지 |
| 잠금 단위 | 타깃 구성에 따라 다름 | 잠금을 넣을지, `queue: max`로 대기시킬지 | 타깃별 그룹 설계 |
| DB 마이그레이션 | 두 버전이 공존하면 expand-contract가 필요 | 샘플 앱을 stateless로 고를지 | 해당될 때만 |

### 배포 방식보다 먼저(또는 동시에) 정하는 편이 나은 상위 전제
1. **아티팩트를 컨테이너 이미지로 통일하는가**: 이미지 스캔, 서명, SBOM의 적용 여부가 여기서 갈립니다.
2. **인프라를 사전 프로비저닝하는가, 매 배포마다 IaC를 돌리는가**: IaC 스캔, Infracost, 드리프트 검사가 데모 경로 안에 들어오는지가 달라집니다.
3. **레포를 공개하는가**
   - 공개 레포면 secret scanning, CodeQL과 Autofix, dependency-review, attestations, environments, 표준 러너가 무료입니다.
   - 반대로 로컬 배포용 셀프호스티드 러너는 비공개 레포여야 안전합니다. 트레이드오프가 있습니다.
4. **CI 플랫폼과 "원터치 시스템"의 관계**: 자체 오케스트레이터나 AI 에이전트가 CI를 호출하는지, 스스로 파이프라인을 실행하는지에 따라 게이트를 해석하는 주체가 달라집니다.
5. 레지스트리 전략(단일 대 클라우드별), 샘플 앱 언어와 stateless 여부.

### 늦출 때의 리스크
배포 방식 결정이 마지막 날까지 밀리면 스모크, 롤백, DAST 연결이 한꺼번에 몰립니다. 늦어도 개발 2일차까지는 정하는 편이 안전해 보입니다 [추측].
