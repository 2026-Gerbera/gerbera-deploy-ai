# 최종 보고서: 기본 툴 카탈로그와 해결할 개발자 이슈 고려안

- 작성일: 2026-09-29
- 상태: **고려안(미확정)**
- 대상: SoftBank Hackathon 2026 Term1 예선(서울 오프라인, 10/3~4)
- 입력 자료: 통합 기본 툴 16개, 이슈 후보 11개, 내부 평가자 4명(인프라·회의론·데모 코치·2025 수상 패턴)이 매긴 점수와 지적. 점수는 모두 내부 추정치다.
- 표기 원칙
  - 시간·효과 수치는 따로 표시하지 않았으면 **추정**이고 실측이 필요하다.
  - URL은 앞선 조사와 평가 과정에서 확인한 것만 다시 인용했다.

## 0. 결론 요약

1. **가장 먼저 할 일은 이슈 선택이 아니라 기본 파이프라인을 끝까지 돌게 만드는 것이다.**
   - 기본 툴 25개가 "챗봇 요청 → 로컬·클라우드 공개 URL → 데이터 유지"까지 한 번에 돌아야 한다.
   - 2025년 탈락 사례가 바로 "버튼→실제 배포" 연결을 못 한 팀이었다.
2. **점수만으로는 이슈 하나를 고를 수 없다.**
   - 가중 점수 1~6위가 3.14~3.37로, 차이가 0.23밖에 안 된다.
   - 그래서 서로의 약점을 메우는 **조합**으로 판단했다.
3. **1순위 고려안 A "고치는 배포"**
   - 구성: 이식성 패치(I2를 업로드로 좁히고 I1과 패치 엔진 공유) + 클라우드 계약 리허설(I5, 결함을 드러내는 층) + 설정 계약(I4, 입력층).
   - 장점: 주제 문구 "코드를 자동으로 변경하면서 적절하게 인프라 환경까지 구축"에 정면으로 답한다. 2025 수상작의 공통 기준(데이터 유지, 이중화, 실제 서빙)을 라이브로 증명한다.
4. **2순위 고려안 B "증명하는 배포"**
   - 구성: 변경 맞춤 판별 프로브 + 로컬↔클라우드 교차 비교(I7) + 설정 계약(I4).
   - 장점: 코드를 고치지 않고 클라우드 배포도 1회뿐이라 라이브 위험이 낮다.
   - 단점: 문제를 찾아낼 뿐 흡수하지는 못해 클라우드 30점 기여가 A보다 약하다.
5. **결정 게이트(제안): 10/1 정오**
   - 샘플 변형 10개 중 8개 이상에서 LLM 패치가 20초 안에 테스트를 통과하면 A, 아니면 B로 간다.
   - 기본 툴은 두 안이 같이 쓰므로 어느 쪽을 골라도 버려지는 작업은 없다.
6. **모든 결정보다 D(클라우드 배포 시간) 실측이 먼저다.**
   - D가 60초를 넘으면 두 조합안 모두 클라우드 검증 장면을 이전 실행 기록으로 대신해야 한다.

## 1. 기본 툴 카탈로그 (무조건 있어야 하는 것)

**설계 원칙**
- AI는 계획 JSON과 좁은 분류·생성만 맡는다. 실행은 고정 실행기가 AI 없이 한다.
- AI는 IaC를 만들지 않는다(Team Daisy와 겹침 회피). 클라우드 API도 직접 호출하지 않는다.
- 한 번 빌드한 같은 digest를 두 환경에 배포한다.
- 느린 작업(terraform plan, LLM 요약)은 데모 핵심 경로에서 빼고, 무대 밖에서 쓰는 준비 툴을 따로 명시한다.

| 운영 | `preflight_check` (신규) | 발표 직전 점검: 자격증명 만료, 레지스트리 로그인, 캐시 예열, 서비스 안정, `ensure_infra` 변경 없음, Jev·LLM 지연, 업로드 속도 | 전체 | 스크립트 | 동일 | 화면 카드 5 |

**기본 경로 합계(추정): 약 120~140초**
- 요청·계획 약 10초 + 빌드·테스트·push 30~50초 + 설정 주입 3초 + D 60초 + 검증 약 15초 + 보고 2초.
- 배경 문서의 '파이프라인 약 85초 + D' 예산과 맞는다.

### 1-2. 조건부·권장 툴

| 툴 | 언제 넣나 | 이유 |

| `load_probe` | 권장 | '배포 중 요청 오류 0건'을 수치로 보여 준다. Orange가 부하 수치를 제시했다 |
| 공유 저장소(잠금·이력) | I10을 채택하거나 오케스트레이터가 여러 대일 때 | 그 외에는 과잉이다 |

### 1-3. 초안 대비 보정 (심사위원 지적 반영)

**누락 보강**
- 입구와 실시간 진행 화면 (2025 평가자)
- AI 관문과 계획 호출을 툴로 명시 (회의론·데모)
- 공통 승인 툴 (인프라·회의론·데모)
- 배포 후 관찰 (4명 공통)
- HTTPS·이중화를 `ensure_infra` 범위에 명시 (인프라·데모·2025)
- AI 입력 전 비밀값 마스킹 (인프라)
- 데모 재현성·정리 툴 (회의론·데모·2025)
- 조건부 마이그레이션 시 직전 덤프 (인프라)
- 롤백 후 재검증 (데모)

**과잉 제거**
- 매 배포 terraform plan → preflight와 infra/ 변경 시에만
- 통합 테스트·스모크·리허설 → 스크립트 하나로 통일하고 대상 스택만 바꿈
- DynamoDB 공유 저장소 → 오케스트레이터 SQLite
- `validate_plan` 재지시 2회 → 1회
- 데모 중 `post_report` LLM 요약 끔

**구현 보정**
- 안정화 판정: `aws ecs wait services-stable`은 15초 간격으로 폴링한다. 그래서 직접 짧게 폴링한다(https://docs.aws.amazon.com/cli/latest/reference/ecs/wait/services-stable.html).
- 롤백 트리거: ECS 서킷 브레이커는 기동 실패가 임계만큼 쌓여야 판정해 느리다. 자체 판정으로 트리거하고, 두 롤백이 경합하지 않게 서킷 브레이커 롤백은 끈다(https://docs.aws.amazon.com/AmazonECS/latest/developerguide/deployment-circuit-breaker.html).
- 이미지 고정: digest로 고정하고 레지스트리 태그를 불변으로 설정한다.
- CPU 아키텍처: Apple Silicon에서 amd64로 교차 빌드하면 에뮬레이션 때문에 느릴 수 있다(https://docs.docker.com/build/building/multi-platform/). 클라우드를 ARM64 Fargate로 맞추는 안을 실측해 보고 정한다(https://aws.amazon.com/blogs/aws/announcing-aws-graviton2-support-for-aws-fargate-get-up-to-40-better-price-performance-for-your-serverless-containers).
- Web 빌드 시점 변수: 런타임 config.js 주입을 샘플 앱 규약으로 기본 채택한다. 그래야 '한 digest, 두 환경' 원칙이 유지된다.
- 버전 확인 규약: 앱이 `X-App-Version`을 내보내고 `APP_VERSION`을 주입받는 것을 샘플 앱 규약으로 명시한다.
- Terraform 밖 변경: 파이프라인이 태스크 정의를 바꾸면 매번 드리프트로 잡히므로 `ignore_changes`를 건다(https://developer.hashicorp.com/terraform/language/meta-arguments/lifecycle).

## 4. 상위 이슈 상세

가중 상위 4개는 I2·I3·I4·I7이다. 다만 아래처럼 조정해 상세를 쓴다.
- **I3**은 팀 전제와 충돌해 조건부로 돌린다(4-5).
- **I5**는 조합안 A에서 결함을 드러내는 층이라 상세에 넣는다.
- **I1**은 I2와 패치 엔진이 같아 4-1에 합친다.

### 4-1. 이식성 패치 (I2 업로드 한정 + I1 패치 엔진 공유) — 조합안 A의 주력

**개발자 불편과 근거**
- 로컬 단일 컨테이너에서는 되던 업로드가, 클라우드에서 태스크가 교체되거나 2개로 늘면 사라진다.
- 하드코딩된 주소, CORS, 프록시 헤더 문제로 클라우드에서 연결부터 깨진다.
- 근거
  - 12-factor Processes: 메모리·디스크 상태가 다음 요청에 남아 있다고 가정하지 말라(https://12factor.net/processes).
  - ECS 바인드 마운트 데이터는 태스크가 멈추면 삭제된다(https://docs.aws.amazon.com/AmazonECS/latest/developerguide/bind-mounts.html).
  - Flask 문서: 프록시 뒤에서는 앱이 요청을 로컬 주소에서 온 것으로 본다(https://flask.palletsprojects.com/en/stable/deploying/proxy_fix/).
- 강도: 메커니즘은 강함(1차 문서). 발생 빈도 통계는 없음.

**범위**
- 지원 패턴은 네 가지로 제한한다.
  - P1(주력): 로컬 디스크 업로드 → S3 호환 어댑터(`STORAGE_BACKEND`)
  - P2: 하드코딩 주소·CORS → 환경변수(로컬 기본값 유지)
  - P3: ProxyFix / trust proxy 추가
  - P4: /health 추가
- 세션 저장소 교체는 뺀다. 평가자 지적대로 JWT나 DB 세션으로 흔히 우회되고, ElastiCache 비용·준비 부담이 크다.

**강조 툴**

| 툴 | 동작 | 로컬 | 클라우드 |
|---|---|---|---|
| `scan_portability_risks` (detect_local_state 통합) | 규칙이 후보 줄을 모으면 Jev가 [영속 데이터 / 캐시·임시 / 하드코딩 주소 / CORS / 프록시 / 무해] 중 하나로 분류 | semgrep·정규식 + Jev | 클라우드 속성(HTTPS LB, 다중 태스크)과 대조해 '클라우드에서만 깨지는 것'만 남김 |
| `generate_portability_patch` | 토글 ON일 때만 LLM이 지원 패턴 안에서 패치. worktree 커밋 → 테스트 통과 → 승인 → 계획부터 재진입. 새 키는 매니페스트에 등록(I4 연결) | MinIO 대상 통합 테스트 | 코드는 하나. 버킷 이름은 IaC 출력값에서 매핑 |

| `verify_statelessness` + `prove_fix_both_envs` | 태스크 2개가 번갈아 응답해도 파일이 유지되는지 확인하고, 패치 전/후 증거 표를 만든다 | 리허설 스택의 복제본 2개 | desired 2, 응답 헤더에 태스크 ID. 강제 교체는 백그라운드 |

**AI가 필요한 이유(한 문장)**: 같은 파일 쓰기라도 영속 데이터인지 캐시인지 가르고, 앱마다 모양이 다른 저장 코드를 의미를 지키며 객체 스토리지 호출로 바꾸는 일은 규칙 치환으로 할 수 없다. 규칙은 후보까지만 뽑는다.
- 단, 이 주장은 실측표로 뒷받침해야 한다. 샘플 결함 커밋 10개를 코드 모양을 다르게 만들어, 'semgrep autofix만' 대비 '규칙+AI'의 탐지·수정 성공률을 비교한다.

**3분 데모 장면**
- 0:15–0:25 Jev 분류 카드
- 0:25–0:45 리허설 빨간불과 동시에 패치 생성
- 0:45–0:58 diff 승인
- 2:25–2:45 휴대폰으로 공개 URL 접속, 태스크 ID가 바뀌어도 사진 유지
- AI가 보이는 구간 합계 약 45초(추정). 전체는 5장 조합안 A 참조.

**비슷한 2025 작품 대비 나아지는 점**
- Mango는 AI가 인프라 파일(Dockerfile)만 만들었다. 우리는 **앱 코드**를 고치고, 패치 전·후 증거 표를 병합 조건으로 삼는다.
- 증거 표 6칸 중 5칸이 라이브다. '패치 전 클라우드' 칸만 이전 기록이다.

**겹침 회피**

**난이도**: 업로드 한정이면 중(추정), 원안은 중~상.

### 4-2. I7 변경 맞춤 판별 프로브 + 교차 비교 — 조합안 B의 주력

**개발자 불편과 근거**
- 배포 성공이 곧 기능 성공은 아니다. 고정 스모크는 '이번 변경'을 확인하지 않는다.
- 근거
  - Microsoft fabric-cicd 이슈 #1125(배포 성공 보고 후 런타임 실패)(https://github.com/microsoft/fabric-cicd/issues/1125)
  - 같은 저장소 #491(완료라는데 반영 안 됨)(https://github.com/microsoft/fabric-cicd/issues/491)
  - RDS MySQL 기본 시간대는 UTC(https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/MySQL.Concepts.LocalTimeZone.html)
  - Google SRE: 장애의 약 70%가 라이브 시스템 변경에서 온다(https://sre.google/sre-book/introduction/)
- 강도: 중(사례 수준, 교차 환경 불일치 빈도 통계는 없음).

**강조 툴**
- `generate_change_probe`
  - LLM이 diff를 읽고 선언형 프로브 JSON 1~3개를 만든다(HTTP 순서, JSONPath 단언, SELECT만).
  - 빌드와 병렬이라 핵심 경로에 시간이 더해지지 않는다.
- `check_probe_discriminates`
  - 로컬에서 **현재 실행 중인 이전 버전에는 FAIL, 일회용 스택의 새 이미지에는 PASS**여야 채택한다.
  - 클라우드에서는 실행하지 않는다.
- `compare_env_results`
  - 프로브와 고정 시나리오를 로컬(localhost)과 클라우드(공개 HTTPS)에 동시에 돌려 필드 단위로 비교한다.
  - 정규화는 ID와 생성 시각에만 적용한다. **검증 대상 필드(eta)는 정규화에서 빼야** 결함이 지워지지 않는다(회의론 지적).
- `diagnose_parity_gap`
  - Jev가 원인 범주를 고르고 LLM이 조치를 설명한다.
  - 자동 조치는 `rollback_tier`와 CDN 무효화만 한다. 나머지는 I4 동기화 등으로 제안만 한다.

**AI가 필요한 이유(한 문장)**: 새 필드의 이름·경로·형식은 커밋마다 달라 규칙으로 변경 맞춤 검사를 만들 수 없고, LLM이 만든 결과는 판별력 검사와 교차 비교가 결정적으로 검증한다.

**3분 데모 장면**
- 0:13–0:35 생성된 프로브 3줄
- 0:35–1:05 '이전 FAIL · 새 PASS'
- 2:05–2:15 양쪽 모두 초록불
- 2:15–2:35 클라우드만 불일치 → 롤백 + 원인 '시간대'

**결함 재설계**
- 날짜가 어긋나는 시각은 KST 00~09시뿐이다(데모 코치 지적). 그래서 프로브 입력 시각을 **08:30 KST(=전날 23:30 UTC)로 고정**해 발표 시각과 상관없이 재현되게 한다.
- 심어 둔 결함이라는 사실은 공개한다.

**비슷한 2025 작품 대비 나아지는 점**
- Deploy Land는 단일 클라우드에서 헬스로 판정했다. 우리는 로컬을 **대조군**으로 쓰는 교차 비교와 판별력 검사 결과를 화면에 보여 준다.
- 발견한 차이를 I4 조치로 이어, 찾기만 하는 도구에서 벗어난다.

**겹침 회피**
- Checksum·Octomind·Meticulous는 계속 유지하는 AI 테스트다.
- 우리는 **배포 1회용 판별 프로브**이고, Web→WAS→DB를 관통하며, 두 환경에서 동시에 돌고, 결과가 롤백 게이트에 바로 연결된다.
- 차별점은 반드시 '교차 환경 비교'로 말한다.

**난이도**: 중.

### 4-3. I4 설정 계약 — 두 조합안 공통 입력층

**개발자 불편과 근거**
- ECS는 지정한 시크릿이 없으면 ResourceInitializationError로 태스크 시작에 실패한다(https://docs.aws.amazon.com/AmazonECS/latest/developerguide/resource-initialization-error.html).
- 시크릿 값을 바꾼 뒤에는 재배포해야 반영된다(https://docs.aws.amazon.com/AmazonECS/latest/developerguide/secrets-envvar-secrets-manager.html).
- Vite `import.meta.env`는 빌드 때 정적으로 치환된다(https://vite.dev/guide/env-and-mode).
- Next.js `NEXT_PUBLIC_` 값은 빌드 때 번들에 인라인된다(https://nextjs.org/docs/app/guides/environment-variables).
- 강도: 메커니즘은 강함. 빈도 통계는 없음.

**강조 툴**
- `extract_config_contract`
  - 규칙이 설정 읽기 지점을 모은다.
  - Jev가 키마다 tier, 시점(빌드/런타임), 종류(비밀/일반/주소), 필수 여부, 클라우드 값 출처를 고른다.
- `reconcile_config_targets`
  - 계약, 로컬 .env, 클라우드 저장소·태스크 정의를 **이름 목록으로만** 대조한다(값은 읽지 않음).
  - 누락이 있으면 계획에 단계를 추가한다.
- `sync_env_to_cloud`
  - 일반값과 IaC 출력 매핑값은 자동으로 등록한다.
  - 비밀값은 배포를 멈추고 `request_approval`로 사람이 입력한다.
- `rebuild_web_for_target`
  - 런타임 config.js 규약을 기본으로 채택하면, 이 툴은 규약 위반을 감지해 대상별 재빌드 단계를 병렬로 추가하는 역할로 줄어든다.

**AI가 필요한 이유(한 문장)**: '누가 언제 읽고 클라우드에서는 어떤 값이어야 하나'(빌드 치환 여부, localhost → 관리형 엔드포인트 매핑)는 스택마다 달라 접두사 규칙만으로는 모자란다.
- 다만 70~80%는 규칙으로 된다는 점을 **먼저 인정**한다. 호출 비용이 작다는 점을 'AI 비용 대비 효과' 서사에 쓴다.

**3분 데모 장면**: 계획 카드에 'by ai' 단계 1~2개(10~20초). 예: A에서는 패치가 만든 `S3_BUCKET` 키를 IaC 출력값으로 매핑해 자동 등록한다.

**2025 대비 나아지는 점**: Yoitang이 칭찬받은 신뢰 경계를 '비밀값은 AI와 파이프라인이 보지 않고, 사람 승인으로만 등록한다'는 설계 결정으로 설명한다.

**겹침 회피**
- Doppler·Infisical·Vercel 환경변수 UI·zod/envalid와 겹친다.
- 우리 차별점은 연결이다: diff에서 새 키 발견 → 분류 → 계획 단계 자동 추가.
- 단독 주력으로는 쓰지 않는다.

**난이도**: 하~중.

### 4-4. I5 클라우드 계약 리허설 — 조합안 A에서 결함을 드러내는 층

**개발자 불편과 근거**
- Cloud Run 컨테이너 계약: 메모리 기반 파일시스템, 인스턴스 임의 종료(https://docs.cloud.google.com/run/docs/container-contract).
- AWS Security Hub ECS.5: 루트 파일시스템 읽기 전용을 요구한다(https://docs.aws.amazon.com/securityhub/latest/userguide/ecs-controls.html).
- Compose가 read_only·tmpfs·replicas를 지원한다(https://docs.docker.com/reference/compose-file/services/).
- Hilton 2017: 긴 빌드가 장벽이라는 응답(https://www.cs.cmu.edu/~mhilton/docs/Hilton_CI_Tradeoffs.pdf).
- 강도: 약~중. 리허설이 실제 클라우드 결함을 얼마나 잡는지는 근거가 없다.

**강조 툴**
- `derive_cloud_constraints`: 매핑 표(규칙)로 `compose.cloudsim.yml`을 만든다(read_only, tmpfs, mem_limit, 비root, WAS 복제본 2개).
- `rehearse_cloud_profile`: 같은 이미지를 격리 스택에 띄워 같은 스모크를 돌린다. 실패하면 클라우드 배포를 막는다. 클라우드 호출은 0회다.
- `diagnose_contract_violation`: Jev가 증상을 위반 유형으로 분류한다.

**AI가 필요한 이유**: 약하다는 점을 솔직히 밝힌다. 이 층은 AI 점수가 아니라 두 가지로 기여한다.
- **클라우드 실패를 라이브에서 안전하고 결정적으로 보여 주는 데모 안정성**
- 클라우드 제약을 로컬로 가져오는 '환경 차이 흡수 설계'

**3분 데모 장면**: 0:25–0:45. 복제본 A에 업로드 → 복제본 B에서 조회 404 + read-only 쓰기 오류 → 빨간불, 클라우드 배포 차단.

**2025 대비 나아지는 점**: 대응하는 작품이 없다. Blue식 PoC처럼 '결함 커밋 N개 중 리허설이 클라우드 실패를 몇 건 미리 잡았나' 실측표를 설계문서에 넣는다.

**겹침 회피**: act·LocalStack·Skaffold와는 방향이 반대다. 그것들은 로컬 개발 루프나 AWS API를 흉내 내고, 우리는 클라우드의 런타임 제약을 로컬로 가져온다.

**난이도**: 하~중.

## 6. 하위 후보를 버리는 이유와 설계문서 문구

**버리는 이유(한 줄씩)**
- **I3**: 조건부 보류. 팀 전제(3tier, DB 사전 배포)와 충돌하고, 주최 측 예시라 겹치며, ORM이면 AI 몫이 작다. SQLite 샘플 앱을 택할 때만 A의 고치는 층을 대체한다.
- **I1 단독**: 버리지 않고 I2와 패치 엔진을 공유해 흡수한다. 단독이면 semgrep·codemod로 대체된다는 공격에 약하다.
- **I5 단독**: A에서 결함을 드러내는 층으로만 쓴다. 단독이면 AI·클라우드 기여가 약하다.
- **I6**: 클라우드 배포가 2회라 3분에 안 들어가고 'AI 로그 분석'과 겹친다. 기본 `collect_diagnostics` + 규칙 롤백으로 줄이고, 환경 지문 diff만 I7 진단에 재사용한다.
- **I11**: AI가 필요 없고 작년 우승작 재현이며, ECS 기본 설정으로는 3분이 불가능하다. 컴퓨트를 고른 뒤 트래픽 전환형 롤백 옵션층으로만 검토한다.
- **I9**: 스키마 고정이면 범위가 사라지고, 판정을 리허설이 대신한다. `prepare_db`의 직전 덤프만 기본에 흡수한다.
- **I10**: 클라우드 기여가 없고 결말이 '보류'다. `acquire_deploy_lock`(FIFO·TTL)로 킥오프 예시에 최소 대응한다.
- **I8**: shift-deploy와 정면으로 겹치고, 규칙 도구로 대체되며, D가 두 번 들어간다. `validate_plan` 규칙 표의 'DB→WAS→Web 순서' 한 줄로 흡수한다.

**설계문서 "검토한 대안" 문구(초안, A 채택 시)**

> **검토한 대안.** 개발자 불편 11개를 인프라·회의론·데모·2025 수상 패턴의 네 관점으로 점수화했다. 실패 원인 AI 분석은 불편 근거가 가장 강했지만 클라우드 배포가 두 번 필요해 3분 라이브에 들어가지 않았고, 기존 제품·작품과 겉모습이 같아 제외했다. 블루그린 선언은 작년 최우수작과 겹치고 AI가 필요하지 않았다. 롤백 안전성, 배포 순서, 동시 배포 의미 충돌은 소규모 3tier 앱에서 빈도 근거가 약하고 규칙 도구로 상당 부분 대체되어, 각각 덤프 게이트, 순서 규칙, 배포 잠금으로 기본 파이프라인에 흡수했다. SQLite→관리형 DB는 주최 측 예시라 겹침 가능성이 높아 보류했다. 우리는 '로컬 전제 코드를 AI가 고치고 두 환경에서 증명한 뒤 배포한다'를 택했다. AI의 모든 판단은 빌드·테스트·리허설·스모크라는 결정적 검증으로 닫고, AI는 IaC 생성, 클라우드 권한 변경, 비밀값 열람을 하지 않는다.
