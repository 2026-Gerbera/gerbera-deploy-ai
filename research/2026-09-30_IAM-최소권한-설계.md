> 질문(정준우): ① 배포할 때마다 DB·시크릿·KMS 등 필요한 권한이 달라서 결국 모든 권한을 주게 되지 않나. ② 로컬 한 곳에서 CI·CD를 다 돌리면 권한 격리가 어렵지 않나.
>

>
> 액션·리소스 유형·조건 키는 AWS Service Authorization Reference 웹 페이지(`list_ecs.html` 등)의 Actions 표와, 같은 데이터의 공식 JSON(`servicereference.us-east-1.amazonaws.com/v1/<서비스>/<서비스>.json`, 2026-09-30 내려받음)으로 대조했습니다. JSON의 `Operations` 표는 "boto3 메서드 → 인가되는 IAM 액션" 대응을 줍니다(7절 테스트에 씀).
>
> **적대적 검토 반영(2026-09-30, 같은 날 재검토).** 액션 이름·조건 키가 SAR JSON에 있는지는 다시 대조했고, 모두 있었습니다. 고친 것:
> - **데모를 깨뜨릴 수 있는 것(정상 호출이 거부됨):**
>   - ELB 조건 키 두 개는 다중값 키입니다. 그래서 `ForAnyValue`/`ForAllValues`로 바꿨습니다(ELB 문서 예시와 같은 형태).
>   - `acm:RequestCertificate` 호출에는 `ValidationMethod`·`KeyAlgorithm`를 반드시 명시해야 합니다.
>   - 태스크 정의 등록을 패밀리 ARN으로 제한하면 정상 호출도 거부될 수 있습니다. SAR은 리소스 수준 권한을 지원한다고 적고, ECS 개발자 안내서는 지원하지 않는다고 적어 서로 다릅니다.
>   - StartBuild override Deny도 정상 빌드를 막을 수 있습니다.
>   - `aws login` 프로필을 Python 앱이 쓰려면 `botocore[crt]`가 필요합니다. 로컬에는 `awscrt`가 설치되어 있지 않습니다.
>   - Lambda 동기 호출에서 읽기 시간 초과가 나면 botocore가 같은 요청을 다시 보냅니다.
> - **과장이던 주장:**
>   - "컨테이너 코드는 실행 역할 권한을 못 쓴다"는 틀렸습니다. 배포 역할은 실행 역할을 *태스크 역할*로도 붙일 수 있습니다(E2).
>   - "P1이면 노트북이 털려도 안전"도 고쳤습니다. 소스는 여전히 노트북이 올리므로, 그 코드는 앱 비밀과 DB 계정으로 실행됩니다(E17).
> - **추가한 경로:** E15(SECRET_KEY를 아는 값으로 덮어쓰기), E16(P1 롤백으로 P0 시절의 악성 리비전 되살리기), E17(코드 출처).
> - **범위:** 예약 동시성 1은 신규 계정에서 사실상 불가능합니다(예약하고도 비예약 100이 남아야 함). 9-4에 3일 범위 판정표를 넣었습니다.
>
> **AI Terraform 결정 반영(2026-09-30 새벽, single-app 장부 21~24).** 이 문서의 원래 전제 "인프라·IAM은 사람(C1)이 Terraform으로 만들고 앱은 배포만 한다"가 바뀌었습니다. 이제 **Terraform도 AI가 짜고**(플랫폼까지 전부, 공유 RDS 안에 앱 DB·계정), **IAM은 AI가 설계 → 사람이 검증·승인 → 생성**, 앱 역할·DB 계정은 최소 권한, 테스트 때 권한은 넓게입니다. 그래서:
> - 파이프라인이 IAM 역할을 만들게 되어 "역할을 만들 수 있으면 관리자 역할도 만들 수 있다"는 권한 상승 경로가 생깁니다. 대응은 **권한 경계**로 IAM 생성을 위임하는 AWS 공식 패턴입니다(**13절 신설**: 경계 정책 JSON, 위임 문, 부트스트랩 모드 권한, SCP 비교).
> - 6절 권한 상승 경로 표에 E18~E26을 더했고 E14를 고쳤습니다(부트스트랩 모드는 승인 시점에 관리자 자격을 씀).
> - 1·2·7·8·9절의 "Terraform(사람)"·"C1이 apply" 문장은 "AI Terraform + 사람 승인"으로 정리했습니다. 4·5절의 배포 역할(`ddak-deployer`)·Lambda 설계는 앱 배포 step의 권한으로 그대로 유효합니다.
> - 13절 JSON은 공식 패턴을 적용한 **초안**입니다. 파싱만 확인했고, Terraform이 부르는 읽기·보조 액션이 빠졌을 수 있어 테스트 계정 CloudTrail로 확정해야 합니다.
>
> **같은 날 적대적 재검토(9/30).** 고친 것:
> - 부트스트랩 순서가 성립하지 않았습니다(plan은 승인 전에 도는데 상태 버킷·plan 자격은 apply 때 생김). → **기반 준비**(상태 버킷·경계·파이프라인 역할, 코드 고정 템플릿, 별도 승인)를 먼저 두고, 파이프라인 역할·경계는 AI Terraform 상태 밖에 둡니다(13-7).
> - `NoSelfModification`이 `iam:*` Deny라 `GetRole`까지 막아, 파이프라인 역할이 상태에 있으면 개선 배포 refresh가 전부 실패했습니다. → `NotAction`으로 읽기를 빼고, refresh용 `ReadIamForRefresh`를 더했습니다(13-4·13-5).
> - 배포 역할의 PassRole ARN이 경로 없는 이름(`role/ddak-ecs-exec-app`)이라, 앱 역할이 `/ddak/app/` 경로로 생기면 정상 배포가 거부됩니다. → 경로를 넣고, 이름은 코드 소유 이름 규칙 변수로 고정합니다(4-1·5-2).
> - 경계로 못 막는 경로 E27(신뢰 정책 주체), E28(앱 경로 관리형 정책을 경계 없는 역할에 부착 후 버전 교체), E29(마스터 시크릿), E30(AI HCL의 파일 읽기 함수로 자격증명 유출), E31(승인 버튼 CSRF)를 더했습니다. 대응은 정적 게이트 규칙·자격 전달 방식·승인 POST 검사입니다.
> - 좁은 파이프라인 역할·읽기 세션은 3일 범위에서 P1로 내렸습니다(P0는 장부 24대로 테스트 프로필 + 앱 경계 + 정적 게이트 + 사람 승인).
>
> **9/30 낮 결정 반영(single-app 장부 25~36, 14절 신설).** 이 문서보다 결정이 우선입니다.
> - ✅ 장부 28: **이미지 저장소 기본 = Docker Hub**, ECR은 옵션 어댑터. 그래서 배포 역할·CodeBuild 역할·ECS 실행 역할·앱 경계·파이프라인 경계·plan 읽기 세션에서 **ECR 권한을 뺐고**, 토큰 시크릿 읽기를 넣었습니다(CodeBuild = `ddak-platform/dockerhub-push`, 실행 역할 = `ddak-platform/dockerhub-pull`). 온프렘은 AWS 자격 없이 읽기 전용 토큰으로 pull합니다. 4-1·4-3·4-4·13-3·13-5·13-6 JSON을 고쳤고 변경 요약과 ECR 옵션 표는 14절입니다.
> - ✅ 장부 32: 데모 시크릿 장면. v2의 새 SECRET_KEY는 AI Terraform이 **앱 층**에 시크릿(값 없음) + 실행 역할의 그 시크릿 읽기 권한을 추가하고(사람 승인), 값은 파이프라인 코드가 PutSecretValue합니다. 실행 역할 정책의 v1 → v2 차이와 배포 역할이 바뀌지 않는 이유는 14-4절입니다.
> - 💭 장부 36: 이름 통일. 시크릿 `ddak/<앱>/<KEY>`(예 `ddak/flaskr/SECRET_KEY`), 플랫폼 시크릿 `ddak-platform/*`. 옛 `ddak/app/*`·`ddak/db/*`(이 문서)와 `flaskr/cloud/*`(single-app 옛 문서)를 대체합니다. 역할 이름 권고(`ddak-<앱>-<용도>`)는 14-2절 대응표로만 두고 0~13절의 역할 이름은 그대로 둡니다(N44 확정 뒤 일괄 교체).
> - 💭 장부 35: DB 계정은 앱(DML)·마이그레이션(DDL)으로 나누고 비밀번호는 Secrets Manager(`ddak/<앱>/DATABASE_URL`, `ddak/<앱>/DATABASE_URL_MIGRATOR`). RDS IAM 인증은 P2.
> - 새 경로 E32~E34(CodeBuild 환경 변수 type override로 push 토큰 읽기, 빌드 중 push 토큰 탈취, 실행 역할을 태스크 역할로 붙여 pull 토큰 읽기)는 14-6절입니다. JSON 파싱 확인 결과는 14-7절입니다.

## 1. 전제와 자리표시자

정책 JSON의 `${...}`는 자리표시자입니다. AI Terraform 이후(13절)에는 두 가지로 씁니다: (a) 권한 경계처럼 **코드가 소유하는 정책**은 부트스트랩 때 코드가 값을 채워 만들고, (b) 앱·배포 역할 정책은 AI가 HCL로 설계하되 이 문서의 JSON을 **기준(reference)**으로 받아 `CheckNoNewAccess`로 대조합니다. 값은 인프라 출력과 코드 소유 변수에서 옵니다. IAM 정책 변수(`${aws:username}` 등)는 쓰지 않으므로 충돌하지 않습니다.

| 자리표시자 / 이름 | 뜻 | 비고 |
|---|---|---|
| `${account_id}` | 계정 ID | 리전은 `ap-northeast-2` 고정 |
| `${source_bucket}` / `sources/ddak-src.zip` | 소스 버킷(버저닝) / **고정 키 하나** | 업로드할 때마다 새 버전이 생기고, StartBuild의 `sourceVersion`에 그 버전 ID를 줍니다. 키가 고정이라 PutObject 리소스를 객체 1개로 좁힐 수 있습니다 |
| `ddak-build` | CodeBuild 프로젝트 | buildspec은 플랫폼이 고정 |
| 클러스터 `ddak`, 서비스 `web`·`was` | ECS | |
| 패밀리 `ddak-web`·`ddak-was`·`ddak-migrate` | 태스크 정의 | docs/17은 `flaskr-app`·`flaskr-migrate`로 적음 → 이름 통일 **확인 필요** |
| 저장소 `ddak-web`·`ddak-was` | ~~ECR, IMMUTABLE 태그~~ → 9/30 낮 ✅ 장부 28: **Docker Hub 비공개 저장소**(`docker.io/<조직>/<이미지>@sha256`), ECR은 옵션일 때만 이 이름 | docs/17은 `flaskr-web`·`flaskr-was`. Docker Hub 저장소 수·이름은 single-app N37 |
| `ddak-platform/dockerhub-push`, `ddak-platform/dockerhub-pull` | Docker Hub 읽기·쓰기 토큰 / 읽기 전용 토큰 시크릿(💭 이름, 장부 36). 컨테이너는 AI Terraform, 값은 사람 | push는 CodeBuild 역할만, pull은 ECS 실행 역할(`repositoryCredentials`)만 읽음. 앱 경계 `ddak/*` 패턴 밖(14-2) |
| `${alb_name}/${alb_id}` | ALB | 80 리스너는 Terraform, 443은 `ensure_tls` |
| `${hosted_zone_id}` / `${app_domain}` | 허용 호스팅 영역 1개 / 서비스 도메인 | 도메인은 소문자, 끝 점 없이(Route 53 조건 키 정규화 규칙) |
| `ddak/${app}/*` (옛 `ddak/app/*`) | **파이프라인이 쓰는** 앱 비밀(예: `ddak/flaskr/SECRET_KEY`, 💭 장부 36). `${app}` = 앱 이름(flaskr) | 배포 역할은 쓰기만, 읽기 없음. v2의 `SECRET_KEY` 시크릿 리소스는 AI Terraform이 앱 층에 만듦(✅ 장부 32) |
| `ddak/${app}/DATABASE_URL`, `ddak/${app}/DATABASE_URL_MIGRATOR` (옛 `ddak/db/app`, `ddak/db/migrator`) | DB 비밀(앱 사용자 / DDL 사용자, 💭 장부 35) | **AI Terraform이 값 없이 컨테이너만 만들고, 값은 부트스트랩의 DB 초기화 step(코드, 난수)이 한 번 씁니다**(13절, 옛 "사람(C1)만 씀"을 대체). 개선 배포 run은 읽지도 쓰지도 않음. 옛 `flaskr/cloud/*`(single-app)도 이 이름으로 통일(💭 장부 36) |
| 로그 그룹 | `/aws/codebuild/ddak-build`, `/ecs/ddak-web`, `/ecs/ddak-was`, `/ecs/ddak-migrate`, `/aws/lambda/ddak-deploy` | 전부 인프라 step(AI Terraform)이 미리 만듦 → 런타임 역할에 `CreateLogGroup` 불필요 |
| 시크릿 컨테이너 | AI Terraform이 **값 없이 생성**(`aws_secretsmanager_secret_version`은 값이 상태에 평문으로 남으므로 정적 게이트로 금지) | 파이프라인은 `CreateSecret` 없이 `PutSecretValue`만. ✅ 장부 32로 결정(새 앱 비밀도 AI Terraform이 컨테이너를 만들고 코드가 값을 씀). docs/17의 "DescribeSecret→CreateSecret" 흐름은 쓰지 않음 |

## 3. 액션별 리소스 수준 권한 · 조건 키 검증표

"필수" = SAR 표에서 리소스 유형에 `*` 표시. "없음" = 리소스 유형이 없어 `Resource: "*"`만 가능.

| 액션 | 쓰는 툴 | 리소스 유형 | `"*"`만? | 쓸 수 있는 조건 키 | 우리 제한 | 비고 |
|---|---|---|---|---|---|---|
| `s3:PutObject` | receive_deploy_request | object (선택형: object·accesspointobject 중 하나) | 아니오 | `s3:x-amz-server-side-encryption` 등 | 객체 1개(`sources/ddak-src.zip`) | boto3 `upload_file`이 8MB를 넘어 멀티파트로 가도 CreateMultipartUpload·UploadPart·Complete는 `s3:PutObject`로 인가, 중단만 `s3:AbortMultipartUpload` [확인: Operations 표] |
| `codebuild:StartBuild` | build_image | project (필수) | 아니오 | `codebuild:source.buildspec`(Null만), `source.location`, `environment.image`, `environment.privilegedMode`, `serviceRole`, `environment.environmentVariables.name` 등 64개 | 프로젝트 1개 + override Deny 6개 | **`sourceVersion`·timeout·debugSession 키는 없음** → 코드 검증 [확인: 선행 조사, SAR]. `environmentVariables.name`이 StartBuild override에 적용된다는 점은 CodeBuild 조건 키 문서 예시("MY_APP_VERSION override 거부")로 [확인]. `environment.image`·`privilegedMode`·`serviceRole`·`source.location`은 **양쪽 방향 모두 [실측 필요]**: override 필드만 보는지, 아니면 프로젝트 설정까지 합친 값을 보는지. 합친 값을 보면 Null Deny가 **모든 정상 빌드를 막습니다**. 10/1 양성 스모크에서 막히면 이 4개 Deny를 빼고 코드 검증(툴 스키마에 노출 안 함)으로 대신합니다 |

| `EcsUpdate*`의 `ArnLikeIfExists` | `forceNewDeployment`만 보내는 호출(태스크 정의 없음)도 허용하려고 | 키가 없으면 통과하므로 서비스 설정 변경(loadBalancers 등)은 코드 검증이 막음 |

| `TlsModifyOwnListeners` | 우리 ALB 리스너만. `SecurityPolicy` 키는 ModifyListener에만 있어 문장을 따로 둠(AddListenerCertificates·ModifyListenerAttributes에는 이 키가 없음 [확인]). `ForAllValues`는 키가 없으면 참이라, SslPolicy가 없는 80→301 호출은 통과하고 SslPolicy를 바꾸는 호출은 허용 목록만 통과 | ModifyListener로 80을 **외부 URL로 redirect**하는 것은 IAM으로 못 막음 → 코드 검증(대상 호스트 = `${app_domain}`, 포트 443만). **Terraform 드리프트:** 80 리스너는 Terraform 소유라 C1이 다시 `apply`하면 301이 forward로 되돌아감 → `lifecycle { ignore_changes = [default_action] }` 필요(C1) |

| 항목 | 값 | 근거 |
|---|---|---|
| 누가 | 팀 IAM 사용자(`ddak-*`) 또는 Identity Center 권한셋 역할. **루트는 `aws:PrincipalArn`이 `:root`라 매치되지 않음** | [확인] aws:PrincipalArn은 역할 세션이 아니라 역할 ARN을 반환 |

| MFA | **신뢰 정책에 `aws:MultiFactorAuthPresent`를 넣지 않습니다.** 이 키는 연동(federated) 신원에는 없어서 SSO 사용자가 막힙니다. MFA는 Identity Center(또는 IAM 사용자 콘솔 로그인)에서 강제합니다. `aws login`으로 받은 세션에 MFA 컨텍스트가 실리는지는 **확인 필요** | [확인] IAM 전역 조건 키 문서 |
| 감사 | 프로필에 `role_session_name = ddak-<이름>`. CloudTrail에 사람이 남음 | [판단] |
| Identity Center 경로 | 권한셋 역할 경로에 Identity Center 리전이 들어가는 경우와 안 들어가는 경우가 있어 `sso.amazonaws.com/*AWSReservedSSO_…`로 둘 다 받게 했습니다 [판단]. 계정이 Identity Center를 쓸 수 있는지(주최측 계정 여부) **확인 필요** | – |

로컬 프로필 예(`~/.aws/config`). `aws login`(CLI 2.32+) 또는 `aws sso login` 뒤 앱이 `ddak-deployer` 프로필을 씁니다. 로그인 세션은 CLI가 15분마다 갱신하고 최대 12시간입니다 [확인].

```ini
[profile ddak-login]
login_session = arn:aws:iam::<account_id>:user/ddak-joonwoo
region = ap-northeast-2

[profile ddak-deployer]
role_arn = arn:aws:iam::<account_id>:role/ddak-deployer
source_profile = ddak-login
role_session_name = ddak-joonwoo
duration_seconds = 3600
region = ap-northeast-2
```

**Python 앱에서 `aws login` 프로필을 쓸 때 필요한 것 [확인: 로컬].** 로컬 botocore 1.43.46의 `LoginProvider`는 `awscrt`가 없으면 `MissingDependencyException`("pip install botocore[crt]")을 냅니다(`credentials.py`). 이 노트북의 Python 3.12에는 `awscrt`가 **설치되어 있지 않습니다.** AWS CLI v2는 자체 Python에 crt를 내장합니다. 그래서 `aws sts get-caller-identity --profile ddak-deployer`는 되는데 앱만 실패하는 함정이 생깁니다.
- 대응: 앱 가상환경에 `pip install "boto3[crt]"`를 넣습니다. 팀원 전원 동일하게 합니다.
- 대안: 별도 프로필 `[profile ddak-login-proc]`에 `credential_process = aws configure export-credentials --profile ddak-login --format process`를 두고, `ddak-deployer`의 `source_profile`을 `ddak-login-proc`로 바꿉니다. 같은 프로필 안에 두면 자기 자신을 다시 부르게 됩니다.
- T6(시작 검사)에서 `login_session` 프로필이면 `import awscrt`를 먼저 확인하고, 실패하면 설치 안내를 띄웁니다. SSO 경로(`aws sso login`)는 crt가 필요 없습니다.

**E13 상세: CodeBuild 서비스 역할 탈취 시 피해 범위**

빌드는 플랫폼 고정 buildspec이지만 사용자 Dockerfile의 `RUN`과 앱 코드가 빌드 중에 실행됩니다. 빌드 컨테이너는 서비스 역할 자격증명을 컨테이너 자격증명 엔드포인트로 받습니다(선행 조사). `docker build`의 RUN 단계에서 그 자격증명에 닿는지는 **확인 필요**이므로 **닿는다고 가정**합니다.

| 할 수 있는 것 | 할 수 없는 것 | 줄이는 방법 |
|---|---|---|
| 저장소에 이미지 push(**이미지 오염**). 9/30 낮: Docker Hub push 토큰 시크릿을 읽을 수 있으므로 토큰 범위 안의 모든 저장소·태그에 push 가능(E33) | ECS 변경, 태스크 정의 등록, PassRole | 배포는 항상 digest 고정(`docker.io/…@sha256`, 실행기는 CodeBuild가 기록한 digest만 씀). Docker Hub 태그 불변 설정 유무는 확인 필요(ECR 옵션이면 IMMUTABLE [확인]). 토큰은 우리 저장소 쓰기로만 좁힘(💭 조직 토큰, N37) |
| 소스 객체 과거 버전 읽기 | 앱 비밀 읽기(GetSecretValue는 push 토큰 하나뿐) | 소스에 비밀을 넣지 않음(dev 값만) |
| 빌드 로그 쓰기(로그 위조) | IAM, 다른 버킷·저장소 | 로그는 판단 근거로 쓰지 않고 BatchGetBuilds 상태·exported variables의 digest로 판단(9/30 낮: Docker Hub. ECR 옵션이면 ECR digest) |

전제 하나: "플랫폼 고정 buildspec"은 Terraform `aws_codebuild_project`의 `source.buildspec`에 **YAML 본문을 인라인으로** 넣어야 성립합니다. 비워 두거나 파일 이름을 적으면 CodeBuild는 소스 zip 안의 파일을 읽습니다. 그러면 buildspec override Deny와 상관없이 소스를 올린 사람이 buildspec을 정합니다 [판단: CodeBuild buildspec 위치 규칙].

한계(정직하게): 빌드가 만든 이미지는 결국 배포됩니다. 빌드 탈취는 곧 이미지 탈취이고, 이는 CI 일반의 성질입니다. 우리가 보장하는 것은 **빌드 탈취가 런타임 비밀·DB·배포 제어로 번지지 않는다**는 것입니다.

## 7. 레지스트리 메타정보로 IAM 선언하기

### 7-1. 필드

현재 `src/ddak/core/registry.py`(단일 패키지 `ddak`, single-app N23)의 `ToolSpec`에 필드 하나를 더합니다. **plane**(ci / cd / read / tls)만 툴이 적고, 어느 역할에 들어갈지는 모드(P0/P1)별 표가 정합니다. 그래서 P0→P1 전환 때 툴 선언은 바뀌지 않습니다.

```python
@dataclass(frozen=True)
class AwsPerm:
    plane: Literal["ci", "cd", "read", "tls"]
    actions: tuple[str, ...]                  # "ecs:UpdateService"
    resources: tuple[str, ...]                # ARN 템플릿(${account_id} 등). "*"는 허용 목록 액션만
    conditions: Mapping[str, Mapping[str, object]] = MappingProxyType({})
    why: str = ""                             # 리뷰어가 읽는 한 줄

# ToolSpec에 추가
#   aws: tuple[AwsPerm, ...] = ()

ROLE_OF = {
    "p0": {"ci": "ddak-deployer", "cd": "ddak-deployer", "read": "ddak-deployer", "tls": "ddak-deployer"},
    "p1": {"ci": "ddak-trigger", "cd": "ddak-deploy-lambda", "read": "ddak-trigger", "tls": "ddak-tls"},
}
# p1에서 cd 권한을 가진 툴이 하나라도 있으면 ddak-trigger에 lambda:InvokeFunction(함수 1개)을 자동으로 더한다.

TD_WAS = "arn:aws:ecs:ap-northeast-2:${account_id}:task-definition/ddak-was:*"
SVC_WAS = "arn:aws:ecs:ap-northeast-2:${account_id}:service/ddak/was"

DEPLOY_TIER_AWS = (
    AwsPerm("cd", ("ecs:RegisterTaskDefinition",), (TD_WAS,), why="digest 고정 새 리비전"),
    AwsPerm("cd", ("iam:PassRole",), (ROLE_EXEC_APP, ROLE_TASK_FLASKR),
            {"StringEquals": {"iam:PassedToService": "ecs-tasks.amazonaws.com"}}),
    AwsPerm("cd", ("ecs:UpdateService",), (SVC_WAS,),
            {"ArnLikeIfExists": {"ecs:task-definition": TD_WAS}}),
    AwsPerm("read", ("ecs:DescribeServices",), ("arn:aws:ecs:ap-northeast-2:${account_id}:service/ddak/*",)),
)
```

- **AI Terraform 이후(13절) 이 생성기의 위치 💭:** IAM은 AI가 HCL로 설계합니다(장부 23). 이 생성기의 출력은 정책 그 자체가 아니라 **기준 정책**이 됩니다. `plan_infra`가 `CheckNoNewAccess(기준·경계, AI 설계)`와 "툴 선언 액션 ⊆ AI 설계"를 확인해 과소·과대 설계를 승인 화면에 띄웁니다. 아래 원래 설명(Terraform `templatefile`로 그대로 씀)은 사람이 Terraform을 쓰던 전제입니다.
- 생성: `python -m ddak_core.iam render --mode p0` → 역할별로 같은 (리소스, 조건) 묶음을 합치고, 툴과 무관한 **가드레일 Deny**(override Deny, GetSecretValue Deny, Exec Deny, privileged Deny)를 역할별 고정 목록에서 붙여 `infra/terraform/iam/<역할>.json.tftpl`로 씁니다.
- Terraform은 `templatefile("iam/ddak-deployer.json.tftpl", {...})`로 **그 파일을 그대로** 씁니다. "Terraform 정책과 비교"를 "같은 파일을 쓴다"로 바꾸는 것이 3일 범위에서 가장 싸고 확실합니다 [판단].
- 사람 관리자(C1)는 생성물 diff를 PR에서 승인합니다. 권한이 늘면 diff에 바로 보입니다. (AI Terraform 이후: 사람은 관리 페이지의 IAM diff를 승인합니다, 13-8.)
- P1에서 cd plane 호출은 툴이 아니라 Lambda 안의 `ddak_cloud_core`가 합니다. 그래서 T1은 `mode=direct`(같은 코어 함수를 노트북 세션으로 호출)로 돌려야 cd 선언을 검증할 수 있습니다. `mode=lambda`에서 보이는 호출은 `lambda:InvokeFunction`뿐입니다.
- 3일 안에 생성기를 못 만들면 **기준** 정책 JSON(이 문서 4절)을 손으로 둡니다. 실제로 만들어지는 역할 정책은 AI가 설계합니다(장부 23). "툴 선언 액션 ⊆ AI 설계 정책"과 `CheckNoNewAccess(기준, AI 설계)`만 확인하는 작은 테스트를 둡니다. 발표 문구는 "툴 선언과 AI 설계 정책을 테스트로 대조한다"로 바꿉니다.

## 8. P1 배포 Lambda 설계

### 8-1. 호출 흐름

1. 노트북(`ddak-trigger`): `put_object` → `start_build(projectName=ddak-build, sourceVersion=<버전 ID>, environmentVariablesOverride=[RELEASE_ID, BUILD_TIERS])` → `batch_get_builds` 폴링
2. `invoke(action=migrate)` → `describe_tasks` 폴링(종료 코드 확인)
3. `invoke(action=deploy, migration_task_arn=...)` → `describe_services` + `/version` 폴링
4. 실패 시 `invoke(action=rollback)`

ECS 안정화 대기는 **Lambda 안에서 하지 않습니다.** 각 호출은 등록·갱신·RunTask만 하고 바로 돌아옵니다. 대기와 판단은 노트북이 읽기 권한으로 합니다.

### 8-2. 입력 스키마

```json
{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "title": "DdakDeployRequest",
  "type": "object",
  "additionalProperties": false,
  "required": ["action", "request_id", "run_id", "release_id"],
  "properties": {
    "action": {"enum": ["deploy", "migrate", "rollback", "ensure_app_secret"]},
    "request_id": {"type": "string", "pattern": "^[A-Za-z0-9-]{8,64}$"},
    "run_id": {"type": "string", "pattern": "^[A-Za-z0-9_-]{1,64}$"},
    "release_id": {"type": "string", "pattern": "^rel-[a-z0-9-]{1,40}$"},
    "service": {"enum": ["web", "was"]},
    "image_digest": {"type": "string", "pattern": "^sha256:[a-f0-9]{64}$"},
    "build_id": {"type": "string", "pattern": "^ddak-build:[0-9a-f-]{36}$"},
    "migration_task_arn": {"type": "string", "pattern": "^arn:aws:ecs:ap-northeast-2:[0-9]{12}:task/ddak/[0-9a-f]{32}$"},
    "rollback_to_revision": {"type": "integer", "minimum": 1},
    "secret_name": {"enum": ["SECRET_KEY"]}
  },
  "allOf": [
    {"if": {"properties": {"action": {"const": "deploy"}}}, "then": {"required": ["service", "image_digest", "build_id"]}},
    {"if": {"properties": {"action": {"const": "migrate"}}}, "then": {"required": ["image_digest", "build_id"]}},
    {"if": {"properties": {"action": {"const": "rollback"}}}, "then": {"required": ["service", "rollback_to_revision"]}},
    {"if": {"properties": {"action": {"const": "ensure_app_secret"}}}, "then": {"required": ["secret_name"]}}
  ]
}
```

입력에 **없는 것**: 저장소 이름, 이미지 URI, 역할 ARN, 명령, 환경 변수, secrets, 서브넷, 도메인. 전부 Lambda 코드와 환경 변수(Terraform 출력)에 고정합니다.

### 8-3. 서버 측 검증

| # | 검증 | 방법 | 막는 것 |
|---|---|---|---|
| V1 | 스키마 | 위 스키마, 모르는 필드 거부 | 임의 인자 주입 |
| V2 | 서비스 허용 목록 | `service` → (저장소, 패밀리, 컨테이너 이름, 실행·태스크 역할, secrets 목록, 로그 그룹)을 코드 표에서 조회 | E2·E3 |
| V3 | **digest가 우리 저장소 것인지** | 9/30 낮(✅ 장부 28): 이미지 URI는 `docker.io/<조직>/<고정 저장소>@<digest>`로 코드가 조립하고, digest는 같은 release의 `codebuild:BatchGetBuilds` exported variables(빌드가 기록한 digest)와 같아야 함. (ECR 옵션이면 옛 방식: `${account_id}.dkr.ecr.ap-northeast-2.amazonaws.com/<고정 저장소>@<digest>` + `ecr.describe_images` 성공 + 태그에 `release_id`, IMMUTABLE) | 외부 이미지, 다른 저장소 |
| V4 | 빌드 기록 대조 | `codebuild.batch_get_builds([build_id])`: 프로젝트 = `ddak-build`, `buildStatus = SUCCEEDED`, `exportedEnvironmentVariables`의 `IMAGE_DIGEST_<SERVICE>` = 입력 digest(buildspec `exported-variables`) [확인: Build 모양에 필드 있음] | 빌드를 거치지 않은 push |
| V5 | 태스크 정의는 템플릿으로만 | 코드 템플릿에 digest·release_id만 넣음. `privileged`·`linuxParameters` 없음. 평문 `environment`에 비밀 없음 | E3 |
| V6 | 마이그레이션 | migrate 패밀리 새 리비전(같은 was digest) → `run_task(overrides 없음, enableExecuteCommand=False, clientToken=request_id, startedBy=release_id, networkConfiguration=고정)`. `clientToken`으로 멱등 [확인: botocore 모델] | E6, 중복 실행 |
| V7 | 배포 전 마이그레이션 증거 | was 배포에 스키마 변경이 있으면 `describe_tasks(migration_task_arn)`: STOPPED, 컨테이너 exitCode 0, 패밀리 `ddak-migrate`, `startedBy = release_id`, 이미지 digest 일치 | 순서 위반(노트북이 건너뛰기). **한계:** "스키마 변경이 있는지"를 노트북이 판단하면 건너뛰기를 막지 못합니다. 막으려면 was 배포마다 증거를 요구합니다(마이그레이션은 변경이 없으면 아무것도 안 하는 멱등 명령). 대가는 배포마다 Fargate 태스크 1회(수십 초) [판단] |
| V8 | 갱신 인자 고정 | `update_service(cluster, service, taskDefinition, forceNewDeployment?)`만 | E5 |
| V9 | 롤백 대상 | 같은 패밀리, ACTIVE, 현재보다 낮은 리비전. **추가(검토):** `describe_task_definition`으로 대상의 이미지(우리 저장소 `@sha256`), 실행·태스크 역할, secrets 이름, `privileged` 없음을 서비스 표와 대조합니다. 한 항목이라도 다르면 거부합니다. P1 전환 때 P0 시절 리비전은 C1이 등록 해제합니다 | 다른 패밀리로 롤백 위장, **옛 악성 리비전 되살리기(E16)** |
| V10 | 비밀 생성 | `secret_name` 허용 목록 → `DescribeSecret`으로 AWSCURRENT가 **없을 때만** `secrets.token_urlsafe(48)` 생성 → `PutSecretValue(ClientRequestToken=request_id)`. 응답은 VersionId만, 값은 어디에도 남기지 않음 | 비밀 노출, 의도치 않은 교체(세션 무효화) |

### 8-4. 실행 시간과 호출 방식

| 항목 | 값 | 근거 |
|---|---|---|
| 함수 타임아웃 상한 | 900초(15분) | [확인] Lambda 할당량 |
| 우리 설정 | 60초. 각 액션은 API 2~5회라 수 초 [추정] | – |
| ECS 안정화 대기 | Lambda 밖(노트북 폴링). 새 태스크 RUNNING 30~60초 + 헬스체크 + 드레이닝이라 수 분이 걸릴 수 있음(docs/17 7-1, [추정]) | 15분 안에는 들지만 Lambda를 기다리게 할 이유가 없음 [판단] |
| 호출 방식 | **동기(RequestResponse).** 비동기(Event)는 함수 오류 때 기본 **2회 재시도**, 오류가 없어도 **같은 이벤트가 두 번 올 수 있음** [확인]. 비동기를 쓰려면 `MaximumRetryAttempts=0` + 멱등 필수 | Lambda 비동기 오류 처리 문서 |
| 페이로드 | 동기 요청·응답 각 6MB, 비동기 1MB [확인] | 우리 입력은 1KB 미만 |
| 멱등 | `request_id` → RunTask `clientToken`, PutSecretValue `ClientRequestToken`. 등록은 중복돼도 새 리비전이 하나 더 생길 뿐 | – |
| **클라이언트 재시도(검토 추가)** | botocore는 `ReadTimeoutError`를 재시도 대상으로 봅니다(legacy·standard 모두). 기본 읽기 시간 제한은 60초입니다. 함수가 60초 가까이 걸리면 **같은 Invoke가 다시 나가 배포가 두 번 실행**될 수 있습니다. 노트북의 Lambda 클라이언트는 `Config(read_timeout=함수 타임아웃+15초, retries={"total_max_attempts": 1})`로 만들고, 재시도는 실행기가 같은 `request_id`로 명시적으로 합니다 | [확인: 로컬 botocore `retryhandler.py`·`retries/standard.py`] |
| **오류 판정(검토 추가)** | 함수가 예외를 던져도 Invoke는 HTTP 200이고 응답의 `FunctionError` 필드로만 알려 줍니다. 이 필드를 확인하지 않으면 실패를 성공으로 읽습니다 | [확인: Lambda Invoke API] |
| 동시 실행 | ~~예약 동시성 1로 보조 잠금~~ → **빼기.** 예약 동시성은 "비예약 동시성 − 100"까지만 설정할 수 있습니다. 신규 계정처럼 한도가 10 수준으로 줄어 있으면 1도 예약할 수 없습니다. 한도 1,000 계정이면 가능합니다. 잠금은 실행기 SQLite 잠금(docs/17 8-3) 하나로 둡니다. 노트북은 web·was 배포를 **순차로** 호출합니다 | [확인] Lambda 예약 동시성 문서 "reserve up to the Unreserved account concurrency value minus 100" |

### 8-5. 로그

- 액션마다 JSON 한 줄: `request_id`, `run_id`, `release_id`, `action`, `service`, `image_digest`, 등록한 태스크 정의 ARN, 배포 ID, 결과, `duration_ms`, 거부 사유(V1~V10 번호). 비밀 값과 비밀 ARN 전체는 남기지 않습니다.
- 로그 그룹 `/aws/lambda/ddak-deploy`, 보존 7일(Terraform). 트리거 역할이 읽어 관리 페이지에 보여 줍니다.
- 누가 호출했는지는 이벤트에 실리지 않습니다. CloudTrail에서 Lambda Invoke는 데이터 이벤트라 별도 설정이 필요하다고 알고 있으나 설정·비용은 **확인 필요**. 그 전까지는 실행기 run 로그에 호출자 ARN(`get_caller_identity`)을 남깁니다.

### 8-7. 로컬 실행과 같은 코드 쓰기

| 층 | 내용 | 의존 |
|---|---|---|
| `ddak_cloud_core`(순수) | `validate(req, cfg)`, `render_task_definition(cfg, service, digest, release_id) -> dict`, `deploy(clients, cfg, req)`, `migrate(...)`, `rollback(...)`, `ensure_app_secret(...)`. **boto3 클라이언트를 인자로 받음** | 표준 라이브러리 + boto3만(Lambda 패키징을 쉽게) |
| 로컬 어댑터(C2) | `mode=direct`: 노트북 세션의 클라이언트로 위 함수 호출(P0). `mode=lambda`: `lambda.invoke(Payload=req)`(P1) | pydantic 계약 모델은 여기서만 |
| Lambda 핸들러 | `handler(event, ctx)`: 환경 변수에서 cfg, 기본 세션에서 clients → 위 함수 → dict 반환. 약 50줄 | – |
| 테스트 | 같은 단위 테스트를 botocore Stubber로 두 모드에 돌림 | – |

- pydantic-core는 네이티브 휠이라 Lambda 아키텍처에 맞는 휠을 따로 받아야 합니다. 코어 모듈을 표준 라이브러리로 두면 이 문제가 없습니다 [판단].
- Lambda Python 런타임에 들어 있는 boto3 버전이 RunTask `clientToken` 등을 지원하는지 **확인 필요**. 안 되면 boto3를 번들합니다.

### 9-2. 발표 문구

- **P0만 했을 때:** "배포 권한은 닫힌 목록입니다. 앱이 부르는 AWS API는 툴 레지스트리가 전부이고, 그 선언과 IAM 정책을 테스트로 대조합니다(생성기를 만들었다면 'Terraform이 생성된 파일을 그대로 씁니다'). 배포 역할 자신은 비밀 값을 읽을 수 없고(명시 Deny) IAM·KMS·DB 권한이 없습니다. DB와 비밀은 ECS 실행 역할만 씁니다. 권한 밖 호출이 거부되는 것은 테스트로 보여 드립니다."
- **P1까지 했을 때:** "CI·CD·런타임 권한을 나눴습니다. 개발자 노트북은 요청만 합니다(업로드, 빌드 시작, 배포 요청, 조회). 빌드는 CodeBuild 역할이 이미지 push만 합니다. 배포는 고정 코드 Lambda가 우리 ECR digest와 허용된 서비스만 받아 템플릿으로 태스크 정의를 만듭니다. 비밀 값은 ECS 실행 역할만 읽고, 비밀 생성도 Lambda 안에서 합니다. 노트북이 뚫려도 역할 배치·비밀 값·TLS·DNS는 바꿀 수 없습니다."
- **정직한 한 줄(질문 대비):** "배포할 수 있는 주체는 런타임에서 코드를 돌릴 수 있습니다. P1에서도 소스를 올리는 쪽이 코드를 정하므로, 올린 코드는 그 앱의 비밀과 DB 계정으로 돕니다. 그래서 런타임 역할과 DB 계정을 작게 두고, 배포 입력을 서버에서 검증합니다. 코드 출처까지 나누는 것(리뷰된 커밋만 빌드)은 다음 단계입니다."

### 9-3. 권고

1. **10/1:** P0. 4-1 정책 + 4-3·4-4 역할 + T6(실행 자격 검사, `awscrt` 확인 포함). Terraform 적용 직후 **T5a 양성 스모크** → 막히는 조건은 3절 대체안으로 완화. C2 어댑터는 처음부터 "클라이언트 주입 + 순수 함수".

## 10. 온프렘 쪽 권한

온프렘에는 IAM 같은 중앙 정책이 없습니다. 그래서 "닫힌 목록"을 **tier별 SSH 키 + 원격 명령 허용 목록**으로 구현합니다.

| 항목 | 최소화 방법 | 남는 위험 | 근거 |
|---|---|---|---|
| 키 | tier별 키 쌍(`ddak-deploy-web`, `ddak-deploy-was`). **DB 호스트는 키 없음**(마이그레이션은 was 호스트의 일회성 컨테이너, docs/17). 키는 `.secrets/ssh/<tier>`(gitignore) | 자동화용이라 패스프레이즈 없음 → 노트북 디스크 보호에 의존. 데모 후 authorized_keys에서 제거 | [판단] |
| authorized_keys 옵션 | `restrict,from="<컨트롤 호스트 IP>"`. B안은 `command="/usr/local/sbin/ddak-agent"` 추가 | – | [확인] sshd `restrict`는 포워딩·PTY·rc 금지, `command=`는 클라이언트 명령을 무시하고 `SSH_ORIGINAL_COMMAND`로만 전달, `from=`은 출발지 제한 |
| A안(P0): `DOCKER_HOST=ssh://ddak-deploy@<tier>` | 전용 사용자 `ddak-deploy`. docker 그룹이 필요 | **docker 그룹 = 그 호스트의 root 동등**. 피해 범위가 컨트롤 호스트가 아니라 해당 tier 호스트로 좁혀지는 것이 이득. `restrict`와 `docker system dial-stdio`의 호환은 **확인 필요** | [확인] Docker 보안 문서 "신뢰하는 사용자만 데몬 제어", 선행 패키징 조사 |
| B안(여유 시): 강제 명령 에이전트 | 사용자는 docker 그룹에 넣지 않고, sudoers 한 줄로 에이전트만 root로 실행. 에이전트는 `SSH_ORIGINAL_COMMAND`를 파싱해 **허용 명령만**: `pull docker.io/<조직>/<우리 저장소>@sha256:<64hex>`(9/30 낮: Docker Hub 기본, ECR 옵션이면 우리 ECR 저장소), `up <service> <digest>`, `rollback <service>`, `migrate <digest>`(was만), `status`, `logs <service> <N>`. `docker run` 인자는 에이전트가 고정(`--privileged` 없음, 볼륨·네트워크·env 파일 경로 고정, 레지스트리는 우리 Docker Hub 조직(또는 ECR 옵션)만) | 에이전트 코드 약 100줄 [추정]. `DOCKER_HOST=ssh://`는 못 씀(원격 CLI가 아니라 에이전트 호출로 바뀜) | [판단] |
| 레지스트리 인증 | 9/30 낮 ✅ 장부 28: **Docker Hub 읽기 전용 토큰**을 각 tier 호스트에서 `docker login`(프로비저닝 때 김준석). 노트북·AWS 자격 불필요. (ECR 옵션이면 옛 방식: 노트북이 `ecr:GetAuthorizationToken` → SSH로 `docker login --password-stdin` → pull → `docker logout`, 토큰 12시간) | 원격 `~/.docker/config.json`에 토큰이 남음(credential helper가 없으면 base64 평문) → 읽기 전용 토큰만, 호스트 파일 권한, 데모 뒤 토큰 폐기 | [확인] SAR "12시간"(ECR), Docker Hub 토큰 범위는 확인 필요 |
| 비밀 | `SECRET_KEY`는 **호스트에서 생성**해 볼륨 파일(0600, root)에 둠(docs/17). 노트북은 값을 받지 않음. 온프렘 DB 비밀은 호스트 파일, 파이프라인은 경로만 | 호스트 root = 비밀 접근 | [판단] |
| 컨테이너 모드(자원 부족 시 1호스트) | docker socket proxy로 API 종류 제한 | **CONTAINERS+POST를 열면 privileged·호스트 `/` 마운트 컨테이너 생성이 통과**(선행 조사 실측) → root 동등성은 그대로, 공격면만 줄어듦. 발표에서 먼저 말함 | 선행 패키징 조사 |
| rootless Docker | 데몬을 root 없이 실행 | 3일 범위 밖(포트·네트워크 설정). 향후 과제 | [확인] Docker 문서에 rootless 모드 안내 |
| 레지스트리와의 대칭 | 툴 메타에 `onprem_ops: ("up", "migrate")`를 적고 B안 에이전트 허용 목록을 생성 | 선택 | [판단] |

| 앱 역할(path `/ddak/app/`: 실행·태스크·마이그레이션 실행·DB 초기화 실행) | ECS | AI 설계(최소 권한, 장부 23) | `ddak-app-boundary`(13-3) |
| `ddak-deployer`(4절) | 앱 배포 step | 42개 액션(옛 47개, ECR 제거) | 💭 `ddak-app-boundary`와 별개. 필요하면 배포 역할에도 경계 |

- AWS provider의 `assume_role { policy / policy_arns }`로 세션 정책을 붙일 수 있습니다 [확인: provider 문서]. 다만 이것은 **provider 호출에만** 걸리고 S3 백엔드(상태 읽기)는 따로 자격을 씁니다. 💭 그래서 코드가 `sts:AssumeRole(RoleArn=ddak-pipeline-infra, Policy=13-6)`으로 받은 단기 키를 terraform 자식 프로세스 env로 넘기는 편이 백엔드·provider 둘 다에 걸리고 단순합니다(provider 블록은 코드 소유라 어느 쪽이든 AI가 못 바꿈). `plan_infra`는 읽기 세션으로, `apply_infra`만 승인 뒤 쓰기 세션으로 돕니다.
- 💭 3일 범위: P0(10/1 E2E)는 장부 24대로 테스트 프로필(넓은 권한)로 plan·apply합니다. 이 표의 좁은 파이프라인 역할·읽기 세션은 P1(데모 전 전환, N30)입니다. P0에서도 앱 경계(13-3)와 정적 게이트·사람 승인은 씁니다.

### 13-3. 앱 역할 권한 경계 `policy/ddak/boundary/ddak-app-boundary` (💭 초안)

AI가 설계한 실행 역할·태스크 역할·마이그레이션 실행 역할·DB 초기화 실행 역할의 상한입니다. 권한을 **주지 않고** 상한만 정합니다.

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {"Sid": "ReadDockerHubPullToken", "Effect": "Allow", "Action": "secretsmanager:GetSecretValue",
     "Resource": "arn:aws:secretsmanager:ap-northeast-2:${account_id}:secret:ddak-platform/dockerhub-pull-??????"},
    {"Sid": "LogsOwnGroups", "Effect": "Allow",
     "Action": ["logs:CreateLogStream", "logs:PutLogEvents"],
     "Resource": "arn:aws:logs:ap-northeast-2:${account_id}:log-group:/ecs/ddak-*:*"},
    {"Sid": "ReadAppAndDbSecrets", "Effect": "Allow", "Action": "secretsmanager:GetSecretValue",
     "Resource": [
       "arn:aws:secretsmanager:ap-northeast-2:${account_id}:secret:ddak/*",
       "arn:aws:secretsmanager:ap-northeast-2:${account_id}:secret:rds!*"
     ]},
    {"Sid": "NeverIamOrgAccount", "Effect": "Deny",
     "Action": ["iam:*", "organizations:*", "account:*", "sts:AssumeRole"], "Resource": "*"}
  ]
}
```

- 9/30 낮(✅ 장부 28): 옛 `EcrAuth`·`EcrPullOwnRepos`를 빼고 `ReadDockerHubPullToken`(읽기 전용 토큰 시크릿 하나)을 넣었습니다. push 토큰(`ddak-platform/dockerhub-push`)은 경계 **밖**이라 앱 역할에 어떤 설계가 와도 못 읽습니다. `ddak/*` 패턴은 `ddak-platform/…`과 맞지 않습니다(`ddak/` 뒤에 슬래시가 있어야 함). ECR 옵션을 켜면 이 경계를 **다시 만들어야** 합니다(경계 수정 Deny) → 기반 준비 전에 저장소를 정합니다(14-5).
- `secret:rds!*`는 RDS 관리형 마스터 시크릿(`manage_master_user_password = true`)을 DB 초기화 태스크 실행 역할이 읽기 위한 것입니다. 앱 실행 역할에는 신원 정책에서 주지 않습니다(경계는 상한일 뿐). 이름 패턴은 확인 필요(11절 #32).
- ⚠️ `kms:*` Deny를 넣지 않습니다(0절: Secrets Manager가 호출자 권한으로 KMS를 부름).
- 이름 통일은 💭 장부 36으로 시크릿 `ddak/<앱>/<KEY>`(경계의 `ddak/*`가 덮음)·플랫폼 `ddak-platform/*`로 정리했습니다(14-2, 11절 #16). 역할 이름은 N44. ⚠️ 경계는 기반 준비 때 먼저 만들어지고 이후 수정이 Deny이므로, **경계의 리소스 패턴을 코드 소유 이름 규칙 변수에서 만들어야** 합니다. 패턴과 실제 이름(AI HCL이 쓰는 저장소·로그 그룹·시크릿 이름)이 다르면 정상 태스크 시작(ECR pull·로그·시크릿 주입)이 거부됩니다. 기반 준비 전에 확정합니다.

### 13-4. 파이프라인 인프라 역할의 IAM 생성 위임 문 (💭 초안)

AWS 공식 위임 패턴(IAM 사용자 가이드의 경계 위임 예시 `CreateOrChangeOnlyWithBoundary`·`NoBoundaryPolicyEdit`·`NoBoundaryUserDelete`, Prescriptive Guidance의 역할 버전)을 역할에 적용했습니다. 이 문장들은 `ddak-pipeline-infra`의 신원 정책 중 IAM 부분이고, 플랫폼 리소스(EC2·ELB·ECS·RDS 등) 부분은 테스트 계정 CloudTrail로 확정합니다.

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {"Sid": "AppRolesOnlyWithBoundary", "Effect": "Allow",
     "Action": ["iam:CreateRole", "iam:PutRolePolicy", "iam:DeleteRolePolicy", "iam:AttachRolePolicy",
                "iam:DetachRolePolicy", "iam:PutRolePermissionsBoundary", "iam:UpdateAssumeRolePolicy", "iam:DeleteRole"],
     "Resource": "arn:aws:iam::${account_id}:role/ddak/app/*",
     "Condition": {"ArnEquals": {"iam:PermissionsBoundary": "arn:aws:iam::${account_id}:policy/ddak/boundary/ddak-app-boundary"}}},
    {"Sid": "AttachOnlyAllowlistedPolicies", "Effect": "Deny", "Action": "iam:AttachRolePolicy", "Resource": "*",
     "Condition": {"ArnNotLike": {"iam:PolicyARN": [
       "arn:aws:iam::${account_id}:policy/ddak/app/*",
       "arn:aws:iam::aws:policy/service-role/AmazonECSTaskExecutionRolePolicy"]}}},
    {"Sid": "TagAndReadAppRoles", "Effect": "Allow",
     "Action": ["iam:TagRole", "iam:UntagRole", "iam:GetRole", "iam:GetRolePolicy", "iam:ListRolePolicies",
                "iam:ListAttachedRolePolicies", "iam:ListInstanceProfilesForRole", "iam:ListRoleTags"],
     "Resource": "arn:aws:iam::${account_id}:role/ddak/app/*"},
    {"Sid": "AppManagedPolicies", "Effect": "Allow",
     "Action": ["iam:CreatePolicy", "iam:CreatePolicyVersion", "iam:DeletePolicy", "iam:DeletePolicyVersion",
                "iam:GetPolicy", "iam:GetPolicyVersion", "iam:ListPolicyVersions", "iam:TagPolicy"],
     "Resource": "arn:aws:iam::${account_id}:policy/ddak/app/*"},
    {"Sid": "ReadBoundaryPolicies", "Effect": "Allow",
     "Action": ["iam:GetPolicy", "iam:GetPolicyVersion"],
     "Resource": "arn:aws:iam::${account_id}:policy/ddak/boundary/*"},
    {"Sid": "PassAppRolesToEcsOnly", "Effect": "Allow", "Action": "iam:PassRole",
     "Resource": "arn:aws:iam::${account_id}:role/ddak/app/*",
     "Condition": {"StringEquals": {"iam:PassedToService": "ecs-tasks.amazonaws.com"}}},
    {"Sid": "SlrOnlyKnownServices", "Effect": "Allow", "Action": "iam:CreateServiceLinkedRole", "Resource": "*",
     "Condition": {"StringEquals": {"iam:AWSServiceName": [
       "ecs.amazonaws.com", "elasticloadbalancing.amazonaws.com", "rds.amazonaws.com"]}}},
    {"Sid": "NoBoundaryEdit", "Effect": "Deny",
     "Action": ["iam:CreatePolicyVersion", "iam:DeletePolicy", "iam:DeletePolicyVersion", "iam:SetDefaultPolicyVersion"],
     "Resource": "arn:aws:iam::${account_id}:policy/ddak/boundary/*"},
    {"Sid": "NoBoundaryRemoval", "Effect": "Deny",
     "Action": ["iam:DeleteRolePermissionsBoundary", "iam:DeleteUserPermissionsBoundary"], "Resource": "*"},
    {"Sid": "ReadIamForRefresh", "Effect": "Allow",
     "Action": ["iam:Get*", "iam:List*"], "Resource": "*"},
    {"Sid": "NoSelfModification", "Effect": "Deny",
     "NotAction": ["iam:Get*", "iam:List*"],
     "Resource": "arn:aws:iam::${account_id}:role/ddak/pipeline/*"},
    {"Sid": "NoUsersOrKeys", "Effect": "Deny",
     "Action": ["iam:CreateUser", "iam:CreateAccessKey", "iam:CreateLoginProfile", "iam:AttachUserPolicy", "iam:PutUserPolicy"],
     "Resource": "*"}
  ]
}
```

| 문장 | 근거 |
|---|---|
| `AppRolesOnlyWithBoundary` | 8개 액션 모두 `iam:PermissionsBoundary` 조건 키 지원 [확인: SAR IAM]. CreateRole은 요청의 경계를, PutRolePolicy·AttachRolePolicy 등은 대상 역할에 이미 붙은 경계를 봄 → 경계가 붙은 역할만 수정 가능. 경로 `role/ddak/app/*`로 이름 접두사 제한(Prescriptive Guidance는 `role/app/*`) |
| `AttachOnlyAllowlistedPolicies` | `AttachRolePolicy`는 `iam:PolicyARN` 지원 [확인]. 관리자 정책 부착 차단 |
| `TagAndReadAppRoles` | `TagRole`은 `iam:PermissionsBoundary` 미지원 → 리소스 ARN으로만 제한. CreateRole에 태그를 주면 `iam:TagRole`도 필요 [확인] |
| `AppManagedPolicies` | `CreatePolicy` 등은 경계 조건 키 미지원 → 리소스 ARN 경로 |
| `PassAppRolesToEcsOnly` | ⚠️ **PassRole은 `iam:PermissionsBoundary` 미지원** [확인]. AWS는 태그(`ResourceTag`)로 PassRole을 제어하지 말라고 명시("not reliable") [확인]. 공식 방법 = 역할 ARN·접두사 + `iam:PassedToService`. 경로 안에서는 경계를 붙여야만 역할이 생기므로 경로 제한이 곧 경계 제한 |
| `SlrOnlyKnownServices` | `iam:AWSServiceName` [확인]. 부트스트랩에서 미리 만들면 불필요할 수 있음(11절 #31) |
| `NoBoundaryEdit`·`NoBoundaryRemoval` | 공식 예시 `NoBoundaryPolicyEdit`·`NoBoundaryUserDelete`. `DeleteRolePermissionsBoundary`는 공식 예시가 무조건 Deny. AWS Security Blog는 이 권한을 "full administrators"에게만 주라고 권고 |
| `ReadIamForRefresh` | 개선 배포 plan의 refresh는 상태에 있는 **모든** IAM 리소스(플랫폼 역할인 CodeBuild·배포 역할 포함)를 읽음. 앱 경로 읽기만 주면 refresh가 AccessDenied로 실패 |
| `NoSelfModification` | 파이프라인 역할이 자기 정책·신뢰·경계를 바꾸고 자기를 PassRole하는 것 차단. **`NotAction`으로 읽기는 뺌**: 처음 초안의 `iam:*` Deny는 `GetRole`까지 막아, 파이프라인 역할이 상태에 있으면 모든 개선 배포 plan이 refresh에서 실패함. 그래도 파이프라인 역할·경계 정책은 AI Terraform 상태에 넣지 않고 기반 준비(13-7)에서 코드가 만듦 |

- ⚠️ 부트스트랩 모드에서 관리자가 `/ddak/app/` 경로에 경계 없는 역할을 만들면 "경로 = 경계 부착" 보장이 깨집니다 → 정적 게이트가 그 경로의 모든 `aws_iam_role`에 `permissions_boundary`를 강제합니다(`aws_iam_role`에 `path`, `permissions_boundary` 인자 있음 [확인]).
- ⚠️ **이 위임 문이 못 막는 것(9/30 적대적 검토):** ① 신뢰 정책 내용(E27) — `CreateRole`·`UpdateAssumeRolePolicy`에 신뢰 주체를 거는 조건 키가 없음. ② `policy/ddak/app/*`를 경계 없는 역할에 붙여 둔 뒤 `CreatePolicyVersion`으로 넓히기(E28). ③ 경계 안에서 앱 실행 역할에 `rds!*` 읽기(E29). 셋 다 정적 게이트 규칙과 사람 승인으로 막습니다(13-8).
- `iam:PermissionsBoundary` 조건 키 지원은 2026-09-30 SAR JSON(`servicereference.us-east-1.amazonaws.com/v1/iam/iam.json`)으로 다시 대조했습니다: `DeleteRole`·`UpdateAssumeRolePolicy`·`UpdateRole` 포함 지원, `TagRole`·`CreatePolicyVersion`·`PassRole`은 미지원.
- Terraform이 역할을 만들고 지우면서 부르는 읽기·보조 액션(예: 인스턴스 프로파일 조회, 태그 조회)은 이 목록에서 빠졌을 수 있습니다 → 11절 #28.
- 💭 신원 정책의 플랫폼 부분(CloudTrail로 확정)에 `secretsmanager:GetSecretValue`, `ecs:RunTask`·`ecs:ExecuteCommand`, `codebuild:StartBuild`는 넣지 않습니다. Terraform은 이것들을 부르지 않고, 넣으면 인프라 역할이 비밀 읽기·임의 코드 실행 경로(예: DB 초기화 실행 역할로 태스크를 띄워 마스터 비밀번호 주입)를 갖습니다. 경계(13-5)는 서비스 단위 상한이라 이것을 막지 않습니다.

### 13-5. 파이프라인 역할 자신의 경계 `policy/ddak/boundary/ddak-pipeline-boundary` (💭 초안)

위임받는 쪽(Zhang)에도 경계를 붙이는 공식 예시를 따릅니다. 서비스 단위 와일드카드는 **상한**이라 허용하고, 실제 권한은 신원 정책(13-4 + 플랫폼 부분)이 좁힙니다.

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {"Sid": "PlatformServicesInSeoul", "Effect": "Allow",
```

### 13-6. plan 읽기 세션 정책 (💭 초안)

`plan_infra`가 `ddak-pipeline-infra`를 assume할 때 붙이는 세션 정책입니다(**P1**, 13-2). 실제 권한 = 세션 정책 ∩ 신원 정책 ∩ 경계. 코드가 `sts:AssumeRole`의 `Policy`로 붙여 받은 단기 키를 terraform env로 넘겨야 S3 백엔드에도 걸립니다(13-2).

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {"Sid": "StateRead", "Effect": "Allow", "Action": ["s3:GetObject", "s3:ListBucket"],
     "Resource": ["arn:aws:s3:::${state_bucket}", "arn:aws:s3:::${state_bucket}/*"]},
    {"Sid": "RefreshReads", "Effect": "Allow",
     "Action": ["ec2:Describe*", "elasticloadbalancing:Describe*", "ecs:Describe*", "ecs:List*",
                "rds:Describe*", "rds:ListTagsForResource", "logs:Describe*", "logs:ListTagsForResource",
                "logs:ListTagsLogGroup", "codebuild:BatchGetProjects", "secretsmanager:DescribeSecret",
                "secretsmanager:GetResourcePolicy", "iam:Get*", "iam:List*", "s3:GetBucket*",
                "s3:GetEncryptionConfiguration", "s3:GetLifecycleConfiguration", "acm:DescribeCertificate",
                "route53:Get*", "route53:List*", "sts:GetCallerIdentity",
                "access-analyzer:ValidatePolicy", "access-analyzer:CheckNoNewAccess",
                "access-analyzer:CheckAccessNotGranted"],
     "Resource": "*"}
  ]
}
```

- 9/30 낮(✅ 장부 28): ECR 읽기 4개(`ecr:Describe*`·`List*`·`GetLifecyclePolicy`·`GetRepositoryPolicy`)를 뺐습니다(ECR 옵션일 때만 다시).
- 읽기 세션은 S3 네이티브 잠금 파일(`<key>.tflock`, `s3:PutObject` 필요 [확인: S3 백엔드 문서])을 쓸 수 없으므로 `plan -lock=false`로 돌리고 동시 실행은 실행기 배포 잠금으로 막습니다 💭.
- `secretsmanager:GetSecretValue`가 없습니다. 그래서 AI HCL에 `aws_secretsmanager_secret_version`(값이 상태에 평문)이 있으면 refresh가 실패합니다 → 정적 게이트로 먼저 금지.
- Terraform refresh가 부르는 읽기 액션은 리소스 타입마다 달라 빠진 것이 있을 수 있습니다 → 11절 #29.

### 13-7. 부트스트랩 모드 권한: 관리자 자격은 승인 시점에만 (💭)

| 항목 | 내용 |
|---|---|
| 누가 | 사람 관리자(C1). root 사용 금지. IAM Identity Center 권한셋 또는 MFA IAM 사용자 |
| 언제 | 승인 버튼을 누를 때만: ① [기반 승인](기반 준비), ② [IAM·인프라 승인](플랫폼 apply). 사람이 그때 로그인(`aws sso login` 또는 `aws login`)해 단기 세션을 만듦. 역할 세션은 약 1시간 |

| 왜 기반을 먼저 따로 | `plan_infra`는 상태 버킷(S3 백엔드)과 plan 자격이 있어야 돕니다. 부트스트랩 plan이 승인 **전**에 돌아야 하므로, 버킷을 apply 때 만드는 순서(옛 초안)는 성립하지 않습니다. 또 파이프라인 역할·경계를 AI Terraform 상태에 넣으면 `NoSelfModification`·`NoBoundaryEdit` 때문에 개선 배포 refresh·apply가 깨지고, AI가 자기 상한을 설계하게 됩니다 |

| 이후 | 개선 배포는 `ddak-pipeline-infra`만(P1). 관리자 자격은 경계 정책을 바꿔야 할 때만 사람이 별도로(파이프라인 밖) |
| 테스트 기간 | ✅ 장부 24: 넓은 권한. 💭 테스트 전용 새 계정·Budgets. P0는 테스트 프로필로 기반 준비·plan·apply. 10/2 리허설 전에 위 구조로 전환하고 T5a(양성 스모크) 재실행 |
| 한계(정직하게) | 부트스트랩 apply 자체는 상한이 없습니다(관리자 자격). 그래서 정적 게이트·Checkov·Access Analyzer·사람 승인이 유일한 방어이고, 부트스트랩 plan 요약·승인 기록·녹화를 남깁니다 |

- 첫 상태 버킷은 코드가 만듭니다(💭). HashiCorp 문서에는 부트스트랩 절차가 없고 S3 백엔드는 버킷이 "이미 있다고 가정"합니다 [확인]. 관행(로컬 상태로 버킷 apply → `terraform init -migrate-state`)도 되지만, 상태에는 민감값이 평문으로 들어가므로(RDS `password` 인자 설명 "stored in the state file" [확인]) 결정적으로 만드는 편이 안전하고 로컬→원격 이전 단계도 사라집니다. ⚠️ 장부 22는 **상태 버킷도 AI Terraform 범위**로 적었으므로, 코드가 만드는 이 안(single-app N27 B)은 사용자 확인이 필요합니다. 장부 문구를 따르면 A(AI HCL로 버킷 apply → 로컬 상태 이전)이고, 그때도 plan 자격·순서 문제는 기반 준비와 같은 방식으로 풀어야 합니다.

### 14-4. 데모 시크릿 장면의 실행 역할 권한 (✅ 장부 32, 모양 💭)

흐름: 분석이 새 키 `SECRET_KEY`를 찾음 → AI(Jev)가 secret으로 분류 → 인프라 요구 해시 변경 → `generate_infra`가 **앱 층**에 `aws_secretsmanager_secret`(`ddak/${app}/SECRET_KEY`, 값 없음) + 실행 역할 정책에 그 ARN 읽기 추가를 제안 → 정적 게이트·Checkov·`plan_infra`("+ 시크릿 1, IAM 정책 1 변경, 삭제 0")·Access Analyzer → 사람 승인 → (G1 뒤) `apply_infra` → `terraform output -json`으로 새 ARN을 환경 정보에 기록 → `sync_env_to_cloud`(배포 역할)가 난수를 PutSecretValue → 태스크 정의 `secrets` valueFrom = 새 ARN → ECS 배포.

v1(부트스트랩 뒤) `ddak-ecs-exec-app`:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "ReadDockerHubPullToken",
      "Effect": "Allow",
      "Action": "secretsmanager:GetSecretValue",
      "Resource": "arn:aws:secretsmanager:ap-northeast-2:${account_id}:secret:ddak-platform/dockerhub-pull-??????"
    },
    {
      "Sid": "WriteAppLogs",
      "Effect": "Allow",
      "Action": ["logs:CreateLogStream", "logs:PutLogEvents"],
      "Resource": [
        "arn:aws:logs:ap-northeast-2:${account_id}:log-group:/ecs/ddak-web:*",
        "arn:aws:logs:ap-northeast-2:${account_id}:log-group:/ecs/ddak-was:*"
      ]
    },
    {
      "Sid": "ReadAppSecretsAtTaskStart",
      "Effect": "Allow",
      "Action": "secretsmanager:GetSecretValue",
      "Resource": [
        "arn:aws:secretsmanager:ap-northeast-2:${account_id}:secret:ddak/${app}/DATABASE_URL-??????"
      ]
    }
  ]
}
```

v2(시크릿 장면 뒤)는 4-4의 JSON입니다. 차이는 `ReadAppSecretsAtTaskStart`의 `Resource`에 `…:secret:ddak/${app}/SECRET_KEY-??????` 한 줄뿐입니다.

| 점검 | 내용 |
|---|---|
| "IAM 정책 1 변경"이 되는 모양 | 실행 역할 권한이 **제자리 수정(update)되는 정책 리소스 하나**(예: `aws_iam_role_policy` 인라인 정책)에 있어야 plan이 `~ 1`입니다. AI가 시크릿마다 새 정책 리소스를 만들면 `+ 1`(create)이 되고, 이것은 single-app N39의 "G1 전" 대안입니다(plan이 create뿐 → `additive_prep`). 어느 모양으로 쓰게 할지는 프롬프트 규칙(💭) |
| ARN 조립 | 정책 안에서 같은 plan이 만드는 `aws_secretsmanager_secret.x.arn`을 참조하면 plan 시점에 정책이 computed가 되어 fail-closed로 실패합니다(13-8). → 이름 규칙 변수로 `…:secret:ddak/${app}/SECRET_KEY-??????`를 조립 |
| 배포 역할 | **바뀌지 않습니다.** `AppSecretWriteOnly`가 이미 `ddak/${app}/*`에 PutSecretValue·DescribeSecret을 줍니다. `CreateSecret`은 없습니다(시크릿 리소스는 Terraform 소유) |
| 앱 경계 | **바뀌지 않습니다.** `ReadAppAndDbSecrets`(`secret:ddak/*`)가 새 시크릿 읽기를 상한 안에 둡니다. 경계 수정 Deny와 충돌하지 않음 |
| 파이프라인 인프라 역할(P1) | 시크릿 생성은 플랫폼 부분(`secretsmanager:CreateSecret`·`TagResource`·`DescribeSecret`·`GetResourcePolicy`, 리소스 `secret:ddak/*` 💭, CloudTrail로 확정), 실행 역할 정책 수정은 13-4 `AppRolesOnlyWithBoundary`(실행 역할이 경계를 달고 있으므로 `iam:PutRolePolicy` 허용). `GetSecretValue`는 주지 않음(13-4 끝). 테스트 기간은 넓은 권한(장부 24) |
| 값 쓰기 | 배포 역할 PutSecretValue, **값이 없을 때만**(→ `additive_prep`). 값은 Terraform state·AI·화면·로그에 없음. 대안 write-only `secret_string_wo`(Terraform·provider 버전 확인, single-app N41)를 쓰면 정적 게이트의 `aws_secretsmanager_secret_version` 금지를 "`secret_string_wo`만 허용"으로 바꾸고 인프라 역할에 PutSecretValue가 필요 |
| IAM 전파 | 정책 update 직후 새 태스크가 새 시크릿을 못 읽을 수 있음(최종 일관성) → 리허설 실측(11절 #39), 💭 태스크 정의 등록 전 짧은 대기·재시도 |
| 되돌리기(리허설 초기화) | v1 앱 층으로 돌리면 시크릿 delete + 정책 update → 개선 배포의 V23이 BLOCK. 사람이 실행하는 초기화 스크립트로(single-app 03 9-2). 테스트용 `recovery_window_in_days = 0`이어야 같은 이름을 바로 다시 만듦 |

### 14-7. JSON 파싱 확인 (9/30)
