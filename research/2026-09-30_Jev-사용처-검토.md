# 조사 결과: jev (2026-09-30, 조사 워크플로 원문)

> 조사 에이전트 원문을 그대로 저장했습니다. 판단은 docs 반영 단계에서 합니다.

## Jev 검토 결과

### 결론

- **Jev는 실제로 있는 모델이고, 한국에서도 호출할 수 있습니다.** TypeSafe AI가 2026-09-15에 공개했고, 텍스트 대신 정해진 형식의 판단(예/아니오, 보기 중 하나, 점수)과 확률을 돌려줍니다. 다만 **직접 가입은 9/22부터 중단**돼 있고, 재개 공지는 찾지 못했습니다. 키를 구하는 것부터가 첫 관문입니다.
- **골든 패스(flaskr v1→v2)에서는 4개 판단 지점 모두 규칙만으로 결정됩니다.** Jev를 붙여도 v2 배포 계획이 바뀔 가능성은 낮습니다. 그래서 Jev를 "결정권자"로 발표하면 "Jev가 없어도 결과가 같다"는 지적을 받습니다.
- **그래도 쓸 자리는 있습니다: ① 플랜의 step 선택.** 새 계획 구조(단계 순서 고정, 단계 안 step만 넣고 뺌)에서 step 선택은 결국 "이 step이 필요한가"라는 예/아니오의 묶음입니다. Jev가 가장 잘하는 형태입니다. Claude를 CLI로 부르는 것보다 수 초 빠릅니다.
- **권고:**
  - 쓸 곳 1 (조건부): ① 플랜. step 선택과 환경 키 분류를 Jev 한 번 호출로 묶습니다. 규칙이 반드시 들어갈 step(바닥)을 정하고, Jev는 step 추가와 경고만 합니다.
  - 쓸 곳 2 (선택, 골든 패스 끝까지 성공한 뒤): ⑤ 원인 분석(`diagnose_parity_gap`)의 원인 범주 분류. 규칙 시그니처에 안 걸린 경우에만 씁니다.
  - 쓰지 말 곳: 마이그레이션이 데이터를 지우는지 판정, 게이트·롤백 판단, 보고 심각도, 채팅 의도 분류.
  - 채택 조건을 10/1 오전에 확인해서 하나라도 못 맞추면 Jev는 빼고 규칙으로 갑니다.

### 2. 로컬 실측

- **서울에서 Jev까지의 네트워크 지연:** 인천 엣지까지 10~30ms. 키 없이 보낸 요청이 403으로 돌아오기까지 160~183ms(5회). 서버 본체는 미국 서부로 보입니다(블로그도 서부 서비스라고 적음). 여기에 제공사 발표 지연을 더하면 **서울에서 호출 한 번에 약 0.25~0.7초로 추정**합니다. 실제 추론 지연은 키가 없어 재지 못했습니다.
- **골든 패스 요청 시제품 (Noul 4개 + Choice 3개, 잘못된 키):** 요청이 서버까지 가서 약 170ms에 인증 오류(`TypeSafeAuthenticationError`)를 받았고, 규칙만으로 계획을 세우는 대체 경로로 정상 전환됐습니다. 요청 형식이 서버 검증까지 통과하는지는 인증 단계에서 막혀 확인하지 못했습니다.
- **비교: Claude CLI로 같은 분류** (`claude -p --json-schema`, 결과 2칸, 3회):

| 모델 | 전체 시간 | 그중 API 시간 | 결과 |
|---|---|---|---|
| haiku (claude-haiku-4-5) | 11.5초 / 8.8초 | 6.8초 / 5.7초 | 정답, 형식 맞음 |
| sonnet (claude-sonnet-5-5) | 4.0초 | 1.4초 | 정답, 형식 맞음 |

  - CLI가 보고한 비용 환산은 호출당 $0.016~0.137입니다. Claude Code 시스템 프롬프트가 같이 들어가서 커진 값이고, 구독 로그인이라면 돈 대신 사용량 한도가 줄어듭니다.
  - Jev 호출 한 번(입력 약 1k 토큰)은 약 $0.00004입니다.
  - 표본 3회라 참고용입니다.

### 3. 파이프라인의 "정해진 보기 중 고르는" 판단 지점 전체

| # | 단계 | 판단 | 골든 패스에서 규칙으로 충분한가 | Jev 적합도 | 권고 |
|---|---|---|---|---|---|
| P1 | ① | 바뀐 tier(web/was/db) | 충분 (경로 규칙) | 낮음 | 규칙 |
| P2 | ① | build step: was 이미지·web 이미지 재빌드 | 충분 (was/, web/, nginx 설정 경로) | 낮음 | 규칙 (Jev 확률은 옆에 표시만) |
| P3 | ① | deploy step: 마이그레이션 필요 여부 | 충분 (마이그레이션 파일 변경) | 중간 (ORM·간접 스키마 변경) | 규칙이 바닥 + Jev 추가·경고 |
| P4 | ① | 마이그레이션이 데이터를 지우는가 (추가형/파괴형) | 충분하고 **반드시 규칙** (SQL 파서, 예: sqlglot) | 금지 | 규칙만. AI가 안전 판정을 느슨하게 만들 수 없게 |
| P5 | ① | deploy step: 시크릿 동기화 필요 여부 | 충분 (코드에서 `os.environ`·`getenv` 찾기 + 대상 저장소 조회) | 중간 (간접 읽기) | 규칙 + Jev 추가 |
| P6 | ① | 환경 키 종류: 비밀/일반/주소 | 충분 (키 이름 패턴) | 중간 (DSN, PUBLIC_KEY처럼 애매한 이름) | 규칙 + Jev, 애매하면 사람 확인 |
| P7 | ① | 실행 시/빌드 시 | 충분 (Flask는 전부 실행 시. 프런트는 `VITE_` 같은 접두사로 판별) | 낮음 | 규칙 |
| P8 | ① | 검증 step: 어떤 스모크 시나리오(로그인 등) | 충분 (경로→시나리오 매핑) | 중간 | 규칙 + Jev 추가 |
| P9 | ②④ | 계획 검증, 로컬→클라우드 게이트, 롤백 실행 | 결정적 코드 | 금지 (실행 경로에 AI 없음 원칙) | 규칙 |
| P10 | ⑤ | 두 환경 차이가 예상된 차이(스킴, Secure, HSTS)인가 | 충분 (허용 목록) | 낮음 | 규칙 |
| P11 | ⑤ | 실패·불일치 원인 범주 | 알려진 유형은 충분 (로그 시그니처) | **높음** (시그니처에 없는 드문 오류들) | 규칙 먼저 → 안 걸리면 Jev |
| P12 | ⑤ | 롤백으로 해결되는 유형인가 | 보고용 정보일 뿐 | 중간 | 보고 표시만 허용, 실행 판단 금지 |
| P13 | ⑤ | 이슈 심각도 | 충분 (이슈 유형→심각도 고정 표) | 낮음 | 규칙(표) |
| P14 | 공통 | 채팅 의도(배포/상태/롤백/설명) | 충분 (한국어 키워드) | 낮음 (한국어 약점, 부작용 있는 명령은 어차피 버튼 확인) | 규칙 |

**"빼기"는 누가 하나.** 사용자가 정한 "계획이 step을 알아서 넣고 뺀다"는 기존 안전 원칙(AI는 추가만)과 이렇게 맞추면 됩니다.
- 빼기는 규칙이 "불필요"라고 판정한 step만 합니다. 예: nginx가 안 바뀌었으니 web 재빌드를 뺌.
- 규칙이 필수로 정한 step은 AI가 뺄 수 없고, 검증기가 막습니다.
- AI는 step 추가와 경고만 합니다.

### 4. 요청받은 4개 지점 상세

**(1) 계획 단계 step 선택 (P2·P3·P5·P8)**
- **규칙으로 충분한가:** 골든 패스에서는 그렇습니다.
  - was/ 변경 → WAS만 빌드·배포
  - nginx 무변경 → web은 뺌
  - 마이그레이션 파일 추가 → 마이그레이션 step
  - `SECRET_KEY`를 새로 읽고, Secrets Manager에 아직 없음 → 시크릿 동기화 step
  - auth 경로 변경 → 로그인 스모크 시나리오
- **Jev를 쓰면 좋은 점:**
  - step 후보 전부를 Noul로 한 요청에 담습니다(문서의 speculative fan-out 패턴). 약 0.25~0.7초(추정), 약 $0.00004.
  - 계획 JSON은 코드가 답을 모아 조립하므로 형식이 깨질 일이 없고, 다시 물어보는 루프도 필요 없습니다.
  - 결정마다 확률이 나오므로, 규칙과 Jev가 다르게 판단하면 보고 이슈로 올릴 수 있습니다.
- **Claude 구조화 출력과 비교:**
  - Claude도 `--json-schema`나 strict 도구로 형식과 보기 목록을 보장합니다. 형식 보장 자체는 Jev만의 장점이 아닙니다.
  - 차이는 세 가지입니다. 속도(CLI 실측 4~11.5초, 계획용 긴 프롬프트면 더 길 것), 확률이 붙는지, 매번 답이 흔들리는지.
  - Claude가 나은 곳은 여러 파일을 오가는 추론입니다. 예: "쿼리가 스키마에 없는 컬럼을 쓰는가". Jev가 약한 간접 추론입니다.
- **실패 시 대체:**
  - `call_ai` 관문에서 타임아웃 2초, 재시도 1회 뒤 규칙만으로 계획을 세우고 배포는 계속합니다.
  - SDK 기본값(10초, 재시도 2회)은 반드시 바꿔야 합니다.
  - 버전은 `jev-1.13.0`으로 고정합니다(문서 권장).
  - 코드 diff는 신뢰할 수 없는 입력이고, 문서가 판단할 내용 안의 악의적 문장에 답이 흔들린다고 인정합니다. 그래서 Jev 답은 step을 늘리거나 경고를 내는 쪽으로만 영향을 주게 둡니다.
- **데모에서 보여주는 방식:** 계획 카드에 step마다 포함/제외, 누가 정했는지(규칙/Jev), 확률, "Jev 0.4초 · $0.00004 · jev-1.13.0"을 표시합니다. Jev가 안 되면 "규칙 대체 동작" 배지를 띄웁니다.
- **Jev가 실제로 일을 하는 예시 (정직한 버전):** Flask의 `app.config.from_prefixed_env()`는 `FLASK_`로 시작하는 환경변수를 간접으로 읽습니다(공식 소스로 확인). `os.environ`을 찾는 정규식 규칙은 이걸 놓치고, Jev에게 "새 설정을 읽는가"를 물으면 잡을 수 있습니다. 다만 규칙에 한 줄만 더하면 규칙도 잡으니, "규칙이 모르는 경우를 위한 보조"라고 설명해야 합니다.

**(2) 분석 단계 환경 키 분류 (P6·P7)**
- **규칙으로 충분한가:** 그렇습니다. SECRET_KEY → 비밀·실행 시, DB 호스트 → 주소, DB 비밀번호 → 비밀. 실행 시/빌드 시는 Flask라서 전부 실행 시입니다.
- **Jev를 쓰면 좋은 점:** 키 N개를 Choice N개로 (1)의 요청에 같이 넣습니다. 추가 지연이 거의 없고, 애매한 이름에 확률을 줍니다.
- **Claude와 비교:** 결과는 비슷하게 낼 수 있지만 느립니다.
- **실패 시 대체:** 규칙을 씁니다. 규칙과 Jev가 다르거나 신뢰도가 0.7 미만이면(제안값) 비밀로 취급해 안전 쪽으로 보내고, 관리 페이지에서 사람이 확인합니다. Jev에는 키 이름과 코드 줄만 보내고 **값은 절대 보내지 않습니다**.
- **데모에서 보여주는 방식:** 키 표에 종류와 판정 주체를 표시합니다.

**(3) 배포 실패·불일치 원인 범주 (P11, `diagnose_parity_gap`)**
- **규칙으로 충분한가:** 골든 패스에서 날 수 있는 실패는 시그니처로 충분합니다. 아래 문자열은 예시입니다.
  - 시크릿 누락: `KeyError: 'SECRET_KEY'`, ECS `ResourceInitializationError`
  - MySQL 1146(테이블 없음), 1045(접속 거부)
  - `CannotPullContainerError`
  - ALB 헬스체크 실패
- **Jev를 쓰면 좋은 점:** 시그니처에 안 걸린 드문 오류에서 원인 범주 약 8개 + unknown 중 하나를 확률과 함께 즉시 고릅니다. Vercel이 배포 실패 조사 가이드로 같은 패턴을 공개했습니다. 선례가 있다는 뜻이지만, 그만큼 독창성은 약합니다.
- **Claude와 비교:** 원인 설명과 조치 문장은 Claude가 맡습니다. Jev는 범주만 고릅니다.
- **실패 시 대체:** "unknown" + 로그 발췌 + Claude 설명으로 넘어갑니다. 이 툴은 읽기 전용이고, 롤백은 이미 규칙이 실행한 뒤입니다.
- **데모에서 보여주는 방식:** 데모에 실패 장면이 있어야만 보입니다. 없으면 보이는 효과가 없으므로 2순위입니다.

**(4) 보고 단계 이슈 심각도 (P13)**
- **규칙으로 충분한가:** 이슈 유형별 고정 표로 충분하고, 설명하기도 쉽습니다. 예: 코드에 기본 비밀키 = high, 두 환경 불일치 = high, 쿠키 Secure 누락 = medium, `http://` 하드코딩 = low.
- **Jev를 쓰면 좋은 점:** 자유 텍스트 이슈에만 의미가 있습니다. 문서도 Score 값을 단계 사이 수치로 해석하지 말라고 합니다.
- **Claude와 비교:** 이슈를 Claude가 만든다면 같은 호출에서 심각도 보기를 함께 받으면 됩니다.

### 6. 조사 중 발견한 골든 패스 문제

1. **flaskr 공식 `schema.sql`은 `DROP TABLE IF EXISTS user; DROP TABLE IF EXISTS post;`로 시작합니다.**
   - 파이프라인이 이 파일을 "마이그레이션"으로 다시 실행하면 두 환경의 v1 게시글이 모두 지워집니다.
   - 공식 `post.author_id`는 `NOT NULL` + FK라서, 이미 데이터가 있는 테이블에 그대로 추가하면 실패하거나 위험합니다.
   - 대책: v2 변경은 별도 추가형 마이그레이션 파일로 만듭니다(`CREATE TABLE user`, `ALTER TABLE post ADD COLUMN author_id INT NULL`). 파괴적 SQL은 검증기가 막거나 사람 승인을 받게 합니다.
2. **flaskr `create_app`은 `SECRET_KEY="dev"`를 기본값으로 둡니다.**
   - 시크릿 주입이 빠져도 앱은 멀쩡히 뜨고, 로그인 세션은 공개된 키로 서명돼 위조할 수 있습니다.
   - 즉 "환경변수 → Secrets Manager" 차이가 크래시가 아니라 조용한 보안 결함으로 나타납니다. 보고 단계 이슈(규칙 탐지, 심각도 high)로 쓰기 좋은 사례입니다.
   - v2 코드는 `os.environ['SECRET_KEY']`처럼 값이 없으면 바로 실패하게 만드는 것을 권합니다.
