## 0. 결론

1. **권장은 (a)입니다.** 이미지는 하나(`ddak-cp`)만 만들고, compose에서 역할별 컨테이너 4개로 나눕니다(admin(실행기 포함), mcp-validate, mcp-pipeline, mcp-verify). 여기에 docker socket proxy를 하나 붙입니다. MCP 전송은 compose 안에서는 Streamable HTTP, 로컬 개발·테스트에서는 stdio·인메모리를 씁니다. 전환은 설정 한 줄입니다.
2. 이렇게 나누면 **도커 API(= 호스트 root)는 mcp-pipeline에만** 들어가고, 웹에 노출된 admin과 LLM 자격증명이 있는 컨테이너에는 들어가지 않습니다. 단일 컨테이너안(b, c)에서는 이 분리가 사실상 불가능합니다. 같은 UID 프로세스끼리는 서로의 env를 읽을 수 있다는 것을 [실측]으로 확인했습니다.
3. 클라우드 쪽 컨트롤 플레인은 **따로 두지 말고**, 로컬 컨트롤 플레인이 AWS API로 원격 배포하는 방식을 권장합니다. ECS에 컨트롤 플레인을 올리면 온프렘 도커 API를 인터넷 쪽으로 열어야 해서 보안상 가장 나쁜 선택입니다.
4. 관리 페이지는 **FastAPI + Jinja2 + HTMX(SSE 확장)**를 권장합니다. FastAPI 0.135+에는 SSE가 내장돼 있고, 하위 프로세스 출력이 줄 단위로 바로 흘러가는 것을 [실측]으로 확인했습니다.
5. 기존 결정 중 바뀌는 것은 16번 문서의 I-8b(stdio 고정)와 17번 문서 10-2의 도커 주소입니다. 아래 "기존 문서와 충돌" 절에 정리했습니다.

## 1. 패키징 선택지 비교

### 1-1. WebGoat는 실제로 이렇게 배포됩니다 [문서]
- README 기준 명령: `docker run -it -p 127.0.0.1:8080:8080 -p 127.0.0.1:9090:9090 webgoat/webgoat` (시간대는 `-e TZ=...`로 추가)
- Dockerfile: `eclipse-temurin:25-jdk-noble` 기반, 비root 사용자 `webgoat`, Java 프로세스 하나, HEALTHCHECK로 actuator를 curl합니다. **supervisord는 쓰지 않습니다.** WebGoat와 WebWolf가 한 JAR에서 포트 2개를 엽니다.
- 한 줄 배포가 안전한 이유는 **호스트 마운트도, 자격증명도 없는 단일 프로세스**이기 때문입니다. 우리 컨트롤 플레인은 도커 API, AWS 자격증명, LLM 자격증명이 필요해서 구조가 다릅니다. `docker run` 한 줄로 숨기는 것보다, compose 파일에 마운트와 권한을 드러내 두는 편이 검토와 발표에 유리합니다.

### 1-2. 세 가지 안

| | (a) compose 다중 서비스 (권장: 이미지 1개 × 컨테이너 N개) | (b) 단일 이미지 + 프로세스 관리자 | (c) 단일 파이썬 프로세스 |
|---|---|---|---|
| MCP 전송 | Streamable HTTP (컨테이너 분리 가능) | stdio(실행기가 자식 프로세스로 띄움, supervisord 불필요) 또는 컨테이너 안 HTTP(supervisord 필요) | 인메모리(`Client(MCPServer 인스턴스)`) [문서: SDK Client docstring] |
| 자격증명 분리 | **컨테이너별 secrets 파일.** PID·파일시스템·네트워크 네임스페이스가 따로라 서로 못 봄 [실측 T1·T2] | env 허용목록뿐. 같은 UID면 `/proc/<pid>/environ`으로 옆 프로세스 env를 읽힘 [실측 E8] | 없음 (import-linter만) |
| docker.sock 위치 | mcp-pipeline(프록시 경유)에만 | 관리 웹과 같은 컨테이너 → **웹 취약점 하나가 곧 호스트 root + AWS deployer + LLM 키** | 같음 |
| 실행 | `docker compose up -d --build --wait` | `docker run` 한 줄 (WebGoat와 비슷) | `python -m ...` |
| 추가 작업 | HTTP 래퍼(bearer, Host 허용목록, /healthz, 약 30줄. 실험 코드로 동작 확인), compose, 비밀 스크립트. **반나절 안팎 [판단]** | 거의 없음 (현재 설계 그대로) | 없음 |
| 발표 | "도커 API와 배포 권한은 이 컨테이너에만 있다"를 그림과 `docker inspect`로 보여줄 수 있음 | "책임 분리(관례)"까지만 말할 수 있음 | MCP 3개로 나눈 의미가 사라짐 |
| ECS 이식 | 쉬움. Fargate에서는 같은 태스크의 컨테이너끼리 localhost로 통신 [문서] | 가능하지만 한 덩어리 | 한 덩어리 |

- Docker 공식 문서도 컨테이너 하나에 서비스 하나를 권장하고, supervisord는 무겁고 재시작을 가린다고 적고 있습니다 [문서].
- **MCP 전송과의 관계 [문서: 2026-07-28 명세]:** stdio는 클라이언트가 서버를 하위 프로세스로 띄우는 방식이라 같은 컨테이너(프로세스 트리)가 필수입니다. Streamable HTTP는 서버가 독립 프로세스이고, 이번 revision부터 **프로토콜 세션이 없어져** 서버 재시작에 강합니다. SDK 2.2.0 기본(`mode="auto"`)으로 붙였을 때 협상 버전이 `2026-07-28`로 나왔습니다 [실측 E3].
- **권장 운용:** ToolGateway가 `DDAK_MCP_TRANSPORT=stdio|http`만 보고 `Client(StdioServerParameters)` 또는 `Client(url)`을 고르게 합니다. SDK `Client`가 둘 다 받습니다 [문서: SDK 소스]. 개발(`make run`)과 테스트는 stdio·인메모리, compose는 HTTP로 갑니다. 10/1 E2E에서 HTTP 쪽에 문제가 생기면 설정만 바꿔 (b)로 후퇴합니다.

## 2. 온프렘 배포에 필요한 도커 접근

### 2-1. 방식별 위험

| 방식 | 위험·특징 | 해커톤 적합도 |
|---|---|---|
| docker.sock 직접 마운트 | 데몬을 제어하면 호스트 `/`를 마운트해 마음대로 바꿀 수 있고, 키를 가진 사람은 root와 같다고 Docker 문서가 명시 [문서] | 금지 |
| **docker socket proxy** (Tecnativa) | API 종류별로 허용/차단. 기본은 EVENTS·PING·VERSION만 허용 [문서]. **하지만 배포에는 CONTAINERS+POST가 필요하고, 이 조합이면 `--privileged -v /:/host` 컨테이너 생성이 그대로 통과합니다 [실측 E4]** (생성만 하고 시작하지 않은 채 삭제). 즉 **공격 면적은 줄지만 root 동등성은 그대로** | 채택하되 이 한계를 발표에서 먼저 말함 |
| `DOCKER_HOST=ssh://deploy@vm` / `docker context` | 원격 사용자는 그 VM의 docker 소켓 권한이 필요 = **그 VM의 root 동등** [문서]. 대신 피해 범위가 컨트롤 호스트가 아니라 해당 tier VM으로 좁아짐. 여러 번 부를 때는 ControlMaster 권장 [문서]. 원격에 docker CLI가 있어야 함 [판단] | VM 모드에서 채택 |
| 원격 도커 TLS (tcp 2376, tlsverify) | CA와 인증서 관리 부담, TCP 포트 노출. 평문 HTTP 노출은 금지 [문서] | 비권장 |

**권장:** 컨테이너 모드는 sockproxy(CONTAINERS, IMAGES, NETWORKS, POST, D22 헬퍼용 VOLUMES만 허용)로, VM 모드는 compose override로 sockproxy를 빼고 tier별 `ssh://`를 씁니다. 실제로 막아 주는 것은 **코드 정책**입니다. `DockerTierHost`가 아래를 강제해야 합니다.
- ECR 이미지를 `@sha256` digest로만 생성
- privileged, cap_add, bind mount, host network·pid 거부 (named volume만 허용)
- 생성 시 `ddak.managed=true` 라벨을 붙이고, stop·rm은 이 라벨이 있는 컨테이너만

프록시는 요청 본문을 검사하지 못하므로, 이 필드 화이트리스트가 진짜 방어선입니다.

### 2-2. 도커 밖에서 도커를 부를 때의 함정 [실측]
- **E5: bind mount 경로는 데몬 호스트 기준입니다.** mcp-pipeline 안에서 만든 파일을 `-v /tmp/x:/x`로 넘기면 빈 디렉토리가 보입니다. D22(비밀을 도커 볼륨에 두는 안)가 맞는 방향입니다.
- **E6: 온프렘 앱 접근.** Docker Desktop에서는 `host.docker.internal`로 127.0.0.1에 공개된 포트까지 닿습니다. `internal: true` 네트워크에서는 이름 해석 자체가 안 됩니다. 리눅스에서는 `extra_hosts: host-gateway`가 필요합니다 [판단]. 대안은 mcp-verify를 대상 앱 네트워크에 external로 붙이는 것입니다.

### 2-3. 발표용 신뢰 경계 (문구 초안)
```
[브라우저] --127.0.0.1, 로그인+CSRF--> [admin/실행기]  (도커·AWS·LLM 자격 없음)
                                          | cp 네트워크 (internal, bearer 토큰, Host 허용목록)
          +-------------------------------+--------------------------+
   [mcp-validate]                  [mcp-pipeline]                [mcp-verify]
   LLM 자격, AWS 없음              AWS deployer + 도커 API       AWS 읽기 전용 + HTTP 검사
                                   | dockerapi 네트워크(internal)
                                   [sockproxy] --> 호스트 도커 = 온프렘 root 동등
```
> "도커 API 접근은 호스트 root와 같습니다. 그래서 이 권한을 AI가 없는 파이프라인 컨테이너 하나에만 주었고, 웹에 노출된 컨테이너와 LLM 키가 있는 컨테이너에는 주지 않았습니다. 소켓 프록시가 권한 상승을 막지 못한다는 것도 직접 확인했기 때문에, 생성 요청 필드는 코드에서 화이트리스트로 막았습니다."

## 3. AWS 자격증명 주입

- **환경변수를 금지할지:** AWS 문서가 env 자체를 금지하지는 않습니다. 하지만 env 값은 `docker inspect`에 그대로 보이고 [실측 T8], 같은 UID 프로세스가 읽을 수 있습니다 [실측 E8]. 그래서 **파일로 넣고, env에는 경로와 프로필 이름만** 둡니다.
- **`~/.aws`를 통째로 마운트하지 않습니다.** 모든 프로필과 SSO 캐시가 들어갑니다. Claude Code devcontainer 문서도 클라우드 자격증명 파일을 마운트하지 말고 단기 토큰을 쓰라고 권합니다 [문서].
- **권장 흐름:**
  1. 호스트에서 `make creds`를 실행합니다. 내부적으로 `aws configure export-credentials --profile ddak-deployer`를 부릅니다. 출력은 credential_process 형식의 JSON이고 env 형식도 됩니다 [문서].
  2. 이 값을 `.secrets/aws/deployer/credentials`(ini, gitignore) 파일로 씁니다.
  3. 디렉토리를 읽기 전용으로 마운트하고 `AWS_SHARED_CREDENTIALS_FILE`, `AWS_PROFILE`을 지정합니다 [문서: 환경변수 목록].
  4. 서비스별로 나눕니다: mcp-pipeline은 deployer, mcp-verify는 verifier(읽기 전용), mcp-validate와 admin은 **자격증명 없음**.
- **갱신 함정 [실측 E10]:** compose `secrets:`처럼 파일 하나를 bind mount한 상태에서 호스트가 원자적 교체(mv)를 하면, 컨테이너 안에서 파일이 사라지고 재시작 전까지 복구되지 않습니다. 제자리 쓰기는 반영됩니다. **디렉토리 마운트는 원자적 교체도 반영됩니다.** 그래서 갱신되는 AWS 자격증명은 디렉토리로 마운트하고, 툴 호출마다 새 boto3 Session을 만듭니다(파일에서 읽은 정적 자격증명은 세션이 스스로 다시 읽지 않는다고 봅니다 [판단, 리허설 확인]).
- **데모 당일:** 역할 세션 만료(기본 1시간 수준)에 대비해 권한 세트 세션 시간을 늘리거나, 리허설 전에 `make creds`를 다시 돌립니다. 해커톤 계정에서 Identity Center를 쓸 수 있는지는 [확인 필요]입니다.

## 4. 컨테이너 안에서 Claude CLI 인증 (요점)

- **저장 위치 [문서]:** macOS는 키체인, 리눅스는 `~/.claude/.credentials.json`(0600). **맥 호스트의 로그인은 리눅스 컨테이너로 옮길 수 없습니다.** 컨테이너 안에서 다시 로그인해야 합니다(브라우저 콜백이 안 닿으면 코드를 붙여넣는 흐름).
- **유지:** 명명 볼륨을 `~/.claude`에 붙이고 `CLAUDE_CONFIG_DIR`를 같은 경로로 지정합니다. `~/.claude.json`이 디렉토리 밖에 있어서 볼륨만 붙이면 로그인이 풀립니다 [문서].
- **대안 [문서]:** `claude setup-token`으로 1년짜리 토큰을 만들어 `CLAUDE_CODE_OAUTH_TOKEN`으로 넣는 방법(모델 요청만 가능), 또는 `ANTHROPIC_API_KEY`나 `apiKeyHelper`(파일을 cat하는 스크립트라 env에 안 남음). 버전은 `npm i -g @anthropic-ai/claude-code@X.Y.Z` + `DISABLE_AUTOUPDATER=1`로 고정합니다 [문서].
- **배치:** CLI와 자격증명은 AI 허용 컨테이너(mcp-validate·mcp-verify, 또는 이 둘만 붙는 `llm` 컨테이너 하나)에만 둡니다. 관리 페이지 채팅은 admin → AI MCP 툴 → CLI 순서로 갑니다. admin 프로세스가 직접 `claude`를 exec하면 "실행 경로에 AI 없음"과 4겹 경계 중 물리 겹이 깨집니다.
- **약관 위험 [문서]:** 구독(OAuth) 인증은 Claude Code 같은 Anthropic 네이티브 앱의 일반 사용 용도이고, 제품·서비스를 만드는 개발자는 API 키를 쓰라고 합니다. 자기 앱에 claude.ai 로그인을 붙이거나 사용자 대신 구독 자격으로 요청을 중계하는 것은 허용하지 않는다고 명시돼 있습니다. 계정 주인이 127.0.0.1에서 혼자 쓰는 경우는 회색 지대이고, **외부에 노출된 채팅이 개인 구독으로 돌면 명백히 금지 패턴**입니다. 데모 경로는 API 키를 권장합니다. 비용 환급은 AWS만 언급됐으니 LLM 비용은 [확인 필요]입니다.
- 웹 → CLI 실행 → 스트리밍 자체는 된다고 봅니다. 대체 프로세스로 SSE가 줄 단위로 흐르는 것은 [실측 E11]로 확인했고, 실제 `claude -p --output-format stream-json`은 자격증명을 쓰지 않아서 실행하지 않았습니다. 세부는 llm-cli 조사를 참조하세요.

## 5. 클라우드 쪽 컨트롤 플레인 위치

| 안 | 장점 | 단점 |
|---|---|---|
| **A. 로컬 컨트롤 플레인 → AWS API로 원격 배포 (권장)** | 가장 단순. 컨트롤 플레인 하나, 잠금·상태 DB 하나. 빌드는 이미 CodeBuild가 함 | 노트북에 단기 AWS 자격증명 필요. "클라우드 배포가 노트북에 의존한다"는 질문 가능 → "배포 제어면은 관리망에 두고 클라우드는 API로 제어한다"로 답변 |
| B. ECS에 컨트롤 플레인 | 태스크 역할이라 정적 키가 없고 클라우드 네이티브라는 이야기를 할 수 있음 | **온프렘 도커에 닿으려면 도커 API를 터널이나 VPN으로 외부에 노출해야 함.** Fargate는 privileged와 호스트 접근이 불가 [문서]. 관리 페이지용 ALB와 인증 추가. 구독 CLI를 클라우드 서비스에서 쓰면 약관 위험 |
| C. 둘 다 | – | 잠금과 상태가 둘로 갈라짐(split-brain), 테스트 두 배. 3일 안에는 불가 |

**권장은 A입니다.** 발표에서는 향후 방향으로 "컨트롤 플레인을 ECS로 옮기되, 온프렘에는 아웃바운드만 쓰는 pull 에이전트를 둔다"(self-hosted runner 방식)고 말하면 됩니다. (a) 패키징을 해 두면 같은 이미지를 ECS 태스크(사이드카끼리 localhost 통신)로 옮기기 쉽습니다.

## 6. 관리 페이지 스택

| | FastAPI + Jinja2 + HTMX (권장) | React |
|---|---|---|
| 언어 규칙 | 파이썬 단일 (I-7 예외 불필요) | Node 툴체인, 별도 빌드 |
| SSE | `fastapi.sse.EventSourceResponse` 내장(0.135+). 15초 keepalive, `X-Accel-Buffering: no` 자동 [문서]. 서버 쪽 동작을 [실측 E11]로 확인. 프런트는 `htmx-ext-sse`(npm 최신 2.2.4, htmx 2.0.11) | EventSource 직접 구현 |
| 배포 | admin 컨테이너에 그대로 포함. JS는 static에 벤더링(데모 중 CDN 의존 없음) | 빌드 산출물을 서빙하거나 컨테이너 추가, CORS 설계 |
| 한계 | 복잡한 상태 UI는 불편 | 디자인 단계에서 유리 |

- **최소 화면:** 프로젝트 설정(도메인 등), 실행 버튼, 실행 목록, 실행 상세(온프렘·클라우드 2열 SSE), 승인, diff(서버에서 렌더링), 결과·이슈 카드, 코드 수정 토글(기본 OFF, 서버에서 강제), 채팅.
- **SSE 주의 [문서: MDN]:** HTTP/1.1에서는 브라우저·도메인당 동시 연결이 6개로 제한됩니다. 2열이라도 **스트림은 하나로 두고 `event:` 타입으로 나눕니다.** EventSource는 커스텀 헤더를 보낼 수 없으므로 인증은 같은 출처 쿠키로 합니다.

### 7-2. compose 핵심 (실험 파일을 바탕으로 정리. 전체 조합을 한 번에 띄워 보지는 않음)
```yaml
name: ddak
x-cp: &cp
  image: ddak-cp:local
  build: { context: ../.., dockerfile: compose/control-plane/Dockerfile }
  read_only: true
  tmpfs: ["/tmp", "/home/app"]
  cap_drop: [ALL]
  security_opt: ["no-new-privileges:true"]
  restart: unless-stopped
services:
  admin:                                  # 실행기 + 관리 API/웹 (같은 프로세스). 자격증명 없음
    <<: *cp
    command: ["ddak-admin"]
    ports: ["127.0.0.1:8080:8080"]        # internal 네트워크만 붙이면 공개 포트가 안 닿음 [실측 E7] → front 필요
    networks: [front, cp]
    volumes: [cpdata:/var/ddak, workspace:/workspace]   # SQLite 상태 DB, var/runs/<id>/context.json
    environment: { DDAK_MCP_TRANSPORT: http, MCP_VALIDATE_URL: "http://mcp-validate:8000/mcp", MCP_PIPELINE_URL: "http://mcp-pipeline:8000/mcp", MCP_VERIFY_URL: "http://mcp-verify:8000/mcp" }
    secrets: [mcp_token]
    depends_on: { mcp-validate: {condition: service_healthy}, mcp-pipeline: {condition: service_healthy}, mcp-verify: {condition: service_healthy} }
  mcp-validate:                           # ①② AI 허용, AWS·도커 없음
    <<: *cp
    command: ["ddak-mcp", "validate"]
    networks: [cp, egress]
    volumes: [workspace:/workspace:ro, cpdata:/var/ddak:ro]
    secrets: [mcp_token, anthropic_key]   # YAML merge는 리스트를 합치지 않음 → 서비스마다 전부 적기
  mcp-pipeline:                           # ③④ AI 없음, AWS deployer + 도커 API
    <<: *cp
    command: ["ddak-mcp", "pipeline"]
    networks: [cp, egress, dockerapi]
    environment: { DOCKER_HOST: "tcp://sockproxy:2375", AWS_PROFILE: deployer, AWS_SHARED_CREDENTIALS_FILE: /run/aws/credentials, AWS_REGION: ap-northeast-2 }
    volumes: [workspace:/workspace:ro, cpdata:/var/ddak:ro, ../../.secrets/aws/deployer:/run/aws:ro]
    secrets: [mcp_token]
  mcp-verify:                             # ⑤ AWS 읽기 전용 + HTTP 검사 + AI 보고
    <<: *cp
    command: ["ddak-mcp", "verify"]
    networks: [cp, egress]
    extra_hosts: ["host.docker.internal:host-gateway"]
    environment: { AWS_PROFILE: verifier, AWS_SHARED_CREDENTIALS_FILE: /run/aws/credentials }
    volumes: [cpdata:/var/ddak:ro, ../../.secrets/aws/verifier:/run/aws:ro]
    secrets: [mcp_token, anthropic_key]
  sockproxy:
    image: tecnativa/docker-socket-proxy@sha256:1f5038b54f06c3e18422902cf00ba21803d1c97805aae032e5e6673d532d3459
    environment: { CONTAINERS: 1, IMAGES: 1, NETWORKS: 1, VOLUMES: 1, POST: 1 }   # EXEC/BUILD/SECRETS/SYSTEM 0
    volumes: ["/var/run/docker.sock:/var/run/docker.sock:ro"]
    networks: [dockerapi]
networks:
  front: {}
  egress: {}
  cp: { internal: true }        # egress 차단, 서비스 이름으로만 통신 [실측 T7]
  dockerapi: { internal: true }
volumes: { cpdata: {}, workspace: {} }
secrets:
  mcp_token: { file: ../../.secrets/mcp_token }
  anthropic_key: { file: ../../.secrets/anthropic_key }
```

MCP 서버 쪽에는 공통 래퍼(`mcp_kit`)가 필요합니다: `TransportSecuritySettings(allowed_hosts=["<서비스명>:8000"], allowed_origins=[])` + bearer 검사(hmac 비교) + `/healthz`.

### 7-4. 보안 주의 5개
1. **도커 API는 호스트 root와 같습니다.** mcp-pipeline에만 주고, admin과 AI 컨테이너에는 절대 소켓을 주지 않습니다. 프록시는 API 종류만 줄입니다(privileged + `/` bind 생성이 통과하는 것을 실측). 그래서 `DockerTierHost`에 필드 화이트리스트와 라벨 한정을 둡니다.
2. **MCP HTTP 기본값 함정:** SDK 2.2.0은 127.0.0.1·localhost·::1에 바인드할 때만 Host/Origin 검사를 자동으로 켭니다. 컨테이너에서 필요한 0.0.0.0에서는 꺼집니다 [문서: SDK 소스]. 위조한 Host·Origin, 토큰 없는 요청이 그대로 프로토콜 단계까지 통과했습니다 [실측 E2]. 설정 후에는 Host 위조 421, Origin 위조 403, 토큰 없음 401이 나왔습니다 [실측 T4~T6]. 명세도 Origin 검증을 MUST로, 인증을 SHOULD로 둡니다 [문서]. 여기에 internal 네트워크와 포트 미공개를 더합니다.
3. **관리 페이지는 곧 배포 버튼입니다.** 127.0.0.1 바인드, Host 허용목록(DNS rebinding 대응), 로그인 + `SameSite=Strict` 쿠키 + POST CSRF 토큰을 둡니다. 운영자가 여는 아무 웹사이트나 localhost를 공격 대상으로 삼을 수 있습니다. 코드 수정 토글 OFF는 UI가 아니라 서버에서 강제합니다.
4. **비밀은 env가 아니라 파일로:** docker inspect 노출과 /proc environ 노출을 둘 다 실측했습니다. 서비스별 최소 자격(deployer / verifier / 없음), `~/.aws`·`~/.claude` 통째 마운트 금지, 단기 자격증명, `.secrets/` gitignore를 지킵니다. 참고로 Docker Desktop(mac)에서는 0600 파일도 uid 10001이 읽을 수 있었습니다 [실측 E9]. 맥의 파일 권한은 경계가 아니고, 리눅스 팀원은 반대로 권한 때문에 읽기에 실패할 수 있습니다 [판단].
5. **하드닝과 공급망:** 비root, `read_only`, `cap_drop: ALL`, `no-new-privileges`, 서드파티 이미지 digest 고정, egress는 필요한 서비스에만(admin은 egress 없음). AI가 만든 패치는 컨트롤 플레인 안에서 절대 실행하지 않습니다.
