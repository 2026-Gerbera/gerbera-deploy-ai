너는 클라우드·DevOps·보안 분야의 냉정한 해커톤 심사위원이자 시니어 아키텍트다. 아래 우리 팀의 확정 주제와 설계를 최대한 상세하고 비판적으로 검토해 줘. 칭찬은 필요 없고, 약점·위험·빠진 것·과장된 것을 찾아 줘. 확인된 사실과 추측은 구분해서 표시하고, 사실 주장에는 가능하면 출처(공식 문서 링크)를 붙여 줘.

# 1. 대회
- SoftBank Hackathon 2026 Term1 예선(서울, 10/3~10/4). 6명 팀. 10/3 10:00에 저장소·설계문서(Notion)·발표 자료 링크 제출 → 중간보고 7분, 10/4 최종 발표(라이브 데모 3분 포함).
- 주제(주최 측): 로컬에서 만든 웹앱을 AI를 활용해 로컬(온프레미스)과 클라우드 양쪽에 원터치로 배포하는 시스템. 평가 대상은 앱이 아니라 배포 시스템. 킥오프 예시로 "SQLite → 적절히 설정된 RDS" 같은 환경 차이 흡수가 언급됨.
- 배점(100): 완성도·데모 30(배포 시스템이 실제로 동작하고 로컬·클라우드 양쪽 배포를 현장에서 시연, 배포된 앱에 누구나 접근 가능한가) / 클라우드 활용 30(환경 차이 흡수·이식성·클라우드 고유 기능) / 팀 개발 20(대안·논의·고찰 기록) / 독창성 10 / AI 활용 10.
- 작년(2025) 예선 수상작은 AI 없이 "끝까지 동작하는 배포"(Slack 기반 CI/CD + Blue/Green, Git URL → 빌드 → HTTPS 도메인까지 가는 PaaS)로 뽑혔다. 신뢰 경계 결정(비root 빌드 등)이 심사평에서 칭찬받았다.

# 2. 확정 주제
"로컬에서 만든 앱을 딸깍 한 번으로 로컬(온프레미스)과 클라우드에 동시에 배포하면서, 환경 차이로 깨지는 부분은 AI가 고치고, 두 환경이 똑같이 동작하는지 교차 검증까지 끝내는 파이프라인"

# 3. 파이프라인 (확정)
① 플랜 → ② 검증(계획 검증) → ③ 빌드 → ④ 배포 → ⑤ 검증 및 보고. 단위·통합 테스트 단계는 시간 문제로 제외. 로컬(스테이징) 배포 후 스모크 통과를 클라우드 배포의 관문으로 씀(로컬 → 클라우드 순차).
- ① 플랜: 코드 분석(환경변수, SQLite 사용, 로컬 디스크 파일 저장, localhost 하드코딩 인지) → LLM이 계획 JSON 생성(미리 정의한 툴 이름만 사용) → (코드 수정 토글 ON일 때) LLM이 이식성 패치(SQLite 전용 SQL → DATABASE_URL 기반 공용 SQL, 로컬 업로드 → S3 호환 저장소 어댑터, localhost → 환경변수, 프록시 헤더 처리).
- ② 계획 검증 스크립트: JSON 스키마, 허용 툴 목록, 필수 단계 누락, 토글 검사. AI는 단계를 "추가"만 가능. 불합격 시 재지시 1회 → 규칙 기본 계획으로 대체. 코드·git diff는 신뢰할 수 없는 입력(프롬프트 인젝션) 전제.
- ③~⑤ 실행: 고정 실행기(코드)가 계획 순서대로 툴 호출. 빌드·배포·검증 실행·롤백·잠금에는 AI 없음. 실패 시 규칙 롤백 → AI가 원인 분류(Jev라는 빠른 분류 모델) + LLM 설명 → 보고. 토글 ON이면 수정 패치 → 사람 승인 → 계획부터 재실행.
- AI가 들어가는 곳은 분석, 계획, 패치 3종, 불일치 원인 분석, 보고 요약뿐. AI는 비밀값을 보지 않음(비밀값은 사람이 관리 페이지에서 입력).

# 4. 아키텍처
- 배포 대상: 3티어(Web=nginx/정적 화면, WAS=Flask 등, DB). 샘플 앱은 "사진 게시판"(글 작성·목록·검색·사진 업로드, 원래 SQLite raw SQL + 로컬 디스크 업로드 + localhost 하드코딩 = 일부러 로컬 전용 패턴 포함).
- 로컬(온프레미스): Docker Compose. DB는 RDS와 같은 엔진의 컨테이너(예: Postgres), 업로드는 MinIO. 로컬 HTTPS는 보류(퍼블릭 IP 필요 여부 미정), http://localhost 로 서빙.
- 클라우드: AWS 서울. CodeBuild(빌드 환경 재현성 목적, 로컬 코드를 zip으로 S3에 올려 빌드) → ECR. 로컬도 같은 이미지 digest를 ECR에서 받아 씀. ECS Fargate + ALB + RDS(미리 생성, TLS 강제) + S3 + Secrets Manager. 인프라는 Terraform으로 사전 구축. 클라우드 배포 시간 목표 60초 이내.
- HTTPS: 클라우드는 필수. 도메인은 사람이 관리 페이지에 입력하고 파이프라인이 그 값으로 ACM 인증서(DNS 검증) 확인/발급 → ALB 443 + 80→443 리다이렉트 → DNS 레코드. 파이프라인이 도메인을 사지는 않음.
- 구조: "툴 하나 + 환경별 어댑터(local/cloud)". 실행기가 설정으로 어댑터를 고름(AI가 고르지 않음). 툴 파라미터는 좁게(tier, target enum).
- MCP 서버 3개로 구성(파이썬): 검증 MCP / 파이프라인 MCP(빌드·배포) / 검증 및 보고 MCP. 툴은 MCP 명세로 미리 정의하고, 실행 때는 LLM이 아니라 실행기 코드가 순서대로 호출. 툴은 약 33개(요청 수신, 분석, 계획, 패치 3종, 계획 검증, 빌드, 배포 잠금, 설정·시크릿 주입, 클라우드 시크릿 동기화, DB 준비, 저장소 준비, TLS 확인, tier 배포, 롤백, 헬스체크, 스모크, TLS 검증, 교차 비교, 배포 후 관찰, 진단 수집, 원인 분석, 로그, 보고, 승인, 진행 이벤트, 운영 도구 등).
- 관리 페이지(배포 대상과 별개 웹앱): 챗봇 "배포해줘" + 로컬 경로/깃 주소 입력, 코드 수정 토글, 계획(규칙/AI 배지와 이유), 패치 diff 승인, 비밀값 입력, 로컬·클라우드 2열 실시간 진행, 결과 카드(공개 URL, 교차 검증 표, 단계별 시간, AI 호출 수·비용, 로그, 수동 롤백).
- 교차 검증: 같은 스모크 시나리오(글 작성 → 목록 조회, 사진 업로드 → 다른 복제본에서 조회, 배포 버전 확인)를 두 환경에 실행하고 결과 비교. 데모용 결정적 결함 예: 로컬 디스크에 저장한 사진이 클라우드의 다른 복제본에서 404.

# 5. 데모와 범위 (확정)
- 클라우드·온프레미스 모두 3티어를 미리 띄워 둔다. 라이브 데모에서는 웹서버나 WAS 코드만 수정하고, 파이프라인이 자동으로 타서 양쪽에 배포되게 한다(업데이트 배포).
- 데모에서는 시간 때문에 보여주지 않지만, 완전 처음 코드를 배포하는 것(초기 배포)도 파이프라인으로 되게는 해야 한다.
- 최우선 목표: 엔드투엔드로 무사히 배포된다는 것을 보이는 것. AI 기능은 그다음.
- 역할(6명): 클라우드 3(인프라/Terraform·IAM·HTTPS, 빌드·배포 어댑터, 클라우드 검증+관리 페이지) + 온프레미스 3(Compose 런타임+실행기, 입구·분석+AI 계획·계획 검증, AI 패치+샘플 앱+교차 검증).
- 일정: 9/30 계약·뼈대 → 10/1 정오 게이트(빌드 + 로컬 스모크, AI 패치 성공률 10개 중 8개·20초 이내 목표) → 10/1 정상 경로 E2E → 10/2 통합·리허설 → 10/3 10:00 제출.

# 6. 검토 요청 (항목별로 번호 붙여 상세히)
1. 배점 5개 항목별 예상 점수(범위)와 감점 요인, 점수를 올릴 구체적 방법.
2. 주제의 차별성: 같은 대회 다른 팀들이 할 법한 것(AI 에이전트 배포 파이프라인, AI Terraform 생성 등)과 비교해 무엇이 강하고 무엇이 흔한가. "규칙 몇 줄이면 되지 않나?"라는 반론에 대한 답이 성립하는가.
3. 3일·6명 기준 기술적 실현 가능성: 가장 위험한 구간 5개와 각각의 대체안(폴백).
4. 아키텍처의 결함이나 빠진 것: 초기 배포(bootstrap) vs 업데이트 배포 설계, 로컬→클라우드 순차 관문, 같은 이미지 digest 공유, DB 스키마 변경 처리, 롤백, 배포 잠금, 시크릿, 상태 저장, 관찰.
5. "웹서버/WAS 코드만 수정 → 자동 배포" 데모에서 "환경 차이를 AI가 고친다"와 "교차 검증"을 3분 안에 설득력 있게 보여주는 대본 제안(시간 배분 포함). 코드 수정 내용은 무엇이 좋은가.
6. AI 활용 10점: 우리 AI 경계(실행에는 AI 없음)가 오히려 약점으로 보일 위험이 있는가. 더 설득력 있게 보이려면.
7. MCP 서버 3개(검증 / 파이프라인 / 검증 및 보고) 구조와 "실행기가 MCP 툴을 순서대로 호출" 방식이 적절한가. 심사위원이 "그럼 MCP가 왜 필요한가"라고 물으면 어떻게 답할까.
8. HTTPS/도메인 방식(관리 페이지에 도메인 입력 → ACM DNS 검증 → ALB 443)의 함정과 데모 전에 해 둘 일.
9. 보안·신뢰 경계에서 심사위원(보안 전공자 포함)이 찌를 부분과 대응.
10. 로컬(온프레미스)에서 "배포된 앱에 누구나 접근" 조건을 어떻게 다룰지 선택지.
11. 우선순위: 반드시 할 것 / 하면 좋은 것 / 과감히 뺄 것 목록.
12. 심사위원 예상 질문 10개와 모범 답변 요지.
13. 우리가 틀렸을 가능성이 큰 가정이나 확인해야 할 사실 목록.
